# Ora 插件系统概览

## 核心设计

Ora 插件以 Deno 运行 `main.js`。`main.js` 只承担协议适配、参数转换和流程编排，是插件与 Ora 宿主之间的胶水层，不直接拥有宿主操作系统能力。

插件进程默认以零权限启动（这一点是选型 Deno 的决定因素，node 和 bun 并不具备）。除加载并执行插件入口所必需的运行条件外，Ora 不向其授予以下 Deno 权限：

- 文件系统读写
- 网络访问
- 创建子进程
- 读取或修改环境变量
- 以及：动态库加载、系统信息获取、硬件设备访问、高精度计时

插件需要使用这些能力时，必须调用 Ora SDK 暴露的宿主方法。SDK 将调用转换为插件协议请求，由 Ora 宿主完成身份识别、参数校验、授权、资源约束、实际执行和结果返回。插件不能绕过该通道直接访问系统资源。

这一模型类似操作系统的用户空间与内核空间：

- Deno 插件进程相当于用户空间，只运行插件业务胶水代码；
- Ora 宿主相当于内核空间，拥有并管理系统资源；
- Ora SDK 相当于系统调用接口，是插件申请宿主能力的唯一入口。

```text
Plugin main.js (Deno, zero permissions)
                │
                │ Ora SDK request
                ▼
      Ora plugin protocol boundary
                │
                ▼
Ora host (validate, authorize, execute, audit)
                │
                ├── File system
                ├── Network
                ├── Child processes
                └── Environment and other host services
```

## 设计约束

1. 插件的系统能力不能通过 Deno 启动参数直接开放；新增能力必须先形成明确的 Ora SDK 与宿主协议。
2. 安全检查必须由 Ora 宿主执行。SDK 中的客户端校验只用于改善开发体验，不能作为安全边界。
3. 宿主只向一次调用暴露完成该操作所需的最小数据和最小操作范围，不把底层系统句柄或不受约束的通用访问能力交给插件。
4. 文件、网络、子进程和环境变量等操作均经过统一的身份识别、授权、审计、超时、取消和错误映射机制。
5. 插件随包附带的二进制也不能由 `main.js` 直接启动；必须由 Ora 宿主通过 SDK 请求代为启动并管理其生命周期与标准流。

因此，插件的可用能力由 Ora 宿主协议定义，而不是由 Deno 进程权限定义。Deno 的零权限运行时负责建立基础隔离，Ora SDK 与宿主实现负责提供受控、可演进的插件能力面。
