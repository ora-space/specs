## 背景与现状

### 今天实际生效的能力判定

`requireRepositoryAccess`（`cloud/internal/core/repository_credentials.go`）在部署级拒绝之后、任何授权
产生之前，把引用的能力集合规范化，并要求它包含 `clone`：

- `cloneauth.CanonicalCapabilities` 拒绝空集合、未知成员、重复成员与不按规范顺序的集合
  （`internal/cloneauth/capability.go`）；
- `cloneauth.HasCapability(capabilities, cloneauth.CapabilityClone)` 是唯一的正向要求；
- 该集合随后进入 `cloneauth.Binding` 并有 `MaxLifetime` 上限，执行器侧再比对一次
  （`internal/cloneexec` 的 `matchBinding`），因此"授权说的"与"执行要的"必须逐字一致。

这就是连续性 D4 所说的"执行计划固定……所需能力"的完整实现面。**它是收窄的，不是完整的**：词汇表
只有一个成员，所以今天不存在"读"与"写"的区分，也没有任何一条路径会因为"这个凭据只能读"而放行或
拒绝。

### 三个必须在语义层先回答的问题

Issue #16 的验收与工作包 P2 各提出一个超出现有词汇表的诉求，它们把三个此前没有文字答案的问题推到
了前面：

1. **`clone` 到底授权了什么？** 今天它由实现定义（一次性、只读、单仓库、有期限），没有文字定义。
   不写下来，此后每一个新成员都会被拿来与 `clone` 类比，而类比没有基准。
2. **"读取"与"推送"是不是两个新能力？** 它们与 `clone` 的差别不在"读/写"这个词上，而在**次数、
   发起者与副作用的归属**上（D2）。
3. **一次只读的候选验证需要什么？** 它要么复用 `clone`，要么要求一个新成员（D4）。这个选择决定了
   P2 是否依赖一次词汇表扩展。

### 部署托管的旧式引用：一个已经产生、但直到安装执行器才会暴露的后果

`ConfigureCredential`（`cloud/internal/core/store.go`）是**部署专用**的管理路径，它的 `INSERT` 不列出
`capabilities`，因此这些引用落在列默认值 `'[]'`——与它们落在空 `repository_scope` 是同一个原因。
准入判定对**空 scope** 有一条显式的兼容豁口（"`ConfigureCredential` 写下的、早于这条绑定存在的引用，
为兼容保持不设范围"），但 `capabilities` 没有对称的豁口：空集合被规范化为"不允许任何操作"，于是
**部署托管的引用会被能力条款拒绝**。

今天这条后果不可观测：`cloud/AGENTS.md` 与凭据 ADR D11-B 要求的执行器尚未安装，任何带凭据的 clone
都先被部署级拒绝拦下（`repository_credential_executor_unavailable`），所以集成套件里那些
`ConfigureCredential` 引用仍然看到旧的码。它会在**解禁那次变更**中暴露：装了执行器之后，一条未声明
`clone` 的部署托管引用，其 clone 会被 `repository_credential_capability_unsupported` 拒绝，而此前它
会被准入。D5 就是这条后果的迁移策略。

## 决策

### D1：`clone` 的准确语义——一次性、只读、单仓库、有期限、身份绑定

`clone` 授权的是**一次执行计划内的一次仓库读取**。它的边界逐项如下；每一项都在实现侧有对应的强制点，
因此这不是愿景而是对既有行为的文字化：

| 维度 | `clone` 的语义 | 强制点 |
|---|---|---|
| 次数 | **一次**。授权被兑换一次即消费；重放被拒绝 | Credential Store 的兑换记录（`internal/credentialstore`）；`internal/cloneexec` 的消费测试 |
| 方向 | **只读**。执行端只组装一条固定的 clone 命令行，环境是 7 变量白名单，没有推送路径 | `internal/cloneexec` 的 `cloneArguments` 与 `gitEnvironment` |
| 对象 | **一个仓库身份**（按 `CanonicalRepository` 折叠拼写后比较）+ **一个凭据版本** | `cloneauth.Binding`；执行端 `matchBinding` |
| 期限 | **有期限**，不长于一次 clone 的命令超时；兑换时刻再按 Store 自己的时钟判一次 | `cloneauth.MaxLifetime`；Store 的兑换校验 |
| 身份 | 绑定接收方 Node 实例与运行代次；出示方自述必须与绑定值一致 | `cloneauth.Binding`；执行端比对 |
| 归属 | 绑定 tenant、owner、project、workspace、clone execution、credential id | 同上 |

**`clone` 不蕴含的东西**（逐条都是"必须另立决策"的边界）：不蕴含 fetch、pull、push，不蕴含对同一
仓库的第二次读取，不蕴含对另一个仓库的读取，不蕴含任何远端写入。**它也不是"读权限"的同义词**：
把 `clone` 读成"这个凭据可以读"，就等于用一个一次性授权解释一个无限次授权，正是 D3 不变量 3 禁止的
那次外推。

### D2：`read` 与 `push` 的语义在此写定，但两者都不进入 V1 词汇表

两个候选成员的语义按 D1 的六个维度展开如下。"进入词汇表的额外条件"一列是本文的推荐结论：**今天
一条都不满足**，因此 A 项维持 `["clone"]`、C 项不开放 `push`。

| 维度 | `read`（未引入） | `push`（未引入） |
|---|---|---|
| 授权什么 | **多次、由非执行计划发起的只读取**：把镜像同步到既有 checkout、在管理员验证流程中读取候选仓库、为派发通道读取一次交付对象 | **一次远端写入**：把某个本地版本写入远端仓库的某个 ref |
| 与 `clone` 的差别 | 差别不在"读"而在**次数与发起者**：由谁在什么时机发起读取、读多少次、每次是否重新授权 | 差别在**副作用的归属**：写的是**用户的远端仓库**，一次失败或部分成功会在用户资产上留下痕迹 |
| 今天的缺口 | 没有任何路径需要它；一旦引入，必须定义"读取记账"（一次 read 授权能不能被复用为无限次读取）与"谁来发起" | 执行端**没有推送路径**；凭据今天从不携带写授权；Node 侧凭据隔离（D14-B 义务面）要求凭据对 Agent 身份不可读，而推送的发起者恰恰在那个身份上 |
| 进入词汇表的额外条件 | 出现一条真实的产品路径 + 读取记账语义 + 三处强制点 | 一篇独立的 `approved` 决策，含执行端推送契约、ref 范围、有效期、失败与部分成功语义、审计，以及 D14-B 面在 Node 侧的落地；公开契约枚举同步变更 |
| 本文的推荐 | **不引入** | **不开放**；Issue #16 验收第 2 项的推送一侧继续如实标注 `Missing` |

为什么"读取与推送能力分别验证"不构成"顺手加一个枚举值"的理由：词汇表的每个成员都同时定义一次
**授权**。在没有推送执行契约时把 `push` 加进枚举，等于让 `CanonicalCapabilities` 接受一个没有任何
路径强制的取值，也就是把一个说得出口、做不到的授权写进契约——这正是 fail-closed 要防的事。把
`read` 加进枚举同理：它今天唯一的作用是让"只读"这个词看起来被区分过。

**不引入不等于不回答。** 本文把两者的语义固定下来，是为了让此后每一次扩展都对着同一张表论证；把
语义与成员资格分开处理，是本次裁决的核心取舍。

### D3：授权与执行边界——能力是引用的属性，三处同时强制，只读证据不得记为写许可

1. **能力属于引用，不属于调用方。** 所需能力由执行计划固定（今天守卫里写死的就是 `clone`），可得
   能力来自 `credential_refs` 的当前行；请求体、查询参数与客户端自述都不能增加能力。因此本文的任何
   扩展都只能通过"改引用的行"生效，不能通过"改请求"生效。
2. **三处同时强制，缺一不算实现**：准入（`requireRepositoryAccess`）、签发（`cloneauth.Binding` 的
   载荷与有效期）、执行（`cloneexec` 的逐字比对，加上 Store 的单次消费）。只在一处强制，等于制造
   一个说得出口、做不到的授权。
3. **只读证据不得被记录、导出或复用为写许可。** 一次读取的结果、一次验证的成功、一次镜像同步的完成，
   都不得写回任何授权位（不更新 `capabilities`、不更新 `repository_scope`、不生成可用于后续操作的
   授权）；后续真正需要读取或写入的操作必须重新走完整的准入与签发。
4. **封闭词汇表**：未知、重复、空集合与不按规范顺序的集合继续被拒绝，`'[]'` 继续被读作"不允许任何
   操作"。扩展词汇表不得让任何既有取值的行为发生静默变化。
5. **fail-closed 的形状不因扩展而改变**：部署未安装执行器时，带凭据的 clone 依旧无条件被部署级
   拒绝；本文不解除它。

### D4：候选验证复用 `clone`，不新增 `verify`／`validate` 成员

P2 要求管理员在重绑前对候选引用做一次**受控验证**：在声明的目标仓库上证明候选引用可用，把结果
（引用版本、仓库、已验证能力）写回，再在不改变绑定版本的前提下原子切换。

**推荐：验证就是一次真实的一次性 `clone`**，其能力取 `clone`，走既有的准入、签发、执行与销毁链路；
验证的产物只有"验证结果"这一条记录，**不产生任何授权位**（D3 第 3 条）。因此：

- **不新增成员**：能力词汇表描述的是"这个凭据能做什么"，而验证就是一次一次性只读——正是 `clone`
  的定义。把 `verify` 加进词汇表，等于让词汇表开始描述"我们为什么读"，而这是流程属性，不是凭据属性。
- **不需要新的凭据解析机制**：今天唯一的机密解析路径就是授权兑换；验证借用它，比新增一条"只解析不
  授权"的旁路更不容易被误用——旁路一旦存在，就必须由执行端与 Store 各自证明它不能被升格为授权。
- **与 approved D2 兼容**：不新增成员，所以 A 项与公开契约都不动。
- **本文不实现 P2 流程本身**：验证端点、管理员重绑入口、失败重绑（失败不得覆盖原绑定）、迟到结果的
  隔离（过期的验证结果不得复活一个已被替换的候选）属于**重绑流程决策**，不在本文范围。本文只回答
  "它需要哪个能力"这个问题。

被否决的两支：新增只读成员 `verify`（需要一次词汇表扩展，而收益只是词汇表里多一个词），以及不做
验证、重绑时立即写入并注明"未验证"（与连续性 D4 的"管理员显式绑定并验证后，才能恢复受影响的新远程
操作"直接冲突，并把未经核实的绑定固化成产品行为）。

### D5：旧式 `capabilities='[]'` 的迁移——源头显式声明 + 既有行逐条显式迁移

空集合继续被拒绝（D3 第 4 条），**不给它一条与空 scope 对称的兼容豁口**，也不改列默认值。迁移分两步
（第 1 条是源头，第 2 条是既有行），两步都要求"声明"，不要求"推断"；第 3、4 条是这一步的两条硬约束
——不得批量授权、无依据者不授权；第 5 条列出仍然不做的事：

1. **源头：`ConfigureCredential` 在创建时显式声明能力。** 该 `INSERT` 增加 `capabilities` 列并写入
   字面量 `'["clone"]'::jsonb`。这是一次**授权声明**而不是格式补录：部署在创建这个托管引用时，
   明确声明它用于 clone。声明必须**明确且可追踪**（评审条件一）：值是字面量而不是从部署参数、环境
   变量或归属推导出来的结果；同一次创建必须在部署托管创建路径的既有记录里可审计（哪次操作、为哪个
   Project、声明了什么能力），使"这条引用为什么有这个能力"在事后可以逐条回答，而不是靠"它是走这条
   路径建的"来推断。理由是它与归属无关——声明来自"谁在创建它、创建它做什么"，而这个问题的答案就在
   这条 SQL 的调用点上，不需要猜测任何既有行的归属。
2. **既有行：由部署逐条核验、逐条显式迁移。** 对已经落在 `'[]'` 上的引用，在**解禁那次变更**中
   执行一次显式、可审计的一次性迁移，且**必须由操作者给出具体的引用清单**（引用 id 列表），不得用
   任何谓词批量匹配。清单里的每一条都必须在迁移记录中落成四项可核对的事实（评审条件二）：
   **来源**（该引用由哪条路径、哪次操作创建）、**Scope**（`repository_scope` 覆盖哪些仓库）、
   **所有权**（`owner_user_id` 与 `attribution` 各自表达什么、谁有权处置它）、**原有授权依据**
   （它在此之前凭什么被当作可用——例如当时的能力判定、部署约定或那次绑定的批准记录）。四项都能落成
   事实的引用才允许迁到 `'["clone"]'`；`attribution='unknown'` 只能作为操作者核验时的线索，
   **不得作为判据**，也不得单独充当"原有授权依据"：连续性 D2 明确禁止推断归属，而"看起来是部署
   托管的"正是一次归属猜测，把它变成一次授权就是本文要防的错误。
3. **不得无条件授予：不存在批量授权。** 第 2 条的清单是唯一的授权入口（评审条件三）。因此
   `UPDATE credential_refs SET capabilities='["clone"]'` 这类**不带具名 `WHERE` 的语句一律禁止**，
   以谓词批量筛选同样禁止——`attribution='unknown'`、`capabilities='[]'`、租户、创建时间窗都不是
   授权判据。一次迁移里的每一条授权都必须能回溯到第 2 条清单中具名的一行；无法回溯的改动视为越权。
4. **无法证明授权依据的引用保持冻结或拒绝，不允许匿名兜底。** 四项核验没有全部通过的引用**不迁移**
   （评审条件四）：它继续以 `'[]'` 被读作"不允许任何操作"，继续在准入处由
   `repository_credential_capability_unsupported` 拒绝，或由部署显式删除／解绑该引用。**不允许任何
   兜底**：不得为它临时放开空集合、不得给它"默认可用"的解释、不得借用另一个引用的清单或授权、
   也不得用匿名 clone 代替它自己的授权。冻结与显式拒绝都是合法结论，无依据的授权不是。
5. **除此之外不做的三件事**：不改列默认值（会把"未分类"读成"已授权"，并让一次 migration 变成一次授权
   变更）；不加空集合的兼容豁口（需要区分"部署托管的旧引用"与"声明为空的用户引用"，而今天只能借归属
   近似）；不在 migration 文件里自动回填（迁移会重放，而授权声明不应随 schema 变更悄悄发生）。

**本文已批准第 1 步，但批准本身不改代码**：`ConfigureCredential` 的 `INSERT` 形状只在**解禁那次
变更**中改变（落地顺序第 3 步），并与第 2–4 条的逐条迁移同批出现。在那之前 `ConfigureCredential`
继续写入 `'[]'`，实现保持"空集合即不允许任何操作"，该后果在执行器安装前不可观测。

## 不变量

1. `credential_refs.capabilities` 被准入判定认可的正向能力集合在本文中只有 `clone`；新增成员必须由
   新的 `approved` 决策承载，并同时变更公开契约的枚举。
2. `clone` 的语义是 D1 的六条（一次性、只读、单仓库、有期限、身份绑定、归属绑定）；它不蕴含 fetch、
   pull、push，也不蕴含"可以读"这一无限次解释。
3. 能力是引用的属性：所需能力由执行计划固定，可得能力取自引用的当前行，请求方自述不增加能力。
4. 任何新能力必须在准入、签发与执行三处同时被强制；只在一处强制不算实现。
5. 只读证据（一次读取、一次验证、一次同步的结果）不得被记录、导出或复用为写许可，也不得写回任何
   授权位。
6. 未知、重复、空集合与不按规范顺序的能力集合继续被拒绝；`'[]'` 继续被读作"不允许任何操作"，本文
   的批准不改变这一点。
7. `push` 在本文被批准后仍然不可用；开放推送需要独立的 `approved` 决策与执行端推送契约。
8. 团队凭据的**归属与成员离开规则**不由本文决定；P2 若落地，需要团队归属决策与本文 D4 同时成立。
9. 本文的批准**不解除任何 fail-closed**，也不改变任何运行时行为：A–D 是把既有判定写成文字，E 是
   一次有条件授权的规则，其 `INSERT` 形状变化与逐条迁移只在解禁那次变更中落地（D5、落地顺序第 3 步）。
10. 迁移既有 `'[]'` 引用必须逐条核验来源、Scope、所有权与原有授权依据，并留有具名清单；任何无条件
    `UPDATE` 或按谓词批量的授权都无效（D5 第 2、3 条）。
11. 四项核验未全部通过的引用保持冻结（继续 `'[]'`、继续被拒）或由部署显式删除／解绑；不允许匿名
    兜底、默认可用、借用其他引用的授权等任何替代（D5 第 4 条）。
12. 新部署托管引用的 `clone` 声明必须明确且可追踪：字面量写出，并随创建路径的既有记录可审计；不由
    环境、参数或归属推断得出（D5 第 1 条）。

## 为什么不是这些替代方案

| 方案 | 优势 | 否决理由 |
|---|---|---|
| 直接按 Issue 验收第 2 项把 `push` 加进枚举 | 一步满足验收行 | Issue 是需求来源，不是决策来源；在写权限语义、执行端推送路径与只读授权防滥用三处都未定义时扩展枚举，等于让 `CanonicalCapabilities` 接受一个没有任何路径强制的能力（不变量 4） |
| 把 `read` 加进枚举，让"读取能力"名副其实 | 词汇表看起来更完整 | 今天没有任何路径需要它（D2）；引入后必须同时定义读取记账，否则一次 read 授权会被当作无限次读取的解释，与不变量 5 冲突 |
| 新增 `verify` 成员承载 P2 的候选验证 | 验证与授权在词汇表里就分开 | 词汇表描述凭据能做什么，不描述我们为什么读；分开的成本是一次契约变更，收益只是命名（D4） |
| 给空集合一条与空 scope 对称的兼容豁口 | 保留部署托管引用的既有可用性 | 需要一个判据区分"部署托管的旧引用"与"声明为空的用户引用"，今天只能借 `attribution='unknown'` 近似，而连续性 D2 禁止推断归属：这条豁口会把一次归属猜测变成一次授权（D5） |
| 把 `capabilities` 的默认值从 `'[]'` 改成 `["clone"]`，让既有引用"自动可用" | 少一次重绑 | 会把"未分类"读成"已授权"，与连续性 D5 的"预留列只应记录为无读写者"冲突，并让一次 migration 变成一次授权变更（D5 第 3 条） |
| 由本文顺手把 P2 的团队归属规则也定下来 | 一次裁决两件事 | 与 D2"`team` 的授权与成员离开规则另立决策"以及例外 ADR 不变量 3 直接冲突；两份尚未成形的规则塞进一篇 ADR，会让两者都无法单独评审与单独验收（不变量 8） |
| 保持"本文不选任何方案"，继续把它当方案目录 | 不推动任何选择 | 方案目录已经把选择推迟了两轮，而推迟的成本落在实现侧（P2 停滞、验收行悬空）。把推荐写清楚、把批准权留给评审者，比继续比较方案更有用；本文因此把"推荐"与"批准"分开：推荐是本文的结论，生效仍需 `approved` |

## 失败与恢复语义

| 情形 | 对外结果 | 持久事实与恢复 |
|---|---|---|
| 引用未声明 `clone`，被 `repository_credential_capability_unsupported` 拒绝 | 该次 clone 被拒 409，Operation 结算为 `failed` + 该码 | 见[把带凭据的拒绝结算为终态](../operation/20261012-credentialed-clone-refusal-is-terminal.md)；本文不改变该语义 |

| 有人把一次只读验证的结果记为推送许可，或写回授权位 | 拒绝该改动 | 不变量 5 |

| 有人要求用"看起来是部署托管的"批量回填能力 | 拒绝该主张，要求逐条清单 | D5 第 2 条；连续性 D2 禁止推断归属 |
| 有人要求本文一并裁决团队凭据归属 | 拒绝，并指向团队归属决策 | 不变量 8 |
