# `push` 进入能力词汇表：一次推送＝一个 upstream、一个 ref、一个提交、一次人工授权，只由身份 C 执行

本文是[能力词汇表](20261012-repository-credential-capability-vocabulary.md)（`approved`）C 项留给后续
决策的那一次扩展，也是[推送执行权限](../../node/repository/20261012-push-execution-authority.md)
（`approved`）落地顺序第 3 步所说的"词汇表扩展决策"。它把 `push` 加入 `capabilities` 枚举，同时变更
公开契约、准入、签发与执行四处强制点，并写定把这条能力从"说得出口"变成"做不到也拒绝"的**端到端写入
协议**：谁能请求、请求里必须绑定什么、由谁执行、秘密怎么到场与退场、撤销如何生效、远端结果不确定时
如何结算。

**本文已于 2026-10-13 按正式流程获批**（A–G 全部按本文建议批准，并同时批准了对推送执行权限 ADR 的
两处修订），结论见[批准记录](#批准记录2026-10-13)。**但批准不等于开放，也不等于启用**：`push` 仍不在
词汇表中，`CanonicalCapabilities` 继续拒绝它，`permittedCapabilities` 继续只认 `clone` 与
`mirror_prepare`，任何推送路径、任何签发、任何契约变更都只能在落地顺序第 2 步那次变更里开始——本文的
批准本身不产生任何运行时变更。按 `specs/AGENTS.md` 的生命周期，核心测试用例在本文变为 `approved`
之后依据最终同意的方案补充，并同步更新词汇表 ADR 的"本决策未解决的问题"一节。

本文提出的核心收紧只有一条，但它决定了其余全部：**一次授权对应恰好一个 upstream、一个完整 ref 名与
一个提交，且这个提交必须是该 ref 当前值的后代。** 因此不存在"ref 范围"，也就不存在"部分成功"——把
写入面从"一个仓库"收窄到"一条引用的一个提交"，是本文与失败语义、审计粒度、撤销对象三者同时对齐的
地方。

涉及的模块：`internal/cloneauth`（词汇表、`Binding`、签发与验签、`permittedCapabilities`）、
`internal/core`（准入与请求面）、`internal/cloneexec`（写向作业与 Git 约束）、
`internal/credentialstore`（兑换、用途绑定、单次消费）、`internal/contract` 与 `api/openapi.json`
（公开契约枚举与生成客户端）、`frontend/src/api`（生成产物）。兼容性边界：`capabilities` 的公开枚举、
`credential_refs.capabilities` 的既有取值与默认值 `'[]'`、`Binding` 的字段存在性规则、
`CloneExecutionSpec` 的形状、已应用的迁移、既有 clone 与 mirror_prepare 两条链路的逐位行为。

本文**不承担**：不实现推送、不改写任何已批准 ADR、不定义管理员重绑入口、不定义团队凭据归属、不解除
任何 fail-closed、不替代真实私仓推送验收（那是落地顺序的第 4、5 步）。

## 背景与现状

词汇表今天只有一个成员。`cloneauth.capabilities` 是 `[]Capability{CapabilityClone}`
（`internal/cloneauth/capability.go:33`），`CanonicalCapabilities` 拒绝任何其他成员
（同文件 `:73-80`），`permittedCapabilities` 只回答两个操作且都返回 `["clone"]`
（`internal/cloneauth/authorization.go:84-91`），准入要求恰好包含 `clone`
（`internal/core/repository_credentials.go:121`），执行器再比一次
（`internal/cloneexec/executor.go:339-340`），公开契约把枚举写死为 `enumeration("clone")`
（`internal/contract/openapi.go:114`）。五个位置互相印证，因此"今天没有推送路径"不是遗漏而是判定。

`capabilities` 是**引用的属性**而不是请求的属性（词汇表 D3 第 1 条）：可得能力来自
`credential_refs` 的当前行，所需能力由执行计划固定。这意味着扩展词汇表**不会**让任何既有引用自动获得
写能力——一条今天写着 `["clone"]` 的引用，在本文获批后依然是 `["clone"]`，只有显式写入 `push` 的引用
才可能有写能力。这是本文最重要的兼容性事实，也是 D1 只改"成员集合"而不改"判定规则"的原因。

同时，`Binding` 已经为"由 C 执行、不依赖 Node 运行时"的作业准备了形状：`OperationMirrorPrepare` 用
`OperationID`＋`PreparationGeneration`＋`ExecutorIdentity`＋`Ref` 这一组字段承载一次不由 Node 执行的
写入，并**禁止** clone 的 `ExecutionID` 与运行时 fencing 字段（`internal/cloneauth/authorization.go`
的字段存在性规则）。推送与 mirror_prepare 在这一点上同形——都由 C 执行、都由 Cloud 的单次授权驱动、
都在一个 ref 上产生远端副作用——因此 D3 复用 executor identity 与 ref 这两个字段而不是新造一套，同时
**不用** `PreparationGeneration`：那个字段存在是为了让"只有仍然当前的尝试可以发布"成立，而一次推送
不重试（重试是一份新授权，不变量 2），所以本文禁止它，而不是签一个没有检查读取它的值。

## 威胁模型

写权限比读权限更难撤销、更难审计，也更容易被当成绕过受控权限的捷径。本文的每一条决策都要能回答下表
中的一行；表中"今天的挡箭牌"一列说明在本文获批前是什么在阻止它，以免把"还没有这条路径"误当成
"已经防住了"。

| # | 威胁 | 手法 | 今天的挡箭牌 | 本文要求的边界 |
|---|---|---|---|---|
| T1 | 秘密外泄给 Agent | Agent 与会话身份 W 读取执行器物化的秘密或兑换响应 | C≠W 的 OS 隔离；Node 侧没有执行器 | D4：只由 C 执行，秘密只出现在 C 的进程内存与一次管道之间；D9 要求负向验收 |
| T2 | 授权被窃取后重放 | 截获单次授权，在别处或稍后再次兑换 | 只读方向已由 Store 的单次消费记录挡住 | D5、D6：用途绑定使 clone 授权不可兑换为写；单次消费对写向同样成立；重放返回"已消费"而不是重新签发 |
| T3 | 写入面被扩大 | 用一次授权更新多个 ref、删除 ref、改默认分支 | 不存在写路径 | D1、D3：一次授权恰好一个完整 ref 名与一个提交；禁止 `+`、删除、tag、通配 refspec |
| T4 | 历史被改写 | 强推覆盖远端已有提交 | 不存在写路径 | D3：新提交必须是该 ref 当前值的**后代**，且当前值被写进授权；祖先判定在做任何网络写入之前于本地完成 |
| T5 | upstream 被替换 | 授权写的是 A 仓库，实际推给同 host 的 B 仓库，或经重定向落到第三处 | 读向的 host＋path scope 校验已落地 | D3：upstream 是规范化仓库身份、逐字节比对，并进入物化 scope；禁重定向（写向同样 `http.followRedirects=false`） |
| T6 | 混淆代理（confused deputy） | 让 Agent 的会话事件、Thread 消息或工具调用被读成"人类批准了一次推送" | 不存在写路径 | D2：请求方必须是被认证、被授权的人通过受控入口发起的动作；Agent 的任何输出都不构成请求，也不构成批准 |
| T7 | 只读证据被复用为写许可 | 用一次成功的读取、验证或镜像同步推出写权限 | 词汇表不变量 5 | D2、D7：只读证据不得写回任何授权位；一次成功的推送也不得被复用为下一次推送的许可 |
| T8 | 远端结果被推断 | 响应丢失时把"可能已成功"记成成功，或盲目重试造成第二次写入 | 不存在写路径 | D7：不确定记为不确定，按稳定外部身份（ref 的当前提交）对账；重试需要新授权而不是重放 |
| T9 | 撤销不生效或撤销后被继续消费 | 撤销凭据之后仍用旧授权兑换，或物化残留 | 撤销先用例已覆盖读向 | D6：Cloud 的元数据变更是权威且先提交，撤销后兑换被拒；授权本身也可在到期前被作废 |
| T10 | 契约与实现漂移 | 枚举改了而强制点没改，或改了三处而 Store 不认 | 不存在写路径 | D8：四处强制点与公开契约必须同一次变更，生成产物不得手改 |
| T11 | 审计泄露秘密或丢失对象 | 审计行含 token、或无法回答"这次授权允许改什么" | 读向的 D7 审计只记 id 与结果 | D9：审计只记标识、ref、old/new 提交、结果码；不记任何秘密或可复原秘密的片段 |

## 决策

### D1：`push` 成为词汇表的第二个成员，判定规则一字不改

`capabilities` 的正向集合从 `["clone"]` 变为 `["clone", "push"]`，规范顺序固定为 `clone` 在前、
`push` 在后。除此之外，`CanonicalCapabilities` 的规则全部不变：空集合、未知成员、重复成员与不按规范
顺序仍被拒绝，`'[]'` 仍被读作"不允许任何操作"。

同时新增一个操作名 `push`，其 `permittedCapabilities` 返回恰好 `["push"]`——**不是**
`["clone", "push"]`。一次推送不需要读能力：写向作业读的是执行器自己的 checkout（推送执行权限
决定 D12 的"推送不依赖 checkout 所有权交接"），而把 `clone` 一并签进写向授权，等于让一次推送的授权
在兑换后还能被用来做一次读取。两个操作各自回答自己的能力集合，是既有代码的写法，本文照办。

能力名与操作名共用同一个拼写（`CapabilityClone` 与 `OperationClone` 今天都是 `"clone"`，
`internal/cloneauth/authorization.go:58`），`push` 照此办理：**能力** `push` 说的是"这条引用被允许
做什么"，**操作** `push` 说的是"这次作业在执行什么"。两者是不同维度的值，共用拼写不构成把它们混为
一谈的理由，但评审时值得确认这一点是有意为之。

**为什么不是"给 `clone` 加一个写标志"**：能力是引用的属性，一条引用的能力集合是它对**所有**后续操作
的授权面。把读写塞进同一个成员，等于让每一个今天只需要读的引用同时携带写授权，而撤销时无法说清撤销的
是哪一半。

### D2：一次推送＝一次单次人工授权，请求方永远不是 Agent

一次远端写入需要一份**单次**授权，与 clone 同构（`internal/cloneauth` 的 `Issue`／`Verify`）：
签名覆盖实际传输的字节，绑定项见 D3，有效期不超过一次推送命令预算且受 `MaxLifetime` 上限约束，
授权是 bearer、是秘密，不进日志、不进审计明细、不落任何持久介质。

请求方必须是：

- 一个**被认证且被授权的人**——凭据所属的项目所有者或管理员——通过受控入口发起的一次操作；或
- 产品自身**受控的交付流程**，且该流程的每一次写入仍然对应一个可具名到人的批准记录。

以下**不构成**推送请求，也不构成对某次推送的批准：Agent 的会话事件、Thread 消息、工具调用、
模型输出、任何由 Agent 写出的文件或提交信息。这条不是修辞：它是本文与"允许 Agent 提交代码"这一
产品想象的分界线，因此它必须是**结构性**的——授权只能由持有签名私钥的进程签发，而该私钥不在 Agent
可达的任何位置（推送执行权限决定 D5）。

**"单次人工授权"的确切含义**：每一份授权对应一次写入，消费一次即失效；授权不可批量预置、不可被
"以后再用"地持有、不可由系统在无人发起的情况下自行签发（这正是禁止自动 Push 的形状）；同一时刻
不存在"待用的写授权池"。若产品未来需要一个"批准后自动重试"的形态，那是本文范围之外的新决策，且必须
先回答重试与单次约束如何共存。

### D3：绑定是精确的——一个 upstream、一个完整 ref、一对提交

授权的绑定项在 clone 的绑定之上取 mirror_prepare 的形状（由 C 执行，不依赖 Node 运行时），并加入
写向特有的三项。存在性规则沿用既有做法：每个操作**禁止**另一个操作才需要的字段，而不是忽略它们。

| 绑定项 | 含义 | 存在性 |
|---|---|---|
| 租户、所有者、Project、Workspace | 这次推送属于谁 | 与既有操作一致 |
| 操作名与操作标识 | 这次推送是哪个受控流程的一步 | 必填，对应 `Binding.Operation`／`OperationID`；**禁止** clone 的 `ExecutionID` 与运行时 fencing 字段，也**禁止** mirror_prepare 的 `PreparationGeneration`（一次推送不重试，重试是一份新授权） |
| 执行者身份 | 只允许部署给 C 的那一个 SPIFFE 身份兑换 | 必填 `Binding.ExecutorIdentity`；Store 从已校验的客户端证书解析，不接受请求体自述 |
| 凭据 id 与版本 | 用哪一份凭据的哪个版本 | 必填；版本对着 Store 自己的记录校验 |
| **upstream** | 规范化仓库身份（小写 host 去掉 `:443`、path 去一个前导 `/`、一个尾随 `/` 与一个尾随 `.git`，不做百分号解码） | 必填；与凭据的 `repository_scope` **逐字节相等**，并作为物化 scope 交给 helper 比对 |
| **ref** | **完整** ref 名，逐字节比对 | 必填 `Binding.Ref`；不接受前缀、通配或 `refs/*` 形式 |
| **old commit** | 发起时观察到的该 ref 当前值 | 必填；在执行前对着远端再核一次 |
| **new commit** | 允许把该 ref 更新到的唯一提交 | 必填；执行器核对本地该提交确实存在且等于授权值 |
| 有效期与一次性 | 见 D2 | 必填 |

由此产生四条对外可观察的规则：

1. **一次授权只更新一个 ref。** 多 ref 一次授权不在本文范围内，因此**不存在部分成功**——写入面从
   "一个仓库"收窄到"一条引用的一个提交"。
2. **祖先关系在本地判定。** 执行器在做任何网络写入之前，先证明 old 是 new 的祖先；不成立即拒绝
   （这是"禁止 force"的完整含义，而不仅是"不加 `+`"）。因此强推覆盖远端既有提交在结构上不可能。
3. **当前值用比较交换固定。** 网络写入使用 `--force-with-lease=<完整ref>:<old>`，把远端该 ref 的值
   在服务端原子地钉在授权写下的 old 上。这是本文唯一出现"名字里带 force 的标志"的地方，而它**只可能
   收窄**：祖先判定已在本步骤之前于同一批对象上完成，lease 只保证远端没有被第三方移动；两者同时成立
   时，结果只能是一次快进。删除 ref、删除 tag、`--all`、`--mirror`、`--tags`、`--delete`、裸 `--force`
   一律不在允许范围内，且必须在准入处拒绝，而不是等远端拒绝。
4. **远端仍可能拒绝。** 受保护分支、权限不足、hook 拒绝都是稳定的远端拒绝结果，如实记为失败且不含
   远端细节；Cloud 不"修正"它，也不自动改用别的 ref 或别的 upstream。

**为什么把 old commit 也绑进去**：只绑 ref 名，授权就只是"允许改这条引用"，一个被移动过的远端会让
一次快进变成一次覆盖；只绑 new commit，执行器无法区分"远端就是我以为的那样"和"远端已经变了"。绑上
old 之后，"这次授权允许改什么"有了一个可以逐字节回答的答案，撤销与审计才有稳定对象。

### D4：只由部署固定的执行器（身份 C）执行

写向作业由与 clone 同一个部署固定执行器（`cmd/clone-executor`、`internal/cloneexec`）执行，凭
`ExecutorIdentity` 兑换凭据。Node 会话身份与 Agent **既不执行也不请求**推送，也不能选择执行器：
请求体、查询参数与客户端自述都不能指定它（沿用既有 Store 的"对端身份从证书解析"做法）。

写向作业的 Git 配置是读向配置的写向对应物，逐条都在命令行上以 `-c` 表达，使"被校验的配置"与"被使用
的配置"是同一份字节：

- 传输：`protocol.allow=never` 只放开 `https`，与读向相同——`ssh` 会绕开凭据路径，使 helper 的仓库
  范围失去意义；
- 凭据：清空继承的 helper 后只装部署固定的那个，并保持 `credential.useHttpPath=true`，使 helper 拿到
  path 而不是只有 host（该收紧已于 2026-10-13 落地）；
- 出网：`http.followRedirects=false`、`http.proxy=`、`http.sslVerify=true`，与读向相同；
- **写入面**：子进程环境沿用既有的**从零构建的白名单**做法（`internal/cloneexec/git.go:101-123`：
  `GIT_CONFIG_NOSYSTEM=1`、`GIT_CONFIG_GLOBAL=/dev/null`、`HOME` 指向一个什么都不含的目录、
  `GIT_TERMINAL_PROMPT=0`、`GIT_ASKPASS=`、`SSH_ASKPASS=`、`GIT_LFS_SKIP_SMUDGE=1`、`GIT_OPTIONAL_LOCKS=0`
  与固定的 `PATH`），因为继承后再过滤会让宿主级的 `credential.helper`、`url.<x>.insteadOf` 与
  `http.proxy` 落进一个从未被检查的窗口；hooks 继续由 `core.hooksPath=/dev/null` 关闭；不使用
  `--all`／`--mirror`／`--tags`；refspec 的两侧都写完整 ref 名；秘密不经环境变量传递。

  写向沿用**同一份**白名单，不新增环境变量：推送需要的是远端写入，不是本地索引锁。

**为什么不让 Node 会话（W）执行**：W 与 Agent 同身份，且没有 C 独占的物化根，秘密必然可被 Agent 读取
——这正是 clone 侧已经否掉的形态。

### D5：Store 的用途隔离——不新增能力、不新增交换面，写向也必须出示用途

Store 今天把三种互不重叠的能力分给三个身份：`write`（存、轮换、撤销）、`resolve`（兑换一个秘密）、
`keys`（部署侧密钥操作）（`internal/credentialstore/identity.go:18-26`）。**本文不新增第四种能力，也不
新增任何交换面**：推送复用既有的 `resolve` 路由，凭据只经既有的单次兑换路径到场。

但"复用同一条兑换路径"会带来一个新问题：clone 的授权与 push 的授权在那条路径上形状相同，Store 若只
比对凭据 id 与版本，一次 clone 授权就可能被拿去兑换出**写向**秘密。挡它的不是新的 Store 能力，而是既有
机制的一个必须成立的性质：

1. 用途在**签名载荷内**（`Binding.Operation` 与 `Binding.Capabilities`），Store 在验签之后比对它，
   因此用途不可由请求方自述改变；
2. 存在性规则禁止跨操作字段混装，因此一个"看起来像 clone 又像 push"的载荷在验签阶段就被拒绝
   （既有 `ErrAuthorizationPurpose` 的语义）；
3. 兑换出的秘密只是 token 本身——**凭据不带"只能读"或"可以写"的标注**，写权限完全由远端对该 token 的
   授权与 Git 的 ref 规则决定。这一点必须写清楚：Store 隔离的是**用途与兑换**，不是 token 的远端权限；
   因此 D3 的 ref／commit 约束与 D4 的执行器约束是真正的写入面控制，Store 侧不是。

单次消费的顺序不变，且对写向同样不可颠倒：**先校验、再落消费记录、才交付秘密**。崩溃只允许留下
"已消费未交付"，绝不允许"已交付、消费记录缺失"。消费记录只记授权标识、时刻、出示者与结果，不含秘密
或任何可复原秘密的片段。

### D6：撤销与重放

| 情形 | 对外结果 | 持久事实与恢复 |
|---|---|---|
| 授权从未兑换 | 无任何远端写入 | 无；授权到期即失效 |
| 授权已消费 | 拒绝，码区分"已消费"与"过期" | 消费记录已落；不得重放，重试必须重新签发（D7） |
| 凭据在签发后被撤销 | 兑换被拒（`credential_revoked`） | Cloud 的元数据变更是权威且先提交，凭据自该时刻起不可用；物化销毁是尽力而为，未确认销毁的记为残留而不是报成撤销失败 |
| 凭据在兑换后、写入前被撤销 | 写向作业终止，不执行远端写入——**限于复核在写入命令之前观察到该撤销**（竞态边界见下） | 已消费的授权不因撤销而复活；已交付的秘密随作业收尾销毁 |
| 物化残留 | 记为残留 | 撤销不报告为"失败"，但残留必须可见；不得因残留而放宽后续判定 |
| 授权提前作废 | 兑换被拒 | 作废只影响未消费的授权；已消费的授权本来就不可重放 |

**兑换之后、写入之前的复核。** 兑换与远端写入是两个不同的时刻，因此撤销有两个判定点；只做第一个
判定点，就等于把"兑换时还有效"当成"写入时仍然有效"：

1. **兑换时**：Store 用自己的记录判定凭据版本可用且未被撤销（上表第 3 行）。这是权威判定，输入是 Store
   自己的状态，而不是载荷里的自述。
2. **写入前**：执行器在发起**任何网络写入之前**，必须再取得一次该凭据的权威可用性判定。Cloud 的元数据是
   权威来源；这次判定走哪条通道属于落地顺序第 4 步的实现选择，本文只固定两件事——它必须发生在写入命令
   之前，且它的输入必须是权威状态而不是缓存、不是载荷自述、不是上一次兑换的结论。判定不通过即终止作业。

复核失败一律 **fail-closed**，且"失败"包括全部三种情形，不区分对待：**复核被拒**（凭据已撤销，或版本已
不可用）、**复核不可得**（Cloud 不可达、超时、响应不可解析）、**复核没有给出权威结论**（只读到缓存、
只读到自述值）。三者都终止作业：不发起任何网络写入、销毁物化、按上表把未确认销毁的记为残留，并把该次
授权结算为"未写入"。复核失败不得降级为一条告警后继续，也不得把"不确定"读成"可以继续"。

**竞态边界（不承诺系统无法保证的原子性）。** 协议能保证的是"**复核通过之后才发起写入**"，不能保证
"复核与写入之间被撤销的凭据一定不会写入"。撤销提交在 Cloud 的元数据上，远端写入在用户的远端仓库上，
两者之间没有共同的事务，也没有任何协议能把一次已经被远端接受的写入收回。因此：

- 撤销**不约束已经发起网络写入**的作业：对那一次写入，撤销什么都没有阻止，也不能声称"撤销阻止了写入"。
- 复核通过、写入随后发起、撤销在两者之间提交，这一窗口内的写入必须如实记为**不确定**（D7），不得记为
  "撤销生效"。审计里"撤销发生了"与"这次写入的结果是什么"是两件事，不得互相顶替。
- 由此，D9 第 6 条的验收对象是**写入之前**的撤销，其证据必须落在"复核发生在写入命令之前"这一**顺序**上；
  仅凭"撤销之后没有观察到写入"不足以证明该义务成立（那也可能只是这次写入本来就失败了）。

撤销与 D7 的"不确定"共用同一个判据：**撤销后的对账只读远端，不重放写入**。

### D7：远端结果不确定性——不确定记为不确定，对账按 ref 的当前提交

写入的终态只有三种，且必须如实区分。但"成功"那一格里有**两件不同的事实**，把它们分开是本节的关键：
**观察到远端该 ref 等于授权的 new commit，只证明目标状态符合预期，不证明这次写入是本次作业做的。**
远端是一个多方都能写入的地方：一个"现在等于 new"的观察可以由本次作业造成，也可以由另一次写入造成，
而一次读取无法在事后把两者区分开。

| 终态 | 判据 | 持久事实 |
|---|---|---|
| **已确认达成** | 远端该 ref 的当前值等于授权的 new commit，且这是本次作业自己的观察。达成**必须**同时记录归属，二选一：**本次写入已被证实**（有可归因于本次作业的证据，例如远端对本次会话该 refspec 的成功响应，或服务端为该次会话记录的结果）／**写入者不可归因**（只有观察到的值，没有可归因证据） | 记达成，并记下 ref、old/new 与归属；只有"本次写入已被证实"才可以在面向人的结论里写成"本次推送成功" |
| **已确认失败** | 远端明确拒绝，或写入前本地判定不成立 | 记稳定的失败码，不含远端细节 |
| **不确定** | 连接中断、响应丢失、进程被杀、执行器失联，且尚未取得上述任何一条可观察结论 | **记不确定**，并留下足够的对账依据（upstream、ref、old、new、授权标识） |

**归属不可证时不得伪造结论。** 观察到"远端等于 new"而本次作业没有收到可归因的成功响应时，唯一成立的
结论是"目标状态已满足、写入者不可归因"：不得因为"多半是本次写入造成的"就记为成功（那是把概率写成
事实），也不得反过来推断"某个第三方写入了 new"（那是发明一个本文没有证据的写入者）。审计里保留的是
可观察事实本身——观察到的 ref 值、观测时刻、观测者——以及"本次写入不可归因"这一结论。

不确定性下的四条规则：

1. **不得推断成功。** 一次未收到确认的推送不得被记为成功，也不得被记为失败——两者都是编造。
2. **不得盲目重放。** 重放同一份授权被 Store 以"已消费"拒绝（D5）；即使技术上可行也不允许，因为一次
   重放可能造成第二次写入或一次覆盖。
3. **对账按稳定外部身份。** 恢复判据是"远端该 ref 的当前值是什么"：等于 new 即**目标状态已满足**
   （是否由本次写入造成仍需归属，不可归因时不得作出该结论），等于 old 即目标状态尚未满足，等于第三个
   值即期间有第三方写入且本次授权已经失效。对账只读远端（`ls-remote` 一类），不写入。
4. **归属不因对账而补记。** 对账能补上的只有"目标状态如何"，补不上"是谁写的"——一次事后读取永远
   无法把写入者证出来。因此因响应丢失而落到不确定或不可归因的作业，其归属结论是终局的，不因后来观察
   到 new 而改写为成功。

**一次成功不得被复用为下一次的许可**（承接词汇表不变量 5）：一次推送成功只结算该次授权，不写回任何
授权位、不产生可用于下一次推送的授权、不改变引用或 Project 的能力与范围。

### D8：公开契约与四处强制点必须同一次变更

`capabilities` 是公开契约里的枚举（`internal/contract/openapi.go:114`），因此这次扩展**同时是一次公开
契约变更**：Go 契约源、`api/openapi.json` 与 `frontend/src/api` 的生成产物必须在同一次变更里更新
（`task frontend:generate`），生成产物不得手改。若推送需要一个新的请求面，该请求面的形状也必须在这一
次变更里定稿，并遵循既有边界：严格解码（拒绝未知字段、多余 JSON 值、错误类型）、拒绝服务端自有的身份
与范围字段、把幂等键与外部效应计划在派发之前持久化。

四处强制点缺一不算实现，**且第四处是本文新增的要求**：

1. **准入**（`internal/core`）：所需能力是 `push`，可得能力来自引用的当前行，请求方自述不增加能力；
2. **签发**（`internal/cloneauth`）：能力集合进入签名载荷，`permittedCapabilities("push")` 返回恰好
   `["push"]`，有效期受上限约束；
3. **执行**（`internal/cloneexec`）：逐字比对绑定，包括能力、upstream、ref、old、new 与执行者身份；
4. **兑换**（`internal/credentialstore`）：用途与绑定在验签后比对，单次消费原子成立。

### D9：审计与隔离的验收标准

**审计**（不变量 12 的可观测面）：每一次写向作业都必须能回答"哪个被授权的人、在什么受控流程下、用哪一份
凭据的哪个版本、把哪个 upstream 的哪条 ref 从哪个提交更新到哪个提交、结果是什么（达成时还必须记录它是否
可归因于本次写入）"。审计与日志只含标识、
ref、old/new 提交与稳定结果码；不含 token、不含任何可复原秘密的片段、不含授权本身。Agent 可见的部分
只有元数据。

**隔离验收**（Issue #16 验收第 2 项的推送一侧）：以下每一条都必须有**直接**证据，缺一即 `Missing`：

1. 真实私有仓库、真实远端、受控凭据；不得用 mock、内部交付 ref 通道或定向单测顶替（不变量 14；推送执行
   权限 D8）；
2. 一次授权消费一次即失效，重放被拒（含重启后仍被拒）；
3. ref 与提交严格按授权执行：授权外的 ref 被拒、old 不匹配被拒、非后代被拒、force／delete／wildcard
   被准入处拒绝而非依赖远端；
4. Agent（身份 W）读不到秘密：以负向控制证明物化根与兑换响应都不可达，而不是只断言"没看到"；
5. 执行结束（成功、失败、超时、中断）后物化被销毁，残留被如实记录；
6. 撤销在写入前生效即阻止写入，撤销后对账不重放；
7. 不确定终态被记为不确定，并能按远端当前值对账出三种结果；
8. 秘密不进入 Node、Agent、浏览器、Cloud 业务库、日志、存储卷或 Revision；
9. 只读证据与一次推送成功都不得被复用为写许可（T7）。

**本文不能声称的事**：这些判据在本文获批并实现之前一条都没有证据，推送一侧继续如实标 `Missing`。
本文只固定判据，不产生任何证据。

### D10：首版凭据的选择——独立、最小权限的 Push 写凭据

**首版部署为推送单独配置一份最小权限的写凭据**，而不是复用 clone 用的那份材料。这是一条**部署选择的
偏好**，不是不变量：它不改变任何拒绝路径，也不构成写入面的控制。

必须区分两个层面，把它们混起来会把"授权隔离"误当成"凭据隔离"：

- **同一次授权**（同一个单次 bearer）：本文**已经**结构性禁止跨用——`permittedCapabilities("push")`
  返回恰好 `["push"]`（D1），用途在签名载荷内、由 Store 验签后比对（D5），clone 的 `ExecutionID` 与
  运行时字段在 push 载荷里是禁止字段（D3）。**不存在"通过 Clone 授权获得 Push 权限"的路径**，这一点
  与凭据怎么配无关。
- **同一份凭据材料**（同一个 token、同一行 `credential_refs`）：这是部署选择。D3 只要求授权绑定"凭据
  id 与版本"，两种配法都合规。

**为什么首版优先独立**：D5 第 3 点写明凭据不带读写标注，**写权限由远端对该 token 的授权决定**，Store
不控制它。复用同一份材料时，远端侧该 token 的写权限就是恒定存在的；配一份作用域更窄（仅目标仓库）、
可独立轮换与撤销的写凭据，等于在远端侧增加一层与 Cloud 侧正交的约束，撤销时也不必连带撤销读凭据。

**边界**：独立凭据是**纵深，不是替代**。D3 的 ref／commit 约束与 D4 的执行器约束仍是真正的写入面
控制，D9 的九条验收一条都不能少。两种配法都不能免除本文的任何一条不变量：Push 必须有自己的授权
（不变量 2、8）。

## 不变量

1. `push` 是词汇表的第二个成员，规范顺序为 `clone` 在前、`push` 在后；除成员集合外，`CanonicalCapabilities`
   的判定规则一字不改，`'[]'` 继续被读作"不允许任何操作"。
2. 一次推送对应一次单次人工授权；授权不可重放，重试必须重新签发；不存在待用的写授权池，也不存在无人
   发起时自行签发的路径。
3. 一次授权恰好绑定一个 upstream、一个完整 ref 名与一对提交（old／new）；不存在多 ref 授权，因而不存在
   部分成功。
4. new commit 必须是 old commit 的后代，祖先判定在做任何网络写入之前于本地完成；因此强推覆盖既有提交在
   结构上不可能。
5. 禁止 force、删除 ref、删除 tag 与任何通配或前缀 refspec；这些在准入处拒绝，不依赖远端拒绝。
6. upstream 是规范化仓库身份，与凭据的 `repository_scope` 逐字节相等，并进入物化 scope 由 helper 比对。
7. 推送只由部署固定的执行器（身份 C）执行；Node 会话与 Agent 不执行、不请求、不选择执行器。
8. 请求方必须是被认证且被授权的人或产品自身受控的交付流程；Agent 的会话事件、Thread 消息与工具调用
   不构成请求，也不构成批准。
9. Store 不新增能力、不新增交换面；用途与绑定在验签后比对，单次消费的顺序（校验 → 落消费记录 → 交付）
   不可颠倒。
10. 远端结果只有"已确认达成／已确认失败／不确定"三种终态；"已确认达成"必须同时记录归属（本次写入已被
    证实／写入者不可归因），无法归因时不得记为成功；不确定不得推断为成功或失败。
11. 恢复只按远端该 ref 的当前值对账，只读远端，不重放写入。
12. 审计只含标识、ref、old/new 提交与稳定结果码，不含秘密、授权或任何可复原秘密的片段。
13. 公开契约枚举与四处强制点必须在同一次变更里同时更新，生成产物不得手改。
14. 内部交付 ref 通道与用户远端仓库写入是两条通道；任何一侧的证据都不得充当另一侧的。
15. 本文获批不解除任何 fail-closed，也不改变任何既有引用的能力：一条今天写着 `["clone"]` 的引用在
    本文获批后依然是 `["clone"]`。本文获批也不构成本文落地顺序第 4、5 步的授权。

## 为什么不是这些替代方案

| 方案 | 优势 | 否决理由 |
|---|---|---|
| 让 Agent 用同一身份推送 | 一步打通"Agent 提交代码" | 直接违反不变量 7、8：写权限落到会话身份上，"能不能推"就取决于提示词与工具白名单，撤销与审计都没有稳定对象（T1、T6） |
| 给 `clone` 加一个写标志 | 不用新增枚举成员 | 能力是引用的属性，读写塞进同一成员会让每个只需读的引用同时携带写授权，撤销时无法说清撤销的是哪一半（D1） |
| 保留"ref 范围"，允许多 ref 一次授权 | 更贴近一次交付的直觉 | 多 ref 意味着部分成功，而部分成功的结算、撤销与审计都要求逐 ref 记账；把写入面收窄到一个提交使这三者同时变简单（不变量 3、D7） |
| 不绑 old commit，只绑 ref 与 new | 少一次远端读取 | 远端被第三方移动时，一次本意是快进的写入会变成覆盖；绑上 old 才有"这次授权允许改什么"的可逐字节回答（D3、T4） |
| 用 `--force` 保证"推得上去" | 实现最省事 | force 直接违反推送执行权限 D3 与本文不变量 4、5；"推不上去"是正确的失败，不是要绕开的障碍 |
| 只做前端的 `ls-remote` 检查，不用 lease | 不依赖 lease 语义 | 检查与写入之间的窗口可被第三方写入利用；lease 把 check-and-set 放到服务端原子完成（D3 第 3 条） |
| 响应丢失时按"大概率成功"记为成功 | 避免用户看到一个含糊状态 | 把不确定性伪装成事实，正是 Cloud 既有规则禁止的推断（D7、不变量 10） |
| 响应丢失时自动重试同一授权 | 体验上"重试即成功" | 重放被 Store 拒绝，且一次重放可能造成第二次写入或一次覆盖；重试必须重新签发（D2、D7） |
| 给推送新增一种 Store 能力或新路由 | 让 Store 能区分读写 | 凭据本身不带读写标注，Store 能区分的只有用途；新增能力会扩大 Store 的攻击面而不增加真实控制（D5） |
| 复用 `mirror_prepare` 操作承载推送 | 少一个操作名 | 那个操作用户远端仓库之外的内部交付地址；两者是不同的信任边界与不同的对象，混用会让一侧的证据冒充另一侧（不变量 14） |
| 本文顺手把产品入口与审批链也定下来 | 一次裁决到位 | 推送执行权限 D2 与本 ADR 都只回答"谁不构成请求方"；入口形态是产品决策，塞进来会让两件事都无法单独评审（"本决策未解决的问题"） |

## 失败与恢复语义

| 情形 | 对外结果 | 持久事实与恢复 |
|---|---|---|
| 引用未声明 `push` | 准入拒绝，稳定能力码 | 不产生授权；不改变引用（不变量 15） |
| 没有授权、授权过期或已被消费 | 拒绝，码区分"未授权／已消费／过期" | 无远端写入；需要重新签发 |
| 请求方是 Agent 或无法具名到人 | 准入拒绝 | 无授权产生；这是 T6 的判据 |
| ref 不在授权内（不同名、前缀或通配） | 准入拒绝 | 无远端写入；授权不因被拒绝而复活 |
| old commit 与远端当前值不符 | 执行期拒绝 | 无远端写入；授权作废，需要按新观察值重新签发 |
| new 不是 old 的后代 | 本地拒绝，做任何网络写入之前 | 无远端写入；提示需要先合并或变基后重新申请 |
| 远端拒绝（受保护分支、权限不足、hook） | 稳定的远端拒绝码，不含远端细节 | Blame 在远端策略；不自动改用其他 ref 或 upstream |
| 网络超时或中断 | 终态"不确定" | 留下对账依据；按远端当前值对账，不重放（D7） |
| 执行结束（任何终态） | 物化销毁，失败也执行 | 已消费授权不得重放；残留如实记录 |
| 执行器不可用 | `repository_credential_executor_unavailable` 一类部署级拒绝 | 与 clone 相同：部署级拒绝优先，不改写引用状态 |
