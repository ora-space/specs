# 删除对话时回收它的工作目录：成果能由运维从交付恢复、或用户明确丢弃时才删；先在删除的事务里登记，再按精确归属删除，失败和崩溃后启动时继续

用户显式删除一个普通对话时，Cloud 判断这个对话的工作目录能不能由运维从回合交付恢复：会话的最后一轮交付成功、
之后目录没有再变、Agent 的仓库里没有交付带不走的东西（stash、没检出的分支、嵌套仓库）。能恢复的，目录随对话
一起回收；不能恢复的默认保留，只有用户在删除时明确选择丢弃，才一起回收。删除前，界面先列出会丢什么，并在确认
删除之前提供下载 patch 的入口，因为对话删除之后它的交付对用户不再可读，只有运维能按本文的步骤恢复。回收不在删除
请求里直接删目录了事：删除对话的同一个事务里先登记一条**工作目录回收**，再按登记去删；删除失败或 Cloud 崩溃，
登记还在，下次启动接着做。删的时候确认目录只属于这个对话、没有会话还在用、路径没有经符号链接逃出 checkout 根。

本 ADR 为 `implemented`：owner 2026-11-19 在 circus #1318 评审通过，由 circus #1196 的运行 #1319 实现（cloud PR #419，
`d4ec60d5`）；后续 circus #1354（运行 #1387，cloud PR #435，`fe0b378b`）补上嵌套 Git 目录内的摘要边界，见 D2。实现中对 approved 稿的修改见“实现时的修改”一节，核心测试用例见
[工作目录回收用例](../../../test-cases/cloud/project-git/workspace-reclaim.md)。依据是 owner 2026-11-16 在 circus #1191
选定的方案 A 第二阶段和 2026-11-19 在 #1196 列出的判断条件；实测依据是 #1119：24 小时内 101 个工作目录全部保留，
其中 45 个属于已删除的普通对话。它是[回合交付](20261112-single-machine-turn-delivery.md)（下称“交付 ADR”）的后续决策，同时修改
[Cloud 单进程根决策](../lifecycle/0-single-process-cloud-on-enterprise-intranet.md)（下称“A1”）的 D3 与 D7 第 3 条。

范围与兼容性边界：

- **涉及**：cloud 的 `v2-server/`（删除对话、回收登记、启动、`workspacefs`、`agentruntime`、运维子命令）和
  `frontend-v2/` 的删除确认框。对话删除接口多一个可选参数、返回回收结果，多一个预览接口。desktop 的 Node 不改。
- **只回收普通对话的工作目录**。工作流运行（共享目录，含整体删除）、任务运行的目录不在本文，以后另写决策。活跃会话
  的目录永远不回收。
- **不在回收范围**：Node 的会话历史 JSONL、Node 的账本、PostgreSQL 记录（含 `v2_workspaces`、交付记录与交付义务）、
  项目镜像、快照 ref、交付 ref。ModelAccess 的临时目录和服务临时包继续由原有生命周期释放。不加任何定时清理。
- **不做数据迁移**：本文落地之前已经删除的对话，目录的归属已随对话记录删除，本文不去找回；需要释放时由运维在停服后
  `-cleanup` 整体清理。本文落地之后用户删除的对话才按本文处理。

## 继承与修改

| 前序约定 | 本文处理 |
| --- | --- |
| 交付 ADR D2：交付只取工作目录里未被忽略的文件的树；不碰、不引用 Agent 的 stash、分支和提交；子仓库只记一个 gitlink 指针 | 继承：交付带不走的这些 Git 状态，使目录判为不能恢复（D1 第 4 条） |
| 交付 ADR D3：每个被接收的回合登记交付义务、至多一条交付记录 | 继承：判定按登记的会话直接查回合、交付记录与交付义务（D1） |
| 交付 ADR D4：对话被删除后，它的交付都不可读 | 继承，不变。所以“能恢复”只承诺**运维**能从镜像里的交付 ref 恢复（D6）；用户要留一份，须在确认删除之前下载 patch（D2） |
| 交付 ADR D6：删除对话时，交付记录和交付 ref 留着；第一版全部保留 | 继承，不变；本文只增加“工作目录可以回收” |
| A1 D3：“工作目录被删除，改动就没有了”（隐含 Cloud 从不删除工作目录，只有运维停服后 `-cleanup` 整体删除） | **修改**：用户删除普通对话时，Cloud 按本文回收这个对话的工作目录；其余工作目录仍不由 Cloud 删除 |
| A1 D7 第 3 条：Cloud 读 Node 的工作目录只经一个模块（`workspacefs`） | **修改**：删除工作目录也只经这个模块；它从“只读”变为“读与按本文删除” |
| A1 D7 第 1 条：Cloud 和 Node 只经 Node 协议通信 | 继承：回收不改 Node 的进程状态和账本；单机下直接删磁盘上的目录，多机时要改 Node 协议（“本决策未解决的问题”2） |
| v2-server 现状：删除对话先结束活着的会话，确认不了就不删 | 继承，不变；回收登记在会话确认结束之后（D3） |

## 决策

### D1：什么样的工作目录算“能恢复”

回收登记记着会话 ID 和工作目录身份（D3），判定按登记直接查 `v2_execution_turns`、`v2_turn_deliveries`、
`v2_turn_delivery_work`，不依赖对话记录还在（`WorkspaceDeliveryView` 要求对话行存在，删除提交后会返回不存在，所以不
复用它）。**最后一轮**指这个会话在 `v2_execution_turns` 里位置最大的回合，被接收的回合都算，包括 Agent 还没开始就被
停止的回合。

工作目录能恢复，当且仅当下面五条同时成立；判为不能恢复时给出第一条不满足的原因：

| # | 条件 | 不满足时的原因 |
| --- | --- | --- |
| 1 | 会话的所有回合都已结束，且这个会话没有交付义务（`v2_turn_delivery_work` 里没有它的回合，即 `HasWork` 为假，不是只看 `InProgress`） | `delivering`：还有回合在跑、在交付，或交付义务留给了下次启动（含第一轮还在跑的新对话） |
| 2 | 会话至少有一条回合交付记录 | `legacy`：没有交付记录且没有交付义务，即交付 ADR 落地前的旧会话 |
| 3 | 最后一轮有交付记录，结果是 `delivered` 或 `empty`（用现有的 `turn_id`、`position` 列判断，不加新列） | `last_turn_undelivered`：最后一轮交付失败，或最近一条记录落在更早的回合上 |
| 4 | Agent 仓库里没有交付带不走的 Git 状态：没有 `refs/stash`；`refs/remotes/` 之外的每个本地 ref 都指向起点提交、起点的祖先或 `HEAD` 的祖先（含 `HEAD` 本身）；指向的对象剥开（annotated tag 剥成提交）后是提交，指向非提交对象的判为不满足；`HEAD` 是起点或起点的祖先，或者 `HEAD` 提交的树里每个路径的内容都与比对的交付树或起点树的同路径条目相同；index 没有冲突，每个条目都等于比对的交付树、起点树或（`HEAD` 合格时）`HEAD` 的同路径条目（intent-to-add 只要求交付树里有这个路径，物化技能路径先剔除）；交付树里没有和起点不同的 gitlink；顶层 `.git/modules/` 下没有仓库；顶层以下没有任何名为 `.git` 的条目（目录、gitfile、符号链接都算，被忽略的目录如 `vendor/` 也扫） | `git_state` |
| 5 | 目录在最后一轮交付之后没有再变：按交付的快照规则（交付 ADR D2 的临时索引、忽略规则、物化技能剔除）重新生成树，与最后一次 `delivered` 交付提交的树相同（最后一轮是 `empty` 时与起点的树相同） | `changed_after_delivery`；内容本身无法验证（排除文件或 Git 元数据不能安全读取、改动超过交付大小上限、分不清物化的技能）时为 `unverifiable`；
  磁盘、镜像或 Git 调用临时失败不是 `unverifiable`，按 D3 重试 |

- 第 4 条的检查只读：ref 与 stash 在 Agent 仓库上用 Git 查询（只运行列 ref、算祖先这类不调用外部程序的命令），命令行覆盖
  全局与系统配置、hooks、fsmonitor，不弹认证提示；Git 仍会读这个仓库自己的本地配置，但这些命令不执行 filter 等外部程序，
  第一版 Agent 与 Cloud 是同一个系统用户（A1 D2），这不扩大 Agent 的权限。gitlink 与嵌套 `.git` 按第 5 条生成的树和不跟随
  链接的遍历检查。命令行覆盖的配置至少包括 `core.fsmonitor`、`core.hooksPath`。顶层 `.git` 不存在时（Agent 删掉了它）没有
  本地 ref 和 stash 可查，只查嵌套 `.git` 和 gitlink；顶层 `.git` 存在但解析不出来（gitfile 指向不存在或越界的位置等）判为
  `unverifiable`，不当作“没有 `.git`”跳过。reflog 和 `ORIG_HEAD`、`MERGE_HEAD`、`FETCH_HEAD` 这类伪 ref 不算成果。`HEAD` 解析不出可读的提交时，只有它**直接**
  指向不存在的 ref 的符号引用（还没有任何提交）才跳过 `HEAD` 的比对，其余（detached 的对象 ID 解析不了、指向的 ref 存在却读不出
  提交、读不出它的树）都判 `unverifiable`；ref、stash、提交遍历遇到对象缺失或损坏同样判 `unverifiable`，其他 Git 调用失败（读不到、IO、权限、
  启动失败、超时与取消）按 `check_failed` 重试；输出里同时有 IO 或权限诊断时，按可重试处理，优先于随后的“对象缺失”类描述；
  `HEAD` 的直接目标直接读 `HEAD` 文件得到，不依赖较新 Git 的参数；“提交缺失”还要在磁盘上确认（对象目录可读且没有这个对象、
  pack 都能打开、没有 alternates），确认不了按可重试。`HEAD` 解析失败时按诊断依次判定：超时或取消、IO 或权限诊断按可重试；明确的对象损坏、对象不存在或不是提交判
  `unverifiable`；没有任何诊断的失败按可重试。ref 不只信 Git 列出的结果：还直接读公共 Git 目录和工作树 Git 目录里的 loose ref 与
  `packed-refs`，只看 Git 会当作 ref 的名字（按 `check-ref-format` 的规则，跳过 `.lock` 等被中断的 Git 留下的文件），内容必须是合法的对象 ID
  或符号引用（先于运行 Git 校验格式，`packed-refs` 按 Git 的读法逐行校验结构），且对象 ID 形式的都出现在 Git 列出的结果里，否则判 `unverifiable`
  （Git 会跳过损坏的 ref 并照样成功退出）。
- 嵌套仓库全部判为不能恢复：`git submodule update --init`、`git worktree add` 生成的 `.git` 是 gitfile，子模块里没提交的改动
  不改变 gitlink，只按“名为 `.git` 的目录”或只比 gitlink 会让默认的 `reclaim` 删掉它们。
- 第 5 条生成的树只在临时 Git 目录里，不写镜像、不写交付 ref；生成期间持有交付对这个目录的锁（`DeliveryFS.LockWorkspace`），
  和交付互斥。
- 被忽略规则（`.gitignore` 与 `.git/info/exclude`）排除的文件不算成果：交付的定义就是未被忽略的文件，验收和 patch 也
  只给这些。目录里确实有被忽略的文件时，删除前告诉用户（D2）。检测时 `.opencode`、`.claude` 两个目录整体不计（物化的技能在里面），
  这两处用户自己被忽略的文件不提示，作为已知限制。

为什么只看最后一轮、再比对树：每次交付都是相对起点的完整快照（交付 ADR D2），最后一轮交付成功，说明**那一刻**的
工作目录都在交付 ref 里；之后目录还可能变（Agent 留在后台的进程写文件、空闲会话被删除时不会再交付一次），比对树把
“那一刻”推到“回收的这一刻”。只看最近一条交付记录会漏掉后面没有登记交付的回合。

为什么 Git 状态算不能恢复：交付只取工作目录的树。Agent 存进 stash 的改动、提交在没检出的分支上的改动、嵌套仓库里
的提交都不在树里；子仓库在交付里只是一个指针，指向的提交只在工作目录里。这些东西只在目录里有一份，删了就没了。

### D2：删除前告诉用户，确认删除前可以下载，删除时由用户选

- **预览**：新增一个只读接口，返回：
  - `workspace`：`none`（附 `no_workspace`：会话没有登记过工作目录，例如首轮结果不确定、会话为空；或 `workspace_missing`：
    登记过但目录已不存在）、`recoverable`、`undelivered`（附 D1 的原因）；
  - `ignored`：`recoverable` 时目录里有没有被忽略规则排除的文件，只有确实有时界面才提示；
  - `undeliveredChanges`：`undelivered` 时相对最后一次成功交付（没有时相对起点）列出未交付的改动（路径、增删），有上限，
    超过时给出总数；只有内容检查成功时才列出（`legacy` 相对起点列出）；`delivering` 不做检查，检查判为 `unverifiable` 时也
    不填，这时可能保留 `legacy`、`last_turn_undelivered` 等原因，空列表不代表没有未交付的改动；
  - `git`：原因是 `git_state` 时列出发现了什么（`revision` 始终包含 Git 状态）：stash 数量、有问题的 ref 名和各自不在起点与 `HEAD` 祖先里的提交数、
    `HEAD` 与交付不一致（`headDiffers`，及超出起点的提交数）、index 与交付不一致（`indexDiffers`）、
    嵌套仓库的路径（顶层以下的 `.git`、`.git/modules/` 下的仓库和变动过的 gitlink 合并去重）。这时 `undeliveredChanges` 可能为空，界面不能显示“未交付的改动：无”；
  - `latestDelivery`：最近一次 `delivered` 交付的 ID，界面据此提供现有的 `…/workspace/deliveries/{id}/patch` 下载；
  - `discardable`：只有判为 `undelivered`、不在交付中、做过内容检查并且 Git 相关内容的摘要完整时为真，界面据此决定给不给
    丢弃选项；
  - `revision`：这份预览所依据的状态的标识，包含最后一轮、最近一次交付、判定与原因、按交付规则生成的快照树，以及**会随目录
    删除、交付又带不走的 Git 相关内容的字节摘要**：顶层仓库每个 ref 的目标、`HEAD`、stash 每一条的对象 ID 和 index 文件的
    内容；每个嵌套仓库的整棵子树（工作树和它的 Git 目录，对象在内）；嵌套仓库的 `.git` 是 gitfile、符号链接或含 `commondir`
    的目录时，指向的 Git 目录在 checkout 内就连同整棵目标（同一目录只算一次）。摘要读文件不调 Git、不跟随链接，先 `Lstat`
    再以不跟随、非阻塞的方式打开并复核；与交付共用字节上限，条目上限 10 万。超出上限、遇到特殊文件、读取失败、指向 checkout
    之外或解析不了，摘要都记为不完整，并且一旦不完整不会再恢复。嵌套 Git 目录内部同样不跟随：目录里出现符号链接或特殊文件、
    每个解析到的 Git 目录（及顶层 `.git/modules/<name>`）下存在 `objects/info/alternates`（只查这一层；没有被工作树解析到的
    更深层 Git 目录——例如嵌套仓库已 deinit 的 `.git/modules/<x>`——不查，因为 ref 已经绑定，加不出可达的成果）、
    `.git/modules/<name>` 里存在 `commondir`，或者 Git 目录解析到 checkout 根，都判摘要不完整（`discardable` 为假，`discard`
    按下方顺序校验，默认删除保留的目录由运维按 D6 处理）；fail-closed 的代价是嵌套仓库的 hook 是符号链接、
    `clone --shared`/`--reference`、`submodule.alternateLocation` 这些合法布局同样不可丢弃，交运维处理；嵌套仓库工作树里的符号链接
    仍只记录链接目标，不影响摘要是否完整。所以同一路径、同样增删行数的内容改写，stash 被替换、ref 改指向、暂存区被替换，
    都会改变它；`discard` 时要带回。顶层 `.git` 含 `commondir` 时不另读共享仓库：顶层的 ref 是在 checkout 上列出的，已经包含
    共享仓库里的全部 ref 及其目标，没有 ref 指向的对象不算会丢掉的成果。
- **删除参数** `workspace`：
  - `reclaim`（默认，调用方不带参数时也是它）：能恢复就回收；不能恢复就保留目录，对话照样删除；
  - `discard`：用户明确丢弃，不管能不能恢复都回收。请求必须带回预览的 `revision`（不带时返回 400）；删除时（结束会话之前）重新计算，
    不一致、或还在交付（`delivering`），返回 `409 deletion_preview_stale`，对话和目录都不动，界面重新取预览。之后判为
    `undelivered` 而 `discardable` 为假（`unverifiable`、Git 相关内容的摘要不完整）时，返回 `409 discard_unverifiable`，什么都
    不动；默认删除照常，不能恢复的目录保留，由运维按 D6 处理。`revision` 一致而判为 `recoverable` 或 `none` 时，`discard` 照常
    删除对话，按判定回收或不涉及目录（这时没有未交付的东西可丢）。界面只在 `discardable` 为真时提供丢弃选项。
- **删除的返回值** `workspace`：`reclaimed`（已回收，附释放的字节数和文件数）、`kept`（附原因）、`pending`（附原因：
  `delivering`；`in_progress`，后台继续删；`check_failed`、`removal_failed`，等启动时重试；`reclaim_unavailable`，见下）、`none`。
- **Cloud 没有 Agent 运行时、无法判定时**（例如没有配置 Node 资产启动，但磁盘上还有以前的 checkout）：对登记过工作目录的
  对话，预览和 `discard` 在结束会话和删除事务之前返回 `503 workspace_reclaim_unavailable`，什么都不改；默认 `reclaim` 照常
  删除对话、登记 `pending`，返回 `pending`/`reclaim_unavailable`，留给以后有运行时的启动按 D1 判定。界面说明“删除后先保留，
  等能检查时再按交付情况决定是否回收”，不提供丢弃；预览读不到时禁用删除并提供重试。删除结果以删除时的判定为准，可能和预览不同。
- **界面**：确认框按预览说明后果。
  - `recoverable`：说明工作目录会一起删除，删除后只有运维能从交付恢复；提供“下载改动（patch）”；有被忽略的文件时说明
    “被忽略规则排除的文件不在交付里，会一起删除”。
  - `undelivered`：说明原因，列出未交付的改动；默认保留工作目录，另给一个需要用户主动勾选的“同时丢弃未交付的改动”，
    写明丢弃后无法找回；有成功交付时同样提供下载。`discardable` 为假时不提供丢弃，并说明原因（还在交付；或无法确认丢弃的
    是哪些内容，请先自行处理）。
  - `none`：不提工作目录；`workspace_missing` 时说明目录已不存在。

为什么 `reclaim` 不用 `revision`：`reclaim` 只删能恢复的目录，删除时重新判定，预览之后状态变了，结果只会是“删了能
恢复的”或“保留”，都不会丢掉运维恢复不了的东西。`discard` 会丢东西，所以要求用户看到的就是被丢弃的。

为什么不写“改动已保存在交付里”：对话删除后它的交付对用户不可读（交付 ADR D4），用户无法自己取回；能做的承诺只是
运维能恢复，以及删除前给用户下载的机会。

为什么默认保留不能恢复的目录：#1191 否决了方案 C，首次默认行为不能悄悄丢掉唯一的一份成果。

为什么删除时不先补一次交付：`chat.Service.Delete` 只对活着的会话调 End，空闲会话删除时不会再交付；活着的会话结束时
最后一轮会交付（交付 ADR D1、D5）。在删除路径里补交付会让删除变慢、可能卡住，结果仍要按 D1 判定；D1 第 5 条的树比对
已经覆盖了“最后一轮交付之后又写入”的情况。

为什么不提供“能恢复也保留目录”（`keep`）：对话删除后，留下的目录没有任何入口能再访问，只占磁盘。

### D3：先在删除对话的事务里登记，再回收

- **登记**：用户删除对话时，在删除对话记录的同一个事务里写一条工作目录回收：`WorkspaceID`、项目、会话 ID、来源对话、
  路径、`clone_execution`（取自 `v2_workspaces`）、模式、登记时间，状态 `pending`。会话没有登记过工作目录的不登记。登记
  只在用户删除对话的路径上发生；`Create` 首轮被拒后回滚对话的删除不是用户删除，不登记。模式登记后不可变，由数据库触发器保证。
- **状态**：`pending → deleting → reclaimed | kept`，另记尝试次数、最后一次错误、最后一次尝试时间，结束时记释放的字节数
  与文件数，`reclaimed` 时记依据的交付（交付 ID、交付提交、起点提交，供运维恢复，D6）。
  - `pending`：每次执行按 D1 判定。`delivering`（两种模式都一样，`discard` 也要等交付义务清空）→ 保持 `pending`；
    `reclaim` 模式下其他不能恢复的原因 → `kept`；其余 → 进入 `deleting`。
  - `deleting`：只重查 D4 的身份与路径，不再按 D1 判定，避免删了一半却因为目录已经变了而落到 `kept`。
- **执行时机**：删除请求在事务提交、会话确认结束后立即执行一次。这次执行用服务生命周期的上下文（不随 HTTP 请求取消），
  有自己的时间预算：5 秒内删完就返回 `reclaimed`，删不完就返回 `pending`（原因 `in_progress`），在后台继续删完；服务关闭
  时取消，记录留在 `deleting` 给启动。删除事务提交之后出的错，返回值里如实报告回收的状态，不报成“对话没有删除”。
  Cloud 启动时在 `boot.Recover` 里、`RecoverTurnDeliveries`
  之后、恢复工作流和开始服务之前，把 `pending` 和 `deleting` 的再执行一遍。运行中不再另外触发：删除时还在交付的，
  留到下次启动。不加定时任务。
- **同时只执行一次**：进程内按 `WorkspaceID` 互斥，拿到后对记录的状态做 compare-and-set（只有状态仍是读到的
  `pending`/`deleting` 才推进）；v2-server 是持有数据目录锁的单进程（A1），所以这两层就够。
- **错误怎么处理**：
  - 判为 `kept`、不再重试：`reclaim` 模式下不能恢复；D4 的身份或路径检查不通过（越界、经过符号链接、dev/inode 不一致、
    目录被别的会话用过、有未结束的会话、登记与 `v2_workspaces` 不一致）。原因写进记录。
  - 保持原状态、下次启动重试：数据库不可用、IO 错误、权限错误、上下文取消；判定时生成快照树或检查 Git 状态因磁盘、镜像、
    Git 调用失败（记 `check_failed`，不下结论）；删除前统计时读不到某个条目（列出后消失的条目跳过、不计入）。尝试次数加一、记最后一次错误、写日志；单次检查最长 2 分钟，超时同样记 `check_failed`。
    运维能列出（D6）。
- **`v2_workspaces` 不删**：交付记录和重启恢复都按 `WorkspaceID` 查它；回收记录就是“这个目录已经删了”的记录。

为什么不在删除请求里直接删目录：删目录可能失败，Cloud 也可能在删到一半时崩溃。没有登记，目录就成了没有主人的目录，
以后只能整项目 `-cleanup` 或者盲扫，#1191 明确禁止。

为什么不把对话改成软删除：回收只需要目录的身份和路径；软删除要让所有读对话的地方都过滤已删除的对话，“删除的对话
不可读”就依赖每处查询都不写漏。

为什么运行中不在交付完成时再触发：那要在交付落库处加回调并处理与删除请求的竞争，换来的只是“正在交付时被删除的对话”
提前到下次启动之前回收；这类对话很少，等到启动的代价只是磁盘晚一些释放。

### D4：只删精确属于这个对话的目录

回收只经 `workspacefs` 删除（A1 D7 第 3 条，本文修改），由 `agentruntime` 先摘掉进程内的引用。删除前依次确认：

1. **数据库**：登记的路径和 `clone_execution` 与 `v2_workspaces` 里这个 `WorkspaceID` 的行一致，没有别的行用同一个路径；
   用过这个 `WorkspaceID` 的会话只有登记的那一个，且已结束（按 `v2_execution_sessions.data->>'WorkspaceID'` 查询，由表达式
   索引支撑）。
2. **进程内**：
   - 项目 runtime 在时，持 `skillsMu`，在 `p.mu` 下确认 `p.owners[WorkspaceID]` 为空、从 `p.checkouts` 去掉这个工作目录，
     再从 `<项目目录>/skill-checkouts.json` 去掉这个路径，然后**释放** `skillsMu`。两份列表都已摘掉，之后的技能投影不会再
     遍历到它。
   - 项目 runtime 不在时，用按项目 ID 的锁代替 `skillsMu`：Driver 在 `d.project()` 插入新的 `projectRuntime` 之前先拿这把锁，
     回收只在改 `skill-checkouts.json` 期间持有它。
   - 统计和删除只持交付对这个目录的锁（`DeliveryFS.LockWorkspace`），不持 `skillsMu` 或项目锁：删一个十万级文件的目录可能要
     几分钟，期间同项目的会话准入、`attachSkills`、`attachUserSkills`、`ApplySkill` 都不被阻塞。
   - 加锁顺序：`LockWorkspace` → `skillsMu`（或项目锁）→ `p.mu`。
   - 兜底：技能投影遇到已经不存在的 checkout（检查和打开时的 `ENOENT`）跳过，不让整次投影失败。
3. **路径**：checkout 根是 `<项目目录>/w/r`。登记的路径必须在它之下；从 checkout 根起经目录句柄逐级打开到 checkout，
   每一级先 `Lstat` 确认是目录、不是符号链接，打开后比对 dev/inode 与 `Lstat` 一致，任何一级在检查与打开之间被换掉都判为
   不安全。统计、给目录加属主写权限、删除内容都经 checkout 的句柄进行，删除 checkout 目录本身经父目录的句柄进行，之后
   不再按路径重新打开，不跟随任何符号链接。
   目录已经不存在时，当作已回收（释放 0 字节）。
4. **统计**：删除前经同一个 root 遍历，不跟随链接，统计普通文件的逻辑大小之和作为释放的字节数，所有条目（文件、目录、
   链接）的个数作为文件数，写进记录和日志。

不变量 6 依赖的事实：对话的 `WorkspaceID` 每次新生成（只有工作流同一运行复用），所以对话的目录结构上不会被别的会话
接回；Node 的 clone 路径按 clone 执行唯一。第 1 步把这两条在执行时再核对一次。

为什么要在进程内也确认：数据库只知道会话结束了没有，不知道进程里还挂着哪些引用。技能投影会遍历记下的 checkout 逐个
写链接，目录在它检查完存在之后、打开之前被删，会让整次投影失败，影响同项目的其他会话。

为什么要逐级 `Lstat` 再比对 dev/inode：登记的路径来自 Node 的回复，第一版 Agent 和 Cloud 是同一个系统用户（A1 D2），
Agent 能在磁盘上改目录结构；只检查一次路径，检查和打开之间被换成链接就可能删到项目之外的文件。

### D5：并发

- 同一个对话的删除、发消息、停止仍按现状在同一把对话锁里串行；回收在对话记录删除之后执行，这时已经没有请求能找到
  这个对话。
- 同一条回收同时只执行一次（D3）。
- 回收和交付互斥：判定要求没有交付义务，D1 第 5 条和删除都持有交付对这个目录的锁。

### D6：运维怎么列出、恢复和丢弃

第一版不做用户界面，运维用 v2-server 的子命令：

- **列出**：只读子命令列出回收记录，可按状态筛选，可以在服务运行时执行：`kept` 的目录和原因、`pending`/`deleting` 的尝试
  次数与最后一次错误、`reclaimed` 的释放量和依据的交付。
- **恢复已回收目录的成果**：记录里有交付提交和起点提交，项目镜像在 `v2_projects` 记的镜像路径下。在镜像上
  `git diff --binary <起点> <交付提交>` 得到完整 patch（能在起点上 `git apply`），或 `git archive <交付提交>` 取出整棵树。
  `empty` 的交付没有改动可恢复。项目被删除时镜像连同交付一起删除（交付 ADR D6），就无法恢复了。
- **保留的目录**：直接按记录里的路径取用；要丢弃时，停服后用离线子命令按记录丢弃一条 `kept` 的回收：持数据目录锁，
  按 D4 检查后删除，记为 `reclaimed`、原因写明是运维丢弃。

## 不变量

1. 只有用户显式删除的普通对话的工作目录会被 Cloud 回收；活跃会话、工作流运行、任务运行的工作目录不会被回收。
2. `reclaim` 模式下，只有能恢复（D1 五条全部成立）的目录会被删除。
3. 被删除的目录，要么在判定时运维能从交付完整恢复它的未被忽略的文件、且 Agent 仓库里没有交付带不走的 Git 状态，要么
   用户在删除时看过未交付的改动并明确选择了 `discard`。
4. 每个被回收的目录在用户删除对话的同一个事务里有一条回收登记；没有登记的目录 Cloud 不删；对话首轮失败的回滚不登记。
5. 删除只发生在：登记与 `v2_workspaces` 一致、目录只被登记的那个已结束的会话用过、进程内没有存活会话占用、路径位于
   checkout 根之下且不经过符号链接。
6. 回收失败或 Cloud 崩溃后，`pending` 与 `deleting` 的回收在下次启动时继续；进入 `deleting` 后不会因为重新判定落到
   `kept`；重试不会删到别的目录。
7. 回收不删除、不修改交付记录、交付义务、交付 ref、快照 ref、项目镜像、`v2_workspaces`、Node 的会话历史和账本。

## 为什么不是这些替代方案

| 方案 | 优势 | 否决理由 |
| --- | --- | --- |
| 删除对话就删目录，不看交付（#1191 方案 C） | 最直接，磁盘释放最多 | owner 已否决：会永久丢失未交付、交付失败和旧会话的改动 |
| 只给日志限额，目录全部保留（#1191 方案 B） | 不引入删除语义 | owner 已否决：磁盘随对话数量和仓库大小增长 |
| 只看最后一轮交付成功，不比对树 | 不用在回收时生成树 | 最后一轮交付之后目录还可能变，空闲会话删除时也不会再交付（D1 第 5 条） |
| 只看最近一条交付记录是否成功 | 判定更简单 | 后面的回合没有登记交付时会误判能恢复（D1 第 3 条） |
| 删除时先补一次交付再判定 | 能恢复的比例更高 | 删除变慢、可能卡住；树比对已覆盖交付之后的写入（D2） |
| 删除后仍让用户读已删除对话的交付 | 用户能自己取回 | 改变交付 ADR D4 的读取边界，已删除的来源要有新的可读入口；删除前下载已能满足（D2） |
| 提供 `keep` 模式（能恢复也保留目录） | 留现场 | 对话删除后目录没有入口可访问，只占磁盘（D2） |
| 删除请求里直接删目录，不登记 | 少一张表 | 失败或崩溃后目录没有主人，只能盲扫或整项目清理（D3） |
| 对话改软删除，回收完再真删 | 不用新表 | 所有读对话的地方都要过滤（D3） |
| 交付完成时由回调再触发回收 | 正在交付时删除的对话能更早回收 | 多一处与删除请求的竞争；这类对话很少，等到启动只是晚一些释放（D3） |
| 删除时连 `v2_workspaces` 一起删 | 数据库更干净 | 交付记录和重启恢复按 `WorkspaceID` 查它；数据库记录不在回收范围 |
| 定时扫描已删除对话的目录 | 不用改删除路径 | 归属随对话记录删除后已经不可知，只能靠猜；#1191 也不加定时任务 |

## 本决策未解决的问题

1. **工作流运行、任务运行的目录**：共享目录和运行整体删除的回收以后另写决策。
2. **多机**：单机下 Cloud 直接删磁盘上的目录（A1 D2）。多机时 Cloud 读不到 Node 的工作目录（A1 D7、交付 ADR D7），判定
   里的 Git 状态检查、树比对和删除都要改为 Node 协议请求，并让 Node 清掉账本里对应的 clone 执行。第一版 Node 账本里这条
   记录不删，接受它随对话数量增长；它只在工作流运行重启后接回目录时被读，对话不会接回（D4）。
3. **交付清理**：回收之后，记录引用的交付 ref 是这个对话成果的唯一一份。以后清理交付的决策必须保留 `reclaimed` 记录引用的
   交付，或者明确放弃这些成果。
4. **本文落地之前已删除的对话的目录**：归属已经不可知，本文不处理；需要释放时由运维停服后整体清理。

## 实现时的修改

实现（cloud PR #419）经两位成员多轮审查，对 approved 稿做了下面几处修改，正文已按最终实现同步：

1. **`revision` 绑定字节而不是展示统计**：approved 稿写的是“快照树和 Git 状态”。审查中几次构造出预览展示不变、内容却变了的
   反例（stash 被替换、ref 改指向、暂存区被替换、嵌套仓库经 gitfile 或 `commondir` 指向的共享仓库变化、嵌套文件同大小改写并
   恢复修改时间），所以改为 D2 里的 Git 相关内容字节摘要。
2. **`unverifiable` 与摘要不完整时不可丢弃**：approved 稿里 `delivering` 以外都可以 `discard`。摘要不完整时无法保证用户确认的就是
   被删除的，违反 D2“要求用户看到的就是被丢弃的”，所以新增 `discardable`：界面只在它为真时提供丢弃；直接调用 API 时，
   判为 `undelivered` 而它为假的 `discard` 返回 `409 discard_unverifiable`。这类目录默认保留，由运维按 D6 处理。owner 于 2026-11-19 在 circus #1319 得到告知。
3. **检查的时限**：单次检查最长 2 分钟，超时按 `check_failed` 重试，避免嵌套仓库里的特殊文件让 Git 读取挂住、拖住启动。
4. **`HEAD` 与 index 也要被交付覆盖**：approved 稿第 4 条只看 stash、ref、gitlink 与嵌套仓库，只在 `HEAD` 或暂存区里的内容
   （暂存后把工作树改回、提交后把工作树和暂存区还原）会被默认的 `reclaim` 判为能恢复并删除。所以第 4 条加了 `HEAD` 与 index 的
   条件；与起点相同的内容在快照里一直保留，所以与起点树相同也算覆盖。`HEAD` 读不出时一律保留（只有还没有任何提交的
   unborn `HEAD` 例外），对象缺失或损坏判 `unverifiable` 而不是反复重试。起点之后、`HEAD` 之前的中间提交仍按 owner 第 1 轮的口径不算。
5. **执行与约束的具体值**：删除请求里等待 5 秒；模式不可变由数据库触发器保证。
