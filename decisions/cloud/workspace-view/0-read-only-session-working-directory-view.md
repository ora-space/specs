# 工作区查看：只读查看 Agent 会话的工作目录，四个读操作挂在对话、工作流运行和任务运行下，读的是实时目录，不留快照

页面和 desktop 通过同一组只读接口查看 Agent 会话的工作目录：一层目录、一个文本文件、相对克隆时 commit 的变更列表、
一个文件的 diff。这四个读操作挂在三种会话下面：对话、工作流运行、任务运行。能读会话就能读它的工作目录。读到的是
目录此刻的内容，没有快照；会话结束或执行中断后仍可读，直到目录被删除。所有读取都有上限，超出时明确告知，不静默截断；
读取不改动目录，也不改 Agent 的 Git 状态。这些都是 v2-server 现在的做法，本文把它们定为正式的 desktop↔cloud 契约，
不新增机制。

本 ADR 处于 `proposed`：等待 owner 评审，评审通过后改为 `approved` 并补核心测试用例。它是领域 `cloud/workspace-view`
的根决策，属于 circus #1029（phase2：把 v2-server 的候选 API 定为正式契约）。前提是
[Cloud 单进程根决策](../lifecycle/0-single-process-cloud-on-enterprise-intranet.md)（下称"A1"）和
[项目仓库根决策](../project-git/0-external-repository-pull-and-encrypted-token.md)。读取的代码版本为 cloud
[`966a6ba5`](https://github.com/ora-space/cloud/tree/966a6ba590cce07b9629f0c2984aa905dd00be86/v2-server)
（`v2-server/internal/workspacefs`、`internal/server/workspace.go`、`internal/store/workspaces.go`、
`workspace.openapi.json`）。

本文的"工作目录"指 Agent 会话在 Node 上实际读写的那份 Git checkout（A1 D3 的用法），不是
[词汇表](../../../domain/glossary.md#workspace)里 v1 的 `Workspace` 领域身份；"宿主"指工作目录挂在哪种会话下面。

范围与兼容性边界：

- **涉及**：cloud 的 `v2-server/`（接口实现与契约文件）。frontend-v2 已在使用；desktop 现在不调用，phase2 接入 cloud 后
  使用同一契约。
- **不做数据迁移**：v1 没有在线查看工作目录的接口，成果经 Revision 交付；v1 退役时没有要迁移的数据。

## 现状与继承

| 前序约定或现状 | 本文处理 |
| --- | --- |
| A1 D3：Agent 的改动只在 Node 的工作目录里，第一版不交付；Cloud 重启或 Node 退出时执行标为中断 | 继承：中断后工作目录仍可读（D4） |
| A1 D4：每个 API 按租户作用域授权 | 继承：权限跟随宿主（D2） |
| A1 D6：v2-server 已有行为以代码、候选契约和 #1029 定下的正式契约为准 | 本文就是这一领域的正式契约（D1） |
| A1 D7 第 3 条：Cloud 读 Node 的工作目录只经一个模块（`workspacefs`），以后可以换掉数据来源 | 继承，定为不变量（D4、不变量 5） |
| 项目仓库根决策：变更视图由 Cloud 读本机的工作目录得到 | 继承（D3） |
| v2-server 候选契约 `workspace.openapi.json`（"Temporary v2 workspace viewer"） | 定为正式契约，去掉"临时"的说法（D1、落地顺序） |
| v1：没有在线查看，成果经 Revision 交付 | 不继承；Revision 一组由 A1 标为将被取代 |

## 决策

### D1：契约文件和路径

- **契约文件**：正式契约就是 cloud 仓的 `v2-server/workspace.openapi.json`。字段、参数和错误码以它为准；本文规定
  它们的语义和不能破坏的承诺。specs 不复制 schema。
- **路径**：保留 `/api/v2/tenants/{tid}` 前缀。每个宿主下面是同样的四个读操作：

  | 宿主 | 前缀（`…` = `/api/v2/tenants/{tid}`） |
  | --- | --- |
  | 对话 | `…/chat/conversations/{cid}/workspace` |
  | 工作流运行 | `…/workflow-runs/{rid}/workspace` |
  | 任务运行 | `…/tasks/{taskid}/runs/{rid}/workspace` |

  | 操作 | 参数 | 返回 |
  | --- | --- | --- |
  | `GET {前缀}/entries` | `path`，省略为根 | 一层目录：先目录、后文件，各按名称排序；`truncated` |
  | `GET {前缀}/file` | `path`，必填 | 一个文本文件的内容和字节数 |
  | `GET {前缀}/changes` | 无 | 相对克隆时 commit 的变更文件，按路径排序，带状态和增删行数；`baseCommit`；`truncated` |
  | `GET {前缀}/diff` | `path`，必填，可以是已删除的文件 | 这个文件的 unified diff；没有变更时为空字符串 |

- **宿主前缀跟随宿主领域**：宿主的路径由它所属领域的契约决定（对话、协作任务、工作流运行），本文只规定挂在
  `…/workspace` 下面的这一段。新的会话宿主要提供工作目录查看时，挂同样的四个操作，语义按本文。

为什么保留 `/api/v2`：A1 定了 v2-server 就是正式 Cloud，v1 的 `api/openapi.json` 在 I11 退役，没有要对齐的另一套路由。
改前缀会让 frontend-v2 的生成客户端整体换代，换不来任何行为上的好处。

为什么挂在宿主下面，而不是一个独立的 `/workspaces/{id}`：工作目录的身份是 Cloud 内部记录（v2-server 的
`v2_workspaces`），客户端手里只有会话的标识；权限也跟着会话走（D2）。独立资源要么把内部标识暴露出去，要么每次请求
都要反查它属于哪个会话。代价是同样的四个操作在契约文件里写三遍。

### D2：权限跟随宿主

- 能读宿主，就能读它的工作目录；不能读宿主，就读不到，返回和宿主不存在时相同的应答。
- 对话：只有对话的所有者能读；别人读到 404 `not_found`，和对话本身一样。
- 工作流运行、任务运行：本租户的有效成员都能读，和读运行详情一样。
- 先按宿主的规则校验，再找工作目录。没有单独的"工作目录权限"，也不因为能读工作目录而能读宿主的其他内容。

为什么不单独授权：工作目录是会话的一部分，会话里 Agent 的输出本来就描述了它改了什么。单独授权只会出现"能看对话却看不到
文件"或反过来的组合，没有对应的产品场景。

### D3：读的是实时的工作目录，变更相对克隆时的 commit

- **实时**：每次请求读取目录此刻的内容。Agent 可能正在写，两次请求之间内容可以变化；同一时刻的 `changes` 和随后的
  `diff` 不保证一致。契约不提供快照，也不推送变化：客户端在 Agent 的一次工具调用完成和一轮结束时重新读取。
- **基准**：变更和 diff 都相对工作目录克隆时的 commit（`changes` 返回的 `baseCommit`），不是项目默认分支的当前位置。
- **变更包括**：已跟踪文件的修改、新增和删除，以及未跟踪且未被忽略的文件。被 `.gitignore` 忽略的不算。
  Ora 物化进工作目录的技能目录不算变更（v2-server 把它们写进该工作目录自己的 `.git/info/exclude`）。
- **不检测重命名**：重命名显示为一个删除加一个新增。
- **二进制文件**出现在变更列表里，`binary` 为真，增删行数为 0。
- **工作流运行**：同一次运行的 Agent 节点共用一份工作目录，查看的是这一份，只到运行级，不区分各节点分别改了哪些文件。
- **任务运行**：每次运行有自己的工作目录。

为什么不留快照：第一版不交付 Agent 的改动（A1 D3），工作目录就是改动唯一所在的地方；做快照等于另造一套交付。代价是
目录被删除后改动就看不到了（D4）。

### D4：工作目录的三种状态

| 状态 | 什么时候 | 应答 |
| --- | --- | --- |
| 还没有 | 会话的第一轮还没克隆好工作目录；工作流运行还没有 Agent 节点开始 | 404 `workspace_not_ready` |
| 可读 | 克隆完成并登记之后；会话结束、执行中断、Cloud 重启之后仍然可读 | 200 |
| 已删除 | 工作目录被清理删除 | 410 `workspace_removed` |

- 工作目录的位置在 Agent 启动前持久化，所以会话结束和 Cloud 重启不影响查看。
- Cloud 读工作目录只经一个模块（现在是 `workspacefs`）。以后这个模块的数据来源换掉（例如多机后经 Node 读取），
  读不到时也必须落到上表的状态里，不新增客户端要处理的状态；要新增，先改本文。

### D5：读取的边界

- **路径**：只接受相对路径，用 `/` 分隔。绝对路径、反斜杠、NUL 和以 `.git` 开头的路径返回 400 `invalid_path`；
  `..` 先按词法规范化，超出根目录的部分被丢弃，不会越出工作目录。符号链接解析后仍要在工作目录内，否则同样返回
  `invalid_path`；目录列表里跳过指向工作目录外的符号链接，不列出
  `.git`，也不列出普通文件和目录以外的条目。
- **只读**：不写工作目录，不改 Agent 的 index、ref 和配置。计算变更和 diff 用 index 的临时副本；git 调用关闭
  hooks、fsmonitor、外部 diff 和 textconv，不执行仓库里配置的任何程序。
- **上限**：

  | 读取 | 上限 | 超出时 |
  | --- | --- | --- |
  | 一个文件 | 2 MiB | 413 `too_large` |
  | 一次 diff 或变更计算的 git 输出 | 4 MiB | 413 `too_large` |
  | 一层目录 | 5000 项 | 返回前 5000 项，`truncated: true` |
  | 变更列表 | 2000 个文件 | 返回前 2000 个，`truncated: true` |

  含 NUL 或不是合法 UTF-8 的文件返回 422 `binary_file`，不返回内容。调低上限对客户端是不兼容的变化，要先改本文。

为什么上限写进契约：工作目录里有什么由 Agent 和项目决定，不设上限，一个大文件或一次大 diff 就能拖住 Cloud 进程（A1：
Cloud 是单进程）。客户端需要知道"被截断"和"读完了"的区别，所以超限是明确的应答，而不是悄悄截掉。

### D6：错误码

宿主自身的错误（宿主不存在、无权读取）沿用宿主领域的错误码，例如对话的 `not_found`、工作流运行的
`workflow_run_not_found`。工作目录这一段的错误码：

| HTTP | `code` | 含义 |
| --- | --- | --- |
| 400 | `invalid_path` | 路径不合法或越出工作目录 |
| 400 | `not_a_directory` / `not_a_file` | 路径存在，但类型和操作不符 |
| 404 | `workspace_not_ready` | 工作目录还没有（D4） |
| 404 | `path_not_found` | 路径不存在 |
| 410 | `workspace_removed` | 工作目录已删除（D4） |
| 413 | `too_large` | 超过上限（D5） |
| 422 | `binary_file` | 不是文本文件 |

错误码是稳定的，客户端按 `code` 分支，不按说明文字。

### D7：第一版不做的

- 写入、上传、下载二进制文件。
- 文件监听和变化推送。
- 重命名检测。
- 工作流运行按节点查看各自的改动。
- 工作目录删除之后的历史查看。

## 不变量

1. 能读宿主才能读它的工作目录；读不到时的应答与宿主不存在时相同，不能借此判断别人的会话是否存在。
2. 查看不写工作目录，不改 Agent 的 index、ref 和配置，不执行仓库里配置的程序。
3. 任何请求都读不到工作目录以外的文件，也读不到 `.git` 里的内容。
4. 每个应答都在上限之内；超限时明确返回 413 或 `truncated: true`，不静默截断。
5. Cloud 读工作目录只经一个模块。
6. 会话结束或执行中断之后，工作目录在被删除之前一直可读；删除之后返回 410，不返回 404 或 500。

## 为什么不是这些替代方案

| 方案 | 优势 | 否决理由 |
| --- | --- | --- |
| 独立资源 `/workspaces/{id}` | 四个操作只写一遍 | 暴露内部标识，权限要反查宿主（D1） |
| 每轮结束存一份快照 | 目录删除后仍能看，能看历史 | 等于另造一套交付；A1 定了第一版不交付 |
| 经 Git server 读 Agent 推送的分支（项目仓库根决策 2026-11-11 之前的版本） | 多机可用，有权威副本 | 要先有 Git server 和每轮交付，第一版不做 |
| 工作流运行按节点区分改动 | 能看出每个节点做了什么 | 节点共用一份目录串行执行，按节点区分要在每个节点前后各留基准，第一版没有这个需求 |
| 文件监听加 SSE 推送 | 页面实时 | 在工具调用完成和一轮结束时重新读取已经够用，推送要多维护一条事件流 |
| 单独授权工作目录 | 能做"可看对话、不可看文件" | 没有对应的产品场景（D2） |

## 本决策未解决的问题

1. **多机之后的数据来源**：Node 不和 Cloud 同机时 Cloud 读不到工作目录，要先设计交付（A1 D7 最后一段）。接口和状态按
   D4 保持不变。
2. **工作目录什么时候删除**：现在只由运维手动执行 `-cleanup` 删除，没有保留期限。保留策略和自动清理另行决定。
3. **宿主领域的路径**：对话、协作任务、工作流运行的正式契约定下后，如果它们的路径变了，本文的前缀随之变化，四个操作
   和语义不变。
4. **工作流运行按节点查看**（D7）。
