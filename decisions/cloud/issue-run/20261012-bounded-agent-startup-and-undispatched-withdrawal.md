# 创建结果未知与 Agent 启动都有等待上限，业务收尾保留残留责任

Cloud 区分 Workspace 创建、启动意图、派发登记、Node 受理和真实记录。运行 Workspace 创建结果长期未知时，有界放弃该次创建并释放 Project 操作槽，残留执行与资源继续受保护。ready 后，未登记的确定性拒绝立即结算，暂时失败在不续期的启动预算内延后重试；用户结束或总预算耗尽时原子撤回并声明清理。已登记且尚无启动记录的执行先请求结束，结束确认窗口耗尽后 Run 按 `failed/done` 关闭业务等待，保留未知执行和残留资源的对账责任。

本文为 `approved`。第一期交付 D1–D4 的启动与结束等待边界；D5 的创建 blocked 放弃属于独立第二期，第一期不依赖它。继承 [IssueRun 根决策](0-agent-run-in-disposable-isolated-workspace.md) 和前序 [续接提案](20261010-resume-run-from-latest-issue-revision.md)，修改根 D3/D6 的创建与启动缺口，并为根 D4/D5 的真实会话终态与交付链路增加未知执行的有界业务放弃分支。根 D8 已实现的删除放弃规则继续有效；续接提案的 Revision 选择与恢复规则不改。Thread 继承 [根决策](../thread/0-durable-agent-thread-with-user-turns.md) 与 [个人模型输入权限](../thread/20261010-personal-model-initiator-controls-input.md)。控制面仍遵循 [派发前登记与同事务接缝](../controller-integration/20260928-agent-run-executions-thread-and-upload-grants.md)。

## 决策

### D1：未登记是受事务保护的执行不存在证据

撤回必须与派发登记使用同一事务锁，确认没有 Agent 执行登记、已绑定 work 或已投递命令。控制面撤回未派发 work/命令；业务层结算 Thread、丢弃未执行的 queued 轮次并声明 owned delete。任何一步失败全部回滚。迟到派发不能复活已撤回输入。

普通结束或取消在此边界结算为 `cancelled`，`deliveryState=skipped`，不声明 Agent 成功。已初始化的当前 Node 明确缺模型代理能力时，使用 `model_proxy_unavailable` 立即结算 `failed`，不重试同一不可受理输入。主 Workspace、历史 Revision 和其他运行不受影响；Project 忙时沿用已有清理重试。

能力证据继承既有派发准入的 Node 有效性条件：当前 sandbox/generation、已初始化、连接且数据库时间下 30 秒内有心跳。仅有 `connected` 标记但心跳已过期，或 Node 断连、尚未初始化，都属于未知/暂时不可达，不能当作确定性缺能力证据。扫描可受理性与结算事务都须核验这一边界；已有 pending Thread 的冻结意图不因过期能力记录被撤回。

容量不足、领取排队、暂时不可达或服务暂时不可用只说明本次无法推进，不构成确定性拒绝。没有登记且没有结束请求时，保留原启动意图、work 和冻结输入，持久化延后可领取时间，在 D2 的总预算内重试；尚未声明意图的业务启动扫描也受同一截止时间约束。全局领取的分类、退避与公平性由领取调度负责，本 ADR 只固定 Run 的截止及结算边界，不新增另一套队列或退避参数。重复声明不能改变冻结输入，Controller 重启、重复领取、重新连接和延后重试均不重置截止。

总预算耗尽仍无登记时，Cloud 在上述事务边界撤回意图，使用 `agent_start_failed` 结算 `failed`，`deliveryState=skipped`，保存“启动预算耗尽”及已知暂时失败类别。它表示本次 Run 的有界重试已经结束，不把容量或排队问题改判为永久能力拒绝，也不承诺从未领取的工作一定得到一次执行机会。不得自动创建新 Run、Workspace、首条 turn 或执行身份来延长预算；用户重新启动是独立请求。已经持久化的结束请求优先于再次领取。

登记 RPC 响应丢失时，Controller 先按原执行身份查询或幂等重放登记；未经 Cloud 确认无登记，不能套用未登记重试规则。登记与截止撤回竞争时只有一个事务获得后续责任，迟到领取即使持有旧快照也不得在撤回后登记。

| 证据 | 预算内行为 | 最终边界 |
|---|---|---|
| 当前已初始化 Node 明确缺必需模型代理能力 | 确定性拒绝，立即撤回 | `failed` / `model_proxy_unavailable` |
| 未登记，容量不足、排队或暂时不可达 | 同一意图延后重试，不占住不可处理的队头 | 总预算耗尽后撤回，`failed` / `agent_start_failed`，原因类别为预算耗尽 |
| 登记响应未知或已登记而无启动记录 | 查询、重放原登记或对账原执行，不复制会话 | 启动预算耗尽后 D3，结束确认窗口耗尽后 D4 |
| 未登记且用户已结束或取消 | 原子撤回，不再重试 | `cancelled` / `skipped` |

### D2：窗口采用可配置默认值，由数据库时间判断且输入不续期

ready 后的普通启动、恢复启动和结束确认使用三个独立的可配置窗口，默认值分别为 2、6、5 分钟，配置必须为正的有限时长；配置缺省使用默认值，非法值拒绝启动，不能以零或负值隐式关闭收尾。Cloud 为 Run 持久化本次选定的截止，配置调整只影响后来进入对应窗口的 Run；已经开始的窗口不被滚动部署或重启续期。D5 为创建长期未知另设窗口，不把安装耗时混入这三个窗口。

| 窗口 | 默认值 | 起点与覆盖范围 |
|---|---:|---|
| 普通新启动 | 2 分钟 | 运行 Workspace 的 `create_workspace` 成功 / ready；包含意图声明、调度重试、登记和首条真实 Node 记录 |
| Revision 恢复启动 | 6 分钟 | 同一 ready 起点；包含恢复及随后 Agent 启动，替代普通窗口，不是 2+6 分钟 |
| 启动期间已登记未知执行的结束确认 | 5 分钟 | 首次持久化该执行的 `ending` 等待，无论来自用户结束还是策略超时；已有等待不重新计时 |

声明和派发登记不重置启动预算，用户追加轮次、重放和控制连接恢复也不续期。Workspace 的 clone、插件下载/安装在 provisioning 阶段完成，`finishPluginGate` 完成后才打开 admission 并进入 starting，因此它们不计入本段启动等待。Controller 的领取兜底周期为 10 秒，部署中 Node 内的 Agent ready 等待为 30 秒；以下稳定时钟实测的 ready 到首条 Node 记录最大值为 13.059 秒，普通默认 2 分钟约有 9.2 倍于本组最大值的观测余量。默认窗口为业务策略，后续测量用于调参和验证，不是采用默认值的前置门禁。

恢复 prior Revision 的下载、校验和 Git restore 发生在登记之后。现有 Node `RestorePolicy::DEFAULT.deadline=5m` 只包住授权等待、下载及大小/SHA-256 校验；之后的 bundle 结构检查/Git 阶段没有共享这个截止时间，Git 远程补基础提交另受 network timeout 控制。Cloud 的 6 分钟是进入 D3 的策略上限，不能声称大于现有“整体恢复上限”或据此确认物理停止。Node 完整恢复截止、Git 取消和停止确认属于后续 Node 恢复 ADR，本次不以新增整体 5 分钟契约作为采用 Cloud 默认窗口的条件。

### D3：已登记的未知执行进入可恢复的结束等待

超时后 Thread 为 `ending`，公开读取给出安全 `failureCode=agent_start_failed`，停止接受新轮次。已有用户结束原因保留；没有结束请求时声明一个策略取消。工作、登记、未结算轮次、Workspace 和冻结输入保留，Controller 继续按稳定身份对账与投递结束。

窗口内取得真实 Node 终态时，策略超时取消经原交付链路结算为 `failed`；此前已接受的用户结束/取消保持原结果。真实终态之前不能伪造 Node 历史、收据或 Revision，也不能删除 Workspace。结束确认窗口耗尽仍无终态时改按 D4 的未知结果 `failed/done` 收尾，不能把用户结束请求当作 Node 已停止的证明。迟到真实记录仍按既有接管顺序保存，业务终态只结算一次。

### D4：永久失联必须有业务收尾边界，物理释放需要独立证据

只有 D3 不足以形成有界结算：Fleet 的连接观测和 Node 超过 30 秒未心跳只证明当前不可达，并不证明原实例或一个迟到 ensure 已经停止；现有 `DeliveryUnreachableAfter` 只扫描 delivering/releasing，也不会自动收尾 starting/ending。不能直接借它宣称此路径已被覆盖。

采用 D2 的可配置结束确认窗口，默认 5 分钟，由数据库时间判断，重放和迟到记录不续期。窗口内继续投递既有结束请求并接管真实证据；到期仍无真实终态时，Cloud 在同一结算事务中将 Run 置为 `status=failed, phase=done`，Thread 关闭业务输入并记为 `ended`，保留安全原因 `agent_start_failed` 与 Cloud 放弃等待的来源，`deliveryState=failed`，不创建虚假 Revision。这是 Cloud 的业务结算，Node 结果仍为未知，不写入伪造的 `agent_session_ended`、历史或收据。

Cloud 同时关闭该 Run 的新派发与模型授权，撤销尚未投递的用户输入资格，保留 work、执行登记、冻结输入、已接管记录与原资源身份，并在同一事务登记独立清理账本；账本以原 Run、Workspace 和运行代次关联既有责任，重复结算只能取得同一项，不创建第二套执行。保留记录不等于继续可领取。迟到真实记录和终态仍按原执行身份及序号接管、ACK，不能把 Run 改回 starting/running、重新开放输入、重建会话或再次结算。迟到结果只能补充真实证据与残留对账，不能绕过真实交付验证伪造成果已保存。

这里继承根 D8 和不变量 8 的“业务 done 不等于物理删除、残留仍有归属”，但另立启动侧规则：D8 已经过会话结算，删除放弃保持原 `status`；D4 在会话结果未知时首次结算为 `failed`，并新增独立清理账本。D8 的 Node 不可达窗口、失败 delete operation 和现有 Workspace 登记保持原义；不把历史 D8 的 `completed/cancelled` 改成失败，也不把本账本冒充已经实施的后台清理机制。

残留资源责任按下表固定；`done` 不自动解除未知执行的 Workspace 保护，也不把未确认的清理写成成功：

| 负责方 | 当前责任与处置边界 |
|---|---|
| Cloud IssueRun / 控制面 | 独立持久保存租户、Project、Run、Workspace、sandbox/generation、Node、operation/effect/execution 的稳定关联、未知原因和未完成清理状态；尚无 sandbox/Node 时也保存计划身份。授权部署运维按租户与资源范围查询，普通 Run 读取仅显示安全原因，不开放隐藏 Workspace 的公开操作入口；业务结算后继续保留责任，不用 Run 是否 active 决定是否丢弃账本 |
| Controller / Node | 按原身份查询与接管执行、结束和资源证据；断连及心跳超时不充当终止确认，不宣称空闲来绕过未知执行保护 |
| 后续“Agent Run 残留资源对账与回收”ADR | 负责隐藏运行 Workspace 的清理授权、清理任务持久化与重试、真实实例终止及 late ensure fencing、成果救援与删除顺序；明确自动处理者与部署运维接管入口、失败升级及完成证据。制定与实施归 Cloud 控制面、Controller/Fleet 与 Substrate 的联合生命周期工作，不由业务 `done` 隐式触发强停 |

后续回收 ADR 批准、实施前，本 ADR 只承诺残留账本及其责任可查询，不承诺这些资源已自动释放。取得真实终态及交付/放弃证据后，可沿已有 owned delete 路径清理；仍未知的执行不走普通 delete。需要强停时遵循[管理强停与真实终止](../operation/20260927-safe-stop-and-administrative-force-stop.md)及[迟到创建 fencing](../controller-integration/20260927-fenced-runtime-control-delivery.md)的原则，但其对隐藏运行 Workspace 的授权扩展由后续回收 ADR 决定，不能伪造 `impactConfirmed`。确认目标及所有迟到创建已不能写入后，才可计划该 Workspace 的显式数据删除；主 Workspace、其他运行和历史 Revision 不在清理范围。

按默认值，ready 后普通启动的业务等待最多 2+5 分钟、恢复最多 6+5 分钟，另加 Cloud 可用时的周期扫描延迟；未登记在 2/6 分钟耗尽时即可撤回，用户更早请求结束也可以更早进入确认窗口。provisioning 不计入这段 ready 后预算，其长期未知创建由 D5 单独约束。物理释放和 Cloud 整体停机期间不承诺准点完成，恢复后按原持久截止补结算。真实终止证明可以缩短等待；断线或心跳超时不能替代它。D2 的正常 end 实测不证明永久失联已闭环，最终收尾须独立故障验证。

### D5：创建长期未知先有界放弃业务责任，操作槽与残留保护分别处理

本项只覆盖 Agent 运行 Workspace 的 `create_workspace` 已进入 `blocked` 后仍未真实结算的创建，不扩大到普通 Workspace、Project 主 Workspace、项目删除或插件管理 operation。隐藏运行 Workspace 的公开 API 返回 `404`，因此不能依赖用户或管理员人工 retry 解锁；Cloud 的持久扫描承担此分支。

#### 上限与终态

沿用根 D3 原选择的 30 分钟作为可配置默认值，但改变耗尽后的处置。第一次持久写入 `blocked` 时，Cloud 用数据库时间保存该 operation 的起点、选定窗口和绝对截止；重启、配置调整、重复 defer、人工 retry 或重新领取不得续期。临时改回 `running/retry_wait` 也不抹去这次截止，只有原创建取得真实终态才能结束该窗口。`queued` 尚未得到 Project 操作槽不触发本窗口；它不是整个 provisioning 阶段的总时长上限。

到截止仍无真实创建终态时，Run 结算为 `status=failed, phase=done`，安全原因为 `workspace_unavailable`、`deliveryState=skipped`；这里没有已开始 Agent 或可声明的 Revision。原创建 operation 以 `state=failed` 终结，结算来源明确为 Cloud 放弃等待，提议安全码 `provisioning_result_unknown`；原 effect、clone 与插件执行的真实结果仍为未知，不改写为执行失败、absent 或 terminated。没有 Thread 时不新建一条伪造会话；若已有业务输入记录则关闭其资格，保留原记录。

provisioning 中已接受的取消保留原发起人、时间与原因，不追加或重置等待窗口。原创建若先真实结算，沿既有取消/释放链路处理；截止先到且创建仍未知，则按上述 `failed/done` 收尾而非声明 `cancelled` 已物理生效。用户更早取消可以避免之后启动 Agent，但不提供未知沙盒已经停止的证据。代价是取消确认可能等到剩余创建窗口；本项不另设未经评审的第二个取消计时器。

#### 同一事务解除 Project 阻塞，保留外部责任

放弃事务在原创建与阶段接管相同的锁边界内完成下列不可分割的变更：

1. 再核对 Run、原 operation、冻结输入、目标 Workspace 与代次，确认创建尚未真实结算且截止已到；已有成功/明确失败或其他终态走原路径。
2. 关闭该 Workspace 的新执行准入和该 Run 的启动/用户轮次、模型授权，递增操作与控制资格版本，封闭旧普通派发入口；Workspace 继续处于对账保护，不能因 operation 终态自动成为 `idle`。
3. 按 D4 登记同一独立残留账本，包括可能尚未回报资源的 `sandbox_ensure` 计划 ID、预分配 sandbox 身份、运行代次、原 clone/插件执行以及原触发人。Run 与 Workspace 双向归属、既有持久数据引用不删除。
4. 原创建 operation 与业务 Run 终态一并写入。operation 离开 `queued/running/retry_wait/blocked` 后，既有 `one_project_operation` 唯一槽自然释放；账本对账不靠保留一个永远 unfinished 的普通 operation 排队。

任何账本、保护或结算写入失败，整个事务回滚，Project 操作槽不能先释放；不会出现业务 done 但无人持有残留责任的中间态。重复扫描只确认同一结算与账本，不重建 Run、Workspace、ensure 或执行身份。原创建成功接管与截止放弃竞争时只有一个事务能改变业务阶段。

Project 槽可用于另一独立 Workspace 的普通 operation，但新操作仍按当前资源范围检查准入。终态 Run 的残留 Workspace 不能被重新绑定、启动、接管或复用原卷；残留物理资源继续计入部署资源盘点。涉及它的 Project stop/delete 仍要检查未知执行和残留保护，不能通过忽略 done Run 把全部 Project 判断为空闲。槽释放后也不立即给这个未知 Workspace 排普通 delete，否则只是把创建阻塞换成删除阻塞。

#### 旧派发资格隔离与迟到证据

Cloud 终结 operation 后拒绝新的 effect permit、clone/插件派发登记和原 Agent 启动许可；Controller 每次新动作都须取当前许可，不能凭旧 claim/snapshot 继续 ensure、clone 或安装。原 Workspace 的控制资格撤回后，已连接 Node 按既有控制绑定规则关闭旧入口；未确认的远端关闭继续记为未知。这是封闭新派发的资格隔离，不是“旧进程已停止”的物理证明。

截止前已经发出的有效许可、Substrate 中在途 ensure 或已被 Node 接受的工作可能迟到完成。单独递增 Cloud epoch、把 operation 改 failed 或释放 Project 槽不能阻止这种外部完成；不得删掉原 effect、假报 sandbox 缺失，或创建新 generation 并挂载同一可写卷。账本必须覆盖原计划可能生成的资源，直到真实终止与 late ensure fencing 得到确认。物理终止、迟到创建禁止和数据删除仍由 D4 指定的后续回收 ADR 负责。

业务终态后需要独立的事实接管入口：Controller 用当前服务身份/租约，按原 operation、effect、execution 和资源范围提交真实结果，不重新领取已失败的创建 operation 来取得新派发权。Cloud 校验输入与版本身份后，将事实幂等补入原执行记录及账本，取得持久接管后才 ACK；原创建成功回调只能补证据，不能开放 admission、进入 starting 或启动 Agent。仍未知的执行只查询原身份，不复制新执行来试探。迟到真实终止/清理证据可以缩小残留范围，不能再次结算或复活 Run。

#### 兼容与责任范围

前向迁移新增持久截止、Cloud 业务放弃来源及独立残留责任；不改历史执行结果和已应用迁移。存量 blocked 创建只有可靠、不可变的首次 blocked 证据时才能回填原截止，不能把可变 `updated_at` 或 operation 创建时间假称首次 blocked。缺失该证据时，第一次新策略扫描持久记录“存量首次观测”起点并给予一次默认窗口，明确这类存量不能追溯保证原 30 分钟已生效；之后不再续期。

既有 D8 残留的 Workspace 行、运行绑定与失败 delete operation 继续有效，本项不改其状态或自动重建清理任务。新旧残留都不能以 Run done 判断数据可以删；若后续回收 ADR 统一归档旧残留，应按原稳定身份幂等接入并保留原结算来源。

此分支上线前，Cloud、Controller 的事实接管及新派发拒绝必须共同具备直接证据；只增加业务超时扫描不足以开放新语义。旧消费者若只会通过 active operation 接管结果，不能在结算之后继续丢弃迟到资源事实；升级需保持原创建可读与资源对账责任，不能靠恢复可领取状态兼容。

## 不变量

1. 登记与撤回只能有一方获得未派发输入的后续责任。
2. 请求超时、缺回复、Controller 断开均不证明已登记执行未发生。
3. 原始模型 Key、临时授权与供应商正文不进入失败原因或证据。
4. 未登记撤回的清理声明与业务终态原子提交；已登记真实结果沿原交付/清理链路，业务放弃终态保留独立残留账本。
5. 用户、租户、冻结配置和既有结束原因不被恢复流程扩大或替换。
6. 暂时失败的重试保持同一意图与冻结输入，不续期、不复制未知执行；确定性拒绝与预算耗尽分别记录。
7. 业务终态、Node 终止、成果保存和物理清理是不同证据，迟到证据不复活已关闭的 Run。
8. 创建放弃、原 operation 终态、Project 槽释放与独立残留责任原子提交；槽释放不解除目标 Workspace 的未知执行保护。
9. 没有 Agent 派发登记不证明 provisioning 的 ensure、clone 或插件执行没有发生；旧外部计划始终按原身份对账。

## 替代方案与代价

| 方案 | 取舍 |
|---|---|
| 所有 pending 继续等待 Node | 简单，但明确无法派发的输入与结束请求可永久悬挂 |
| 把所有 pending 当作未执行并删除 | 收尾快，但会丢失已登记、响应未知的实际执行与成果 |
| 结束前仍启动完整 Agent | 可复用原终态链路，但可能触发用户已请求停止的模型/工具操作，能力拒绝仍无解 |
| 未登记撤回，已登记保留对账 | 增加状态证据和预算策略；保留已接受外部效应的责任，作为本文方案 |
| 暂时失败一次就结算 | 省去延后领取，但容量不足或短暂断线会被误作永久拒绝；采用总预算内重试 |
| 每次暂时失败重置启动预算或自动新建 Run | 等待恢复机会更多，但无法兑现有界等待，且可能改变冻结输入；采用同一 Run 的固定总截止 |
| 先确认强停再关闭业务等待 | 能合并业务与物理完成，但 Substrate 永久不可用时仍会永久悬挂；业务先有界收尾，资源回收保留独立证据和授权 |
| 创建 blocked 一直等人工 retry | 无新终态规则，但运行 Workspace 对公开 API 为 404，取消与同 Project 后续操作可永久阻塞 |
| 创建超时后直接进入 releasing 并排 delete | 接近根 D3 的原承诺，但原 create 仍占 Project 槽，且未知沙盒缺少终止/fencing 证据；采用原子业务放弃、释放槽与残留保护 |
| 清除未知执行和 sandbox 行后释放 Project 槽 | 看似能恢复调度，但丢失迟到 ensure 与可写资源的归属，允许错误复用/删除；保存独立账本与原记录 |
| 将 Project 全部锁住直到所有残留物理回收 | 最保守，但一个不可达的独立 Workspace 会永久阻塞其他独立运行；释放普通操作槽并继续保护残留目标与涉及它的 Project 级操作 |

## 未决与落地

两期语义均已批准，实施分开：

1. 第一期交付 D1–D4：持久化普通/恢复启动及结束确认截止（默认 2/6/5 分钟），与领取调度共用原意图、work 和冻结输入；未登记原子撤回，已登记未知窗口耗尽后 failed/done，并保留独立残留账本与迟到事实。先同步[核心用例](../../../test-cases/cloud/issue-run/bounded-agent-startup.md)，再以直接事务、重启及故障证据判断交付。
2. 第二期单独交付 D5：创建首次 blocked 截止、业务放弃/Project 槽释放、事实接管入口、旧许可拒绝、存量回填与故障验证。实施追踪为 ora-space/circus#92（总事项 #14）；不作为第一期交付前置。D5 核心义务仍登记在同一核心用例，证据未完成时保持 Missing/Partial。

第一期必须和领取调度对齐固定总预算内的延后与终态出队，不另建队列。登记响应未知只重放原身份；旧 claim 不得越过撤回/结算事务重新登记。永久失联、两副本扫描、重启/配置不续期、取消/截止/迟到事实和租户隔离均须直接验证，并回归正常多轮、结束、Revision 与资源释放。

D1 接受容量持续不足时一次执行机会也没有就失败的代价；D5 的 provisioning 取消沿原 blocked 截止等待，不增设第二个取消计时器。预算和安全错误可解释结果，不保证领取机会或物理释放。

后续“Agent Run 残留资源对账与回收”ADR 负责隐藏 Workspace 的清理授权、真实终止、late ensure fencing、成果救援与删除顺序；Node 完整恢复截止与 Git 停止确认另由后续 ADR 负责。公开取消 API 和新增结算 SSE 不在本文范围。既有 D8 删除放弃保持原条件与状态，不能把本次业务收尾冒充自动物理回收。
