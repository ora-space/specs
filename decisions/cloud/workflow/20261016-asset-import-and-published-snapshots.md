# 插件资产导入产出已发布快照：资产生命周期不改写快照，运行只冻结 snapshotId

本文是[工作流执行根决策](0-cloud-side-scheduler-owns-workflow-execution.md)（`implemented`）的后续
决策，只固定「插件资产导入」与既有运行契约之间的接缝，不改写根决策的任何一条 D：导入产出的是一份
普通 workflow 加一个**已发布**快照，运行侧仍然只认 `snapshot_id`；导入、包升级、卸载与来源消失
都不改写既有快照，也不影响已冻结的运行身份。来源不进入运行契约——运行不关心一份工作流是用户写的
还是某个包投递的。

本 ADR 已 `implemented`：Cloud 侧实现见 [cloud#77](https://github.com/ora-space/cloud/pull/77)，
核心用例见
[资产导入与已发布快照核心用例](../../../test-cases/cloud/workflow/asset-import-and-published-snapshots.md)。
资产生命周期本身（模式 A、来源、T1b 取包、管理员显式安装、四种证据）写在
[cloud/plugin-marketplace 后续决策](../plugin-marketplace/20261016-workflow-plugin-assets.md)；包内容
格式由 [workflow 插件类别根决策](../../desktop/plugin/category/workflow/0-workflow-package-format.md)
拥有。本文不新增 Controller 契约，也不新增运行门禁。

## 决策

### D1：一份文档 = 一份 workflow 加一个已发布快照，不产出「未发布资产」

导入复用编辑器同一套创建与发布规则：创建沿用 tenant 级名称唯一性与图结构校验，发布沿用发布门禁与
版本规则。因此一次成功的导入，其产物自身就是「可被运行引用」的形态——运行契约里没有「已导入但未
发布」这种状态。

为什么不让导入只建 workflow、由用户手动发布：运行只接受 `snapshot_id`，草稿一律拒绝（根决策 D3），
只建不发布意味着必须新增一个「有 workflow 但不能跑」的中间态，并让 `@` 目录投影额外分出一个分支。
反过来，走发布门禁也让一份引用未声明槽位、或含首期不执行节点的图在导入时就被拒绝，而不是等到用户
点运行。

**门禁的连带后果要写进包的制作约束**（门禁本身是 `internal/core/workflow_graph.go` 的
`validateWorkflowGraph`，与编辑器发布同源）：Cloud 首期只执行 `start`、`agent`、`condition`、
`output` 四种节点（其余 kind 报 `node_kind_unsupported`），agent 节点的 `skills`、`mcps`、
`interactive` 只在真正启用时被拒绝（空数组与 `interactive: false` 是编辑器"未选"的默认值，放行），`outputContract`、`retry`、`promptInactivity` 仍是任意非 null 就被拒绝，节点引用的
槽位必须在图里声明（`default` 除外，否则 `slot_not_declared`）。因此包内文档不是「能存进编辑器」
就够，它必须已经是一份可发布的图。**#76 的官方示例包只能在首期子集内制作**，并在制包时用同一套
门禁自检；含首期不执行节点或未声明槽位的文档会逐份导入失败，而不是导入后等用户点运行才发现。
失败结果带上门禁的问题列表（节点、槽位或字段），与编辑器发布时的报错同源。

**快照版本由 Cloud 自己分配**：发布沿用既有的 Cloud 规则——同一 workflow 的下一个整数
（`workflow_snapshots.version`，`MAX(version)+1`，租户内唯一），导入结果里的 `snapshot_version`
就是这个整数，不是文档里写的值。文档自述的 `version` 与包内文件名都不参与，Cloud 也没有按文件名
派生版本的规则，因此不存在「版本不可寻址」这一类失败。

这与 desktop 的本地导入不同：desktop 的发布接受调用方给定的版本字符串，所以那边要按 文档字段 →
文件名词干 → 标题 派生，并在都不可寻址时落到自动版本（见 [workflow 包格式决策](../../desktop/plugin/category/workflow/0-workflow-package-format.md)
D4）。两边共享的承诺只有一条：一次成功的导入必然留下一个已发布快照，且发布门禁先于落库。

**导入的 workflow 与快照不记创建者或发布者**：`workflows` 与 `workflow_snapshots` 只有租户归属，
没有作者/发布者列，导入也不为它们新增这种列——既不把触发安装的管理员写成作者，也不伪造一个系统
身份。副本是租户级的用户数据，比任何一位管理员活得久；运行契约与 `@` 投影都不看作者。需要审计
「谁触发了导入」时，信息记在资产导入的源记录里（触发它的 space 与时间，必要时再加触发者），不写
进这两张表。

### D2：资产生命周期不改写快照，也不影响在途运行

快照是 append-only 且不可变的（`workflow_snapshots` 只有 INSERT，没有改写路径）。导入、包升级、
卸载、来源消失都只能**新增**来源记录或跳过导入，不能触碰既有快照：

- 包升级只导入从未成功导入过的文档路径（新版本新增的路径，以及此前失败、这次可能成功的路径）；
  成功导入过的路径不再导入，也不改写用户副本或它的快照。
- 卸载插件不删除副本、不改写快照：副本是 `local` 用户数据，卸载只是「不再有来源提供更新」。
- 已冻结的运行按 `snapshot_id` 读取那份图，与副本其后被编辑、被归档、来源被删除都无关。

### D3：来源不进入运行契约

运行身份仍然只由根决策 D3 冻结表里的项组成（快照、输入、发起者、Project、Workspace 归属、逐槽位
绑定、插件版本）。`workflow_runs` 不因为「这份工作流来自某个包」而有额外列、额外校验或额外拒绝码；
`@` 目录投影的可见性也只由租户与发布状态决定，不由来源决定。

这样做的直接后果是：卸载提供方之后，从它导入的工作流仍可被发布、仍可被运行——这正是模式 A 想要
的（副本是用户数据）。若将来需要「来源已不可用」的提示，它是展示层的信息，不是运行门禁。

### D4：执行可用性不由导入或发布推导

导入成功与发布可用都不宣称能跑。运行能否启动仍由既有门禁判断：图的节点范围（根决策 D2）、逐槽位
绑定与模型可用性（执行器槽位与模型槽位映射决策）、运行 Workspace 与 Project 的冻结要求。本文不
新增门禁，也不因为「文档来自官方包」放宽任何一条。

包内文档与用户文档受同一份图 schema 约束：`executorSlots`、`default` 槽位、`hint` 的展示语义都
照旧，导入不产生任何豁免或默认值补全。

## 不变量

1. 导入产物在其后的运行契约里与编辑器发布的工作流无差别：运行只看 `snapshot_id`（与 `project_id`、
   逐槽位绑定等既有冻结项）。
2. 导入、包升级、卸载与来源消失都不改写既有快照，也不影响已冻结或已开始的运行。
3. 运行身份不记录资产来源；`workflow_runs` 不因来源不同而有额外约束或拒绝码。
4. 导入走发布门禁：不可执行的图在导入时失败，系统里不存在「已导入但不可运行」的资产状态。
5. 本文不新增 Controller 契约，不改根决策的任何冻结列，也不改变首期可执行节点集合。
6. 包内文档与用户文档受同一份图 schema 与槽位语义约束，没有豁免。
7. 导入的 workflow 与快照不记录创建者或发布者；作者不成为权限、可见性或运行的输入。

## 为什么不是这些替代方案

| 方案 | 否决理由 |
| --- | --- |
| 导入只建 workflow，用户手动发布 | 引入「已导入但不可运行」的中间态，`@` 投影与运行入口都要为它分支；用户会看到一份点不动的工作流 |
| 快照里记录来源，或让运行按来源解析版本 | 运行身份被资产来源污染，不变量 3 失效；卸载/升级会变成运行语义的一部分 |
| 卸载插件时回收副本或它的快照 | 破坏「副本是用户数据」，并让在途运行依赖一个可被删除的对象；与模式 A、不变量 2 直接冲突 |
| 导入时预解析槽位并写入绑定 | 绑定必须在创建运行的同一事务里按调用者解析（模型槽位映射决策 D2/D3）；导入期没有运行实体，预解析会把调用者的权限判定挪到错误的时间点 |
| 为包内文档放宽发布门禁（例如允许先发布后补槽位） | 图 schema 与门禁是运行契约的输入；放宽一处就等于让运行面对它没定义过的图 |

## 本决策未解决的问题

- 来源版本与用户副本之间差异的展示与会话式提示属于界面决策。
- 定时入口触发 workflow 属第二阶段（根决策已注明），与本文的接缝无关：那时它同样只引用 `snapshot_id`。

## 落地

- 阶段 1（#73）：已随资产导入落地，不需要新的运行侧改动。导入的 workflow 是普通租户数据并带
  已发布快照，因此 `@` 投影与直接运行按既有契约读取它；卸载提供方不改动它。证据见核心用例：cloud#114
  补齐了用导入快照创建运行、卸载后再发布与运行、不同管理员视角的直接证据；仍为 `Partial` 的是「归档副本后
  既有运行仍读到冻结的图」与「快照只有 INSERT」的自动检查。
- 本文不改动任何既有运行路径与既有迁移；`workflow_runs`、`workflow_snapshots` 的形状保持原样。
