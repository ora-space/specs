# Cloud 持久化工作延后与退役，Controller 让出队头，登记时拒绝过期领取快照

未登记的 Agent/Revision 工作由 Cloud 保存下一次可领取时间和调度版本；Controller 暂时无法处理时报告
有界原因，收到 Cloud 已提交的延后结果后继续领取。业务已不再需要的工作在其结算事务中退役；登记必须
重新核验工作身份、调度版本、业务资格和绝对截止。已登记而响应未知的执行始终按原身份恢复。

本文为 `proposed`，尚未完成协议评审或实现。范围为 Cloud Internal Control、desktop Controller 和两者与
IssueRun 生命周期的接缝；Workspace Operation 的拒绝结算由
[配套 Operation 决策](../operation/20261014-settle-deterministic-dispatch-refusals.md)承担。
Cloud proto 是唯一契约源，desktop 继续锁定其 commit；本提案不修改 Node 执行内容、模型授权或交付格式。

## 背景与术语

当前 ClaimWork 每次返回最早的可领取项，Controller 遇到 Fleet 中没有目标、能力不足或调度门关闭时直接
结束本批。没有持久延后动作，下一次还是同一项。交付放弃进入 releasing 后，未登记的交付也可能留在
领取队列中，进而阻挡无关运行。

本文使用三个不同身份：**工作身份**是一次冻结的工作声明；**调度版本**只约束该声明当前的领取快照；
**执行身份**是派发前登记、可能已被 Node 接受的执行。延后只改变调度版本和可领取时间，不改变工作或
输入；登记响应丢失不允许通过生成另一个执行身份解决。

## 决策

### D1：工作资格由业务阶段与控制面证据共同决定

`ClaimWork` 保持纯读，在 PostgreSQL 的当前状态下过滤后返回最早到期的合格工作，不因一次 claim
创建租约、转移归属或推进 Run。下列谓词同时适用于领取和新执行登记：

| 工作 | 必须满足的业务资格 |
|---|---|
| agent_session | Run 仍在 starting、没有已接受结束/取消、没有残留放弃记录，持久启动截止尚未耗尽；工作未退役且未登记 |
| deliver_revision | Run 仍在 delivering、没有交付放弃/结算或残留放弃记录；工作未退役且未登记 |
| 两者共有 | 可领取时间已到；Workspace/Run 归属与冻结目标仍相符；新登记另需通过当前 generation、Node、维护控制、准入与权限检查 |

不能只看 Run 的公开 status：例如交付收尾与失败清理有各自的 phase，status 为 failed 不证明所有资源
工作都结束。也不能以“没有 residual 行”代替全部业务资格检查。

历史残留行即使尚未回填退役标记，也被资格谓词排除；其存在不影响另一个租户的合格项。无当前 Node
心跳与缺 Fleet 本地连接只说明暂时不可处理，不能在领取时伪造确定性缺能力证据。

### D2：新增持久工作处置，Controller 报告观察，Cloud 决定后果

在 `ExecutionService` 增加工作处置方法。请求包含 `submission_id`、当前 Controller `epoch`、工作 ID、
预期调度版本、有限原因，以及该原因必要的冻结目标/Node incarnation 观察。响应是互斥的
`deferred`（新版本、available_at）、`retired`、`rejected` 或 `registered`（原执行身份）；不以缺字段
或空对象表示未知。RPC 传输失败和业务处置结果分别处理。

| 观察与 Cloud 复核 | 处置 |
|---|---|
| Fleet 尚无目标、Node 暂时不可达、本地 gate 忙、容量不足 | deferred；保持同一 work、输入、目标 |
| Controller 所见能力不足，但 Cloud 没有当前有效的权威能力证据 | deferred；不能让陈旧客户端永久拒绝一个可执行请求 |
| 当前 generation、initialized、connected、30 秒内心跳的 Node 明确缺冻结输入必需的 model proxy | 调用既有启动拒绝规则，未登记时 rejected；安全原因与启动 ADR 一致 |
| 业务阶段已经结束、已取消/撤回或工作已经退役 | retired；只确认当前事实，不再创建执行 |
| 该工作已有执行登记 | registered；返回原身份并进入恢复，不延后、不撤销已有登记 |
| 调度版本/目标/epoch 不匹配，观察无效或原因未知 | 拒绝本次处置；不修改用户工作 |

其他能力的确定性拒绝需先具备同等有效的能力上报与验证契约；初期不能把所有“客户端不支持”都判为
用户输入错误。服务认证失败、未知枚举或协议解析失败也不等价于 Run 失败。

Cloud 为同一工作的连续临时处置维护持久次数，退避为 5、10、20、40 秒，之后上限 60 秒；调度版本和
次数只在成功提交新处置时递增。重复 submission 返回原结果，不再推迟时间或重复计数。available_at
基于数据库时间；Agent 工作最多推迟到原 startup_deadline_at，已到截止交回启动结算，不能产生越过
截止的新领取资格。交付沿用自己的给定放弃规则，延后不修改首次交付声明时间。

Controller 收到 committed deferred/retired/rejected 后继续本批，登记与处置合计每批最多 16 项，然后
让出执行机会给续租和关停。达到上限可继续下一批；失租或处置响应未知时停止本批并按同一 submission
恢复，不能本地忽略该项而宣称它已经出队。Watch 只是提示，周期领取继续兜底到期的延后工作。

### D3：登记、延后、撤回共用一个事务序列

WorkItem 增加工作 ID 与调度版本；新工作派发的 RecordDispatch 必须回传这两个值。Cloud 在现有控制
事务锁下复核 D1、预期版本、available_at、冻结输入与目标、所有现有授权，再登记执行并绑定 work。

| 同一工作上的竞争 | 唯一允许的结果 |
|---|---|
| 延后先提交，旧领取快照随后登记 | 旧版本登记拒绝，即使之后 available_at 又到期也不能复用旧版本 |
| 登记先提交，随后报告暂时不可用 | 返回原 registered 身份，不退回未登记状态 |
| 截止/取消撤回先提交，随后旧 claim 登记 | 新登记拒绝，不能重建 work、Thread 或会话 |
| 登记先提交，随后截止到期 | 生命周期按“已登记未知”路径对账/结束，不能走“尚未发生”的删除路径 |
| 延后/结算事务失败 | 元数据、业务转换和提交回执共同回滚，下一次从原事实继续 |

新写入必须先检查已有执行/提交的幂等结果，再判断是否允许**新**登记；历史记录可读不代表获得再次
派发的许可。Controller 仍须取得当前许可，终态 Run 的新许可关闭。Run 截止、调度版本与执行登记共用
现有事务锁/明确锁序；不新增只覆盖工作行、却绕开业务撤回的独立锁。

### D4：退役保留证据，业务接缝保持单一所有者

execution_work 增加调度版本、处置次数、最后安全原因和退役时间/原因。业务进入不再需要该工作阶段的
**同一个事务**调用控制面 retire 接缝，包括未登记启动撤回、交付成功/放弃进入 releasing、业务 done
及残留放弃。退役不是执行终止，不删除已有 node_executions、输入、事件收据、交付/资源责任。

控制面负责工作元数据与资格，业务层负责 Run/Thread 转换。确定性启动拒绝与截止处理复用启动 ADR 的
命名接缝；控制面不另写一套 Run 状态机。相同处置只触发一次业务钩子。旧启动实现若物理移除了未登记
工作，整合时统一到退役接缝；撤回语义与“不存在登记”的证明保持不变。

一个运行同时至多一个**未登记且未退役**的工作。部分唯一索引、enqueue 查重、领取查询和登记查询必须
一致更新。旧退役行不得阻止合法的新交付尝试；新尝试仍遵循原交付预算和输入规则，不用于给 Agent
启动续期。未登记延后不创建新的 delivery attempt 或新的 bundle/ref 身份。

### D5：登记响应未知时保留原执行身份

RPC 写超时后先重放同一 submission/execution，必要时经 GetDispatch 按原执行身份查询。已经登记的
工作不再出现在 ClaimWork；新 Controller 从 ListPendingDispatches 恢复原登记，不能用同一 Run 再建
一个会话来绕过未知响应。旧 epoch 重传仍须受 fencing；新持有者用原身份接管，不能伪装旧持有者重放。

如果超时的旧请求尚在途，单次 NOT_FOUND 不证明它将来不会提交。必须先用当前工作版本的 CAS 处置或
新 epoch fencing 排除旧登记，再判定仍未登记；否则继续原身份查询。已登记分支不更新 available_at，
也不重置 Run 的 ready 起点、启动/恢复截止或结束确认窗口。

## 不变量

1. 工作 ID、冻结输入和目标在临时延后期间不变；调度版本不是新执行身份。
2. 处置只有提交成功才影响后继领取；重放不增加退避次数或延长截止。
3. 退役、终态、残留或过期工作既不被领取，也不能经旧快照新登记。
4. 登记/延后/撤回只有一个事务顺序；已登记未知执行不被当作未发生。
5. 控制面只拥有工作/执行证据；业务转换经同事务接缝保持唯一所有者。
6. 真实迟到事实继续可接管/ACK，业务终态不复活、不重复结算。

## 为什么不是这些替代方案

| 方案 | 取舍 |
|---|---|
| Controller 内存跳过集合 | 少一次写入，但重启失效，Cloud 无法解释 pending，多个 worker 各自定义顺序 |
| 只更新 available_at，没有调度版本 | 能让出队头，但已经拿到的旧快照在延后后仍可登记 |
| ClaimWork 一次返回全部工作 | 可本地扫描，但不能修复终态资格、恢复后的顺序或旧快照竞态，队列大小还会进入协议预算 |
| 延后创建新 work/Run | 容易再次调度，但改变冻结身份、绕过总截止并可能复制会话 |
| 删除所有未登记工作作为收尾 | 查询更简单，但丢失可解释的处置记录，且与残留账本/历史交付的审计义务冲突 |
| 将 transport 错误直接转换为 rejected | 能快速结束，但超时可能已提交，会错误丢弃未知执行 |

## 兼容性与迁移

proto 仅新增方法、字段与结果类型，保留已有字段编号和方法，buf breaking 检查继续执行。字段可加并不
代表旧客户端自动获得新语义：旧 Controller 不回传调度版本，不能在新调度模式下继续登记工作。

采用显式分阶段启用：

1. Cloud 先提供新方法与可选字段，默认关闭新工作调度模式；旧模式仍按既有行为运行，不能宣称已修复
   队头阻塞。迁移新增元数据，存量工作保留原输入、目标、created_at、available_at 和执行关联。
2. desktop 按 Cloud 已合入 commit 更新 proto gitlink/生成物，实现处置、版本回传及未知恢复。先在固定
   候选栈验证；部署切换时停止旧 Controller 的领取、等待旧租约失效，不终止既有 Node 执行。
3. 明确启用新调度模式，将可领取 work 的版本初始化为正值，持久记录模式已启用；使用该模式的 Cloud
   启动与 Controller 能力检查必须拒绝无版本的新 work 登记。配置试图关闭数据库已启用的模式时拒绝
   启动；其他种类的既有 RecordDispatch 形状保持。
4. 回填仅退役当前阶段明确不合格的未登记项，分批、可重跑；不删除执行、effect、收据或残留资源。
   Claim 的实时资格过滤先保证旧行安全，回填完成不是正确性的前置。

新模式写入后不能通过关闭配置或回滚到不认识退役/版本的旧程序重新开放旧工作。回滚需停止领取并保持
数据库向前兼容/终态保护，已有执行继续按稳定身份恢复。这里的部署切换与语义门禁需与本提案一起批准，
不能只凭 buf breaking 通过宣称混合版本安全。

## 落地与验收边界

批准后才维护对应核心用例。先合入启动截止决策及其实现，基于同一事务接缝实施 Cloud 工作元数据、
协议、资格/版本校验与 Operation 配套修复；随后更新 Controller，最后启用模式并进行实际联合验收。
保留每个阶段的固定 commit，不能以不同版本的独立成功拼成整链成功。

联合验证至少包含：两个租户的阻塞/健康工作；真实 Controller 在 Fleet 暂缺、gate 忙、当前有效缺能力与
陈旧能力记录下的处置；延后后重启而截止不变；登记与延后/撤回的两种事务顺序；提交响应丢失/迟到；
Node 重连不复制会话；交付已放弃后的旧工作；正常多轮/恢复与残留保护；旧客户端、旧 epoch、模式切换
和迁移重跑。直接更新数据库可用于构造时间边界，不能替代 Controller 真正报告延后的端到端证据。

## 本决策未解决的问题

- 多租约分区、租户配额与高负载调度 SLO；本次保证让出不可处理项，不提供全局配额承诺。
- 创建 blocked 的第二期放弃、隐藏 Workspace 的物理回收；沿各自生命周期决策推进。
- Git 交付载荷与 clone 结果细分；本次保持当前批准的载荷和已有 clone 三次上限。
