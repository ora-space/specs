# 小队的正式契约以 v2-server 为准：编组只表达分工，不授予权限、不触发执行；邀请改由工作区成员入口直接加入，取代 v1 根决策

小队把同一工作区里的人和 Space Agent 编在一起，表达谁负责什么、谁能维护这个队。编组不授予任何访问、模型、凭据或执行
权限，也不触发 Agent 执行。成员是类型化引用：人引用租户成员，Agent 引用系统预装、已安装的可执行 Space Agent。
任何工作区成员都能建队并成为首位维护者；编辑、增删成员和归档限工作区 owner 或本队的有效人类维护者；人类成员可以自己
退出，不设"最后维护者"保护。写操作按小队版本做乐观校验，归档不可恢复，结束的编组保留为历史。邀请新人由工作区成员入口
完成，提交即加入，不再有 v1 的定向加入意图、接受页和审批。这些都是 v2-server 现在的做法，本文把它们定为正式的
desktop↔cloud 契约，不新增机制。

本 ADR 处于 `proposed`：等待 owner 评审，评审通过后改为 `approved` 并同步核心测试用例。它是领域 `cloud/squad` 的后续
决策，属于 circus #1029（phase2：把 v2-server 的候选 API 定为正式契约）。前提是
[Cloud 单进程根决策](../lifecycle/0-single-process-cloud-on-enterprise-intranet.md)（下称"A1"）。依据还有 circus
#808（演示范围：取消邀请接受页）、#813（自己退出、维护者交接、Agent leader）、#924 / #925（已删除账号退出小队）、
#969（成员收进小队）。读取的代码版本为 cloud
[`966a6ba5`](https://github.com/ora-space/cloud/tree/966a6ba590cce07b9629f0c2984aa905dd00be86/v2-server)
（`v2-server/internal/server/squads.go`、`internal/store/squads.go`、`internal/store/invite.go`、
`internal/store/accounts.go`、`squads.openapi.json`）。

**本文取代 [v1 小队根决策](0-workspace-scoped-human-agent-squads.md)。**A1 定了 v1 业务领域的 ADR 在 v1 退役（I11，
circus #1061）时整体标为 `superseded`，由 v2-server 和 #1029 的正式契约取代。为了让那份根决策届时能整篇作废，本文是
自含的：仍然成立的 v1 规则也在下文重新写明，读者不需要再回去读 v1 根决策。

范围与兼容性边界：

- **涉及**：cloud 的 `v2-server/`（接口实现与契约文件）。frontend-v2 已在使用；desktop 现在不调用，phase2 接入 cloud 后
  使用同一契约。
- **不做数据迁移**：v1 的小队只有演示页面，没有落库的真实编组。
- **不在本文**：邀请新人的接口属于身份与成员领域（`POST …/members`），本文只规定它带 `squadId` 时对小队的效果
  （D3）；任务指派给小队的语义属于协作任务领域。

## 决策

### D1：契约文件和路径

- **契约文件**：正式契约就是 cloud 仓的 `v2-server/squads.openapi.json`。字段、参数和错误码以它为准；本文规定它们的
  语义和不能破坏的承诺。specs 不复制 schema。
- **路径**：保留 `/api/v2/tenants/{tid}` 前缀（理由同 A1 D1：v2-server 就是正式 Cloud，v1 的 `api/openapi.json` 在 I11
  退役）。产品和路径都叫 squad，不使用 v1 协议里的 `team`。

  | 操作 | 路径（`…` = `/api/v2/tenants/{tid}`） | 说明 |
  | --- | --- | --- |
  | 列表 | `GET …/squads` | 未归档的小队，带有效的人类、Agent、维护者人数；`nextCursor` 现在总为空，客户端仍按游标读取 |
  | 创建 | `POST …/squads` | 201，返回详情 |
  | 详情 | `GET …/squads/{sid}` | 归档的也能读；含已结束的编组 |
  | 编辑 | `PUT …/squads/{sid}` | 名称、简介、协作说明、leader，整体替换；带 `version` |
  | 归档 | `POST …/squads/{sid}/archive` | 带 `version` |
  | 加成员 | `POST …/squads/{sid}/members` | 201；带 `version` |
  | 改成员 | `PUT …/squads/{sid}/members/{mid}` | 职责文本和维护者标记，两者都必填；带 `version` |
  | 移除成员 | `DELETE …/squads/{sid}/members/{mid}?version=N` | 结束这条编组 |

  所有写操作都返回写入后的完整详情，客户端不需要再读一次。

### D2：身份与成员引用

- **小队身份**：一个稳定的 UUID，属于且只属于一个租户，不能迁移、不能复用。名称不是身份，不要求唯一。
- **可编辑字段**：名称（去掉首尾空白后不能为空、不能带首尾空白，最多 200 个字符）、简介（最多 2000 字符）、协作说明
  （最多 8000 字符）。
- **成员是类型化引用**：`type: human` 引用 `userId`，`type: agent` 引用 `spaceAgentId`，恰好填一个。不使用不分类型的
  成员标识，不按邮箱或显示名匹配身份。
  - 人类成员必须是本租户当前有效的成员和有效用户。
  - Agent 成员必须是本工作区系统预装、可执行、观测为已安装的 Space Agent。用户从插件页安装的市场 Agent 不进入候选。
  - 工作流不是成员。
- **一个对象可加入多个小队**；同一个队里，同一类型同一身份最多一条有效编组，重复加入返回 409 `member_exists`。
- **职责**：每条编组有一段职责文本（最多 500 字符），可以因队而异。它只是说明，不是授权或执行指令。姓名、工作区角色、
  插件身份、模型和凭据仍归原领域。
- **结束不复活**：编组结束（移除、自己退出、归档、账号删除）后保留为历史；再次加入是一条新的编组，不恢复旧的那条。

### D3：读取与写入权限

- **读取**：本租户的有效成员都能读全部小队和成员。不是本租户有效成员时，所有小队接口都返回 404 `not_found`，不能借
  此判断别的租户有没有某个小队。

| 动作 | 工作区 owner | 本队有效人类维护者 | 其他有效成员 |
| --- | --- | --- | --- |
| 查看小队、成员、历史 | 可以 | 可以 | 可以 |
| 创建小队（自己成为首位维护者） | 可以 | 可以 | 可以 |
| 编辑、设置或清除 leader | 可以 | 可以 | 不可以 |
| 加入成员、修改职责和维护者标记 | 可以 | 可以 | 不可以 |
| 移除别人 | 可以 | 可以 | 不可以 |
| 自己退出所在小队 | 可以 | 可以 | 可以 |
| 归档 | 可以 | 可以 | 不可以 |
| 邀请工作区外的人并同时入队 | 可以（经成员入口） | 不可以 | 不可以 |

- **工作区角色**：现在只有 owner 和 member；角色名为 `admin` 的成员按 owner 处理。没有权限时返回 403 `forbidden`。
- **创建**：创建小队和把创建者加为人类维护者在同一事务里完成。`createdBy` 只是审计信息，不带任何特权；创建者退出或
  被撤掉维护者后，和其他成员一样。
- **维护者**：只有人类能当维护者，给 Agent 设维护者标记返回 400 `invalid_member`。维护者可以给别的人类成员加上或去掉
  维护者标记。
- **没有"最后维护者"保护**：最后一位维护者也可以退出或被去掉标记；之后只有工作区 owner 能维护这个队、重新指定维护者。
- **自己退出**：有效人类成员移除自己的编组时不检查维护者身份。
- **邀请即入队**：工作区 owner 经成员入口邀请新人时可以带 `squadId`，账号创建、加入工作区和加入这个小队在同一事务里
  完成，新成员不是维护者。小队必须属于本工作区且未归档。没有待接受的邀请，也没有审批。

为什么去掉定向加入：v2 的登录只需邮箱，邀请提交即创建账号（#808），没有"对方接受"这一步，定向加入意图、接受页和
签发者失权这一整套规则没有发生的场景。企业登录（A6，circus #1050）接入后若重新需要邀请接受，在本文之上追加决策。

### D4：leader 是可选的配置

- 小队可以没有 leader。leader 只能是 Agent，必须满足 D2 对 Agent 成员的要求。
- 设置 leader 时，这个 Agent 还不是本队有效成员的，在同一事务里把它加为成员。
- 移除现任 leader 的编组时，在同一事务里清除 leader；归档时也清除。不会留下一个指向非成员的 leader。
- 编辑时 `leaderAgentId` 必填：给 UUID 表示设置，给 `null` 表示清除；创建时可以省略。
- **配置 leader 不启用任何执行**：没有 leader 路由、自动委派或自动分派。

### D5：版本与并发

- 每个小队有一个 `version`。除创建外的写操作都必须带上客户端读到的版本：缺少时返回 428 `version_required`；
  与当前版本不一致返回 409 `version_conflict`，客户端重新读取后再决定，不以后写覆盖前写。创建时不能带版本。
- 每次成功的写入都使版本加一，包括增删成员和修改成员。
- 同一个小队的写操作（编辑、增删成员、归档、自己退出）按小队串行提交：归档或移除先提交的，之后的加入失败；加入先提交
  的，之后的归档或移除会结束它。不会留下一条属于已归档小队的有效编组。
- 已归档的小队拒绝一切写入，返回 409 `squad_archived`。

### D6：归档

- 归档结束这个队全部有效编组，清除 leader，把它从列表里移除。详情和编组历史仍对本租户成员可读。
- 归档不可撤回，没有恢复接口。
- 归档不改变任务的指派、不取消执行、不改写会话历史。

### D7：账号删除时结束编组

- 账号被删除（软删除）后，它的有效编组结束。
- 被删除账号的编组记录留在库里，但不在小队详情中列出，包括"已退出"的历史，也不计入人数。
- 账号不会因为重新邀请、重启或重新写入用户配置而恢复，已结束的编组也不会恢复。

### D8：编组不授予权限、不触发执行

- 小队成员关系不授予任何项目、对话、任务的访问，不授予模型、Git 凭据或 Node 的使用权。不在某个队，也不减少原有的访问。
- 小队的任何写操作都不启动、不取消 Agent 执行。
- 小队 ID 可以作为任务的指派目标；指派之后谁处理、怎么执行，由协作任务领域规定，不在本文。

### D9：错误码

| HTTP | `code` | 含义 |
| --- | --- | --- |
| 400 | `invalid_json` | 请求体不是合法 JSON、带了未知字段，或超过 64 KiB |
| 400 | `invalid_name` / `invalid_description` / `invalid_charter` / `invalid_role` | 字段不合法（D2） |
| 400 | `invalid_leader` / `leader_required` | leader 不是 UUID；编辑时缺少 `leaderAgentId`（D4） |
| 400 | `invalid_member` | 成员引用不合法，或给 Agent 设维护者 |
| 400 | `invalid_user` / `invalid_space_agent` | 引用的人或 Agent 不满足 D2 |
| 400 | `invalid_version` | 创建时带了版本 |
| 403 | `forbidden` | 没有这项写入的权限（D3） |
| 404 | `not_found` | 小队或成员不存在，或调用者不是本租户有效成员 |
| 409 | `version_conflict` / `squad_archived` / `member_exists` | D5、D6、D2 |
| 428 | `version_required` | 写操作缺少版本 |

错误码是稳定的，客户端按 `code` 分支，不按说明文字。

### D10：第一版不做的

- 邀请接受、加入申请与审批、待加入意图。
- 私有小队、小队嵌套、跨工作区小队。
- 归档后恢复。
- leader 自动委派和小队级的自动执行。
- 变更推送：客户端在写操作之后用返回的详情更新，其他时候重新读取。

## 不变量

1. 有效小队成员必属于同一租户，并满足其引用类型的当前资格；人、Agent 和小队的身份不混用。
2. 同一个队里，同一对象最多一条有效编组；已结束的编组不会恢复。
3. 小队成员关系和维护者身份不授予任何资源、模型、凭据或执行权限；小队写操作不启动、不取消执行。
4. 有效 leader 一定是本队的有效 Agent 成员。
5. 只有人类能当维护者；`createdBy` 不带特权；工作区 owner 总能维护任何小队。
6. 每次写入都基于调用者读到的版本；已归档的小队不接受写入，也没有有效编组。
7. 不是本租户有效成员时，读不到任何小队信息，也不能借错误判断别的租户里是否存在某个小队。

## 为什么不是这些替代方案

| 方案 | 优势 | 否决理由 |
| --- | --- | --- |
| 保留 v1 的定向加入与审批 | 被邀请人明确同意加入范围；签发者失权后旧邀请失效 | v2 邀请即创建账号，没有接受这一步（#808）；企业登录接入后若需要再追加 |
| 设"最后维护者"保护 | 小队总有人维护 | 会挡住成员自己退出；工作区 owner 已经能接管（D3） |
| 新开领域目录写新根决策 | 和 v1 文件完全分开 | 领域没有变，仍是同一个"人机编组"；在同一目录用后续决策取代根决策，历史连续，读者沿着目录就能看到演变 |
| 逐条修改 v1 根决策、保留它为现行 | 改动少 | A1 定了 v1 业务领域 ADR 整体作废；保留它会让现行规则一半在 v1 文件里 |
| 路径改成 `team` | 和 v1 协议同名 | v1 的 Issue 协议随 v1 退役，产品和 v2 代码都叫 squad |

## 本决策未解决的问题

1. **Agent 被卸载或停用时的编组**：v1 根决策要求关闭其编组并清除 leader；v2-server 现在不处理，已卸载的 Agent 仍是
   有效成员。要不要补，补在哪条写入路径上，另行决定。
2. **移除工作区成员**：v2 现在没有这个接口。加上时，要在同一事务里结束他在所有小队的编组和维护者身份。
3. **工作区角色**：企业登录（A6）若引入 owner 和 member 以外的角色，D3 的权限表随之修改。
4. **列表分页**：`nextCursor` 现在总为空；小队数量增长后再实现分页，契约形状已经预留。
