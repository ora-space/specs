# 会话尝试的进程带环境标记，停止时先冻结并杀掉带标记进程，两次扫描干净才确认（Linux）

> 历史决策：D6 已知缺口与“本决策未解决的问题”中的 macOS 项已由[Ora Desktop 只支持 Windows 和 Linux](../../desktop/platform/0-windows-and-linux-only.md)
> 关闭：Desktop 不再支持 macOS，不再为 macOS 另立决策；Windows 项不变。本决策不覆盖 macOS 的说明继续成立。其余
> 决策不变，本提示不改变本决策的状态。

> 历史决策：D4“不会发任何停止信号的情况”第二条、不变量 7 中“保留会话的取消与失败不发任何停止信号”，以及“本决策
> 未解决的问题”第一条，由[保留会话前先停掉这一轮新起的进程](../protocol/20261123-turn-process-fence-before-keeping-session.md)
> （`implemented`）修改：Linux 上，会话被保留的取消或失败之前，Node 复用本决策 D2 的扫描、冻结与杀，只停掉这一轮新起、
> 且不在“这一轮开始前已启动、此刻仍存活的本尝试进程”所在会话中的被认领进程；一轮正常完成后仍不发任何信号。
> 这些部分以该决策为准。其余决策不变，本提示不改变本决策的状态。

Linux 上，Node 给 Agent 尝试和 stdio 探测尝试派发的每个进程设置 `ORA_SESSION_ATTEMPT=<attempt>`，后代经
`fork`/`execve` 继承它。尝试登记前，Node 先持久写下这次尝试的开始时刻和进程用户（范围记录）。停止尝试时，
Node 先用 SIGSTOP 冻结所有在尝试开始后启动、带标记或经仍在的父进程被认领的存活进程，反复扫描到不再出现新进程
（至多 32 轮，冻结至多 2 秒），再全部 SIGKILL，然后才按原线索杀进程组。确认停止除原锁与线索外，还要求连续两次
标记扫描干净，证明记为新值 `lock_processes_and_marks`；账本为每个尝试记录“有范围记录”标志，带标志而范围记录缺失或
损坏为 Unknown，只有不带标志、在标记出现之前登记的尝试保持 `lock_and_processes`。扫描在每个 Node 唯一的阻塞
worker 上串行执行，每次观察连同排队至多 5 秒，超出即 Unknown。行为变化是：会话以任何方式结束、MCP 生命周期替换
Agent 进程时，Agent 启动的一切都会被杀掉，包括脱离进程组的工具后台作业、开发服务器和共享守护进程（Gradle、
sccache）；轮次之间、保留会话的取消都不杀任何进程。保证等级仍是 `StopContainment::BestEffort`。

本 ADR 状态为 `implemented`：2026-11-20 经 owner 评审批准（[specs#318](https://github.com/ora-space/specs/pull/318)），
由 [desktop#802](https://github.com/ora-space/desktop/pull/802)（head `198cc415`，基于已含 desktop#793 的 main `2fc5e2ca`）

`crates/utils`（环境标记、procfs 扫描与冻结）、`apps/ora-node/src/session/stop/`（派发、终止、证据、阻塞 worker）、
`apps/ora-node/src/service/agents.rs`（部署前提告警）、`apps/ora-node/src/main.rs`（关闭上限）和 `crates/node-db`
（停止证明枚举、范围记录标志与 schema 16）。Node Protocol、Controller 契约与 TS 生成物不变：证明名只出现在 Node

## 问题与约束

[circus #1350](https://github.com/ora-space/circus/issues/1350) 报告：Agent 工具起的后台作业（OpenCode bash 工具与
Claude Bash 里的 `cmd &`）在 Node 结束会话之后仍然存活并继续写工作区，而 Node 同时把这次停止记为
`confirmed` / `lock_and_processes`。正常 EndSession、导致会话结束的取消、Node 被 SIGKILL 后的重启恢复、Node
优雅关闭四条路径都会漏出；[circus #1340](https://github.com/ora-space/circus/issues/1340) 用真实 `ora-node` 和部署
的 OpenCode 0.6.11、Claude 0.4.5 插件复现，作业在 Node 报告结束后 6–20 秒写出文件。

刷新决策 D5 的三种手段在这里同时失效：

- **进程组与会话**由进程自己选择。工具 shell 在 `setsid` 下运行，作业属于 Agent 新建的会话，父进程退出后被 init
  收养；按原进程组或按会话 id 都杀不到它。
- **尝试锁**属于打开的文件描述。Bun 起子进程时关闭继承的 fd，作业不持有锁，锁空闲不说明作业已退出。
- **线索**只记 Node 直接起的进程，作业不是 Node 的直接子进程，Agent 会话进程也不登记 reaper。

所以“原锁可取得、线索进程都不在”是假阳性。替换、恢复、资源释放和交付都建立在这份证据上，v2 上同一工作区
的后续节点、交付和回收会与残留作业并发。修复必须满足以下约束：

- **无特权**：当前 Linux 部署是可信本机、无 root、BestEffort，没有委派的 cgroup 子树；修复不能依赖新的部署权限。
- **跨 Node 重启**：Node 可能被 SIGKILL，证据和终止手段必须能从持久文件与内核状态重建，不能只存在于内存。
- **按尝试区分**：一个 Node 同时承载多个会话，进程多半同一 uid；只能杀属于原尝试的进程，PID 复用不能导致误杀。
- **不依赖 Agent 配合**：后台作业来自上游 Agent 和模型生成的命令，插件版本各异，不能要求它们保留 fd 或进程组。
- **轮次之间不打扰**：LSP、MCP 这类常驻进程在会话内跨轮次使用，只能在会话结束或 Agent 替换时停止。
- **失败即未知**：读不到的状态不能当成“没有进程”。
- **不卡住 Node**：扫描要遍历 procfs、读取其他进程的内存，可能很慢甚至挂住；它不能占住 Node 的运行时线程，
  也不能让被冻结的进程一直停着。

## D1：尝试环境标记与范围记录

Linux 上，刷新决策 D5 的会话 spawner 为一次 Agent 尝试或 stdio 探测尝试派发的**每个**进程（插件运行时、Agent
CLI 及其他宿主子进程）设置环境变量 `ORA_SESSION_ATTEMPT`，值为该尝试的 ID。这一项在清空环境与移除继承变量之后、
作为最后一项显式变量写入，调用方传入的环境或清空环境的选项都不能覆盖或去掉它。尝试 ID 是 UUID，不含分隔符
`:`，总能构成合法的环境项。后代进程经 `fork`/`execve` 继承它，与进程组、会话、父进程是否退出无关。

尝试登记进账本之前，Node 在 `session-attempts/<attempt>.mark` 写下这次尝试的**范围记录**，紧接锁标记之后刷盘并
fsync 目录：

| 字段 | 含义 |
| --- | --- |
| `since_ticks` | 写记录时的 `CLOCK_BOOTTIME`，换算为 `/proc/<pid>/stat` 使用的 clock tick；早于本尝试的第一次 spawn |
| `uid` | 本尝试的进程运行所用的用户：继承 Node 身份时为 Node 的 euid，Separate placement 时为 workload uid |

范围记录是只含这两个字段的 JSON，不含 argv、env、URL、Settings 或其摘要；读取上限 1 KiB，出现未知字段或解析失败
都视为损坏。它与锁、线索放在同一目录、同一退休前缀下，按刷新决策 D5 的规则一起回收。HTTP 本地任务没有进程，
不写范围记录；Git 尝试走 `managed/attempt_lock`，不加标记。

账本登记尝试时，同一行记下**有范围记录**标志：范围记录已刷盘后才登记，所以新 Node 登记的尝试总是带标志；
schema 迁移前已存在的行一律不带标志（D7）。标志只说明“这个尝试应当有范围记录”，判定时以它区分“记录丢了”和
“本来就没有”（D3）。登记的幂等比较包含标志：同一尝试以不同标志重放是身份冲突，不会悄悄改写。

为什么用环境变量：它是 Linux 上唯一默认跨 `setsid`、被收养、关闭 fd 都保留下来的、由启动方写入的进程属性；
进程组、会话和 fd 都由进程自己决定去留。为什么记开始时刻：内核按同一 boot 时钟记录进程开始时间并截断为
tick，记录之后 fork 的进程不会报告更早的 tick，所以 `start_ticks >= since_ticks` 能把尝试开始前已存在的进程整体
排除在外，标记被伪造也碰不到它们（D8）。为什么记用户：只在 Node 与尝试用户不同时，读不到的进程才可能属于本
尝试（D6）。为什么登记前写：账本里的每个新尝试都必然有范围记录，记录后、spawn 前崩溃只留下没有进程的范围，
扫描干净，不造成假门禁。为什么另记标志：只凭文件是否存在，新尝试的范围记录被删除或丢失时与旧尝试无法区分，
会悄悄降级为不扫描标记的旧证明；标志让这种情况落到 Unknown。

`since_ticks` 只在原 boot 上有意义。boot_id 不同时不扫描、不发信号，按刷新决策 D5 的跨 boot 规则处理（D3）。

## D2：扫描、冻结与杀，均有上限

**一次扫描**遍历 Node 可见的 procfs 一遍，只看候选进程：存活、不是 Node 自己、`start_ticks >= since_ticks`。
“存活”指线程组里还有线程在运行：主线程已退出（stat 显示 `Z`/`X`）而其他线程仍在的线程组也是候选，经其中一个
存活线程的 `task/<tid>/environ` 读取环境；线程组已空才跳过。每个进程经固定的 `/proc/<pid>` 目录句柄读取，读完
即关闭，再处理下一个，所以一次扫描只持有固定个数的 fd，与进程数无关；PID 复用不会读到另一个进程。观察结果只
保留 PID、启动 tick、父进程、`/proc/<pid>` 目录的属主与环境读取结论：

| 分类 | 条件 |
| --- | --- |
| 带标记 | 存在 `ORA_SESSION_ATTEMPT=` 项，其值按 `:` 切分后有一段与尝试 ID 完全相等 |
| 被认领 | 带标记，或其父进程是被认领的候选进程、且按 PID 与启动 tick 复核仍是本轮观察到的那个进程（反复传递到不动点，PID 回绕时父后子前也成立） |
| 待定 | 未被认领、环境不可读、`/proc/<pid>` 属于范围记录的 `uid`，且 Node 的 euid 不是该 `uid` |
| 无关 | 其余候选 |

“环境不可读”包括：读取被拒绝（EACCES）；环境超过 8 MiB 被截断；以及 Node 不是 root 且 `/proc/<pid>` 属于其他
用户——这时扫描不去读，直接按不可读处理，结论与读取后被拒绝相同，也不会在其他用户的进程上挂住。procfs 无法
枚举、fd 耗尽，或出现“进程已退出”以外的读取错误，整次扫描失败，不当作空结果。

**停止一个尝试**时，Node 在同一 boot 上按以下顺序发信号：

1. 扫描并向每个新出现的被认领进程发 SIGSTOP；再扫描，冻结新出现的；某一轮没有新进程即停，至多 32 轮。某个
   进程的 pidfd 打不开（不是因为它已退出）时不记为已处理，同一次停止的下一轮再试。
2. 向所有已冻结的进程发 SIGKILL。冻结有 2 秒的墙钟上限：一个看门狗线程与扫描轮次共享冻结集合，2 秒一到，
   无论扫描是否返回都杀掉全部已冻结进程；之后仍在进行的轮次对新认领的进程直接 SIGKILL，不再冻结。扫描报错
   时也一样，已冻结的进程一律杀掉，不留在停止状态。收尾杀冻结集合时，某个进程重新确认失败（不是因为它已退出，
   例如暂时的 EMFILE）就被跳过，它留在 T 状态，直到下一次停止观察（25 ms–1 秒之后）再次认领、冻结并杀掉它；
   它仍被扫描认领，证据是 Running，不受影响，只是延迟。Node 恰在此时退出的，由重启收口杀掉。
3. 按刷新决策 D5 的已验证线索终止原进程组。

每个信号都在发送前按 PID 与启动 tick 重新确认进程、再经新开的 pidfd 发出，同一时刻只开一个 pidfd；启动 tick 不
同的 PID 被拒绝。信号是否发送成功不报告，也不构成证据；只有之后的扫描（D3）说明还剩什么。

为什么先冻结：被冻结的进程不能 fork 也不能退出，冻结前刚 fork 出的子进程在下一轮仍以它为父进程，即使子进程
清空了环境也会被认领；直接杀会先让这个子进程变成孤儿，之后再也找不到。为什么先于进程组：组杀会在扫描看到带
标记的父进程之前就把清空环境的子进程变成孤儿；组成员本来也带标记，组杀之后只补那些清空了标记的组成员。为什么
32 轮：一轮里没有新进程通常第二轮就结束；上限只用来防止 fork 风暴拖住停止者，剩下的进程会被证据扫描看见，判为
Running，按原有重试与 `stop_unconfirmed` 规则处理。为什么 2 秒：读一个进程的 `environ` 要等它的内存锁，挂住的
FUSE/NFS 可以让一次读取无限期等待；没有墙钟上限，前几轮冻结的进程会一直停在 T 状态。上限之后改为直接杀，
是以“fork 很快的父进程在被杀前刚 fork 出、清空了环境的子进程可能逃掉”换“不再新增停着的进程”，逃掉的属于 D6 的
已知缺口。为什么重新确认而不一直持有
观察时的 pidfd：窗口里有成千上万个进程时，持有每个进程的句柄会耗尽 fd，使扫描失败、停止永远是 Unknown；
按启动 tick 重新确认能挡住 PID 复用，只剩同一个 tick（通常 10 ms）内 PID 回绕一整圈的理论缺口。为什么复核父
进程：父进程退出、PID 在本轮扫描期间被无关进程接手时，不能把新进程的子进程当成本尝试的；代价是父进程恰好在
观察之后、复核之前退出时，它清空了环境的子进程会漏掉，之后也找不到，这同样属于 D6“清空环境后成为孤儿”的缺口。

**在哪里执行**：扫描、冻结与杀都不在 Node 的运行时线程上执行。每个 Node 只有一个阻塞 worker，所有会话的停止
观察（会话结束确认、重启收口、Agent 替换、探测清理、对账）在它上面串行。一次观察是一次终止加一次证据判定
（`recheck` 中两者分开调度），它的 5 秒预算**包括等待 worker 的时间**；超出预算即为 Unknown，按原有规则在停止
确认期限内重试。替换时，spawn 闸门在锁内关闭，终止在锁外、运行时外执行。

为什么串行且把排队算进预算：挂住的读取会一直占着 worker；只对执行计时，排在它后面的观察就会无限排队，确认循环
不再按期得到 Unknown；不排队而各起线程，则每次重试都多一个挂住的线程。把等待算进预算，后面的观察才会失败即放弃。
代价是多个会话同时结束时，排在后面的观察可能在排队时就用完预算，被记成 Unknown 后重试；这只推迟确认，不产生
假证据。

**挂住时的后果**：一次 `environ` 读取挂住后，worker 被占到读取返回（挂载恢复，或它等待的进程退出），Node 自身
不会自愈；在此之前，这个 Node 所有会话的停止观察都是 Unknown，到期限后记 `stop_unconfirmed`，是失败即封闭。
重启后的 Node 扫描同一窗口，只要那个进程还在、挂载还卡着，就可能再次挂住。已冻结的进程不受影响（看门狗）。
Node 退出时，服务返回之后最多再等 5 秒被放弃的观察，然后退出，结束那个线程；优雅关闭在此之前仍按刷新决策 D5
等会话的确认循环到停止期限，worker 挂住时这段时间里每次观察都是 Unknown。

| 上限 | 值 | 来源 |
| --- | --- | --- |
| 冻结轮数 | 32 | 本决策 |
| 冻结时长 | 2 秒，看门狗保证，扫描挂住时也成立；收尾时重新确认失败的进程留到下一次停止观察 | 本决策 |
| 单个进程 `environ` 读取 | 8 MiB，超出视为不可读 | 本决策；高于 Linux 对新程序参数与环境的合计上限，被截断的环境不被当作“没有标记” |
| 一次扫描持有的 fd | 固定个数，与进程数无关 | 本决策 |
| 范围记录读取 | 1 KiB | 本决策 |
| 证据扫描 | 连续 2 次 | 本决策（D3） |
| 一次停止观察 | 5 秒，含等待 worker；超出为 Unknown | 本决策 |
| 停止 worker | 每个 Node 1 个，所有会话串行 | 本决策 |
| 观察之间的等待 | 25 ms 起倍增，至多 1 秒；确认、对账、替换循环共用 | 本决策；取代刷新决策 D5 的固定 25 ms |
| Node 退出时等待被放弃的观察 | 5 秒 | 本决策 |
| `recheck` 总时长 | 10 秒，每次观察、终止与等待只拿剩余时间 | 继承刷新决策 D5 |
| 停止确认期限 | 默认 10 分钟 | 继承刷新决策 D5 |

## D3：停止证据与证明名

同一 boot 上，Node 按以下顺序判定一个尝试是否停止，任何一步不成立即返回对应结论：

1. 锁标记文件有效，原锁可取得（继承）；
2. 全部线索的直接进程及其进程组都已不在（继承）；
3. 按账本的范围记录标志读取范围记录：
   - 不带标志：这是标记出现之前登记的尝试，它的进程都不带标记，不扫描，证明记 `lock_and_processes`；
   - 带标志，范围记录缺失、损坏或不可读：Unknown；
   - 带标志且范围记录有效：连续两次扫描，任一次有被认领进程即 Running；有待定进程或扫描失败即 Unknown；两次
     都干净，证明记 `lock_processes_and_marks`。

范围记录标志的唯一来源是账本行，每条路径都从账本读取：会话结束确认、重启收口与对账使用读出的停止记录，Agent
替换与探测清理按尝试 ID 回查账本。读不到账本行时不作判定：替换保持受阻、不启动后继，探测清理得不到证明、继续
占用名额。终止不看标志，只要范围记录存在就先按 D2 杀被认领的进程。

为什么两次：一个进程在扫描经过它子进程的槽位时 fork 后退出，PID 又回绕，单次扫描可能漏掉这个子进程；连续两次
扫描不可能都漏掉。为什么只从账本读标志：替换与探测路径的尝试虽然都由本 Node 写入，但“是否有范围记录”若在
代码里另有一处假定，就成了第二个来源，与账本不一致时会悄悄降级。

| 证明 | 产生条件 | 能否解除 `legacy_unknown` | 能否用于 `after-host-reboot` |
| --- | --- | --- | --- |
| `lock_and_processes` | 同一 boot，不带范围记录标志的旧尝试，锁与线索干净 | 不能 | 不能 |
| `lock_processes_and_marks` | 同一 boot，带标志的尝试，锁、线索与两次扫描都干净 | 不能 | 不能 |
| `host_reboot` | 继承：同一可信主机标识，boot_id 不同 | 能 | 能 |
| `fenced_volume` | 继承：部署声明单点挂载与存储层隔离 | 能 | 能 |

`legacy_unknown` 的尝试没有尝试锁，也不带范围记录标志，同一 boot 的两种证明都被账本拒绝，出口仍只有同机重启与
单点挂载保证。`after-host-reboot` 对账要求宿主重启证据，两种同一 boot 的证明都不满足它。

刷新决策 D5 的重启收口表改为：

| 原尝试证据 | 处理 |
| --- | --- |
| boot_id 相同，原锁可取得，全部线索的直接进程都已不在，且带范围记录标志时连续两次标记扫描干净 | 按 BestEffort 确认已停止或从未派发；带标志记 `lock_processes_and_marks`，不带标志记 `lock_and_processes`；正常立即结算 interrupted |
| boot_id 相同，原锁被占用、任一线索的直接进程仍存活，或仍有被标记扫描认领的存活进程 | 先按 D2 冻结并杀掉被认领的进程，再按各条已验证线索终止对应进程组，再查锁、直接进程与标记；没有取得停止证据前保留原责任 |
| boot_id 相同，锁缺失、损坏或不可读 | Unknown，转交对账（继承） |
| boot_id 相同，带标志而范围记录缺失、损坏或不可读，procfs 不可读，扫描有待定进程，或观察超出预算 | Unknown，转交对账 |
| boot_id 不同，且记录的主机标识与当前相同 | 记 `host_reboot` 确认（继承） |
| boot_id 不同，主机标识不同、缺失或不可信 | Unknown，除非部署满足单点挂载保证（继承） |

`recheck` 在至多 10 秒内先核对原锁、全部线索与标记扫描；未停止时按 D2 冻结并杀掉被认领的进程、终止线索进程组，
等待后再观察。每次观察、终止与等待只拿到 10 秒剩下的时间，剩余为零时不再派发；到上限时报告最后一次观察到的
证据。其余规则不变。`StopUnconfirmed` 的 `guarantee` 仍为 `BestEffort`；证明名不进入 Node Protocol，Controller
不会看到它，只有 Node 账本和 root `reconcile-session-stop` 的审计结果记录它，审计可以据此区分扫描过标记与没有标记可扫
的尝试。

## D4：什么会被杀、何时（行为变化）

一个尝试被**停止**时，D2 杀掉它的全部被认领进程。会停止尝试的情况就是刷新决策 D5、D6、D8 已有的停止路径：

| 情况 | 停止的尝试 |
| --- | --- |
| 会话结束：EndSession、Agent 失败、取消决策中以 `session_ending` 结束的取消、Node 优雅关闭 | 本 execution 的 Agent 尝试与探测尝试 |
| Node 崩溃或被杀后的重启收口 | 账本中未确认的原尝试 |
| MCP 生命周期替换 Agent 进程（包版本变化、第九次运行时 load） | 被替换的旧 Agent 尝试；取得新证明后才启动后继 |
| stdio 探测结束或超时清理 | 该探测尝试 |
| root `recheck` | 指定的原尝试 |

被杀的包括 Agent 启动的一切带标记进程：工具后台作业、开发服务器、文件监视进程、MCP 服务与语言服务，以及从
会话中启动的共享守护进程（例如 Gradle daemon、sccache 服务），**即使其他会话或程序仍在使用它们**。需要在会话
结束后继续运行的守护进程，必须在 Ora 之外启动。

不会发任何停止信号的情况：

- 轮次之间：一轮正常完成后，带标记的进程照常存活，供下一轮使用；
- 取消决策中会话被保留的取消（`TurnCancelSettled{stopped}`）与会话被保留的失败：这一轮工具起的后台作业继续
  运行，进入下一轮。按轮次清理属于 #1339 方向 B，见“本决策未解决的问题”。

为什么以尝试为界：尝试是 Node 能持久证明归属的最小单位。Node 无法区分“用户希望它活过会话的守护进程”和
“漏掉的后台作业”，二者同样可能写 checkout；在会话结束时一律杀掉，才能让终态之后 checkout 不再被这个会话的
进程修改。代价由 owner 接受：会话 A 启动、会话 B 也在复用的 Gradle daemon 会随 A 结束而退出，B 正在进行的构建
会失败，下一次构建由 B 自己重新启动守护进程（这时它带 B 的标记）。

## D5：嵌套 Node 的标记链

Node 自己的环境里已有非空的 `ORA_SESSION_ATTEMPT`（它本身是外层某个尝试启动的进程，例如 Agent 在会话里运行
了一个 Node）时，它给子进程的值是 `<继承值>:<attempt>`，例如 `outer:inner`；没有或为空时只写自己的 ID。

- 外层尝试停止时，内层 Node 本身和它所有尝试的进程都带外层 token，一起被杀；
- 内层 Node 只认领值中列出自己 token 的进程，不认领外层尝试的其他进程，也不认领自己（扫描排除 Node 自身）；
- 匹配按整段 token，`inner-2` 或 `XORA_SESSION_ATTEMPT` 都不会命中 `inner`。

为什么保留外层 token：否则内层 Node 给子进程写的值会覆盖外层标记，外层尝试的停止就漏掉内层的整棵进程树，
回到 #1350 的问题。为什么不让内层认领外层：内层 Node 只对自己的尝试负责，认领外层会让它杀掉不归它管的进程。

## D6：读不到环境的进程与已知缺口

`environ` 读不到的进程按下表处理：

| 情况 | 处理 | 理由 |
| --- | --- | --- |
| 被认领进程的子进程，环境不可读 | 经父进程认领，照常冻结并杀 | 父子关系不需要读环境 |
| 尝试用户的孤儿进程，Node 也以该用户运行，环境不可读 | 不认领，也不使证据为 Unknown | 同用户下读不到环境，说明进程把自己设为不可 dump（其 `/proc` 目录归 root）或带 file capability；ssh-agent 这类无关程序同样如此，计入会挡住所有停止 |
| 其他用户的孤儿进程（例如经 `sudo` 或其他 setuid 程序换了用户），Node 不是 root | 不读取，不认领，也不使证据为 Unknown | 它的 `/proc` 目录不属于尝试用户，不满足“待定”；读取必然被拒绝 |
| 尝试用户的进程，Node 以其他用户运行且没有 `CAP_SYS_PTRACE` | 待定，证据为 Unknown | 此时 Node 读不到这个用户的任何环境，读不到不再能说明“不属于本尝试” |
| 带标志而范围记录缺失、损坏或不可读，procfs 无法枚举 | Unknown | 无法判断就不能当作没有进程 |

以下进程不在证据内，仍是已知缺口，因此证据保持 `StopContainment::BestEffort`，不宣称 Strong 或整棵树静止：

- 清空或改写环境的后代（`env -i`，或像 PostgreSQL、nginx 那样把进程标题写进环境区域的守护进程）、设为不可 dump
  的后代、换了用户的后代：父进程还被认领时仍能经父子关系找到，父进程先退出后就找不到；父进程恰在一轮观察与复核
  之间退出，或冻结上限之后 fork 很快的父进程不经冻结被直接杀掉时，这类子进程同样会漏掉（D2）；
- 由尝试之外的服务代为启动的进程（例如经 `docker run` 或 `systemd-run`），它们不继承标记；
- Node 的 procfs 看不到的进程，例如被移到 Node 不可见的 PID namespace 中的进程；
- 同一个 clock tick 内 PID 回绕一整圈后被复用的进程：发信号前的启动 tick 复核挡不住它（D2）；
- macOS 与 Windows：本决策不覆盖，各平台另行实测和决策；
- 标记出现之前登记、升级时仍存活的尝试：不带范围记录标志，它们的脱组作业仍不在证据内（D7）。

**部署前提**：Node 与 workload 以同一用户运行，或 Node 具备 `CAP_SYS_PTRACE`。Desktop 与 cloud v2 当前都以同一
用户运行。Node 启动时，在配置了 Agent 的情况下校验 Agent 配置时检查这一前提：未配置 workload 用户或它与 Node 的
euid 相同即满足；否则读取 Node 自身的有效能力集（`/proc/self/status` 的 `CapEff`），没有 `CAP_SYS_PTRACE` 或读不到
能力集时记录一条告警，但不拒绝启动。检查只看 `CapEff`，检测不到 Yama `ptrace_scope` 或 LSM 的拒绝；这种部署下
读取仍被拒绝，证据同样是 Unknown，只是没有告警。不满足前提时按上表第四行，窗口内凡有 workload 用户读不到的进程，
停止证据就是 Unknown，结果是更多的 `stop_unconfirmed`，而不是假的停止证据。选择告警而非拒绝启动，是因为前提不满足
只削弱确认的可用性，不破坏安全性；拒绝启动则会让一次配置偏差使整个 Workspace 不可用。读不到能力集按“没有”处理，
是让告警偏向谨慎。

## D7：账本 schema 与单向兼容

`session_stop_attempts` 做两处改动，放在 schema 16 这一个迁移里：`evidence` 的 CHECK 增加 `lock_processes_and_marks`，
并新增 D1 的范围记录标志列 `mark_scope`（0/1，默认 0）。SQLite 不能原地放宽 CHECK，迁移在一个事务中重建这张表：
改名旧表、按新定义建表、显式列出旧列拷贝全部行（标志取默认值，即“不带”）、删除旧表、重建索引，并把
`user_version` 升到 16。schema 15 是 desktop#793 的取消结算表，16 排在它之后；v14 与 v15 的库都一次升到 16，v15
的取消结算在表重建后保留。迁移不改写任何既有值：已确认的行保留原证明，升级时仍存活的旧尝试不带标志，之后
仍记 `lock_and_processes`。

兼容是单向的：旧 Node 只接受到它自己的最高 `user_version`（cloud v2-server 锁定的 `2937fc97` 为 1..=14，含
desktop#793 的 Node 为 1..=15），会拒绝打开新库，而不是误读新证明。这沿用刷新决策 D5“不支持原地回滚旧二进制/schema”
的规则：升级后回退 Node 需要先排空并单独处理数据库，本决策不提供降级迁移。Node Protocol、Controller 与 TS 契约不变；
desktop 与 cloud 中没有代码按证明名匹配，cloud 不读 Node 数据库或尝试目录。

升级前仍应排空会话。未排空升级是已接受的缺口，本决策不为它新增规则：升级照常进行、不拒绝启动；来自没有停止
责任表的旧版本的会话，已按刷新决策 D5 标为 `legacy_unknown`；已有停止责任、但早于标记的尝试不带标志，保持
`lock_and_processes`，不获得标记覆盖。

为什么重建表而不是放宽成任意文本：封闭的 CHECK 让新旧程序对证明集合的理解一致，旧程序拒绝打开新库比把新值
当作未知字符串静默接受更安全。为什么新增证明名而不是沿用旧名：审计需要区分“扫描过标记”与“没有标记可扫”，
否则无法从记录判断一次确认是否覆盖了脱组作业。为什么标志与 CHECK 放在同一版：两项改动在同一个尚未发布的变更里，
分成两版只会多一个永远不会单独出现的中间 schema。

## D8：威胁说明

标记不是秘密。任何能读到被认领进程环境的进程（同 uid，或有 ptrace 权限）都能得到 token，并启动带标记的进程：

- 这些进程会在尝试停止时被杀。伪造者只能让**自己**在尝试开始之后启动的进程被杀；
- 伪造者不能让 Node 向尝试开始之前就存在的进程发信号：`start_ticks` 窗口把它们排除在外；把标记写进一个已存在
  的进程需要对它的 ptrace 权限，这本身已包含向它发信号的权限，不构成提权；
- 伪造者可以持续启动带标记的进程，让扫描一直看到 Running，从而拖住确认，直到期限后登记 `stop_unconfirmed`。
  owner 接受这一可用性风险：结果是失败即封闭，残留围栏照常挡住恢复与自身交付，不会产生假的停止证据；而同 uid
  的进程本来就能做更糟的事，例如持有继承的锁 fd，或直接改写 checkout。

反方向上，workload 可以清空环境逃出标记，这与刷新决策 D5“证据假定 workload 配合”的前提一致：标记、锁和线索
对恶意或失控 workload 都只是 BestEffort，不是对抗性隔离。

## 实现与批准文本的差异

desktop#802 在评审中按以下方式偏离或细化了 approved 文本。每一项都已写进上面对应的决策，此处只汇总，便于对照
批准版本：

| 批准文本 | 实际采用 | 原因 |
| --- | --- | --- |
| D2 候选“存活（不是 Z/X 状态）” | 主线程已退出、仍有线程的线程组算存活，经存活线程读环境，按线程组认领和发信号 | 否则主线程退出、工作线程继续写文件的进程被当作已退出；评审复现了这种漏杀 |
| D2“被认领”：父进程是被认领的候选进程 | 另需按 PID 与启动 tick 复核父进程仍是本轮观察到的那个进程 | PID 在扫描期间被无关进程接手时，不能借出它的子进程；代价是父进程在观察与复核之间退出时，其清空环境的子进程漏掉（归入 D6 缺口） |
| D2“待定”：`environ` 读取被拒绝或被截断 | 另加：Node 不是 root 时不读其他用户进程的环境，直接按不可读处理 | 结论与读取后被拒绝相同，同时避免在其他用户的进程上挂住 |
| D2 与不变量 4“经 pidfd 发给扫描观察到的实例” | 观察后关闭句柄，只留 PID 与启动 tick；发信号前重新确认再开 pidfd；pidfd 打不开时下一轮重试 | 持有全部句柄会在进程多时耗尽 fd，使停止永远是 Unknown；剩下同一 tick 内 PID 回绕的理论缺口 |
| D2 第 2 步“即使中途某次扫描失败，已冻结的进程也一律杀掉” | 扫描挂住时也成立：2 秒看门狗杀掉全部已冻结进程，之后的轮次直接杀不再冻结，fork 很快的父进程清空环境的子进程可能因此逃掉；收尾时重新确认失败的冻结进程留在 T 状态，到下一次停止观察才被杀 | 挂住的 `environ` 读取会让已冻结进程一直停在 T 状态；重新确认失败的进程仍被扫描认领，证据为 Running，只是延迟 |
| D2 上限表 | 新增：一次观察 5 秒（含排队）、每个 Node 1 个串行 worker、25 ms→1 秒退避、一次扫描固定个数的 fd、冻结 2 秒、退出时等待 5 秒 | 扫描在运行时线程上会卡住整个 Node；见 D2“在哪里执行”与“挂住时的后果” |
| D2 上限表“`recheck` 总时长 10 秒” | 不变，并写明每次观察、终止与等待只拿剩余时间，到上限报告最后一次观察 | 原实现每轮各有完整预算，最坏会超出 10 秒 |
| D3“按账本的范围记录标志读取” | 不变，并写明每条路径都从账本读；读不到时替换受阻、探测清理无证明 | 实现曾在替换与探测路径假定带标志，已改为读账本 |
| D6 部署前提的启动检查 | 在配置了 Agent 时校验 Agent 配置时执行，只看 `CapEff`，读不到按没有处理；不探测 Yama 或 LSM | 能力位是启动时唯一可靠、无副作用的信号；漏报只少一条告警，证据仍是 Unknown |
| D6 已知缺口 | 另列：改写环境区域的守护进程、换了用户的孤儿、经 `docker run`/`systemd-run` 代启的进程、同一 tick 内的 PID 回绕 | 实现与评审确认这些进程同样不在证据内 |
| D7“desktop#793 所用版本之后的下一个 schema 版本” | schema 16，排在 desktop#793 的 15 之后；v14 与 v15 都一次升到 16 | desktop#793 先合入，占用 15 |

其中 `recheck` 10 秒与 D3 账本标志两行不是规则偏离：评审发现的超时与硬编码标志已在 desktop#802 中改代码，使实现
符合批准规则，列出只为写明实现方式。

## 不变量

1. Linux 上，Agent 尝试与 stdio 探测尝试由宿主派发的每个进程都带 `ORA_SESSION_ATTEMPT`，其值以整段 token 列出该
   尝试 ID；范围记录在尝试登记前已刷盘，新登记的尝试都带范围记录标志。
2. 带标志的尝试，只有原锁可取得、全部线索的进程与进程组都已不在、且连续两次标记扫描既无被认领进程也无待定
   进程时，才确认停止并记 `lock_processes_and_marks`；只有不带标志的尝试记 `lock_and_processes`。范围记录标志只
   来自账本。
3. 带标志而范围记录缺失或损坏、procfs 不可读、扫描失败、有待定进程或观察超出预算时，证据为 Unknown，绝不为
   Stopped。
4. Node 只向在尝试开始之后启动、带标记或经复核仍在的父进程被认领的进程发冻结与杀信号，每次发信号前按 PID 与
   启动 tick 重新确认并经 pidfd 发送；boot_id 不同时不发任何信号。
5. 冻结先于杀，杀先于组终止；冻结轮数至多 32、冻结时长至多 2 秒，扫描挂住时也不例外，只有收尾时重新确认失败
   的进程留到下一次停止观察；任何信号的返回都不构成停止证据。
6. 两种同一 boot 的证明都不解除 `legacy_unknown`，也不满足 `after-host-reboot`。
7. 会话结束（任何方式）、Agent 替换与探测清理杀掉对应尝试的全部被认领进程；轮次之间、保留会话的取消与失败
   不发任何停止信号。
8. 嵌套 Node 传下的值保留外层 token；每个 Node 只认领列出自己 token 的进程。
9. 停止保证仍为 `StopContainment::BestEffort`，不宣称 Strong 或整棵树静止。
10. 新 schema 只能前向迁移；旧 Node 拒绝打开它。
11. Node 与 workload 不同用户且 Node 的有效能力集没有 `CAP_SYS_PTRACE` 时，Node 启动告警；这种部署下的不确定只
    产生 Unknown。
12. 扫描与信号不在 Node 的运行时线程上执行；每次停止观察连同排队至多 5 秒，`recheck` 总共至多 10 秒，Node 退出时
    至多再等 5 秒被放弃的观察。

## 为什么不是这些替代方案

| 方案 | 优势与取舍 |
| --- | --- |
| Node 设为 child subreaper（`PR_SET_CHILD_SUBREAPER`），孤儿收养到 Node 而不是 init | 不依赖环境，`env -i` 的孤儿也能被 Node 看到并回收。但 Node 崩溃后 subreaper 随之消失，孤儿仍被 init 收养，重启收口得不到任何增益；一个 Node 承载多个会话，被收养的孤儿不说明属于哪个尝试；还要新增与 tokio 子进程回收并存的回收循环（约 200 行）。本次不做，可在标记之上作为后续补强 |
| 每个 execution 一个 cgroup v2 子树 | 进程无法在没有权限时离开 cgroup，是唯一能给出 Strong 的方向，[Linux cgroup 决策](../process/containment/linux/0-cgroup-v2-containment.md)已批准该方向。但它需要委派的 cgroup 子树，当前无 root 部署与 cloud v2 都不具备，要改部署才能落地；#1350 是 p1 缺陷，不能等部署变更。留给强纳管的后续决策 |
| 按会话 id（sid）杀 | 实现最小。但作业的 sid 正是 Agent 工具 shell 用 `setsid` 新建的，与 Node 记录的任何 sid 都不同，杀不到，与按进程组杀失效的原因相同 |
| 修插件或上游 Agent：保留 fd、不 `setsid`、自己清理后台作业 | 不改 Node。但行为由上游 Agent 和模型生成的命令决定，各插件版本都要改，用户命令里的 `setsid`/`nohup` 仍会逃逸；Node 的停止证据不能建立在 workload 的配合上 |
| 扫描后直接 SIGKILL，不先冻结 | 少一步。但会先把清空环境的子进程变成孤儿，之后再也认领不到（D2） |
| 同 uid 下读不到环境的进程一律计为 Unknown | 更保守。但 ssh-agent、带 file capability 的程序等无关进程同样读不到，几乎每次停止都会变成 Unknown 并登记残留，围栏失去意义（D6） |
| 只扫描一次就确认 | 更快。但 fork 后退出、PID 回绕的进程可能被单次扫描漏掉（D3） |
| 保留旧证明名，只加强判定 | 不需要 schema 变更。但审计无法区分一次确认是否扫描过标记，升级前后的记录含义不同却同名（D7） |
| 一直持有扫描时打开的 pidfd，直到杀完 | 身份保证不依赖启动 tick，没有同一 tick 内回绕的缺口。但窗口里进程多时会耗尽 fd，使扫描失败、停止永远是 Unknown；按启动 tick 重新确认的缺口窄得多（D2） |
| 停止观察只对执行计时，或每次观察各起线程 | 排队不会让观察超时。但挂住的读取后面会无限排队，或每次重试多一个挂住的线程；把排队算进预算才能失败即放弃（D2） |

## 后果

- 四种会话结束路径和 Agent 替换都会在报告停止之前杀掉保留环境的脱组后台作业；作业仍存活时 Node 不会确认停止。
- 行为变化：Agent 启动的开发服务器和共享守护进程随会话结束或 Agent 替换而退出，其他会话的构建可能因此中断；
  需要长期运行的守护进程要在 Ora 之外启动。
- 每次停止观察都要遍历一次 procfs 并读取窗口内进程的环境；它在独立 worker 上串行，不阻塞 Node 的运行时，但多个
  会话同时结束时排在后面的观察可能先超时为 Unknown 再重试，确认会稍慢；停止确认期限不变。
- 一次挂住的 `environ` 读取会让这个 Node 所有会话的停止观察在读取返回前都是 Unknown，重启后可能再次遇到；冻结的
  进程仍在 2 秒内被杀，Node 退出至多多等 5 秒。
- 进程拒绝退出（不可中断睡眠）或标记被持续伪造时，确认会被拖住，`stop_unconfirmed` 可能比以前多；这是失败即
  封闭，不产生假证据。
- 不满足部署前提（Node 与 workload 不同用户且没有 `CAP_SYS_PTRACE`）时，Node 启动告警但照常服务，窗口内凡有该
  用户读不到的进程，证据就是 Unknown；Desktop 与 cloud v2 当前满足前提。
- 范围记录丢失或损坏的新尝试不会降级为旧证明，而是 Unknown，转交对账。
- 未排空升级时仍存活、早于标记的尝试不获得覆盖，这是已接受的缺口；schema 16 不能回退，排在 desktop#793 的
  schema 15 之后。

## 本决策未解决的问题

- **保留会话的取消后清理本轮新起的进程**（#1339 方向 B）：需要按轮次而不是按尝试划界，涉及取消决策 D2 的保留
  条件，另立决策；本决策提供的扫描手段可以复用。
- **Strong 纳管**：cgroup 子树或 subreaper，需要部署能力，按[纳管保证决策](../process/containment/guarantees/0-explicit-containment-and-cleanup-evidence.md)另立决策。
- **macOS 与 Windows**：macOS 只能做标记扫描，Windows 的私有 Job 可能已覆盖，都要实测后各自决策。
- **清空环境后成为孤儿的进程**：没有 subreaper 或 cgroup 无法覆盖。
- **挂住的 `environ` 读取占住 worker**：Node 无法中断一次内核读取，只能限时放弃并失败即封闭；要让其他会话不受
  影响，需要把读取隔离到可杀的子进程，超出本次 p1 修复的范围。
