# 推送执行权限：只由部署固定的执行器按 Cloud 的单次授权执行，Agent 与会话身份既不请求也拿不到秘密

本文回答推送权限模型的最小问题：**谁执行、谁授权、凭据如何受控兑换、如何避免 Agent 取得秘密**。
结论是把它做成与 clone **同一条受控通道的写向**：执行者是部署固定、由身份 C 承载的同一个凭据执行器
（`cmd/clone-executor` 与 `internal/cloneexec`），授权者是 Cloud（一次 push 一次单次授权，绑定租户、
Project、Workspace、执行、运行代次、仓库、ref 范围与有效期），凭据只经 Credential Store 的兑换路径
进入执行器进程并由部署固定的 helper 交给 Git，Agent 与 Node 会话既不请求推送，也不发不出、读不到、
留不下那份秘密。

本文**不开放推送**：`push` 仍是词汇表外的成员，
[能力词汇表](../../cloud/identity-access/20261012-repository-credential-capability-vocabulary.md)
（approved）的不变量 7 要求由独立的 `approved` 决策把它加入枚举，本文只定义**执行端权限模型**，
是那次扩展的前置，不是它的替代。本文已于 **2026-10-12 按正式流程获批**（A–D、F 批准，E 不批准，
见[批准记录](#批准记录2026-10-12)）：批准只固定执行端权限模型，**不构成实施或启用推送的授权**——
`push` 仍不在词汇表中，`CanonicalCapabilities` 继续拒绝它，任何推送路径都不得先于 E 对应的那篇决策
开始实施。核心测试用例登记在
[推送执行权限核心用例](../../../test-cases/node/repository/push-execution-authority.md)，因尚未实现而
多数保持 `Missing`。

涉及的模块：Cloud 的授权签发（`internal/cloneauth`）、准入与派发（`internal/core`）、执行器
（`cmd/clone-executor`、`internal/cloneexec`）、物化与 helper（`internal/credentialmaterial`、
`cmd/git-credential-ora`）、Store 兑换（`internal/credentialstore`）。兼容性边界：`capabilities` 的
公开契约枚举、`CloneExecutionSpec` 的形状（本文不新增经业务协议传递的字段）、已应用的迁移、
既有匿名与带凭据 clone 链路的逐位行为。本文**不承担**：不实现推送、不扩展词汇表、不定义管理员重绑
入口、不改写任何已批准 ADR、不解除任何 fail-closed。

## 背景与现状

今天**不存在任何推送路径**，这不是巧合而是三处判定的合力：

- 词汇表只有 `clone`（`internal/cloneauth/capability.go:33`），`CanonicalCapabilities` 拒绝任何其他
  成员（`internal/cloneauth/capability.go:73`），而一次 clone 授权只接受恰好 `["clone"]`
  （`internal/cloneauth/authorization.go:181-182`）。因此"用一次 clone 授权去推"在签发与验签两处都
  不成立。
- 准入只承认 `clone` 能力（`internal/core/repository_credentials.go:105-109`），执行器再比一次
  （`internal/cloneexec/executor.go:342-352`）。
- 执行器只构造读取命令：`cloneArguments` 的 `-c` 前缀把协议限定为 `https`，并关掉 hooks、子模块、
  LFS 与重定向（`internal/cloneexec/git.go:120-175`）。

Issue #16 的验收第 2 项要求"读取与推送能力分别验证"，因此推送一侧今天如实为 `Missing`。本文要解决的
不是"如何让推送跑起来"，而是**先回答它凭什么被允许**：一个写权限比读权限更难撤销、更难审计，也更容易
被 Agent 当成绕过受控权限的捷径。

### 三处必须分开回答的问题

| 问题 | 今天的状态 | 本文的回答 |
|---|---|---|
| 谁执行 | 没有执行者 | 部署固定的执行器（身份 C），与 clone 同一个进程身份与同一套 Git 约束（D1） |
| 谁授权 | 没有授权路径 | Cloud 是唯一权威；一次 push 一次单次授权；请求方必须是人或受控系统流程，**Agent 的会话与工具调用永远不是**（D2） |
| 秘密如何到场与退场 | 只有 clone 的兑换与销毁 | 复用 Store 的兑换（mTLS 身份、签名授权、原子单次消费、重放拒绝）与执行结束后的销毁（D4） |
| Agent 能不能拿到 | clone 侧不能（C≠W） | 同样不能：Agent 不请求、不执行、不遍历物化根、不读台账（D5） |

## 决策

### D1：执行者是部署固定的凭据执行器，不是 Node 会话、更不是 Agent

推送由承载身份 C 的凭据执行器执行：进程、生命周期与 Git 调用面沿用
[执行器归属](20261012-credential-executor-belongs-to-the-current-product.md) 已批准的形态
（`cmd/clone-executor`、`internal/cloneexec`），本 ADR 只增加一个写向的作业类型。

- 执行器路径、`git` 路径、helper 路径与物化根都由**部署**固定；推送请求（无论它从哪里来）都不能
  指定其中任何一个。
- Node 会话身份（W）与 Agent **不得执行任何 `git push`**，也不得通过业务协议请求执行器代推：
  推送不是会话能力。
- 执行器继续只做一件事：按授权构造命令、兑换凭据、执行、销毁物化、结算结果。它不判断"这次推送
  是否合规"——那是 Cloud 准入的职责，执行器只核验"这次作业是否被授权、是否属于我"。

**为什么**：写权限一旦落到会话身份上，"Agent 能不能推"就取决于提示词与工具白名单，而不是取决于
授权与身份隔离。把执行者钉在部署固定的 C 上，才使 D5 的隔离承诺对推送同样成立。

### D2：Cloud 是唯一授权权威，一次 push 一次授权，请求方永远不是 Agent

一次推送需要一份**单次**授权，与 clone 的授权同构（`internal/cloneauth` 的 `Issue`／`Verify`），
绑定项在 clone 的绑定之上增加写入侧特有的两项：

| 绑定项 | 含义 | 来源 |
|---|---|---|
| 租户、Project、Workspace、执行 id | 这次推送属于谁、属于哪次执行 | 与 clone 授权一致 |
| 运行代次与 Node 实例 | 已被替换的代次不得继续推 | 与 clone 授权一致（不是 Controller 租约的 epoch） |
| 规范化的仓库身份 | 目标仓库，逐字节比对 | 与 clone 授权一致 |
| 凭据 id 与版本 | 用哪一份凭据的哪个版本 | 与 clone 授权一致 |
| **ref 范围** | 允许更新的 ref（D3） | 新增：写入侧特有 |
| **一次性与有效期** | 授权只能被消费一次，且不长于一次推送的命令预算 | 与 clone 授权一致，另受网络预算约束 |

- 授权的**请求方**必须是已认证、已授权的人（项目所有者或管理员）通过受控入口发起的操作，或是产品
  自身受控的交付流程；**Agent 的会话事件、Thread 消息与工具调用不构成推送请求**，也不得被解释为
  对某次推送的批准。
- 远端说"允许"不构成授权：即使远端凭据具备写权限，没有 Cloud 的授权就没有推送作业（继承隔离 D7
  的"判据是能力而不是连通性"）。
- 授权是 bearer、是秘密：不进日志、不进审计明细、不落任何持久介质。

### D3：写什么必须逐次给出——ref 范围默认拒绝，禁止 force 与删除

授权必须写明允许更新的 ref 集合，**默认拒绝**（没有写明的 ref 不能被更新）：

- 只允许"把某个 ref 更新到某个提交"这一类操作；`+`（force）、删除 ref、删除 tag、改默认分支指向
  都不在允许范围内，且必须在准入处拒绝，而不是依赖远端拒绝。
- ref 名按完整名字比对，不做前缀通配；不承认 `refs/*`、`*` 之类的模式。
- Git host 自己的受保护分支、权限与审计**仍然是最终判据**：Cloud 的 ref 范围是这次作业的上界，
  不是对远端的替代。一次被远端拒绝的推送如实记为失败，不由 Cloud "修正"。

**为什么**：写权限若不带范围，等于把"推送"变成"对仓库的任意写"；而 force 与删除是最难恢复的两类
写操作。把范围固定在授权里，才使"撤销"和"审计"有意义——撤销时能说清撤销的是什么。

### D4：凭据只经既有兑换路径到场，执行结束即销毁

推送**不引入第二条凭据通道**：

- 执行器用签发它的 Store 兑换（`internal/cloneexec/storeclient.go` 与 `internal/credentialstore`
  的兑换路径）：mTLS 服务身份、Cloud 公钥验签、原子单次消费、重放拒绝，顺序与 clone 完全相同
  （校验 → 落消费记录 → 才交付秘密）。
- 秘密只存在于执行器进程内存与**部署固定的 helper 之间的一次管道**（`cmd/git-credential-ora`
  读取执行器物化的单次文件）；它不出现在 URL、argv、环境变量、日志、错误串、业务库、业务事件、
  执行器台账与 Node 的持久记录里，也不写进 Workspace 卷。
- helper 面保持"只读一次、只打印一次"：`store` 与 `erase` 继续是空操作，推送不新增任何让 helper
  记住或落盘的动作。
- 执行结束（成功、失败、超时、中断）都销毁物化；已消费的授权即使从未被交付也**不得重放**。

**必须同时收紧的一点（现状缺口）**：helper 今天只比对 Git 报出的 `host`
（`cmd/git-credential-ora/main.go` 的 `scope` 比对，物化的 scope 文件只存 host，
`internal/credentialmaterial/material.go:157`），而 `internal/cloneexec/git.go:126-129` 把
`credential.useHttpPath=true` 描述成"helper 看到了 path，因此同一 host 下的另一个仓库借不到这份
scope"——**helper 实际上没有使用 path**。读向由执行器自己构造并校验 URL 兜住；写向必须在落地时补上
**仓库范围校验**（把授权里的规范化仓库身份作为物化 scope 的一部分，并由 helper 比对请求的
`host`＋`path`）。这一条属于本文裁决范围内的收紧，未补齐前不得启用推送。

### D5：Agent 取得不了秘密，也换不来一次推送

"避免 Agent 取得秘密"不是一条新机制，而是**已批准隔离的写向适用**，因此它是可判定的一组否定命题：

- Agent 与会话身份 W 读不到 C 的物化根（隔离 D1、D4 的承诺）。
- Agent 不能请求执行器执行推送：请求只能来自受控入口，且必须携带 Cloud 授权；Agent 无法签发授权
  （签名私钥不在 Agent 可达的任何位置），也无法让 Cloud 为它签发一次。
- Agent 不能借"通用 Git 写入能力"绕开：本文不把 `git`（或任何可执行程序）作为工具交给 Agent，
  也不在 Workspace 卷上暴露 helper、执行器或凭据物化。
- Agent 不能凭一次只读结果推出写许可：一次读取或验证的证据不得被记录、导出或复用为写许可（能力
  词汇表不变量 5）。
- 推送结果与台账对 Agent 可见的部分**只有元数据**：谁在什么执行上更新了哪些 ref、结果码是什么，
  不含秘密、不含可直接兑换代码的 URL。

### D6：词汇表与公开契约不由本文扩展

`push` 仍是词汇表外的成员。把它加入 `capabilities` 需要另一篇 `approved` 决策，并同时变更公开契约
枚举（`task frontend:generate`）与三处强制点（准入、签发、执行）。本文只定义执行端权限模型：

- 在那一篇获批之前，`CanonicalCapabilities` 继续拒绝 `push`，本文不修改任何判定。
- 一次推送需要的是**写能力成员**，不是把 `clone` 读成写许可；两者的授权、记账与审计面不同。

### D7：结果、重试与部分成功

- 一次授权只允许一次执行尝试；失败后的重试需要**新的授权**（可以复用同一绑定，但必须重新签发、
  重新消费），因此"重放旧授权"永远不是重试路径。
- 远端只提供逐 ref 的结果，不提供跨 ref 的原子性：多 ref 推送的**部分成功必须如实记录**（哪些 ref
  更新了、哪些没有、错误码是什么），不得汇总成"成功"。
- 失败分类必须能区分：未授权／授权过期或已消费／ref 不在范围／远端拒绝／网络或超时／执行器不可用。
  每一种都映射到稳定的对外码，且不泄露秘密或远端细节。
- 超时与中断走执行器既有的收尾路径：终止 Git、销毁物化、结算为终态，不留下可被再次兑换的授权。
- 审计记录包含：授权标识、请求方（人／受控流程）、执行 id、租户、Project、仓库、允许与被实际更新的
  ref、结果码、时间。**不含秘密、不含 bearer 授权本身。**

### D8：fail-closed、验收，以及与其他推送通道的分界

- 执行器未部署、Store 未配置验签公钥、授权缺失或校验失败、ref 范围缺失——任一情形都逐位拒绝，
  且不产生任何部分写入。
- 本地开发/验收栈可以显式启用受控能力，**生产默认保持 fail-closed**；本文不解除任何解禁条件。
- Issue #16 的真实推送验收要求：真实私仓 + 真实远端 + 真实凭据在受控通道内、且断言"授权单次消费、
  ref 范围生效、Agent 拿不到秘密、执行后销毁"逐条成立。**not-run 不得写成 passed**；在没有真实远端
  证据之前，该项保持 `Missing`。
- 与[推送交付 ref](../revision/20261012-push-delivery-ref-and-fetch-prior-revision.md)
  的分界：那条通道推的是**内部 Git Server 的交付 ref**，不是用户仓库；两侧的证据不得互相充当对方的
  验收证据，也不得用一侧的落地掩盖另一侧的缺口。

## 不变量

1. 推送只由部署固定的执行器（身份 C）执行；Node 会话身份与 Agent 不执行、也不得请求推送。
2. Cloud 是唯一授权权威；远端允许写、网络可达、凭据可写都不构成授权。
3. 一次推送对应一次单次授权；授权不可重放，重试必须重新签发。
4. 授权绑定租户、Project、Workspace、执行、运行代次、仓库身份、凭据 id 与版本、ref 范围与有效期；
   缺一项即拒绝。
5. 未在授权中写明的 ref 一律不可更新；force、删除 ref 与删除 tag 不在允许范围内。
6. 秘密只经既有兑换路径交付给 C，且只出现在 C 的进程内存与本次执行的物化之间；不进 URL、argv、
   环境、日志、事件、业务库、执行器台账与 Workspace 卷。
7. 执行结束（成功、失败、超时、中断）后物化被销毁；已消费的授权即使未交付也不得重放。
8. helper 面保持"读一次、打印一次"，`store`／`erase` 为空操作；启用推送前必须补齐仓库范围校验
   （D4 的现状缺口）。
9. Agent 既拿不到秘密，也换不来一次授权，也借不到通用 Git 写能力。
10. `push` 不在词汇表中；把它加入需要另一篇 `approved` 决策与公开契约变更（D6）。
11. 部分成功如实记录，不汇总成成功；失败分类稳定且不泄露秘密。
12. 本文获批不解除任何 fail-closed；Issue #16 的推送验收在取得真实证据前保持 `Missing`。

## 为什么不是这些替代方案

| 方案 | 优势 | 否决理由 |
|---|---|---|
| 把 `push` 加进词汇表，让 Agent 用同一身份推 | 一步打通"Agent 提交代码" | 直接违反不变量 1、9 与已批准隔离决策：写权限落到会话身份上，"能不能推"就取决于提示词与工具白名单，撤销与审计都没有稳定对象 |
| 让 Node 会话（W）自己推送 | 不用碰执行器形态 | W 与 Agent 同身份、且没有 C 独占的物化根，秘密必然可被 Agent 读取；这正是 clone 侧已经否掉的形态 |
| 用 SSH deploy key 推送 | 绕开 HTTPS 令牌的形态 | SSH 在执行器与旧 Desktop 的取回面上都被禁止，且会引入一份长期有效的写秘密，比单次授权更难撤销 |
| 复用 clone 的一次性只读授权去推 | 少一套授权 | 只读证据不得复用为写许可（能力词汇表不变量 5）；读与写的记账、audit 与撤销对象不同 |
| 不限定 ref，交给远端判 | 实现最小 | 等于把"推送"变成"对仓库的任意写"；审计无法回答"这次授权允许改什么"，撤销也没有边界 |
| 远端成功即算验收，不必本地断言 Agent 拿不到秘密 | 验收成本低 | Issue #16 的推送验收要求"能力分别验证"与受控凭据，缺了隔离断言就无法排除"能推，但 Agent 也能读秘密" |
| 用上游的交付 ref 通道充当本 Issue 的推送验收 | 看起来已有一条写通道 | 那条通道推的是内部交付 ref，不是用户仓库，信任边界与凭据来源都不同（D8） |

## 失败与恢复语义

| 情形 | 对外结果 | 持久事实与恢复 |
|---|---|---|
| 没有授权、授权过期或已被消费 | 拒绝，码区分"未授权／已消费／过期" | 不产生任何远端写入；需要重新签发授权 |
| ref 不在授权范围 | 拒绝该次作业 | 不执行任何 ref 更新；授权仍然只算消费一次（或按实现约定明确记为未消费，二者只能有一种，且必须与 D7 一致） |
| 部分 ref 更新成功、部分失败 | 如实记录每个 ref 的结果 | 失败的 ref 需要新授权重试；不得把整体记为成功 |
| 远端拒绝（受保护分支、权限不足） | 稳定的远端拒绝码，不含远端细节 | Blame 在远端策略，不在 Cloud；不自动改用其他 ref |
| 网络超时或中断 | 终态失败 + 中断语义 | 走执行器收尾：终止 Git、销毁物化、不重放授权 |
| 执行器不可用 | `repository_credential_executor_unavailable` 一类部署级拒绝 | 与 clone 相同：部署级拒绝优先，且不改写引用状态 |

## 本决策未解决的问题

- **谁有权发起推送**：产品形态（管理员入口、项目所有者入口、受控交付流程）与审批链由 P3 之后的产品
  决策给出；本文只固定"Agent 不是请求方"这一条否定命题。
- **多 ref 原子性**：远端不提供跨 ref 事务，本文只要求如实记录部分成功；是否需要"单 ref 一次授权"
  的更强约束，留给实现评审。
- **与正式 Git Server 通道合并后的形态**：若内部 Git Server 成为唯一 Git 面，用户仓库推送是否迁到
  该通道、迁移判据是什么，需要新决策；本文不依赖未来迁移掩盖今天的缺口。
- **管理员重绑与撤销后的重试**：与 P2 的重绑流程、P4 的撤销清理共用同一批入口，本文不重复定义。
