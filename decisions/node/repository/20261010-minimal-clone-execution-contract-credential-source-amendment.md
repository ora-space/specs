# 最小 clone 执行契约 D2 的凭据来源修订：由部署静态配置扩展为受授权的单次 Clone，其余约束逐字保留

[最小 clone 执行契约](20260918-minimal-clone-execution-contract.md) D2 规定"凭据由 Node 部署提供"，并
以此为界写下了一整组禁止面：业务协议不接收秘密、Node／process journal 不复制凭据内容、凭据缺失或需要
交互时明确失败、Git 输出必须脱敏、采用哪个 credential helper 属部署配置。本文承载**这条契约的正式
修订**：凭据来源从"部署静态配置"扩展为"Cloud 侧 Credential Service 按 Project 逐次授权解析"，并同时
把扩张限死在"一次受授权的单次 Clone、只交付给凭据执行身份 C"。D2 的其余每一句都**逐字保留**。

本修订的性质是**扩张来源、不放松约束**。修订后仍然禁止：业务协议携带秘密、请求指定 helper 或任意
可执行程序、放宽 Git 配置、把原始 stderr 存入业务结果、以交互方式取得凭据。因此本文**不放宽**
`20260918` D4 的"可信部署需明确允许的辅助程序"，也**不解除** controlled Node 的
`validate_cloud_policy`——helper 白名单与执行程序固定是修订后的必做项，不是可选加固。

本文于 2026-10-10 经项目负责人批准，状态为 `approved`；`20260918` 仍是 `approved`，其正文与状态都
不因本文而改动。修订以本叶子后续决策的形式生效：`20260918` 保持为历史契约，`20260918` D2 的修改由
本文记录，读取该链的人应同时读到两份（`20260918` 顶部已加入指向本文的阅读入口）。**批准不解除
fail-closed**：`repository_credential_executor_unavailable` 继续拒绝所有带凭据引用的 Project 的 clone，
本文不授权任何实现变更。

涉及模块：`apps/ora-node`（`ProcessConfig`、受管执行、clone 状态机）、`crates/process-runtime` 与
`crates/process`（进程身份与 IPC）、`crates/gitlancer` 的命令行约束。兼容性边界：clone 的对外协议
（`CloneExecutionSpec` 仍只有 `node_id`／`repository`／`branch`）、Node 数据库 schema、已实现的收尾
屏障与 `Interrupted` 判定都按硬边界处理。

## 背景与现状

### 现有 D2 原文

`20260918` D2（逐字）：

> Node 使用显式配置的 Git 程序、运行环境及可信凭据配置；不从 Controller 机器复制其 HOME 或密钥。
> HTTPS 可使用部署已配置的非交互凭据来源；SSH 可使用部署已准备的身份和主机校验配置。
> 凭据缺失、需要询问密码／口令或确认主机时明确失败，不弹窗、不无限等待，不自动接受未知主机。
> 管理的网络及认证子进程同样受运行时收尾和执行期限约束。
>
> 协议不接收秘密，Node／process journal 不复制凭据内容；可记录非秘密配置引用。
> Git 输出可能包含认证敏感信息，持久诊断必须限制和脱敏，不将原始 stderr 直接存入业务结果。
> 是否采用具体 credential helper 或 SSH agent 属部署配置，不由业务请求指定任意可执行程序。
> 当前信任 Node 的管理程序，不等于仓库不需要认证，也不保证抵御恶意同 UID 代码。

### "部署已配置的非交互凭据来源"今天并不存在

受控 Node 上这条子句没有可用实现：`validate_cloud_policy`
（`apps/ora-node/src/repository/config.rs:28-55`）拒绝一切非 `Disabled` 的 SSH 配置，并只允许部署
gitconfig 出现 `[http] sslCAInfo` 一行；该策略在 `worker.rs:50-52` 只在 `controlled` 时生效。也就是说
受控路径今天既不接受静态 HTTPS 凭据来源，也不接受 SSH 身份。因此 D2 的这句更像一条**边界声明**
（"若将来有凭据，它必须来自部署且非交互"），而不是一条已交付的能力。

### 为什么必须在 D2 上做正式修订而不是就地放开

`validate_cloud_policy` 的存在前提是"凭据由部署提供，作用域由部署保证"。换成由用户提交的 PAT 后，
这个前提消失：部署方不再能保证凭据的作用域，凭据的有效期与撤销也不再由部署控制。因此在既有 D2 的
"部署提供"这半句上做正式修订是必要的——它不是措辞问题，而是凭据**来源归属**的变化。

### 修订不能触碰的部分

D2 的其余子句与相邻决策共同构成凭据路径的安全面：协议不接收秘密、不交互、不由请求指定 helper、
Git 输出脱敏、认证子进程受收尾与期限约束、D1 的无凭据 URL、D4 的辅助程序白名单、不变量 4 的禁止传播。
这些与"凭据从哪来"无关，扩大来源不会削弱它们中的任何一条——除非实现时顺手放宽，而那正是 D3 要挡住的。

## 决策

### D1：修订后的 D2 凭据来源条款（权威文本）

D2 中"HTTPS 可使用部署已配置的非交互凭据来源"这一句由以下条款替代，D2 的其余句子保持原样：

> HTTPS 的凭据来源有两种形态，都由部署固定，且都不由业务请求指定：
> 1. **部署静态凭据来源**（原形态），仅用于 standalone／部署自行管理的场景。它在受控 Node 上继续被
>    `validate_cloud_policy` 禁止，**也不得**被当作动态来源的回退：需要用户凭据的 clone 只有动态来源
>    一条路径；
> 2. **按 Project 逐次授权的动态来源**：由 Cloud 侧的 Credential Service 在一次 clone 的授权下解析，
>    且只交付给凭据执行身份 C（见
>    [受控 Node 的仓库凭据执行使用独立 OS 身份](20261010-controlled-node-git-authentication-isolation.md)）。
>
> 动态来源必须满足：授权绑定 tenant、credential owner、project、workspace、clone execution、credential
> ID 与 version、repository identity 与 `operation=clone`，带到期、单次使用与 Node 实例／运行代次
> 约束；授权在签发时**未使用**，由 Store 在兑换时**原子消费**；授权本身是 bearer 凭据，不落任何持久
> 介质；每次重试申请新授权，不得重放。凭据来源不可用、授权到期或被冻结时明确失败，不回退匿名 clone，
> 也不回退部署静态凭据。

中文对照见上；**英文对照不再需要（2026-10-10 裁决）**：本修订不向任何仓库文件写入规则文本，权威正文
就是本文，因此没有需要确定措辞的英文副本。

**standalone 的既有静态认证能力保持兼容**：静态来源在 standalone Node（无控制通道，`validate_cloud_policy`
不生效，`apps/ora-node/src/service/worker.rs:24-52`）上继续按原样工作——本修订不为它增加约束，也不把它
当作受控路径的能力。两条路径的差别在**归属**：standalone 的凭据由部署自管并自担作用域，受控 Node 的
用户凭据属于用户、按次授权。因此"保持兼容"与"受控 Node 不得回退静态 PAT"并不矛盾，它们各自描述一条
不同的部署形态。

D1 与 D2 原有子句的关系是**替换一句、追加条件**，不是重写整节。SSH 一句、凭据缺失与交互失败的处置、
认证子进程的收尾与期限约束都逐字保留。

### D2：扩张的边界——单次、只到 C、不经业务协议

修订后的凭据来源受三条硬边界约束，缺一不可：

- **单次**：一次授权只服务一次 clone execution。失败、超时、`Interrupted` 或崩溃后的重试必须申请新
  授权；Node 不得缓存授权跨执行复用。**强制点在 Store 侧**——授权在兑换时被原子消费，响应丢失或超时
  之后旧授权也不得重发（[Secret Store ADR](../../cloud/identity-access/20261010-user-managed-git-secret-store.md)
  D10）；Node 侧只负责不缓存、不重放。这与 D5 的"到期即失效、不续期"是同一件事的两侧。
- **只到 C**：凭据材料与授权载体都只能对凭据执行身份 C（以及作为可信计算基的管理身份 M）可见。W 读
  不到其文件、环境、文件描述符与进程内存；Agent 不能连接 Broker 端点，也不存在"以 W 身份调用管理面"
  的路径。这条边界由前序决策的验收义务逐条证明，不因本文而放松。
- **不经业务协议**：`CloneExecutionSpec` 仍然只有 `node_id`／`repository`／`branch`，不新增凭据字段；
  授权经控制通道交付到 Node 的凭据执行路径，Token 本体不经 Node 的业务协议、数据库、process journal、
  事件、日志或结果传播。

### D3：逐字保留的子句（修订不得触及）

| D2／相邻决策的子句 | 修订后的状态 |
|---|---|
| 协议不接收秘密；Node／process journal 不复制凭据内容；可记录非秘密配置引用 | 逐字保留 |
| 凭据缺失、需要询问密码／口令或确认主机时明确失败，不弹窗、不无限等待，不自动接受未知主机 | 逐字保留；动态来源不可用时同样明确失败 |
| 管理的网络及认证子进程同样受运行时收尾和执行期限约束 | 逐字保留；凭据物化的销毁接在既有收尾屏障之后 |
| Git 输出可能包含认证敏感信息，持久诊断必须限制和脱敏，不将原始 stderr 直接存入业务结果 | 逐字保留；动态来源不降低这条要求 |
| 是否采用具体 credential helper 或 SSH agent 属部署配置，不由业务请求指定任意可执行程序 | 逐字保留并**加强**：helper 必须白名单化，路径由部署固定、root 拥有且不可写 |
| D1：仓库地址不能含密码／token；不开放任意 Git 选项、shell 字符串、目标路径或逐请求环境变量 | 逐字保留 |
| D4：可信部署需明确允许的辅助程序，不能把任意环境继承称为执行隔离 | 逐字保留并加强 |
| 不变量 4：凭据不经业务消息、命令文本、日志或结果传播；认证不依赖人机交互 | 逐字保留 |

**明确不放松的三件事**，因为它们是"扩大来源"最容易被顺手带开的边界：

1. **不放宽 Git 配置**：`validate_cloud_policy` 的允许键集合、`constrain()` 的 `-c` 约束都不能被改为
   "接受任意 Git 配置"。凭据路径需要新增的是**显式允许的键**（credential helper、匹配粒度、重定向与
   代理相关的键），而不是放开策略。
2. **不放宽可执行程序**：凭据 helper 必须是部署固定的单一组件，与 `git_program` 同级对待；不得由
   Controller 消息、clone 规格或任何业务输入选择。
3. **不放宽交互性**：动态来源同样必须非交互。凭据解析失败时以认证失败结束，不提示、不重试交互、不
   回退到其他身份。

### D4：修订以本链的后续决策生效，`20260918` 正文不改写

- `20260918` 是 `approved`；按 `specs/AGENTS.md`，已批准决策的正文不由后续 ADR 直接改写。修订以本叶子
  后续决策的形式生效，`20260918` 保持为历史契约，其 D2 的修改由本文记录。
- 因此本文必须与 `20260918` **一起**被读：单独读 `20260918` D2 会得到"凭据只能由部署提供"这一已被修订
  的结论。该风险由本文明确声明，并已于 2026-10-10 随批准同步到本链的阅读入口：`20260918` 顶部加入
  指向本文的说明（只加阅读入口，不改写 D2 决策正文），节点侧索引同步指向本文。
- 落地顺序第 5 步（前序决策所要求的那一次 amendment）以本文的批准为完成标志，而不是以代码改动为标志。
  **该步已完成（2026-10-10）**；本步不产生代码或测试证据，因此不构成任何实现或解禁的依据。
- 本文不解除任何 fail-closed：`repository_credential_executor_unavailable` 继续无条件拒绝，直到前序
  决策 D14-B 与本链 Cloud 侧 D11-B 的全部条件满足。本文的生效本身属于**开发准入**（D14-A 的第 3 项、
  D11-A 的 A3），不是功能启用的证据。

## 不变量

1. 凭据来源只有两种形态，都由部署固定：部署静态来源（仅 standalone／部署自管场景），或按 Project
   逐次授权的动态来源（受控 Node 上唯一可用于用户凭据的形态）。
2. 业务请求不能指定凭据来源、helper、代理或任意可执行程序；`CloneExecutionSpec` 不含任何凭据字段。
3. 一次 clone execution 使用一次独立授权；失败、超时、`Interrupted`、崩溃或重试都必须申请新授权，
   不得重放或跨执行复用。
4. 凭据材料与授权载体只对 C（以及作为可信计算基的 M）可见；W 读不到其文件、环境、文件描述符与进程
   内存，也不能连接 Broker 端点或经管理接口提升。
5. 凭据材料不经业务消息、命令文本、argv、日志、结果或任何持久介质传播；Token 本体不在 Node 侧持久化。
6. 凭据来源不可用、授权到期、凭据被冻结时明确失败；不回退匿名 clone，也不回退部署静态凭据——受控
   Node 上静态 PAT 不是用户凭据路径的回退（standalone 的静态能力不受影响）。
7. 凭据 helper 必须是部署固定、root 拥有且不可写的白名单程序；不得因引入动态来源而放宽 Git 配置策略。
8. 修订后的凭据路径仍然非交互：不弹窗、不无限等待、不自动接受未知主机。
9. `20260918` 的正文与状态不因本文改动；本文与其并存，二者必须一起读。

## 为什么不是这些替代方案

| 方案 | 取舍 |
|---|---|
| 直接改写 `20260918` D2 正文 | 规范上更直观，一步到位；但 `20260918` 是 `approved`，已批准决策的正文不由后续 ADR 改写，且改写会抹掉"凭据曾由部署承担"这一历史边界，使评审无法判断变化幅度 |
| 只放宽 `validate_cloud_policy`，不修订 D2 | 改动最小；但策略放开等于把"部署保证作用域"这一前提悄悄替换成"用户提交的 PAT 可信"，而 D2 的"部署提供"正是该前提的文字来源，不修订就没有可评审的范围声明 |
| 保留 D2 并把动态来源当作"部署配置的一种" | 零规范改动；但"凭据由部署提供"与"凭据由用户在运行时提交并按次授权"是两种归属，前者不覆盖后者，硬套会让 D2 的边界声明失去意义 |
| 在 `CloneExecutionSpec` 上增加凭据字段 | 交付路径最短；直接违反不变量 2、5 与 D2 的"协议不接收秘密"，且会把凭据带入 Controller／Cloud 的业务消息与日志 |
| 引入动态来源的同时顺手放宽 Git 配置与 helper 选择 | 实现更省事；D3 明确否决：扩大来源不构成放宽配置与执行程序的理由，两者是独立的安全面 |
| 修订 D2 时一并把 SSH 也纳入动态来源 | 少一次修订；V1 只覆盖 HTTPS，SSH 的主机校验、agent 与身份管理是另一条产品线，且 `validate_cloud_policy` 明确拒绝非 `Disabled` 的 SSH |
| 让动态来源在凭据不可用时回退到部署静态凭据 | 可用性更好；回退会让一次用户凭据的失败静默变成"以部署身份访问仓库"，违反不变量 6，也让"哪次 clone 用了哪个凭据"失去唯一答案 |

## 失败与恢复语义

| 情形 | 行为 |
|---|---|
| 凭据来源不可用（Store／Broker 不可达） | 明确失败；不回退匿名 clone，也不回退部署静态凭据 |
| 授权到期或已被 fencing | 本次 clone 失败；重试申请新授权，不续期、不重放 |
| 凭据在 clone 前被冻结或成员停用 | 拒绝签发新授权；已签发未使用的授权随到期失效 |
| 凭据解析失败或密文不可核实 | 以认证失败结束；不重试交互，不提示，不自动接受未知主机 |
| Git 进程被终止或 Node 停止 | 沿用既有 `Interrupted` 与收尾屏障；凭据物化在收尾时销毁 |
| Node 崩溃或容器被杀 | 启动清扫在受理任何凭据 clone 之前清空物化目录；清扫未完成前拒绝受理 |
| 请求试图指定 helper、代理或可执行程序 | 拒绝；按 D1 与 `20260918` D4，凭据执行只用部署固定的程序 |
| 请求试图在 clone 规格中携带凭据 | 拒绝；`CloneExecutionSpec` 不接受凭据字段（不变量 2） |
| `validate_cloud_policy` 被要求接受任意 Git 配置 | 拒绝该改动；只允许新增显式允许的键（D3） |
