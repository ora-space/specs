# 独占资格之后先恢复核实，再开放运行管理

宿主与 guardian 的单实例约束独立于 IPC。新实例先取得稳定的独占资格，再核实持久记录和实际
运行；guardian 状态不明时不启动替代者，确认失效后关闭 scope 并清理，不接管原活进程。

本根决策为 `proposed`，细化[独立宿主与 Guardian](../architecture/0-node-host-and-scope-guardians.md)
的故障边界。它不将锁释放、PID 消失或数据库可打开视作旧写入结束；旧文件与版本恢复另受
[升级决策](../upgrade/0-version-coexistence-and-safe-migration.md)约束。

## 背景与约束

失联可能来自拥塞、暂停或进程死亡；第二个管理实例可能与仍存活的旧 guardian 竞争。即使独占锁
已经释放，旧业务后代仍可能存活。恢复资格和资源安全必须依据不同证据判断。

## 决策

### D1：按故障层级处理

| 故障 | 行为 |
|---|---|
| Node 断线、租约有效 | 在窗口内恢复连接，运行遵守既定策略 |
| Node 失权或租约到期 | 永久拒绝旧代次，终止或保留等待接管 |
| 宿主重启 | guardian 继续管理；新宿主使旧控制凭据失效，逐 scope 核实 |
| Scope 选择宿主失效时终止 | 由宿主之外的存续机制检测并执行 |
| Guardian 状态不明 | 继续发现与核实，不判死、不创建第二个 guardian |
| Guardian 确认失效 | 关闭 scope、定位并清理运行，不接管原活进程 |
| 结果丢失但清理完成 | 分别保存结果未知与清理完成 |
| 机器重启或局部记录缺失 | 核实启动身份、遗留记录及外部事实，不当作首次启动 |

### D2：稳定锁保护恢复权威

```text
定位稳定目录 → 取得独占资格 → 检查数据版本与恢复记录
  → 核实实际运行 → 开放已满足恢复条件的操作
```

连接失败只能触发发现和恢复。锁释放、数据库可打开、旧 PID 消失只允许开始核实，不证明旧业务
写入结束。Guardian 启动回复丢失时同样先发现原实例，不能直接补启第二个。

锁位置不得由普通清理或数据库迁移删除替换。运行状态目录位于经验证支持所需锁和耐久语义的
本地文件系统；业务工作目录可位于其他存储，但其协调保证需另行核实。

### D3：恢复按 Scope 放行

宿主逐 scope 核实，证据不足的 scope 不阻塞所有无冲突工作。是否冲突由 Node 的
[资源协调](../integration/0-shared-process-entry-and-resource-handoff.md)裁决。宿主权威数据库整体
不可用时限制管理变更，guardian 继续承担既有策略允许的本地责任。

## 不变量

1. 取得独占资格之前不开放管理操作，恢复资格不冒充清理证据。
2. 断线和超时不单独证明 guardian 死亡，同一活跃 scope 不产生竞争 guardian。
3. 结果未知与清理完成可以同时成立，恢复流程不伪造原始退出结果。

## 为什么不是这些替代方案

| 方案 | 取舍 |
|---|---|
| IPC 连接失败即拉起新实例 | 发现简单，但暂停或 endpoint 故障会产生双权威 |
| 新 guardian 接管原活进程 | 可提高存续率，但 I/O、平台句柄和事实交接缺少已证明机制，本版不承担 |
| 全部 scope 恢复后才开放宿主 | 门禁简单，但一个不可核实 scope 会阻塞无冲突工作 |

## 落地与验收

在平台清理证明上补齐稳定锁、恢复扫描与逐 scope 放行。验证并发启动宿主、guardian 回复丢失、
暂时断线、强杀、机器重启与记录缺失；同时证明条件恢复后可继续推进，不能只证明拒绝操作。

## 本决策未解决的问题

宿主失效的 guardian 检测协议、平台身份核实方式、锁与 endpoint 的最终布局，以及损坏记录的
独占恢复工具需先冻结。外部服务管理器停止宿主时如何保留应存续的 guardian，由部署与平台验证共同负责。
