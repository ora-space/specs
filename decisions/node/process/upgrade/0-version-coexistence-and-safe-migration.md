# 运行版本并存，不兼容升级先收尾，程序回滚不回退权威事实

新 scope 使用新 guardian，已有 scope 的 guardian 不做运行中替换。兼容时新宿主恢复管理旧
guardian；不兼容时先由兼容版本收尾，再切换和迁移。可执行文件及数据在恢复责任解除前保留。

本根决策为 `proposed`，约束新旧进程体系及新体系内部版本共存。文件系统布局是硬兼容边界；
本版允许重构 Git／插件 API，不以接口兼容换取覆盖旧运行文件，也不承担 guardian 活进程接管。

## 背景与约束

运行可能跨宿主发布周期继续存续。原地替换二进制、数据 schema 或锁文件会使旧 scope 失去可用
恢复工具；回退数据库还可能复活旧授权、重跑已接受请求或忘记退休身份。

## 决策

### D1：分别判断三个兼容边界

Node—宿主、宿主—guardian、程序—持久数据分别协商／检查兼容性。不理解影响语义的字段、策略
或保证时拒绝，不能忽略后采用默认行为，也不能仅凭 MessagePack 可解码推断兼容。

新 scope 采用新 guardian；已有 guardian 保持原版本，兼容宿主通过协议继续管理。代价是需维护
发布兼容窗口和恢复程序，换取运行事实与 I/O 的连续性。

### D2：隔离路径并保留恢复所需版本

```text
<逻辑 Node 的新运行状态目录>/
    host.sqlite
    scopes/
        <ScopeId>/
            guardian.sqlite
            output/
```

这里只表达存储归属。稳定锁、endpoint、版本化可执行文件和恢复元数据的最终路径需单独核实，
不能与旧体系碰撞。版本化可执行文件不原地覆盖仍有恢复责任的版本，回收遵循
[责任退休条件](../persistence/0-independent-journals-and-responsibility-retirement.md)。
锁位置不能由普通清理或数据库迁移删除替换。

### D3：不能直接改写尚有责任的历史状态

不兼容升级先由兼容管理版本完成旧 scope 收尾，再迁移和切换。旧宿主已故障时使用兼容恢复程序
或经过验证的平台清理；证据不足保持受限，不能删除目录重新初始化来绕过恢复。

程序回滚不等于数据库回滚。禁止恢复旧授权代次、已接受请求或退休记录来适配旧二进制；旧程序
无法理解新数据时应拒绝。迁移失败的恢复路径不能丢弃已经确认的权威事实。

## 不变量

1. 仍有恢复责任的二进制和文件不被覆盖或普通回收删除。
2. 不兼容语义在产生副作用前拒绝，不静默回退默认策略。
3. 迁移、回滚和重建均不倒退授权、去重及退休事实。

## 为什么不是这些替代方案

| 方案 | 取舍 |
|---|---|
| 所有 guardian 随宿主原地热替换 | 版本管理简单，但要求尚未设计的活进程、I/O 与句柄接管 |
| 回滚二进制时恢复数据库备份 | 操作直观，但可能让已经撤销的权限和执行请求重新有效 |
| 新版本忽略未知字段继续运行 | 可用性表面更高，但未知字段可能决定清理保证或授权 |

## 落地与验收

生产接入前确定新旧路径并存规则；持久模型稳定后定义兼容矩阵、恢复程序与迁移事务。
最终切片验证兼容／不兼容升级、旧宿主故障、迁移中断、旧二进制拒绝新数据及有责任版本的保留。
新旧体系迁移时同一尝试不双跑，有活进程的旧体系先明确停止交接。

## 本决策未解决的问题

最终路径、数据版本和迁移失败处理、恢复程序版本覆盖范围、发布兼容窗口及版本文件回收协议
需冻结。本次文档拆分不执行数据库迁移或文件系统布局变更。
