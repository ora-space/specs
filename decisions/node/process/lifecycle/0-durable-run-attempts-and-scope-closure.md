# Run 永久表示一次尝试，Scope 关闭承担持久收尾责任

一个 `RunId` 永久标识一次启动尝试；重传恢复原尝试，业务重试使用新身份。宿主持久接受意图后
通过协调循环承担完成责任。直接进程退出、Run 收尾和 Scope 关闭分别表达，取消等待不取消责任。

本根决策为 `proposed`，基于[架构](../architecture/0-node-host-and-scope-guardians.md)与
[控制权](../control/0-authorized-generations-and-leases.md)边界；不冻结 Rust 类型、命令参数规范化
或 wire schema，也不迁移旧体系中的活进程。

## 背景与约束

创建进程与数据库提交不能假定原子完成。回复丢失、启动器先退出、后代后台化及关闭并发都可能
让单一“成功／失败”状态掩盖残留副作用。恢复必须依据可核实事实，而非再次运行命令来探测结果。

## 决策

### D1：意图、事实和进度分别建模

| 维度 | 必须区分的事实 |
|---|---|
| Scope 期望与控制资格 | 开放／已要求关闭；有效 owner／交接中／无有效权限 |
| Run 启动 | 已接受、可证明未启动、已启动、启动未知 |
| 直接进程结果 | 未退出、退出且结果已知、结果未知 |
| 收尾 | 等待、通知退出、强制清理、核实、阻塞、完成 |
| 清理保证 | 强静止证据、尽力清理完成、未完成／未知 |
| I/O 与责任 | 交付进度、输出结束与完整性、结果接管、资源解除关联、退休资格 |

以上是语义维度，使用带数据的枚举和受约束转换排除非法状态，不直接铺成可任意组合的布尔值
或 `Option`，也不把直接进程失败与安全收尾压成一个总状态。

### D2：启动先记录责任，未知不自动重启

```text
Node 持久关联 Execution / Scope / RunId / 命令尝试
  → 宿主持久接受启动意图 → guardian 持久接受 Run
  → 业务代码执行前落实纳管 → 启动并保存事实 → 宿主汇合并提供查询
```

同 RunId、同参数重传恢复原尝试；同身份不同参数报告冲突。

| 恢复事实 | 允许行为 |
|---|---|
| 能证明未启动，授权与 scope 仍允许 | 继续原尝试 |
| 找到原受管运行 | 恢复观察，按策略保留或终止 |
| 存在完成记录 | 返回原结果 |
| 是否启动或残留未知 | 核实和收尾，不自动重启 |

尽力模式在清理和业务对账完成后可允许新工作，但不能把原启动未知改写为未执行。新业务尝试
仍由 Node 决定并分配新 RunId；运行层不自动重启长期工作负载。

### D3：Run 退出政策与 Scope 关闭独立

Run 默认在直接进程退出后保存结果，限时通知／等待剩余后代，必要时强制收尾；也可启动前显式
选择等待全部受管进程结束，期间继续管理 I/O。后一策略适用于启动器退出、后代继续工作的程序，
启动器退出码不能证明后代业务成功。

单 Run 终止仅影响自身及受管后代，不隐式关闭 scope 或其他 Run。局部归属无法核实或 guardian
失效时可扩大为 scope 收尾，但必须报告。Scope 关闭先封闭接纳，再收尾全部已接受运行；并发启动
要么被拒绝，要么纳入收尾。关闭方向不可逆，关闭后不重开；开放 scope 暂无活进程不表示已关闭。

### D4：停止只能升级，重试不卸除责任

| 停止策略 | 行为 |
|---|---|
| 限时等待完成 | 不主动打断，到期强制收尾 |
| 请求退出后限时等待 | 立即发送约定通知，到期强制收尾 |
| 立即强制收尾 | 直接终止并核实 |

重复停止只能缩短等待或升级，不能延长期限或取消关闭。Node 正常停止时先停止派发，对已有 Git
限时等待；异常失联且 scope 采用终止策略时立即强制收尾。插件业务关闭消息由上层发送，guardian
仅执行声明支持的进程级通知。

通信重传原身份；宿主／guardian 重试发现、核实、清理与事实报告；Node 对账后决定业务重试。
瞬时错误使用有上限间隔的退避及随机扰动，权限或协议等确定性错误进入可观察阻塞，条件改变后
继续协调。超时、暂停或重试耗尽均不自动释放资源。

## 不变量

1. 一个 RunId 至多对应一次启动尝试，未知事实始终保留其不确定性。
2. Scope 关闭与启动并发不存在接受后漏管的运行。
3. 直接退出、收尾完成和业务成功不互相替代；停止等待取消不撤销已接受责任。

## 为什么不是这些替代方案

| 方案 | 取舍 |
|---|---|
| 超时后重新 spawn | 可快速重试，但无法排除已执行，可能重复 Git／插件副作用 |
| 直接进程退出即完成 | 观察简单，但后台后代仍可写入 |
| 每次停止重置等待时间 | 调用直观，但重复请求可无限延后清理 |

## 落地与验收

平台证明后实现持久启动状态机，再接入停止、关闭和恢复。逐一在接受、纳管、启动、落盘及回复
窗口强杀进程，验证原身份去重、未知事实、后台后代和单 Run 隔离；用同步点验证关闭／撤权竞争。

## 本决策未解决的问题

`RunSpec`、`ScopePolicy`、状态枚举、错误类型、命令参数规范化和冲突摘要需冻结；非 UTF-8
路径／参数、环境变量与敏感输入的表示及持久化政策需同时确定。停止与退避默认值必须经负载和
故障测试确定，不能以次数上限替代清理完成证据。
