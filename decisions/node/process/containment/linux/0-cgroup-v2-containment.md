# Linux 强纳管使用受控 cgroup v2 子树

Linux 在实际具备能力且权限正确的 cgroup v2 子树中运行工作负载，业务代码执行前完成纳管。
封闭启动入口后清理并核实空子树；guardian 位于工作负载子树之外，继续承担记录和收尾责任。

本根决策为 `proposed`，选择实现方向而不宣称平台验证通过。能力不足时遵循
[保证契约](../guarantees/0-explicit-containment-and-cleanup-evidence.md)拒绝或启动前降级。
不要求所有 Linux 环境具备委派权限，不迁移旧体系的活进程，也不引入资源配额。

## 背景与约束

cgroup 子树提供后代归属及整体清理边界，但迁出权限、创建窗口和 guardian 死亡后的清理仍需
运行体系负责。仅创建 cgroup 或发送 kill 并不能证明旧写入已经结束。

## 决策

### D1：创建时纳管，权限限制迁出

业务代码执行前进入目标子树，不采用先启动再异步迁移。受管工作负载在声明权限与行为范围内
不能迁出。具体创建机制、委派权限及生命周期必须在生产接入前证明。

cgroup 后代继承成员归属，`cgroup.kill` 可清理子树，`cgroup.events` 的 `populated` 表示
子树存活状态；这些是机制依据，不替代 Ora 的纳管与恢复验证。
参见 [Linux cgroup v2 文档](https://docs.kernel.org/admin-guide/cgroup-v2.html)。

### D2：Scope 与 Run 都有可核实清理边界

Guardian 位于其工作负载子树之外。单 Run 清理必须有独立归属和实现，不能用 scope 总组冒充
Run 隔离。停止先封闭相应启动入口，再清理并核实空子树，避免“观察为空后又启动”的窗口。

Guardian 失效后由宿主或恢复流程定位并清理子树；不假定 cgroup 会随 guardian 死亡自动清空。
完整核实之前保持未完成／未知，不依据旧 PID 或缺失回复放行。

### D3：委派方式可替换，能力逐部署核实

可由 systemd 委派子树，运行核心不硬依赖 systemd，也可接收等价部署能力；只管理获委派范围。
参见 [systemd cgroup delegation](https://systemd.io/CGROUP_DELEGATION/)。外部管理器停止宿主时
不得连带清理声明需要继续存续的 guardian，该部署关系必须验证。

容器、SSH、受限 Linux 与 gVisor 逐环境探测。尽力实现尚未冻结，不能直接把 macOS 或普通
Linux 的测试结果视作这些环境的证据。

## 不变量

1. 强模式工作负载执行前已纳管，在声明权限范围内不能迁出。
2. 静止证据同时包含封闭入口和目标子树为空，guardian 死亡不单独构成该证据。
3. 单 Run 终止不隐式清空其他 Run，管理不越过委派边界。

## 为什么不是这些替代方案

| 方案 | 取舍 |
|---|---|
| 启动后写入 `cgroup.procs` | 便于接入现有 spawn，但业务可在迁移前派生未纳管后代 |
| 仅使用进程组和 PID 扫描 | 部署要求低，可用于经设计的尽力模式，但不满足这里的强保证 |
| 硬依赖 systemd 管理所有环境 | 委派方式统一，但排除提供等价能力的其他部署 |

## 落地与验收

先证明创建窗口和权限隔离，再证明 Run／Scope 清理、guardian 强杀及宿主升级时的存续关系。
使用真实后代、后台化和明确强杀点，记录内核与实际委派能力；同时验证受限环境的拒绝／降级。

## 本决策未解决的问题

确切创建机制、单 Run 子树布局、委派回收、外部管理器关系和 Linux 尽力算法仍需冻结。
这些属于平台证明，不能仅以 cgroup API 文档推导 Ora 已支持强纳管。
