# 启动前声明实际纳管保证，按证据区分清理结果

Scope 在业务启动前确定并保存实际纳管保证。强能力不足时按请求拒绝或预先降级；已按强模式
启动后不能在清理失败时降低标准。强静止、尽力清理完成和清理未完成／未知分别报告。

本根决策为 `proposed`，适用于所有平台，平台实现分别见
[Linux](../linux/0-cgroup-v2-containment.md)、[Windows](../windows/0-creation-time-job-containment.md)、
[macOS](../macos/0-native-best-effort-containment.md)。它不构成恶意程序安全沙盒或外部服务取消协议，
也不自动把旧 reaper 运行提升为强纳管。

## 背景与约束

进程组、后代扫描和强平台容器能够提供的退出证据不同。隐瞒差异会使恢复误放行旧运行仍可能
写入的资源；完全禁止尽力恢复又不能满足原生 macOS 和受限 Linux 的执行需求。

## 决策

### D1：请求策略与实际能力分开

| 请求策略 | 能力不足时 |
|---|---|
| 必须强纳管 | 拒绝启动 |
| 优先强纳管，允许尽力纳管 | 在业务启动前、允许范围内降级 |
| 明确尽力纳管 | 使用经声明的尽力实现 |

Scope 内所有 Run 必须符合已保存契约。启动未知时不能更换实现再次启动同一 Run；清理错误、
重试次数或等待期限都不能触发事后降级。实际保证必须可查询，不凭 Linux、容器或 gVisor 名称推断能力。

### D2：完成结果只承诺已取得的证据

| 结果 | 必须成立 |
|---|---|
| 已确认静止 | 声明纳管范围内取得完整退出证据，并封闭后续启动／写入入口 |
| 尽力清理完成 | 完成承诺的跟踪与清理；仍不能排除未跟踪残留 |
| 清理未完成／未知 | 已知残留、操作失败或事实无法核实 |

尽力完成也需要明确、经测试的平台判据，不是“尝试过清理”。已知冲突进程存活或清理失败时不得
报告完成。Node 按[资源交接规则](../../integration/0-shared-process-entry-and-resource-handoff.md)
在清理和业务对账后放行；尽力恢复可由部署／运行政策一次性选择，无须每次异常交互确认。

### D3：纳管范围不扩展为所有外部副作用

强保证覆盖声明受管环境内的进程，不自动覆盖恶意越权或外部服务执行的任务。插件请求常驻服务
写文件后，本地进程退出不证明服务停止；Git hooks、辅助程序和外部系统的影响由业务领域对账。
无法覆盖的副作用必须可见，不能由本地静止推导业务安全。

## 不变量

1. 实际保证在业务启动前确定并持久保存，所有恢复查询呈现同一保证。
2. 强静止与尽力完成不可互换，错误或超时不制造完成证据。
3. 平台清理完成不替代业务对账或外部副作用协调。

## 为什么不是这些替代方案

| 方案 | 取舍 |
|---|---|
| 所有平台统一宣称全进程树退出 | 接口简单，但进程组与后代扫描不能提供同等证据 |
| 所有部署强制强纳管 | 保证统一，但会排除原生 macOS 和缺少委派能力的 Linux |
| 清理失败后自动降级成功 | 提高表面可用性，但违反启动时的资源恢复承诺 |

## 落地与验收

先为各平台定义能力探测与清理判据，再验证启动前拒绝／降级、启动未知、已知残留和清理失败。
强与尽力模式分别记录证据，受限 Linux／gVisor 不从其他 Linux 环境的测试推导支持。

## 本决策未解决的问题

尽力实现的具体清理算法、Linux／gVisor 能力矩阵及部署默认政策尚需冻结；平台 ADR 负责机制，
本 ADR 负责跨平台保证与结果分类，不引入 CPU、内存或运行数量配额。
