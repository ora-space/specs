# 一轮以取消或失败结束后，Node 先停掉这一轮新起的进程再判定是否保留会话（轮次进程栅栏，Linux）；轮次边界清单按平台登记

> 历史决策：D4 第 1 步“写 `TurnEnded{cancelled}`”、第 8 步与不变量 6，由
> [一轮的失败与取消分开记录](20261124-turn-failure-reason-distinct-from-cancel.md)（`approved`）修改：`TurnEnded` 带 `ended_by`
> 或 `failure`；选择了失败后保留、因失败而停的一轮，第 8 步把 `TurnFailureSettled{kept}` 与并入的取消在同一事务中写入，
> 已受理 `EndSession` 时账本拒绝 `kept`；不变量 6 的期限同样约束 `TurnFailureSettled`。这些部分以该决策为准。其余决策不变。

一轮以取消或失败结束、Agent 已经回应之后，Node 在判定会话能否保留之前，先停掉这一轮新起的进程。范围是本尝试
被认领的进程（带 `ORA_SESSION_ATTEMPT` 标记，或经被认领的父进程认领）中，启动时刻不早于这一轮开始、且所在会话 id
（sid）不属于“这一轮开始前就已启动、此刻仍存活的本尝试进程”所在会话的那些。Node 复用尝试环境标记的冻结、pidfd
杀与“连续两次扫描干净”，称为**轮次进程栅栏**；静默窗口之后、写 `stopped` 之前，Node 再对同一范围只扫描、不杀地复查
一次。只有栅栏与复扫都干净、取消决策 D2 原有的三条静止条件也都成立，会话才保留；扫描不可判定、杀不干净或超出期限
（栅栏 F 为 5 秒，复扫 R 为 1 秒）时，会话以新的 detail `turn_processes_unstopped` 结束。轮次边界的含义随之
从“上游 Agent 自身的属性”改为“Agent 回应 + Node 的轮次进程栅栏”，清单按（插件，版本，平台）登记，一致性测试经真实
Node 验证这个组合。首个登记是 Linux 上的 `official/ora-space.opencode 0.6.11`；ora-node 目前只有 Linux 版，其他平台的
条目不被任何 Node 认可。行为变化是：会话被保留的取消或失败之后，这一轮工具起的后台作业和开发服务器会被杀掉；
一轮正常完成后仍不发任何信号。

本 ADR 状态为 `implemented`：2026-11-23 经 owner 评审批准（[specs#326](https://github.com/ora-space/specs/pull/326)），
依据 [circus#1339](https://github.com/ora-space/circus/issues/1339) 的 owner 结论（方向 B）与
[circus#1380](https://github.com/ora-space/circus/issues/1380) 中的后续裁定：F 为 5 秒，F 内按退避再观察；豁免会话在栅栏
扫描时取；一致性测试不专门构造懒启动场景；栅栏之后、`stopped` 之前只扫描不杀地复查一次。由
[desktop#807](https://github.com/ora-space/desktop/pull/807) 实现，合并提交
[`447a59de`](https://github.com/ora-space/desktop/commit/447a59de6722500cae0be011860e63e5127a3b23)。正文按最终实现同步；
实现对批准文本的细化与偏离已写进对应决策，汇总见“实现与批准文本的差异”。偏离有两项：栅栏只重试可能自行消失的不干净
结论；并入的取消逐条结算，`EndSession` 落在两条之间时结论不同（D4 已知窗口，[circus#1403](https://github.com/ora-space/circus/issues/1403)）。“验证义务”各条已转为核心用例并按该合并提交
登记证据。它修改
[取消一轮并在轮次结束后保留会话](20261116-cancel-turn-and-keep-session-after-turn-ends.md)（下称“取消决策”，`implemented`）的
D1 与 D4 的本地结算期限和 Controller 等待上限 T、D2 的轮次边界与保留条件、D3 的情况表、不变量 2 与 7、风险表中关于
后台任务的一行、验证义务 10 与 13，以及
[会话尝试的进程带环境标记](../agent-runtime/20261120-attempt-mark-in-session-stop-evidence.md)（下称“标记决策”，
`implemented`）D4 中“保留会话的取消与失败不发任何停止信号”一条。涉及 desktop 的 `apps/ora-node/src/session/`（准入
提交时记下轮次开始、D2 判定中的栅栏、新 detail、按平台的清单）与 `crates/utils` 的标记扫描（在认领结果上按轮次收窄，
读出 sid）。Node Protocol 的消息形状不变，只给既有的 `agent_failed` 增加一个 detail 值；账本 schema 不变（D6）；取消结论的
本地结算期限变为 G + F + Q + R = 23 秒（D4）。本决策不处理 Windows Node、Claude 插件的 A2
（[circus#1381](https://github.com/ora-space/circus/issues/1381)）、Strong 纳管，也不弥补清空环境后成为孤儿的进程这一已知
缺口。

放在 `protocol` 叶子目录，因为本决策改变的是取消决策的会话保留条件、协议可见的终态 detail 与结论期限，是取消决策的
直接后续；它只复用标记决策的扫描手段，不改变尝试的停止证据、证明名与账本，对标记决策只修改“保留会话时不发信号”
这一条行为说明。

## 问题与约束

取消决策 D2 只对“回应之后不再有任何本轮工作”的 Agent 保留会话，并把这一点当作上游 Agent 的属性，由一致性测试按
版本证明。[circus#1340](https://github.com/ora-space/circus/issues/1340) 用部署的两个发布包实测，两者都不具备这一属性：
Agent 回应 `cancelled`、工具状态已是 `completed`，工具起的后台 shell 在回应之后仍写工作目录，之后也没有任何本轮的
消息。Node 的三层检测（回应栅栏、静止条件、跨轮次检测）只看 Agent 发来的流量，看不到这种写入，所以清单只能为空，
部署版在运行中取消一轮时会话一律结束（`turn_boundary_unverified`）。

两个 Agent 都把工具命令放进新的会话（OpenCode bash 工具与 Claude Bash 都以 `setsid` 启动每条命令），后台作业在外层
shell 退出后被 init 收养；它们继承了标记决策给尝试设置的环境标记。另一方面，两个 Agent 都会在会话中途懒启动常驻
进程，例如 OpenCode 在第一次需要诊断时启动 `deno lsp`，它在 Agent 自己的会话里，之后跨轮次使用。所以方案必须满足：

- **只杀这一轮的工作**：轮次开始前已有的进程（插件运行时、Agent CLI、前几轮留下的开发服务器、常驻的 LSP 与 MCP）
  不能被杀；这一轮里由 Agent 懒启动、要跨轮次使用的进程也不能被杀。实测“本轮新起的一律杀”会杀掉懒启动的
  `deno lsp`，OpenCode 之后一直报告过期的诊断。
- **先停再派发**：下一轮的 prompt 写出之前，被取消那一轮的进程必须已经不在，否则它们与下一轮并发修改 checkout。
- **失败即结束**：判断不了是否停干净时不能保留会话；兜底是取消决策 D3 的结束会话，它会停止整个尝试。
- **不卡住 Node、有界**：扫描与杀沿用标记决策 D2 的阻塞 worker 和上限；取消结论仍要在有界时间内本地结算，并落在
  Controller 的等待窗口之内。
- **不依赖 Agent 配合**：OpenCode 没有任何能排在取消回应之前执行的钩子；Claude 的任务表管不到普通的 `cmd &`。
- **无特权**：当前 Linux 部署与 cloud v2 都没有委派的 cgroup 子树，方案不能依赖新的部署权限。

## 决策

### D1：轮次开始与轮次范围

**轮次开始**：一轮的准入提交成功之后、`session/prompt` 写给 Agent 之前，Node 在内存中记下这一轮的开始：接收这次
prompt 的 Agent 尝试，以及 `turn_since_ticks`，即此刻的 `CLOCK_BOOTTIME` 换算成 `/proc/<pid>/stat` 使用的 clock tick，与
标记决策 D1 的 `since_ticks` 同一时钟。每个被准入的轮次都记，只是一次时钟读取，不扫描 procfs、不写账本，正常的轮次
没有额外开销。时钟读取失败时，这一轮记为“没有开始时刻”。

**轮次范围**：栅栏每扫描一遍 procfs，就在这一遍里按以下规则收窄标记决策 D2 的认领结果：

1. **豁免会话**：这一遍中被本尝试认领、且 `start_ticks < turn_since_ticks` 的进程所在的 sid，构成豁免会话集合；
2. **范围**：被本尝试认领（认领规则与标记决策 D2 相同，含经父进程认领与父进程复核，父进程可以在范围之外）、
   `start_ticks >= turn_since_ticks`、且所在 sid 不在豁免会话集合中的进程。

满足 2 中启动时刻与 sid 两条、而属于标记决策 D2“待定”的进程（环境不可读、属于尝试用户、Node 不是该用户），使这一遍的
观察为 Unknown；不在范围内的进程，无论是否被认领、是否待定，都与栅栏无关。

为什么用 sid 划界：进程的 sid 只能从父进程继承，或经 `setsid` 新建一个以自己为首的会话，不能加入另一个已存在的会话。
所以本轮新起的进程，sid 属于某个更早的本尝试进程，说明它从那个会话一路继承下来，中间没有进程新建会话，例如 Agent
在自己的会话里懒启动的 LSP、MCP 及其子进程；sid 不属于任何更早的本尝试进程，说明这一轮里有进程新建了它，例如工具
shell。实测的两个 Agent 都把工具命令放进新会话、把懒启动的常驻进程留在自己的会话里，这一规则恰好把两者分开。两者
以后若改变这种安排，一致性测试会发现（D5）。

为什么在栅栏扫描时取豁免会话，而不在轮次开始时做快照（owner 裁定）：

- 每一轮开始时不多一次 procfs 扫描，也就没有“开始时扫描失败、超出预算”这类只为快照存在的故障；
- 豁免会话与被判定的进程在同一遍里读出，都是这一遍存活的会话。内核在会话仍有成员时不会复用它的编号；一遍扫描不是
  原子的，若扫描途中某个更早的会话消失、编号又被这一轮新建的会话复用，单独一遍可能误豁免一次。判定要求连续两次扫描
  都干净（D2），同一次回绕不会在两遍里都发生，所以复用的编号不会让栅栏判定为干净；
- Agent 自己的会话在 Agent 存活期间总是豁免的：Agent 进程在尝试开始时启动，早于任何一轮，栅栏运行时它仍在运行；
- 代价是更保守：一个更早的会话，如果它更早启动的成员在这一轮里全部退出，它在这一轮新起的成员不再被豁免，会被杀。

启动时刻的实际作用：它把候选进程分成“更早”与“这一轮”两类，更早的被认领进程提供豁免会话，这一轮的进程才可能落在
范围内。对被认领的进程，sid 规则本身已经排除了轮次开始前的进程：每个更早的被认领进程都让自己所在的会话豁免，所以
前几轮起的开发服务器、正常完成的轮次留下的后台作业，以及带伪造标记的更早进程，都因此不被栅栏碰到。启动时刻另外
起作用的地方是待定进程：更早启动、读不到环境的进程不计入，否则它们会让每一次栅栏都成为 Unknown（D7）。为什么在
准入提交之后、prompt 写出之前记：这一轮的
prompt 让 Agent 启动的一切都晚于这个时刻；准入之前的时刻会把前一轮结束后、这一轮准入前由更早的工作新起的进程也
算进这一轮。

**范围对后代封闭**：范围内进程的后代也在范围内：它启动得更晚，sid 要么继承自父进程，要么是新建的，两者都不属于任何
更早的本尝试进程，并且经父进程被认领。所以标记决策 D2“先冻结、再杀”保住清空环境的子进程的论证，对栅栏同样成立
（D2）。

### D2：栅栏：只冻结并杀轮次范围，两次扫描干净才算停止

一轮以取消或失败结束、Agent 已经回应、D5 的登记与取消决策 D2 静止条件 2 都已满足时，Node 运行栅栏。栅栏由观察组成，
每次观察：

1. **终止**：按标记决策 D2 第 1、2 步冻结并杀，但只对轮次范围内的进程发信号：逐轮扫描、冻结新出现的范围内进程，
   至多 32 轮，冻结至多 2 秒（看门狗保证），再全部 SIGKILL；每个信号发送前按 PID 与启动 tick 重新确认、经新开的
   pidfd 发出。每一轮扫描都按 D1 重新取豁免会话。不执行第 3 步：不终止任何进程组，不检查尝试锁与线索。信号是否
   发送成功不构成证据。
2. **判定**：连续两次扫描，轮次范围内既没有被认领的进程，也没有待定进程，结论为**干净**；任一次有范围内的被认领
   进程为 **Running**；扫描失败、有范围内的待定进程或观察超出预算为 **Unknown**。

观察在标记决策 D2 的同一个阻塞 worker 上，与这个 Node 所有会话的停止观察串行。栅栏期限 F 为 5 秒（D4），与标记决策
D2 一次观察的预算相同。第一次观察拿到全部 5 秒预算，排队等 worker 的时间也算在内。它提前返回且结论不干净时，Node 按
标记决策 D2 的退避（25 ms 起倍增到 1 秒）等待，再在剩余的预算内观察；之后每次观察同样只拿剩余的预算，剩余时间不够
一次退避时不再观察。所有观察、终止、排队与等待合计不超过 F。栅栏的结果是最后一次观察的结论。干净则继续取消决策 D2 的静默窗口（D4）；否则会话按 D3 结束。

重复观察只用于可能自行消失的不干净结论（Running，或扫描失败、待定进程、worker 上的观察异常结束造成的 Unknown）；观察
超时时预算已经用完，不再重来。这一轮没有开始时刻、接收
prompt 的尝试已被替换时，栅栏不观察、不发信号，直接判为 Unknown；尝试的范围记录缺失或不可读时，这次观察判为 Unknown
并结束栅栏，不再重试。这三种情况重来也不会变干净，重试只会把结束会话推迟到 F 用完。

栅栏从不向轮次开始前已启动的进程（包括插件运行时与 Agent CLI）、豁免会话中的进程发信号。Agent 在栅栏期间照常运行，
它的进程组与停止线索不变。

**结算前的复扫**：静默窗口 Q 结束、空闲期流量检查通过之后，写 `stopped` 之前，Node 对同一轮次范围再做一次只判定、不
终止的观察：按第 2 步连续两次扫描，每一遍照样按 D1 现取豁免会话。复扫在同一个阻塞 worker 上，期限 R 为 1 秒，排队等
worker 的时间也算在内，不重试。结论干净才写 `stopped`；Running、Unknown 或超出 R，会话按 D3 结束。复扫从不发信号。

为什么要复扫：栅栏只证明它结束那一刻范围内没有进程。之后的 Q 里，豁免会话中的进程（Agent、懒启动的 LSP 或 MCP）仍可能
不发任何轮次流量地新起一个 `setsid` 进程，例如隔几百毫秒才重启子进程的 supervisor；没有复扫，它会在 `stopped` 之后存活、
与下一轮并发。复扫把“`stopped` 写入时范围内的进程都已不在”从栅栏结束时延伸到结算时刻。为什么只扫不杀：此时出现的范围
内进程说明豁免进程在回应之后还在为这一轮启动工作，违背了 D5 的边界；再杀一次就要再等一个 Q 观察 Agent 的反应，结束
会话更简单，也是失败即封闭。为什么 R 取 1 秒：正常情况下两次扫描只要几毫秒；1 秒容得下短暂的排队，又让结论期限只增加
1 秒（D4）。代价是 worker 被其他会话的停止观察占满时复扫为 Unknown，本可保留的会话被结束。

为什么复用标记决策的手段与上限：冻结轮数、冻结时长、重新确认与单一 worker 都已为“读挂住、fork 风暴、PID 复用、
fd 耗尽”逐项评审过；栅栏面对的是同一批进程，只是范围更小，实现也只给扫描加了一种收窄方式，冻结、杀与判定都走这同一个
收窄后的范围，没有另起一条杀进程的路径。范围对后代封闭（D1），所以“冻结后它刚 fork 的子进程仍以它为父”的论证不变。
为什么不终止进程组、不查锁：
本尝试的进程组和锁属于仍要继续服务的 Agent，栅栏不是停止尝试。为什么 F 等于一次观察的预算：owner 定 F 为 5 秒，让
最坏的结论期限落在 v2-server 的等待窗口之内（D4）；挂住或排队用满预算的观察之后没有剩余时间，按失败结束。提前返回的
不干净观察在剩余预算内退避后再观察，用于标记决策 D2 已知的短暂情形（收尾时重新确认失败的冻结进程留到下一次观察才被杀）；持续 fork 的
进程让每次观察都不干净，F 用完后按失败结束。

### D3：栅栏不干净时结束会话，detail 为 `turn_processes_unstopped`

以下情况，Node 按取消决策 D3 结束会话，终态 `agent_failed`，detail `turn_processes_unstopped`：

- 栅栏在 F 内没有得到干净的结论：最后一次观察为 Running（杀不掉，例如处于不可中断睡眠；或不断有新的范围内进程出现）
  或 Unknown（扫描失败、范围内有待定进程、观察超出预算）；
- 结算前的复扫不干净：范围内出现了栅栏之后新起的进程，或复扫为 Unknown、超出 R（D2）；
- 这一轮没有开始时刻（D1 的时钟读取失败）；
- 尝试的范围记录缺失、损坏或不可读（标记决策 D1、D3）；
- 接收这一轮 prompt 的 Agent 尝试在这一轮里被替换（例如会话 MCP 刷新 D6 的 MCP 生命周期替换）：新尝试没有能把这一轮的
  进程与新 Agent 自己的进程分开的范围，栅栏不判定为干净。结束会话的停止覆盖两个尝试。

结束决定与并入这次停止的各个 `TurnCancelSettled{session_ending}` 按取消决策 D3 同一事务落账（已持久受理的 `EndSession`
仍按取消决策 D4 优先），之后停止整个尝试：标记决策的停止会杀掉本尝试的全部被认领进程，包括栅栏没能杀掉的那些，终态
仍要等停止证据。

为什么取这个名字：它说出 Controller 关心的事实，这一轮起的进程没有被证明停下，涵盖杀不掉、看不清与时间用完三种
情况（复扫发现的新进程也属于“没有被证明停下”）；与既有的 `turn_cancel_unanswered`、`turn_boundary_unverified` 同为“对象 + 未达成的状态”的形式，Controller 一眼
能看出它与轮次进程有关，而不是 Agent 没回应或版本没登记。不用 `turn_stop_unconfirmed`：它会与会话 MCP 刷新 D5 的
`stop_unconfirmed`（整个执行的停止责任超期）混淆。不用含“fence”的名字：栅栏是 Node 内部的手段，detail 描述可观察的
结果。也不细分 Running 与 Unknown：两者对 Controller 的处理完全相同，细分只增加协议面；Node 日志记录最后一次观察的结论。

新 detail 沿用 `AgentSessionEnded.detail` 这一有界 snake_case 字符串，不改变消息形状，也不需要新的能力：Controller
按取消决策 D5 在声明 `turn_cancel` 时已承诺理解取消决策的 detail，本值与它们一样只出现在 `agent_failed` 中。

### D4：先后顺序与期限

Agent 回应之后，Node 按以下顺序处理一轮的取消或失败：

1. 写 `TurnEnded{cancelled}`（取消决策 D1，不变）。
2. 检查会话选择了对应一项；检查（插件，版本）为本平台登记（D5），否则 `turn_boundary_unverified`；检查静止条件 2，
   否则 `turn_not_quiescent`。这些情况不运行栅栏，直接按取消决策 D3 结束会话。
3. 运行栅栏，至多 F（D2）；不干净按 D3 结束会话。
4. 栅栏干净之后开始静默窗口 Q。
5. 检查自回应起（包括栅栏期间）有没有轮次流量，有则 `turn_not_quiescent`。
6. 对轮次范围只扫描、不杀地复查一次，至多 R（D2）；不干净按 D3 结束会话。
7. 复扫干净之后，最后一次处理队列：此前受理的 `CancelTurn` 并入这次停止；已受理的 `EndSession` 优先，会话以它的原因
   结束，不写 `stopped`。
8. 按受理顺序写并入这次停止的各个 `TurnCancelSettled`（`stopped`，或因失败而停时为 `already_ended`），会话保留；
   之后才准入下一轮，下一轮按 D1 记自己的开始，再写出 prompt。

**栅栏期限 F**：5 秒（owner 裁定），自栅栏开始起算，覆盖每次观察、终止、排队与等待。**复扫期限 R**：1 秒，覆盖一次判定
与排队（D2）。

**结论期限**：

| 这次停止 | 本地结算期限 |
| --- | --- |
| `CancelTurn` 发起，Agent 在截止时刻前回应，栅栏运行 | 自发起的命令受理起 G + F + Q + R，按当前取值为 23 秒 |
| 一轮失败发起，栅栏运行 | 自 Agent 回应起 F + Q + R |
| 并入一次停止的 `CancelTurn` | 不晚于那一次停止的截止时刻加 F + Q + R，因此不超过自本命令受理起的 G + F + Q + R |
| Agent 没有回应、第 2 步已决定结束会话 | 不运行栅栏，与取消决策相同（G + Q 或立即） |

- **期限各自独立**：G 在 Agent 回应时结束，栅栏不占用 G；Q 在栅栏干净之后才开始，栅栏不占用 Q；R 在 Q 与空闲期流量
  检查之后才开始；会话 MCP 刷新 D5
  的停止确认期限（10 分钟）只在作出结束决定之后起算，与栅栏无关，栅栏不干净时它从那次结束决定开始。
- **栅栏期间到达的命令**：栅栏有界，不因命令中断。期间受理的 `CancelTurn` 与 `EndSession` 留在队列中，栅栏返回后处理：
  `CancelTurn` 按取消决策 D1 并入这次停止，与它同时结算；`EndSession` 按取消决策 D4 优先，栅栏干净时在静默窗口中读到
  它，栅栏不干净时也以它的原因结束会话。所以 `EndSession` 的生效最多推迟 F。Agent 进程退出或 ACP
  连接断开，按取消决策 D3 的既有 detail 结束会话。
- **复扫期间到达的命令**：复扫同样不因命令中断，命令在它返回后、写任何结论之前处理（第 7 步）。复扫期间受理的
  `CancelTurn` 并入这次停止，与它同时结算：复扫干净时同为 `stopped`（因失败而停时为 `already_ended`），复扫不干净时同为
  `session_ending`。复扫期间受理的 `EndSession` 优先：不写 `stopped`，会话以它的原因结束，尚未结算的取消得到
  `session_ending`。所以 `EndSession` 的生效在复扫上最多再推迟 R。
- **第 7 步读取之后到达的 `EndSession`**：第 7 步读完队列之后、第 8 步写完之前受理的 `EndSession`，同样不会让 `stopped`
  写出：账本在已持久受理 `EndSession` 之后拒绝 `session_ending` 以外的取消结论，被拒的取消留给结束决定同一事务写成
  `session_ending`，会话在下一次处理队列时以 `EndSession` 的原因结束。这一保证来自账本的拒绝，不依赖读取时机。
- **已知窗口**：第 8 步逐条写并入的取消。`EndSession` 恰好在两条之间受理时，先写的取消已是 `stopped`，后面的得到
  `session_ending`，同一次停止的并入取消结论不同。窗口只在两次账本写入之间，取消决策的实现原本就有，栅栏没有扩大它；
  根治需要一次事务写完全部并入的取消，留给后续修复（[circus#1403](https://github.com/ora-space/circus/issues/1403)），在核心用例中登记为缺口。
- **Controller 的等待上限**：取消决策 D4 的 T 改为必须大于 G + F + Q + R 加上传输余量。cloud v2-server 等结论的窗口是
  30 秒，每收到一条消息重新计时，大于 23 秒，不需要改动。

为什么栅栏在静默窗口之前：杀掉这一轮的进程可能让 Agent 作出反应，例如为被杀的工具补发输出，或像 Claude 那样在后台
任务结束后自己发起一轮；Q 放在栅栏之后才能观察到这些反应，并让“回应之后没有轮次流量”覆盖到杀完为止。反过来先等 Q
再杀，杀后的反应会在下一轮 prompt 发出之后才到，与下一轮的更新无法区分；两者并行能省下至多 F，但有同样的问题。为什么
栅栏在第 2 步之后：已经决定结束会话时，整个尝试都会被停止，栅栏多余，只会推迟结论。为什么下一轮等栅栏：从回应到
杀掉之间这一轮的进程仍可能写 checkout，这些写入属于被取消的这一轮；下一轮在栅栏干净之后才派发，才能保证它开始时
checkout 不再被上一轮的进程修改。为什么栅栏不因命令中断：中断会让栅栏的结论取决于命令到达的时刻；F 很短，让命令
等栅栏返回，规则更简单，`EndSession` 的结果也不变。

为什么 F 独立于 G：G 按 Agent 正常取消的最坏耗时定值（取消决策 D2）；把栅栏塞进 G，栅栏能用的时间就取决于 Agent 回应
得多快，回应慢的 Agent 栅栏时间不够。为什么 5 秒：正常情况下一次观察（几十毫秒）就干净；5 秒等于一次观察的预算，
让最坏期限（连同复扫的 R 为 23 秒）落在 v2-server 30 秒的等待窗口之内并留有余量。代价是栅栏观察因排队或挂住用满预算时没有第二次机会，
会话按失败结束。

### D5：轮次边界是“Agent 回应 + 轮次进程栅栏”，清单按（插件，版本，平台）登记

取消决策 D2 的“可依赖的轮次边界”改为：Agent 回应一次 prompt 之后，不再为这一轮发出任何轮次流量；并且经过 Node 的
轮次进程栅栏之后，没有这一轮的、仍在运行而不报告的工作。栅栏范围之外的工作（Agent 自身进程内的工作、豁免会话中
的进程、被杀后自发起的新一轮）仍须由 Agent 自己保证不存在。

- **登记键**：（插件 ID，插件精确版本，平台）。插件锁定上游版本，精确版本仍是唯一确定 Agent 实现的方式（取消决策
  D2，不变）。平台是 Node 运行的操作系统，取值 `linux` 与 `windows`，各自需要自己的栅栏。CPU 架构不进入登记键：同一
  插件版本在各架构上来自同一份上游源码，栅栏与进程会话语义只取决于操作系统；一致性测试的运行记录写明所用架构与
  发布包摘要。清单编译在 Node 中（`TurnCancelConfig` 的默认值），随 Node 版本发布，部署不能另行配置。
- **Node 如何使用**：Node 只认自己所在平台的条目。ora-node 目前只有 Linux 版（[Ora Desktop 只支持 Windows 和
  Linux](../../desktop/platform/0-windows-and-linux-only.md)），所以 `windows` 条目不被任何 Node 认可；将来的 Windows
  Node 要先有自己的栅栏（例如 Job Object）并在 Windows 上通过一致性测试，才能有 Windows 条目，在此之前它对任何一轮的
  取消或失败都以 `turn_boundary_unverified` 结束会话。只为其他平台登记的版本，在本平台同样是 `turn_boundary_unverified`。
  Node 所在的平台由它的构建目标决定；为 Linux 与 Windows 以外的目标构建的 Node 没有可匹配的平台，不认可任何版本。
- **一致性测试**（取消决策验证义务 13 的修改）：在该平台上，以生产构建的 `ora-node`（栅栏启用）、真实的 Deno 与该版本
  未修改的发布包，由回环模型驱动 Agent 的真实工具。每次运行先执行一个普通轮次（使 Agent 自己的进程在目标轮次之前
  就存在），再执行目标轮次并在运行中取消它（`error` 场景让它自己失败），最后再执行一个普通轮次。场景为：
  - `shell`：取消运行中的 shell 工具；
  - `subagent`：取消带子代理的轮次；
  - `background`：取消起了 Agent 后台任务的轮次；
  - `detached`：取消从普通 shell 调用里放到后台的作业；
  - `error`：模型请求错误。

  一次运行通过，当且仅当：这次停止以 `stopped` 结算、会话保留；结算时，这一轮在 Agent 更早进程的会话之外新起的进程
  都已不在；结算之后作业的延迟写入没有出现；下一轮正常完成。`error` 场景没有取消结论：测试在下一轮的第一个事件到达时
  采样进程，此时 Node 已判定完失败的一轮、运行过栅栏与复扫，所以对这个场景它检查的是会话没有结束、那一刻这一轮在更早
  会话之外新起的进程都已不在、之后没有延迟写入、下一轮正常完成。每个场景重复运行，全部通过的组合才进入清单，测量保存在
  运行 issue 中，条目旁写明发布包摘要与所测架构。一致性测试是按需运行的 Node 测试：它需要安装好的发布包，不在 CI 中
  运行，所以它的结果是登记依据的运行记录，不替代 Node 的进程级测试。
- **首个登记**：Linux 上的 `official/ora-space.opencode 0.6.11`（OpenCode CLI 1.19.3）。circus#1340 在 x86_64 上经真实 Node
  运行，五个场景各 5/5 通过。`official/ora-space.claude 0.4.5` 不登记：`background` 0/3，栅栏杀掉它的后台任务后它自己发起
  一轮，被 Q 发现，会话以 `turn_not_quiescent` 安全结束；这是栅栏范围之外的轮次流量，它的 A2（关闭后台任务、发新插件
  版本）由 circus#1381 承担，发版并通过测试后再登记。

为什么边界改为组合：实测两个 Agent 自身都不满足“回应之后没有本轮工作”，原定义下清单只能为空；它们违约的方式恰好
是 Node 能看到、能杀掉的进程。把栅栏算进边界后，一致性测试验证的是部署中真正起作用的组合，而不是一个已知不成立的
单方承诺；去掉栅栏时，`background` 与 `detached` 场景都有进程逃逸、延迟写入照样出现。为什么按平台：栅栏是操作系统相关的
机制，这一期只在 Linux 上实现和实测；同一插件版本在别的平台没有栅栏，按 Linux 的测试结果放行等于把未验证的组合当作
已验证。

懒启动的常驻进程在被取消一轮之后存活，由 D1 的 sid 规则保证，并由 Node 的进程级测试验证；一致性测试的五个场景不专门
构造懒启动。一个以新会话懒启动常驻进程的 Agent 版本，即使通过一致性测试，也会在保留会话的取消之后失去那个进程
（见“已知风险与待实测”）。

### D6：轮次开始只在内存中，Node 重启按原规则结束会话并停止整个尝试

轮次开始（尝试与 `turn_since_ticks`）只存于 Node 内存，不写账本；豁免会话在每次扫描时现取，本来就不需要保存。账本 schema
不变。这一点依据现有 ADR 成立：

- **会话不跨重启**：协议 D6 规定 Node 重启后会话以 `interrupted` 结束，不恢复 Agent；取消决策 D3、D4 规定重启时没有
  结束决定的会话，在重启收口中写入以 `interrupted` 为原因的结束决定，同一事务为未结算的 `CancelTurn` 写
  `session_ending`。所以重启之后不存在需要继续保留、需要重新运行栅栏的会话。
- **整个尝试被停止**：标记决策 D3 的重启收口表规定，同一 boot 上先按持久的范围记录冻结并杀掉原尝试的全部被认领进程，
  再取停止证据；跨 boot 按宿主重启证据处理。轮次范围是尝试范围的子集（`turn_since_ticks` 不早于尝试的 `since_ticks`，
  认领规则相同），所以栅栏要杀的进程在重启收口中都会被杀，终态之前取得证据。
- **栅栏中途崩溃**：被栅栏冻结、还没被杀的进程停在 T 状态，按标记决策 D2 由重启收口认领并杀掉。

因此 Node 在一轮开始之后、栅栏之中，或在 `TurnCancelSettled{stopped}` 写入之后崩溃，结果都是会话以 `interrupted` 结束、
整个尝试被停止，与本决策之前相同。将来若有决策让会话跨 Node 重启保留，它必须重新处理轮次开始（见“本决策未解决的
问题”）。

### D7：豁免保护什么，不保护什么

| 进程 | 栅栏 |
| --- | --- |
| 轮次开始前已启动的任何进程本身：插件运行时、Agent CLI、前几轮起的开发服务器、正常完成的轮次留下的后台作业、会话开始时启动的 MCP | 不发信号 |
| 轮次开始前已启动的进程（例如之前一轮起的开发服务器、LSP）在这一轮里以新会话起的子进程 | 杀：新会话不属于任何更早进程 |
| 这一轮里 Agent 在自己的会话中懒启动的 LSP、MCP，以及它们在同一会话中的子进程 | 豁免，跨轮次存活 |
| 这一轮里在某个更早进程的会话中启动的进程，例如插件请 Node 代为启动的宿主子进程 | 豁免，不在范围内 |
| 这一轮的工具命令（在新会话中）及其后台作业、开发服务器、文件监视进程 | 杀 |
| 这一轮的工具以 `setsid` 启动的长期守护进程 | 杀 |
| 这一轮里 Agent 以新会话懒启动的常驻进程 | 杀（D5 末段） |
| 一个更早的会话里，更早启动的成员在这一轮全部退出后，这一轮新起的成员 | 杀（D1，更保守的代价） |
| 豁免会话中的常驻进程代这一轮起的工作，例如 MCP 服务的工具在自己的会话里起的后台进程 | 不在范围内，漏掉 |
| 清空环境后成为孤儿的进程、经 `docker run` 或 `systemd-run` 代启的进程 | 不在证据内，漏掉（标记决策 D6，BestEffort） |

**Node 与 workload 不同用户、且 Node 没有 `CAP_SYS_PTRACE` 的部署**（标记决策 D6 的部署前提不满足）：Node 读不到任何
workload 进程的环境，一个进程也认领不到，豁免会话集合恒为空。轮次开始前的进程因启动时刻不计入（D1）；但这一轮只要留下
任何存活进程，包括 Agent 在自己会话里懒启动的 LSP，它都是范围内的待定进程，栅栏为 Unknown，会话以
`turn_processes_unstopped` 结束。这是失败即封闭；这种部署下保留会话的取消实际上总会结束会话。

owner 接受的代价：

- 会话被保留的取消或失败之后，这一轮工具起的开发服务器、后台作业会被杀；一轮正常完成时不受影响，它留下的作业在
  之后的轮次被取消时也不受影响，直到会话结束。需要跨取消存活的服务，要在之前的一轮里或在 Ora 之外启动。
- 从回应到杀掉之间的写入算在被取消的这一轮里，留在 checkout 中，不回滚；下一轮在栅栏与复扫完成后才派发。
- 清空环境的孤儿作业仍会漏掉，与标记决策 D6 相同，是 BestEffort。

### D8：威胁说明

标记决策 D8 的前提不变：标记不是秘密，同 uid 的进程可以伪造它。对栅栏而言：

- 伪造者只能让自己在这一轮开始之后启动、且不在豁免会话中的进程被杀。轮次开始前的被认领进程（包括带伪造标记的）让自己
  所在的会话豁免，因此不被杀；豁免会话中的进程由 sid 排除，而 sid 只能由进程自己经 `setsid` 改变，伪造者不能把别人的
  进程移出豁免会话。
- 伪造者可以启动带标记的早期进程，使某个会话被豁免；它只能这样豁免自己所在的会话，即它自己的进程能留下来，这与它
  本来就可以清空环境逃出标记相同，不扩大逃逸面。
- workload 可以让栅栏一直不干净：持续 fork、进入不可中断睡眠，或在 Node 与 workload 不同用户的部署中让自己不可读。
  结果是会话以 `turn_processes_unstopped` 结束、整个尝试被停止，是失败即封闭，不会在仍有本轮进程存活时保留会话。
- workload 可以逃出栅栏：清空环境后成为孤儿，或请豁免会话中的常驻进程（例如某个 MCP 服务）代为启动后台工作。这与
  会话 MCP 刷新 D5“证据假定 workload 配合”一致：栅栏与标记对恶意或失控的 workload 都只是 BestEffort，不是对抗性
  隔离。用户配置的 MCP 服务不在一致性测试的覆盖范围内。

## 实现与批准文本的差异

desktop#807 在评审中按以下方式细化或偏离了 approved 文本。每一项都已写进上面对应的决策，此处只汇总，便于对照批准版本。
偏离有两项：第 1 行收窄了栅栏的重试范围，第 3 行留下并入取消逐条结算的窗口；其余为细化或说明：

| 批准文本 | 实际采用 | 原因 | 性质 |
| --- | --- | --- | --- |
| D2：提前返回的不干净观察在 F 剩余时退避再观察 | 只重试 Running，以及扫描失败、待定进程或 worker 上的观察异常结束（例如任务 panic）造成的 Unknown；没有开始时刻、尝试已被替换时不观察，范围记录不可用时这次观察即结束栅栏；观察超时已用完预算，不再重来 | 不重试的三种情况重来也不会变干净，重试只会把结束会话推迟到 F 用完 | 偏离：收窄了重试范围，只会更早结束会话 |
| D4 第 7 步：复扫干净之后最后一次处理队列，已受理的 `EndSession` 优先 | 不变，并写明第 7 步读取之后、第 8 步写完之前受理的 `EndSession` 由账本拒绝 `session_ending` 以外的取消结论来保证不写 `stopped` | 读取与写入之间仍有间隙；账本的拒绝是唯一不依赖时机的保证 | 细化：保证不变，写明机制 |
| D4 第 8 步：并入的取消与这次停止同一结论 | 逐条写入；`EndSession` 恰好落在两条之间时，先写的为 `stopped`，其余为 `session_ending` | 取消决策的实现原本就有这个窗口，栅栏没有扩大它；一次事务写完全部并入的取消要改取消结算的路径，留给后续修复（[circus#1403](https://github.com/ora-space/circus/issues/1403)） | 偏离：违背批准文本的 D4 与取消决策“并入的取消与那一次停止同时结算” |
| D5：平台取值 `linux` 与 `windows` | 平台由 Node 的构建目标决定；为其他目标构建的 Node 没有可匹配的平台，不认可任何版本 | 清单只能命名有栅栏设计的平台，其他目标不能借 Linux 的结果放行 | 细化 |
| D5：清单编译在 Node 中 | 清单是 `TurnCancelConfig` 的默认值，与 G、Q、F（`process_fence`）、R（`process_recheck`）同在一处，部署不能另行配置；条目旁的注释写明发布包 sha256、所测架构与测量所在的运行 issue | 放宽登记必须随 Node 版本评审发布；测试可以缩短期限而不改生产默认值 | 细化 |
| D5：一致性测试经真实 Node 运行 | 不变，测试是按需运行的 `#[ignore]` Node 测试，需要安装好的发布包与 Deno，不在 CI 中运行 | 发布包与 Agent CLI 不在仓库中；它的结果是登记依据的运行记录，进程级行为由 echo-agent fixture 的 Node 测试证明 | 说明：不是偏离 |

以下要点按批准文本实现，不是偏离：F 为 5 秒、R 为 1 秒（`TurnCancelConfig::process_recheck`）、结论期限 G + F + Q + R 为
23 秒；豁免会话在栅栏的每一遍扫描时取；detail 为 `turn_processes_unstopped`；清单按（插件，版本，平台）登记，只登记 Linux
上的 OpenCode 0.6.11，Claude 0.4.5 不登记，由 [circus#1381](https://github.com/ora-space/circus/issues/1381) 承担它的 A2。

## 不变量

1. 每个被准入的轮次在准入提交之后、prompt 写出之前只在内存中记下开始；记下开始不扫描 procfs、不写账本。
2. 会话在一轮取消（或失败）后保留，当且仅当：这一轮的 prompt 从未写给 Agent；或者会话选择了对应一项，Agent 的
   （插件，版本）为本平台登记，Agent 连接仍在，静止条件 1、2 成立，轮次进程栅栏在 F 内干净，自回应起到栅栏之后的
   Q 结束都没有轮次流量，且结算前的复扫在 R 内干净。
3. 栅栏只向同时满足“被本尝试认领、`start_ticks >= turn_since_ticks`、sid 不属于同一遍扫描中任何更早启动的本尝试被认领
   进程”的进程发冻结与杀信号；从不向轮次开始前已启动的进程、豁免会话中的进程发信号，不终止进程组。
4. 栅栏干净要求最后一次观察中连续两次扫描既无范围内的被认领进程，也无范围内的待定进程；Running、Unknown、超出 F、
   没有开始时刻、范围记录不可用、尝试在这一轮里被替换，或结算前的复扫不干净，会话都以 `turn_processes_unstopped` 结束；
   复扫从不发信号。
5. `TurnCancelSettled{stopped}` 写入时，这一轮栅栏范围内的进程都已不在：写入紧跟在一次干净的复扫之后；下一轮的 prompt
   在它之后才写出。
6. 栅栏运行时，自发起的 `CancelTurn` 受理起 G + F + Q + R 内结论落账（失败发起时自回应起 F + Q + R）；不运行栅栏的停止，
   期限与取消决策相同。
7. 一轮正常完成后不运行栅栏，不发任何信号。
8. 轮次开始只在内存中；Node 重启后会话以 `interrupted` 结束，整个尝试按标记决策停止，账本 schema 不因本决策改变。
9. Node 只认自己所在平台的清单条目；只为其他平台登记的版本以 `turn_boundary_unverified` 结束会话。
10. 停止保证仍为 `StopContainment::BestEffort`；栅栏干净不宣称这一轮的全部工作已经停止。

## 为什么不是这些替代方案

| 方案 | 优势与取舍 |
| --- | --- |
| A1：Claude 桥接走 ACP 的 JetBrains AIR async-task 扩展，取消时先停掉本轮任务（owner 已否决） | 实测可行，由 Agent 自己停后台任务，Node 不必杀进程。但它是私有扩展；桥接要把取消回应压到停止完成之后再转发、吞掉多出来的消息；管不到普通的 `cmd &`；OpenCode 没有对应的钩子 |
| 只在插件侧解决（A2 `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`，或各插件在取消回应前自己清理） | 不改 Node，边界仍是 Agent 的属性。但 OpenCode 没有排在取消回应之前的钩子；A2 只去掉 Claude 的后台任务，普通 Bash 里的 `cmd &` 仍会逃逸；每个插件版本各自实现，Node 无法验证，违背“不依赖 Agent 配合”。A2 对 Claude 仍然需要，是栅栏之外的补充（circus#1381） |
| 本轮新起的进程一律杀，不按 sid 豁免 | 规则最简单，Agent 懒启动的东西也被清理。但实测会杀掉懒启动的 `deno lsp`，OpenCode 之后一直报告过期诊断，保留下来的会话不可用 |
| 轮次开始时快照豁免会话集合（本 ADR 初稿） | 一轮里先前成员全部退出的会话仍被豁免，少杀一些进程。但每轮多一次 procfs 扫描，多出“开始时扫描失败”这种只为快照存在的故障；快照里的会话之后可能消失、编号被这一轮新建的会话复用，造成漏杀。owner 裁定在栅栏扫描时取（D1） |
| 只观察不杀：回应时仍有本轮新起的进程就结束会话 | Node 不在保留会话的路径上发信号。但开发服务器、后台作业很常见，几乎每次取消都结束会话，而结束会话会停止整个尝试，进程照样被杀；用户既失去会话又失去进程，比“杀掉并保留”严格更差 |
| 每轮一个 cgroup v2 子树，或 Node 做 child subreaper 加启动时刻 | cgroup 是唯一能给出 Strong 的方向，进程无权离开。但它需要委派的 cgroup 子树，当前无 root 部署与 cloud v2 都没有（标记决策的否决理由相同）；subreaper 只让孤儿挂到 Node 下，不说明属于哪一轮，Node 崩溃后失效，还要新的回收循环。两者都还要另行区分懒启动的 LSP 与工具作业，豁免规则不可省；circus#1340 的原型用它们验证了 sid 规则，落地选用已实现的标记扫描 |
| 先等静默窗口 Q，再运行栅栏；或两者并行 | 取消后少等至多 F。但杀掉进程引起的 Agent 反应（补发输出、自发起一轮）会在下一轮 prompt 之后到达，无法与下一轮区分（D4） |
| 栅栏时间计入 G | Controller 的 T 不变。但栅栏可用的时间取决于 Agent 回应得多快，回应慢时栅栏来不及，本可保留的会话被结束（D4） |
| F 取 10 秒，容得下一次用满预算后的第二次观察（本 ADR 初稿） | 排队或挂住一次后仍有机会保留会话。但最坏期限变为 27 秒，逼近 v2-server 30 秒的等待窗口；owner 定为 5 秒（D4） |
| 栅栏期间收到 `EndSession` 立即中断栅栏 | `EndSession` 最多早 F 生效。但栅栏的结论会取决于命令到达的时刻，而 `EndSession` 的结果本来就不变（D4） |
| 轮次开始写入账本 | 重启后可以只杀这一轮的进程。但会话本来就不跨重启，重启收口杀掉整个尝试已经覆盖轮次范围；为一份重启后无人使用的数据升级 schema 只增加迁移和单向兼容的成本（D6） |
| 按 Agent 进程的直接子进程或进程组划定豁免，而不是按 sid | 不依赖会话语义。但懒启动的 LSP 与工具 shell 都是 Agent 的直接子进程，工具 shell 也可能沿用进程组；只有 sid 能区分“在更早进程的会话里起的”和“新建会话的工作” |
| 清单只按（插件，版本）登记，栅栏对所有平台一体适用 | 登记更少。但栅栏只在 Linux 实现和实测，别的平台没有栅栏，按 Linux 结果放行会保留未验证的会话（D5） |

## 已知风险与待实测

| 风险 | 影响 | 处理 |
| --- | --- | --- |
| 某个 Agent 版本以新会话懒启动 LSP 或 MCP | 被取消的一轮里起的常驻进程被栅栏杀掉，下一轮功能退化；一致性测试的五个场景不专门构造懒启动，未必发现 | 实测的 OpenCode 0.6.11 把 `deno lsp` 留在自己的会话里；登记新版本时检查它的懒启动方式（D5 末段） |
| Agent 对子进程被杀作出反应，发出轮次流量 | 会话以 `turn_not_quiescent` 结束，本可保留的会话减少 | 这是设计上要捕获的违约；Claude 0.4.5 正是如此，不登记 |
| 多个会话同时结束，栅栏观察排在后面用满预算；或某次 `environ` 读取挂住 worker | 栅栏为 Unknown，会话以 `turn_processes_unstopped` 结束，F 内没有第二次机会 | 失败即封闭；worker 挂住时与标记决策 D2 的后果相同 |
| 一个更早会话的先前成员在这一轮全部退出 | 它在这一轮新起的成员被杀 | owner 接受的更保守代价（D1） |
| 从回应到杀掉之间的写入 | 下一轮看到被取消一轮写了一半的文件 | owner 已接受（D7）；栅栏与复扫完成前不派发下一轮 |
| 复扫排在其他会话的停止观察之后，超出 R | 复扫为 Unknown，本可保留的会话以 `turn_processes_unstopped` 结束 | 失败即封闭；R 只多 1 秒的结论期限（D2、D4） |
| Node 与 workload 不同用户、且 Node 没有 `CAP_SYS_PTRACE` | 豁免会话集合恒为空，这一轮留下的任何存活进程（包括懒启动的 LSP）都让栅栏为 Unknown，保留会话的取消总会结束会话 | 失败即封闭；部署前提见标记决策 D6，Desktop 与 cloud v2 当前满足（D7） |
| 冻结期间某个进程组成为孤儿进程组，而组内有被冻结的成员 | 内核向整组发 SIGHUP 与 SIGCONT，被冻结的进程被唤醒，在被杀之前可能 fork 出清空环境的子进程 | 继承自标记决策的冻结手段；唤醒的进程仍在冻结集合中，随后被 SIGKILL；漏掉的清空环境子进程属于标记决策 D6 的已知缺口 |
| 只在 x86_64、回环模型上测量 | aarch64、v2 的隔离部署与 model proxy 路径、真实模型下的行为未验证 | 登记键不含架构（D5）；部署时在 v2 上复测（落地顺序第 3 步） |
| `EndSession` 恰好落在并入取消的两次结算写入之间 | 同一次停止的并入取消一部分为 `stopped`、一部分为 `session_ending` | 窗口只在两次账本写入之间，会话仍以 `EndSession` 的原因结束；一次事务写完全部并入的取消留给后续修复（D4，[circus#1403](https://github.com/ora-space/circus/issues/1403)） |

## 验证义务

以下各条转为[轮次进程栅栏核心用例](../../../test-cases/node/protocol/turn-process-fence.md)，编号一一对应。取消决策的
验证义务 10、13 按本决策修改，在[取消一轮用例](../../../test-cases/node/protocol/cancel-turn-and-keep-session.md)中以
“（轮次进程栅栏）”行登记，不另占编号。证据按 desktop#807 的合并提交 `447a59de` 登记：栅栏用例的 21 项义务中 11 项
`Covered`、9 项 `Partial`、1 项 `Missing`；取消一轮用例的 10、19 为 `Covered`，13 为 `Partial`。缺口主要是：几种注入（包括复扫的扫描失败）只在栅栏层断言、没有经会话判定的测试；栅栏干净时命令是否落在栅栏期间、
栅栏是否不因命令中断都没有断言；记下轮次开始不扫描 procfs 只有间接证据；取消发起时 G + F + Q + R 的总期限没有断言；复扫
不干净时的并入取消与上文的已知窗口没有测试；账本 schema 不变只有结构性事实；一致性测试不在 CI 中运行。测试缺口由 [circus#1407](https://github.com/ora-space/circus/issues/1407) 承接，一致性测试的可重复证据由 [circus#1408](https://github.com/ora-space/circus/issues/1408) 承接。

1. 会话被保留的取消：这一轮工具起的新会话后台作业在 `TurnCancelSettled{stopped}` 写入之前已不在，之后不再写 checkout；
   下一轮的 prompt 在 `stopped` 之后才写出。栅栏干净之后，豁免进程（例如 Agent）不发轮次流量地新起一个 `setsid` 进程，
   在复扫时仍存活：会话以 `turn_processes_unstopped` 结束，不写 `stopped`，复扫不向它发信号，它由结束会话的停止杀掉。
2. 这一轮里 Agent 在自己的会话中懒启动的常驻进程在栅栏之后存活，下一轮找到的是同一个进程；轮次开始前已启动的进程
   （包括正常完成的一轮在自己的新会话中留下的作业）不收到任何信号，直到会话结束。
3. 收窄规则：范围内进程 fork 出、清空了环境的子进程经父进程被认领并被杀；更早进程会话中的后代不被杀；先前成员都
   不再被认领的会话不豁免任何进程；豁免会话只取自同一遍扫描中存活的更早进程。
4. 栅栏不干净：持续出现新的范围内进程直到 F 用完、范围记录缺失、扫描失败或待定进程、观察超出预算、没有开始时刻、
   尝试在这一轮里被替换。每种情况都以 `turn_processes_unstopped` 结束会话，并入的 `CancelTurn` 得到 `session_ending`，
   之后没有 `session/prompt`；终态在停止整个尝试、取得停止证据之后才写入。
5. 先后与期限：选择、登记或静止条件 2 不满足时不运行栅栏；栅栏期间到达的轮次流量使会话以 `turn_not_quiescent` 结束；
   Q 从栅栏干净时起算，复扫在 Q 与空闲期流量检查之后、`stopped` 之前；栅栏或复扫期间受理的 `CancelTurn` 与这次停止同一结论；栅栏或复扫期间的 `EndSession` 在它返回后优先，复扫期间受理时不写 `stopped`；
   结论在 G + F + Q + R 内落账（失败发起时自回应起 F + Q + R）。
6. 一轮正常完成后不发任何信号，它的后台作业进入下一轮；没有选择保留、或版本未为本平台登记的会话不运行栅栏。
7. Node 在一轮开始之后、栅栏之中，以及 `TurnCancelSettled{stopped}` 写入之后被杀并重启：会话以 `interrupted` 结束，未结算的
   `CancelTurn` 得到 `session_ending`，被冻结或仍存活的本轮进程在重启收口中被杀，账本 schema 版本不变。
8. 伪造本尝试标记、在轮次开始前启动的进程不收到信号；在轮次开始后启动、在新会话中的伪造进程被杀；持续 fork 的伪造者
   只让会话以 `turn_processes_unstopped` 结束，不会在它存活时保留会话。

取消决策验证义务的修改：

- **10**：Agent 的（插件，版本）只为其他平台登记时，一轮取消或失败后会话以 `turn_boundary_unverified` 结束，栅栏不运行。
- **13**：一致性测试按（插件，版本，平台）经真实 Node 的栅栏运行，场景与通过条件见 D5；Linux 上的 OpenCode 0.6.11 通过后
  才登记，Claude 0.4.5 不登记。

## 本决策未解决的问题

- **Claude 插件**：被杀的后台任务之后自发起一轮，栅栏无法消除；A2 与新插件版本的登记由 circus#1381 承担。
- **Windows Node**：ora-node 还没有 Windows 版；Windows 上的栅栏（例如私有 Job Object 加进程创建时间）需要实测后另立决策。
- **豁免会话中代办的工作**：MCP 服务、LSP 或宿主代这一轮起的后台进程不在范围内，需要能区分“谁请求的”来源，超出进程
  属性能表达的范围。
- **清空环境后成为孤儿的进程与 Strong 纳管**：沿用标记决策的未解决问题，需要 cgroup 或 subreaper。
- **用过子代理的轮次**：仍由取消决策静止条件 2 排除，栅栏不改变它。
- **用户希望跨取消存活的服务**：目前只能在之前的一轮或 Ora 之外启动；是否提供显式保留的方式，留给后续决策。
- **会话跨 Node 重启保留**：若将来允许，必须持久化或重建轮次开始（D6）。
