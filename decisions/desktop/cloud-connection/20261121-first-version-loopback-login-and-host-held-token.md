# Desktop Cloud 连接第一版：经系统浏览器与回环地址登录 v2-server，令牌只在宿主与系统安全存储并绑定登录时的 Cloud 地址；部署身份、自签证书与内网 HTTP、会话轮换与活动上报、deep link 暂停

Desktop 宿主让用户填一个 Cloud 地址，点「登录」后用系统浏览器打开该 Cloud 的确认页，借浏览器里的网页会话（以及企业的
单点登录）由用户点「允许」，再经本机回环地址和 PKCE 换到一个 desktop 令牌。令牌只在 Rust 宿主内存和操作系统的安全存储
里，只发往登录时的那个 Cloud 地址；前端和插件只看到连接状态和显示名。Cloud 返回 `401` 时宿主清掉令牌、提示重新登录，
网络错误和 5xx 只显示“连不上”。没有配置或登录 Cloud 时，本地功能照常可用。可观察的变化：

- 设置里多出「Cloud 连接」：地址、登录 / 取消 / 退出登录，以及状态（未配置、未登录、登录中、已登录为某人、连不上、
  需要重新登录、系统安全存储不可用）。
- 开发版（`V2_LOGIN=email`）和部署版（华为 IDaaS）用同一套 desktop 流程：desktop 只依赖“浏览器里有网页会话”，不关心
  网页用哪种方式登录。

本 ADR 为 `implemented`：owner 2026-11-23 在 ora-space/specs#324 批准，由 cloud#432（`v2-server` 与 `frontend-v2`）和 desktop#806 实现（ora-space/circus#1379），本文已按两者的最终实现同步，验证见文末“落地顺序：实现与验证”。
它是 [宿主连接根决策](0-host-owned-cloud-connection-and-session.md)（下称“根决策”）的后续 ADR，按
[登录与会话根决策](../../cloud/login/0-idaas-or-email-login-with-shared-web-and-desktop-sessions.md)（下称“A6”）D6 的安排写
desktop 一侧的规则。依据是 owner 2026-11-12 在 ora-space/circus#1084 定的第一版范围（填地址、系统浏览器登录、回环回调、
系统安全存储、显示连接状态与登出、Cloud 吊销后提示重新登录；deep link、内网 HTTP、自签证书信任、换地址迁移、会话轮换
不做）。同步时读取的版本为合并后的 desktop `7fc4544f`（ora-space/desktop#806）、cloud `1635cc7d`（ora-space/cloud#432）。

- **涉及**：desktop 宿主（`apps/desktop/src-tauri`）、契约与逻辑操作（`crates/contracts`、`xtask`）、本地配置
  （`crates/user-config`）、通用 HTTP 能力（`crates/utils`）、app-shell 的设置界面与中英文文档。
- **Cloud 一侧不在本文**：确认页、一次性授权码、换令牌、令牌的存储与过期、`Bearer` 优先的认人规则都由 A6 D6 规定，由
  cloud 的 `v2-server` 实现（ora-space/cloud#432）。本文只引用它对 desktop 可见的部分。
- **协议权威**：根决策开头把 [Gateway 原生会话 ADR](../../cloud/identity-access/20261019-deployment-bound-desktop-sessions.md)
  认作认证与会话协议的唯一权威。v2-server 不实现那份协议（A6 取代了 v1 Gateway 的 desktop 会话），本文起 desktop 与
  Cloud 之间的协议以 A6 D6 为准。
- **形态**：只修改根决策的部分条目，根决策保持 `approved`，它的本地独立、宿主所有、插件拿不到凭据等规则继续有效。根决策
  里依赖部署身份和轮换的条目（部署签名身份、TOFU、能力协商、证书固定与内网 HTTP、同身份换地址迁移、活动上报与轮换恢复、
  60 秒发现吊销）**暂停**：A6 已经放弃了它们所依赖的服务端协议，要恢复，需要在 `cloud/login` 和
  `desktop/cloud-connection` 两侧各写后续 ADR，不能凭根决策的 `approved` 直接实现。根决策标题下的
  `> 历史决策：` 指向本文。
- **不做数据迁移**：desktop 现在没有任何 Cloud 连接、账号或令牌数据；本文新增一个本地配置项（Cloud 地址）和一个系统
  安全存储条目，不改动已有的本地文件、模型连接、Agent 凭据和 Git 身份。

## 防什么、不防什么

本文防的是令牌落进不该去的地方：webview 与页面脚本、插件、日志与诊断、URL、明文配置，以及登录时那个 Cloud 以外的
服务器（包括经重定向）。

本文**不防**同一操作系统用户下的本机进程。这类进程能读 Windows 凭据管理器里本用户的条目和已解锁的 Secret Service
条目，能读宿主内存，也能自己发起一次回环登录：确认页分辨不出是哪个本机程序发起的（RFC 8252 §8.6），用户点了「允许」，
令牌就给了那个程序。第一版的确认页写明“允许 Ora desktop 以某人的身份登录”，用户只应在自己刚点过 desktop 的「登录」时
点「允许」。能以同一用户身份运行任意程序的攻击者本来就能读本地工作区和 Agent 凭据，这不是 Cloud 连接新增的暴露面。

## 决策

### D1：Cloud 地址规范化为 origin，HTTPS 是默认要求

- 用户在设置里填 Cloud 地址，宿主把它规范化为 `scheme://host[:port]`：没写协议的补 `https://`，主机名小写，去掉默认
  端口。拒绝用户名密码、查询串、fragment 和除 `/` 以外的路径。v2-server 只接受根地址作为 `V2_PUBLIC_URL`（A6 D2），
  desktop 不需要路径前缀。
- 只接受 `https`。例外：主机是回环地址（`localhost`、`127.0.0.0/8`、`::1`）时也接受 `http`，只为本机开发；它不是根决策
  D4 的“显式内网 HTTP”，局域网和内网地址仍要 HTTPS。
- 地址存在本地配置里（它不是秘密）。改地址或清空地址时，先取消进行中的登录，再删除并尽力吊销旧地址的令牌（顺序同 D6）；
  吊销没确认时同样提示“服务端撤销未确认”。新地址需要重新登录。

为什么不带路径：带路径就要处理同一主机上多个 Cloud 共享 Cookie 与回调的问题，而 v2-server 不支持路径前缀部署。
为什么回环地址允许 HTTP：本机开发的 v2-server 没有证书；流量不出本机，不存在被窃听的网络。为什么 Cloud 地址可以写
`localhost`、回调地址却不行：回调地址由浏览器解析，浏览器可能把 `localhost` 解析到 `::1`，和宿主监听的 `127.0.0.1` 对不上
（D2）；Cloud 地址由宿主自己解析和连接，解析到哪个回环地址都连得上。让 `localhost` 解析到别处要改 hosts 文件，那已在
“不防什么”之内。

### D2：登录事务经系统浏览器和本机回环地址完成

1. 宿主在 `127.0.0.1` 上监听系统分配的端口（不监听 `0.0.0.0`），生成 32 字节随机 `state` 和 PKCE verifier（base64url），
   用系统浏览器打开 `<origin>/desktop/authorize?redirect_uri=http://127.0.0.1:<端口>/callback&state=…&code_challenge=…&code_challenge_method=S256`。
2. 之后的网页登录、确认页、“允许”和一次性授权码都按 A6 D6，由 Cloud 完成。用户在确认页点「取消」时，Cloud 把浏览器
   送回同一个回环地址并带上 `error=access_denied` 和 `state`，desktop 立即以“已在浏览器中取消登录，或授权没有完成”结束事务，不必等超时。
3. 回环监听只认 `GET /callback` 且 `state` 一致的请求：路径或 `state` 不对的回 `404`，事务继续等；对的那一个结束事务——
   带 `code` 就回一个不含脚本的静态页“已收到授权，请回到 Ora”，然后换令牌；带 `error` 或没有 `code` 就回一个静态页“登录没有完成，可以回到 Ora 重试”，并以失败结束。
   回调页不说“已登录”：换令牌还没发生，可能因为连不上或授权码失效而失败，结果显示在 desktop 里。
4. 换令牌只发往事务记录的 origin，带上授权码、verifier 和同一个回调地址。
5. 一个安装同时只有一个登录事务；再点「登录」会取消前一个。事务 5 分钟超时，用户可以取消。成功、失败、取消、超时和
   退出程序都会关闭监听、丢弃 verifier。宿主不会自己重新打开浏览器。授权码到手后，换令牌和写入安全存储在一个不受取消
   打断的后台任务里完成；写入前后都在安全存储锁内核对“代”（D5）。这时已取消（或改地址、再点「登录」）的，不写入或删除
   刚写入的条目，再尽力吊销这个令牌：不会留下没人吊销的令牌，也不会碰到更新一次登录写入的条目。

“限制次数”的含义：每个事务只接收一次合法投递，之后监听关闭；路径或 `state` 不对的请求不计次数，只受每个连接的请求头
读取时限和大小上限约束。

事务结束后（超时、取消或在 desktop 里又点了一次「登录」）再在旧的确认页点「允许」：浏览器被送往已经关闭的端口，显示
连不上本机地址；授权码没人兑换，2 分钟后在 Cloud 失效。网页侧不提供“返回 desktop”的入口，用户回 desktop 重新点
「登录」。如果那个端口这时恰好被别的本机程序占用，它会收到授权码，但拿不到 verifier，换不出令牌。

为什么路径或 `state` 不对时不结束事务：本机任何程序都能访问这个端口，让它们能一次请求就打断用户的登录没有好处；它们
拿不到 verifier，也就换不出令牌。为什么写 `127.0.0.1` 而不写 `localhost`：浏览器可能把 `localhost` 解析到 `::1`，和
宿主监听的地址对不上（RFC 8252 §8.3）；Cloud 一侧也不接受 `localhost` 回调。为什么确认页的「取消」要回到 desktop：
否则 desktop 要白等 5 分钟；Cloud 校验回调地址只能是回环地址，这个跳转不会变成任意地址的开放跳转。

### D3：令牌只在宿主和系统安全存储

- 令牌存进操作系统的安全存储：Windows 凭据管理器、Linux Secret Service（desktop 只发行这两个平台）。条目的作用范围是
  “操作系统用户 + Cloud origin”：以 origin 为键，同时存账号 id 和显示名，让界面在 Cloud 回答之前就能显示“已登录为
  某人”。宿主内存里持有当前令牌，进程重启后从安全存储读回，读回之前本地功能已经可用。
- Windows 上条目只保存在本机（`CRED_PERSIST_LOCAL_MACHINE`），不随漫游配置文件同步到其他电脑：令牌代表“这一台
  desktop”，退出登录只影响这一台（D6），同步出去就会出现别的电脑在用、这台退出时又把那边一起删掉的情况。宿主经 Win32
  凭据接口直接写这个条目（目标名 `<origin>.space.ora.desktop.cloud`），因为 `keyring` 库在 Windows 上固定写会漫游的
  `CRED_PERSIST_ENTERPRISE`；Linux 经 `keyring` 写 Secret Service（服务名 `space.ora.desktop.cloud`、账号为 origin）。
  安全存储的读写不在异步工作线程上执行，所有读写经同一把锁串行，检查、登录落定、退出和改地址不会交错地读写同一条目。
- 开发版（`task run:desktop` 设了自己的 `ORA_DATA_DIR`）和正式包的本地配置各自独立，但条目只按“操作系统用户 +
  origin”区分，两者共用：在开发版里对同一 origin 退出或登录，会删除或覆盖正式包的条目。按应用标识判断的单实例插件阻止
  两者同时运行，所以不会有两个宿主同时读写这个条目。第一版接受这个后果：开发版只给开发者用，分开的条目属于根决策 D3
  暂停的“开发包与正式包隔离”。
- 令牌不进本地 SQLite 配置、webview、日志、诊断包和任何 URL。所有发往 Cloud 的请求都由宿主发出；前端只经宿主命令拿到
  `{状态, Cloud 地址, 显示名}` 和受限操作（设置地址、登录、取消、退出登录），这些命令只授权给主 webview，插件 webview
  不能调用。
- 安全存储不可用（例如 Linux 没有运行 Secret Service）时，状态显示“系统安全存储不可用”和原因，云端功能不可用，本地
  功能照常；不降级为明文保存，也不在内存里“只这一次”地保持登录。

安全存储读写失败的路径：

| 时机 | 宿主行为 |
| --- | --- |
| 换到令牌后写入失败 | 尽力调 desktop 登出接口吊销刚签发的令牌，不在内存里保持登录，显示“系统安全存储不可用”和原因 |
| 退出登录时删除失败 | 照样用内存里的令牌吊销，状态显示“系统安全存储不可用”和原因（不显示成已退出） |
| 改地址时删除旧条目失败 | 只记日志，照样用内存里的令牌请旧服务器吊销，吊销结果照常回报；旧条目以旧 origin 为键，新地址读不到它，保持未登录 |
| 收到 `401` 后删除失败 | 只记日志，状态照样转为需要重新登录 |

删除失败留下的条目会在下次启动时被读回，宿主照常检查：令牌已吊销或已失效就得到 `401`，再删一次。
只有删除失败且吊销也没确认时，残留的令牌下次启动仍然有效；这时界面已经同时提示了“安全存储不可用”和“服务端撤销
未确认”，用户可以在凭据管理器或钥匙环里手动删除。第一版不为此另建“待删除”标记：那个标记只能写在本地配置里，而能
写本地配置却删不掉安全存储条目的情形，用一次启动检查就能收尾。

为什么前端不直接请求 Cloud：令牌一旦进 webview，页面里的任何脚本和插件页面都可能读到一个 30 天有效的令牌，违反根决策
不变量 2；desktop 的前端现在也不发任何网络请求，全部经宿主命令。为什么安全存储不可用时不退回内存登录：用户会以为下次
启动还在登录状态，而且每次启动都要重新打开浏览器，不如明确告诉用户缺什么。

### D4：令牌只发往登录时的 Cloud origin，传输只信系统信任库

- 宿主用于 Cloud 的 HTTP 客户端不跟随重定向：任何 3xx 都按“连不上”处理（D5），令牌不会被带到另一个 origin。
- TLS 使用操作系统的信任库（desktop 已用的平台证书校验）。企业私有 CA 只要装进系统信任库就能用；第一版不提供“信任这个
  自签证书”的入口，也不关闭证书校验。浏览器不信任 Cloud 证书时登录页本身打不开，desktop 同样不绕过。
- 代理按环境变量：客户端先关掉 HTTP 库自己从环境变量取代理的行为，只用宿主按规则选出的那一个——Cloud 地址是回环地址
  或命中 `NO_PROXY` 时直连，否则走 `HTTPS_PROXY` / `HTTP_PROXY`，都没有时退到 `ALL_PROXY`。不用设置里的网络代理：那个设置只作用于选择使用它的 marketplace 源，强加给内网
  Cloud 反而可能连不上。

这条代替根决策不变量 3 的“部署签名身份”：v2-server 没有部署签名身份（A6 D7），第一版能守住的是“令牌只发给用户登录时
确认过的那个地址”。代价是：同一地址被别的服务接管、而它又持有系统信任的证书时，desktop 分辨不出来——这在只连系统信任的
HTTPS 时等价于浏览器的信任边界。回环地址必须直连：开发时常设了 `HTTP_PROXY` 而 `NO_PROXY` 不含回环地址，走代理就会把
`http://` 上的令牌明文交给代理。

### D5：`401` 才清令牌，其余错误只表示连不上

| Cloud 的回答 | 宿主行为 | 状态 |
| --- | --- | --- |
| `2xx` | 正常 | 已登录为某人 |
| `401` | 删除安全存储里的令牌和内存里的令牌 | 需要重新登录 |
| 网络错误、超时、TLS 错误、3xx、`5xx` | 保留令牌 | 连不上（仍显示上次的账号） |
| 其他 `4xx` | 只是这一个请求的错误，不改变会话状态 | 不变 |

宿主在启动时（异步，不阻塞本地就绪）和主窗口回到前台时（两次至少间隔一分钟）调一次 `GET /api/v1/me`；之后的云端功能
发出的任何请求遇到 `401` 也按上表处理。令牌在 Cloud 一侧失效的情形只有 A6 D6 列出的几种：desktop 自己退出登录、连续
30 天没用、账号被停用或删除。desktop 在下一次检查或请求时发现，第一版不承诺发现的时限。

`401` 只对发出请求时的那个令牌生效：宿主核对“代”没变、当前令牌仍是发请求时的那一个，才转为需要重新登录；随后在安全
存储锁内再核对一次，仍是这次结束的会话才删除条目。检查发出后用户退出、改地址或重新登录过，迟到的 `401` 什么也不做，
不会删掉新登录写入的条目。

**检查也算使用**：这次检查是带令牌的请求，v2-server 把它和其他请求一样算作使用，距上次刷新超过 1 小时就把过期时间
顺延到 30 天后（A6 D6）。owner 接受这一点：打开 desktop 本身就是真实的使用，空闲过期要防的是被弃用的设备；不为此新增
一个不刷新使用时间的检查接口。后果：

- 过期的实际含义是“这台 desktop 30 天没启动、也没回到前台”。由于按小时刷新，令牌在最后一次刷新后 30 天减 1 小时到
  30 天之间过期。
- 没有绝对上限：至少每 30 天打开一次的 desktop 会一直保持登录，结束它要靠 desktop 上退出登录或停用账号；第一版没有
  列出和远程吊销 desktop 登录的入口（A6 第一版不做）。

为什么检查而不是轮询：第一版的 desktop 还没有长期在线的云端功能，定时轮询只为提早几分钟发现失效，代价是每台机器常驻
请求；启动和回到前台正好是用户要用云端功能的时候。为什么唤醒和网络恢复不单独检查：唤醒后用户要用 desktop 就会把窗口
切到前台，那时检查一次；没有要恢复的云端操作，提前检查没有收益。

### D6：退出登录只影响这一台 desktop

退出登录时宿主先删除安全存储条目、清内存状态，再用内存里的令牌调 Cloud 的 desktop 登出接口吊销它。登出请求失败
（连不上、超时）也照样清本地，并提示“已在这台电脑退出，服务端撤销未确认”；不保留令牌作重试队列。网页会话和其他设备
的 desktop 令牌不受影响（A6 D6），本地文件、工作区、模型连接、Agent 凭据和 Git 身份都不动。删除失败时按 D3 的表处理。

为什么改成先清本机、再吊销（根决策 D6 是先撤销再清本机）：吊销请求用的是内存里的令牌，不需要条目还在；先删条目，吊销
请求挂起、超时或程序在中途退出时，本机都已经不再持有令牌。反过来先吊销，连不上时要么保留令牌（用户点了退出却没退出），
要么照样删除（和先删结果相同），还多了一段“已决定退出、条目仍在”的窗口。

## 第一版不做（暂停）

以下根决策条目暂停；要恢复，需要在 `cloud/login` 和 `desktop/cloud-connection` 两侧各写后续 ADR。

- 部署签名身份、TOFU、能力协商与最低兼容版本检查（根决策 D3、D4；A6 D7）。
- 自签或私有 CA 证书的固定与确认、显式内网 HTTP、同身份换地址迁移（根决策 D4）。
- 活动上报、续期、轮换与轮换恢复、在线 60 秒内发现吊销（根决策 D5；A6 D7）。
- deep link 回调（根决策 D3）。
- 开发包与正式包分开的连接和凭据（根决策 D3）。

另外不做：同时连多个 Cloud 或多个账号；列出和远程吊销自己的 desktop 登录；读取系统代理或 PAC 脚本（desktop 现有代理
能力的限制）。

## 不变量

1. Cloud 未配置、未登录、连不上或令牌失效，都不阻塞本地启动、编辑和 Agent 运行。
2. desktop 令牌只存在于宿主内存和系统安全存储；前端、插件、本地配置、日志和 URL 里都没有它。
3. 令牌只发往登录时规范化的 Cloud origin；宿主不跟随重定向，不把令牌发给改过的新地址，回环地址的请求不经代理。
4. 只有 Cloud 对当前令牌回答 `401` 才清除令牌；网络错误、超时、3xx 和 5xx 不改变登录资格，迟到的 `401` 不影响之后的
   登录。
5. 同一时刻只有一个宿主进程（单实例插件按应用标识判断，开发版与正式包也不同时运行）、至多一个登录事务；回环监听只绑定回环地址，事务以任何方式结束都会关闭监听。
6. 安全存储不可用时不以明文或其他位置保存令牌，也不在内存里保持登录。
7. 退出登录和改地址只结束这台 desktop 的这一个令牌；网页会话、其他设备和本地工作不受影响。

## 为什么不是这些替代方案

| 方案 | 优势 | 否决理由 |
| --- | --- | --- |
| 新写一份根决策取代根决策 | 读的人只看一份 | 根决策的本地独立、宿主所有、插件拿不到凭据等规则仍然有效；取代会把它们一起作废，再原样抄一遍 |
| 令牌交给前端直接请求 Cloud | 前端调用简单 | 令牌进 webview，页面脚本和插件页面都能读到（不变量 2）；还要 v2-server 为 webview 的源开 CORS、放宽 `Origin` 校验 |
| 用现成的 Tauri OAuth 插件接回调 | 少写一个本地监听 | 这类插件把回调地址交给前端，授权码会经过 webview；也不限制路径、`state` 和次数 |
| 令牌存加密文件（口令派生密钥） | 不依赖系统服务 | 口令本身还得存进安全存储或让用户每次输入，等于没有解决问题，也不是“只进系统安全存储” |
| deep link 回调 | 不占本地端口 | 要在每个平台注册 scheme，会被其他应用抢注；A6 D6 已选回环地址 |
| 设备码（在浏览器里输入短码） | 不需要本地监听 | 多一步手工输入；A6 没有提供设备码接口 |
| 定时轮询检查令牌 | 失效发现更快 | 第一版没有常驻云端功能，代价大于收益（D5） |
| Cloud 加一个不刷新使用时间的检查接口 | 过期严格等于“30 天没用过云端功能” | 打开 desktop 就是真实使用；多一个接口、两种“使用”的定义，换来的只是让偶尔打开 desktop 的人被登出（D5） |
| Windows 条目随漫游配置文件同步 | 换电脑不用重新登录 | 令牌代表一台 desktop，同步后退出一台会删掉另一台的条目，也和“只影响这一台”冲突（D3） |

## 本决策未解决的问题

1. **部署身份与内网证书**：第一次内网部署（ora-space/circus#1059）的 TLS 方式还没定。如果员工电脑不信任内网 CA，浏览器和
   desktop 都会连不上；那时再决定是在部署侧解决证书信任，还是另写后续 ADR 引入证书固定或部署身份。
2. **云端功能接入**：工作流下发、运营统计等以后的云端功能怎么经宿主调用 Cloud（命令形态、缓存、订阅、失败重试），由那些
   功能各自的决策规定；本文只规定它们共用这一个令牌和 D5 的错误分类。
