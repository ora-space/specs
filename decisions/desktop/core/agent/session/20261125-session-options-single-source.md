# 会话选项以 session actor 为唯一来源，设置的响应也走会话事件流，取代返回值写选项

Agent 会话的选项（模型、推理强度等）由该会话的 actor 持有，actor 是当前选项的唯一来源。设置选项的响应和 Agent 主动推送的
选项走同一条会话事件流，actor 按宿主收到 ACP 帧的先后处理，再送给客户端视图。`setSessionConfig` 的返回值只表示成功或
失败。每次采用选项，宿主都用现有的应用级广播通知「会话选项已变」；没有流的视图收到后从 actor 取当前选项，不新建通道。

行为变化：响应早于或晚于推送到达界面，结果都一样；视图不再把设置的返回值当作当前选项写入；会话失去 provider 后，视图
记下这一状态，用户再选模型就是记下次附着的意图，不再向已停止的会话发设置请求。

本文已 `implemented`，描述最终系统承诺。只定三件事：当前选项的唯一来源（D1）、按什么顺序处理（D2）、怎么送达（D3）。

- **涉及**：`ora-agent-runtime` 的 actor 与会话路由、公共契约里的 `setSessionConfig` 和 `AppEvent`、Desktop 宿主的应用
  事件、前端会话 store 与选择器。
- **兼容边界**：没有持久化数据，不需要迁移；ACP 与插件契约不变，Agent 不需要改动。
- **不涉及**：会话何时连接 Agent、附着与重建的条件、会话前发现、命令列表的送达、历史记录的内容。

## 背景

设置选项时，Agent 的答复作为 `setSessionConfig` 的返回值到达前端，Agent 自己推送的 `config_option_update` 经会话事件流
到达。两条路没有共同的先后，前端按到达顺序写，晚到的旧值会盖掉新值。宿主里同样有两条路：答复经命令队列交给 actor，推送
经事件队列；没有回合时，推送还会转成一条命令排到命令队列末尾，落到更晚的答复之后。

| 编号 | 场景 | 结果 |
| --- | --- | --- |
| P1 | Agent 先答复 B、再推送 C；前端先收到 C、后收到 B | 界面显示 B，Agent 实际是 C |
| P2 | 建会话时带模型意图，短收集窗口之后、设置答复之前到达的旧推送 | 旧推送在答复之后被采用，之后的加载得到旧值 |
| P3 | 会话空闲，旧推送转成命令，排在「采用答复」之后 | 旧推送盖掉答复 |
| P4 | 设置期间会话被重建，旧 provider 会话的答复晚到 | 调用方曾得到旧会话的值；现有实现已改为返回替代会话的选项 |
| P5 | 标题轮询期间收到的选项推送先被采用，又留到下一回合开头重放 | 期间用户的设置被重放的旧推送盖掉，视图也收到旧值 |
| P6 | 恢复会话时应用模型意图，恢复答复之后、意图答复之前到达的推送留在事件队列里 | 推送在意图答复之后才处理，盖掉意图答复 |
| P7 | 会话已附着时的 prompt 流开头不带当前选项，失去 provider 后视图也不知道 | 视图没有可靠的起点；选择器继续向已失去 provider 的会话发设置请求 |

都只影响显示，不改变 Agent 实际使用的选项。P1 在前端复现过，P4 有用例；其余按代码推断，没有
复现；没有在真实 Agent 上观察到。P7 不是排序问题，但 D3 的规则依赖它。

## 术语

会话选项（`Session Options`）和 `Agent Binding`（下文简称绑定）见[词汇表](../../../../../domain/glossary.md#agent-conversation)。

- **视图**：持有一份会话副本的前端状态。一个视图可能正在接收这条会话的加载流或 prompt 流，也可能没有流。现在 Desktop 只有一个
  主窗口、一份会话副本，模型和推理强度选择器共用它；规则按可以有多个视图来写。
- **有 provider**：actor 持有该会话的 provider 通道，包括被进行中的操作占用的通道。不按选项是否为空判断。

## 决策

### D1：actor 持有当前选项，视图只持有副本

1. 会话有 provider 时，当前选项只由该会话的 actor 持有。新视图加载、正在跟随的视图、没有流的视图取到的都来自这一份。
2. 选项只由这些 ACP 帧更新：`session/new` 和 `session/load` 的答复（包括刷新 MCP 时的 `session/load`）、设置选项的答复、
   `config_option_update`。带选项的帧都是完整集合，整体替换，不逐项合并；空集合也是一份选项。
3. 只采用属于当前绑定的帧。绑定已更换时，旧 provider 会话晚到的答复和推送都不改变当前选项（P4）。
4. `setSessionConfig` 的返回值只表示成功或失败，契约中不再带选项。Agent 答复了就是成功，哪怕它没有照用户所选的值生效，选择器
   显示 Agent 报告的值；Agent 返回 ACP 错误是失败。答复属于当前绑定时，actor 处理完它之后才返回成功。
5. 同一会话的多个在途设置不串行，最终值由 Agent 答复的先后决定，每个调用的成功只表示 Agent 处理了它。
6. 设置超时按失败返回，绑定不变时，之后才到的答复仍按 D2 采用，因为 Agent 可能已经生效。
7. 会话没有 provider 时没有当前选项，设置请求返回失败（沿用现有错误码 `session_stopped`，不新增错误码）。没有 provider 时选择模型，
   或模型设置因失去 provider、在写给 Agent 前遇到 `Stop` 而收到该错误时，视图只记为下次附着的模型意图，不报错。推理强度不记意图（D3.6）。
8. 视图不把设置的返回值当作选项写入，也不按用户点击的值乐观写入会话副本；选择器可以在「进行中」显示所选的值。启动会话和切换 Agent 的返回值仍带选项，视图把它当作一次
   取回的结果，按 D3.5 处理。

为什么：顺序问题出在有两个写入者。只留一个持有者，视图就不需要各自判断新旧；答复先由 actor 处理再返回，保证调用成功之后
打开的视图能看到这次改动，这一点和现有行为相同。

**在途设置的收尾**：actor 释放或替换绑定时，旧通道不再有人读，途中的答复无法再到达，因此由 actor 自己结束在途设置，不等答复。
规则是：由我们主动放弃绑定的，成功；由 Agent 失联或失控而失去绑定的，失败。

| 原因 | 在途设置返回 | 理由 |
| --- | --- | --- |
| 会话被重建 | 成功，视图得到替代会话的选项 | 用户选的值不在替代会话上重发，也不报错，和被拒绝的设置照样成功同一语义 |
| `Stop` 命令：用户停止、切换 Agent、删除会话 | 成功 | 设置已经发给 Agent，停止不把它变成失败；切换和删除到原来的 actor 都只是 `Stop` |
| 流的接收方放弃 | 成功 | 不是 Agent 的问题，同上 |
| Agent 失联或失控：事件队列溢出、连接断开（包括 Agent 进程被替换）、不活跃超时、取消无应答、刷新 MCP 失败 | 失败 | 不知道 Agent 是否生效，也没有后续事件可以更正 |

Agent 进程被替换不再有独立事件，只表现为连接断开，故并入断连，以断连用例作代表，没有单独的进程替换用例。积压时「流的接收方放弃」
与「事件队列溢出」可能同时成立，按先检测到的原因收尾。

### D2：响应和推送按宿主收到 ACP 帧的先后处理

1. 同一绑定内，答复和推送进入同一条有序的会话事件流，先后以宿主从该连接读到帧的先后为准，actor 逐个处理。
2. 顺序在任何时候都成立：回合中、空闲、标题轮询、MCP 刷新，以及建立和恢复会话的阶段（P2、P3、P5、P6）。不得把其中一类帧改走另一条
   队列，再插回到别的帧之后。
3. 建立或恢复会话时应用模型意图的答复和其他设置的答复同等对待：在它之前到达的推送，不会在它之后被采用或送给视图（P2、P6）。
   留到以后再送的更新不含选项，选项不重放（P5），需要时按 D3.2 给出 actor 的当前选项。
4. 绑定之间没有先后比较。换绑定时当前选项由新绑定建立或恢复的答复重新确立，旧绑定的帧按 D1.3 处理。

为什么：同一连接上读帧的先后是宿主能得到的、最接近 Agent 更新先后的唯一事实。按处理时刻、墙钟时间或到达前端的时刻排序，都会
引入第二个顺序。需要应答的请求已有「答复随会话事件有序送达」的机制，设置选项改用它即可，不需要新的排序字段。

| Agent 发出的顺序 | 当前选项 |
| --- | --- |
| 答复 B → 推送 C | C |
| 推送 C → 答复 B | B |
| 旧推送 A → 答复 B（建立或恢复会话的模型意图） | B |
| 标题轮询中推送 A → 设置答复 B → 下一回合开始 | B |
| 旧绑定的答复 A，在换绑定之后到达；新绑定报告 B | B |

### D3：有流随流送达，没有流的视图靠应用级广播通知后再取

1. 有进行中的加载流或 prompt 流时，actor 每采用一个携带选项的帧都按处理的先后随流送出，不比较值是否变化，接收该流的视图按流内先后
   写入。
2. 会话有 provider 时，每条会话流（加载、跟随、prompt）开头都带 actor 的当前选项，包括空集合；会话在 prompt 受理前已经附着
   也一样。没有 provider 时不带，视图由取回的结果得知。
3. actor 每采用一个携带选项的帧，不比较值是否变化，以及会话变为「没有 provider」时，宿主都发出应用级广播「会话选项已变」，参照现有的会话标题更新通知，只带 Ora
   会话 id，不带选项。不看会话当时是否空闲，不新建通道。
4. 没有流的视图收到广播后，用只取选项的只读查询从 actor 取，得到当前选项，或「没有 provider」。查询不回放历史，也不等
   回合结束：回合、MCP 刷新、标题轮询期间立即答复；附着、恢复、建会话、加载回放、取消结算、关闭会话等步骤不读命令，完成后答复。
   不用加载代替它：加载会回放全部历史，还会清掉对话里的「已切换模型」标记。
5. 取回的结果和流之间的先后由视图按下面的规则保证，不加版本号：
   - 同一会话同时只有一次在取；取的期间收到广播，取完再取一次。
   - 取的期间从流收到选项，或开始接收流，就丢弃这次结果。
   - 有流的视图收到广播不立即取，只记下。流结束时，若期间记下过广播，或流没有送来选项
     （例如没有 provider 时的加载），就取一次。空集合也算送来了选项。
6. 视图得知「没有 provider」就记下这一状态，不清空最后的选项。可设置的模型选择器按这个状态（不按选项是否为空）改为「记为下次附着的
   意图」，不再用最后的选项；工作流节点的只读选择器继续把最后的选项作标签显示。从流或取回的结果得到选项，就解除这一状态。
   推理强度没有意图通道，下次附着不会带上它，所以没有 provider 时隐藏推理强度控件；工作流节点的只读推理强度控件仍显示最后的强度。
7. 发起设置的视图何时结束「进行中」：调用失败就结束；调用成功后，没有流时主动取一次，有流时按流内的选项。成功，且请求发出后收到过
   选项或得知「没有 provider」，就结束；没有流时以成功后取的这一次为准。值没有变也算收到。成功时有流、
   流结束时仍未满足的，从流结束起就是没有流，同样取一次；流结束时已按第 5 点在成功之后取的，就用那一次。设置成功后的那次读如果失败，
   「进行中」也结束，界面停在原来的选项上，不重试。

   「已切换模型」标记由发起设置的视图在结束「进行中」时记：模型和发起前不同就记一次。没有设置在途时，Agent 自己改的模型不记。切换
   Agent 的标记沿用现状。设置在途时的推送可能使视图略早结束，或使标记归到用户、漏记，只影响显示。

   同一会话重叠的多个设置共用一个基准：这组首个设置发起前的模型。每个成功结束的设置按当前模型判断标记：偏离基准就记下或替换这组的标记，
   回到基准就撤掉这组自己的标记。替换和撤掉只针对这组设置自己留下的标记，不影响之前已结束设置在同一位置的标记：一组设置替换掉更早设置
   在同一位置的标记时先记下它，撤掉自己的标记时再放回去；放回前按位置（`afterTurnCount`）判断同一位置是否已有更新的标记（如切换 Agent 刚
   写入的），有就不覆盖。失败只结束该次设置，不改变这组的基准和标记；组内所有设置都结束后，下次设置才重新取基准。
8. 广播是尽力而为的失效通知，可能丢失或合并。视图（重新）订阅应用事件之后，对正在展示的会话重新取一次，补上断开期间的变化。
9. 广播和查询都是只读的，不访问 Agent，不改变会话何时连接 Agent，不写历史。

为什么：空闲时没有流，为选项单独建会话级通道要处理订阅、重连和与现有流的先后，代价大于收益。广播只说「变了」，值由视图去
唯一来源取，丢一次通知不会让错误的值留在某处被当成事实。不看会话是否空闲都广播，是因为加载完成的视图不会自动跟随之后由工作流等后端
发起的回合，只在空闲时广播会漏掉它。

流开头带当前选项，视图才可以在流开始时放心丢弃取回的结果。流结束时补取，是因为广播和流是两条路：会话空闲后的变化只有广播，
广播可能先于流的结束到达视图，若只是忽略，唯一的新值就丢了。

## 不变量

1. 任一时刻一条会话至多有一份当前选项，由 actor 持有。
2. 同一绑定内，当前选项等于 actor 处理的最后一个携带选项的 ACP 帧的内容，处理的先后就是宿主读到帧的先后。
3. 旧绑定的帧不改变当前选项。
4. 答复属于当前绑定时，`setSessionConfig` 返回成功意味着 actor 已处理完它。
5. 会话选项停止变化后，已从流收到最终状态、或在最后一次变化后取过一次的视图，与之后的加载显示同一份选项。漏掉广播、尚未重新同步
   的视图可以保留旧值（D3.8）。
6. 每条会话流在有 provider 时以 actor 的当前选项开头。
7. actor 释放或替换绑定之后，没有仍在等待的在途设置。
8. 会话选项不写入历史，广播不携带选项。

## 为什么不是这些替代方案

| 方案 | 优势与否决理由 |
| --- | --- |
| 响应和推送带同一份单调序号，各方只接受更大的 | 不改返回值的语义。但契约多一个字段，连接或会话重建后要说明怎么接续，新旧仍由每个消费方各自判断 |
| 保持现状，等真实 Agent 触发再处理 | 没有改动成本。但规则只在代码里，以后新增写入者或消费方会再次出现两个顺序 |
| 为空闲会话新建会话级通道 | 空闲时也能直接带值送达。但多一条通道的订阅、重连和与现有流的先后；应用级广播已经覆盖同类通知 |
| 只在会话空闲时广播 | 通知少。但加载完成、没有跟随当前回合的视图会漏掉回合中的变化 |
| 用加载代替只读查询 | 不加契约。但每次变化都回放全部历史，还会清掉「已切换模型」标记 |
| 广播直接携带选项 | 少一次取值。但广播可丢、可合并、与流没有先后，等于再多一个来源 |
| 前端按发起设置的先后过滤晚到的返回值 | 改动最小。但只能比较前端自己的请求，判断不了 Agent 的推送，其他视图也看不到 |

## 风险

- **广播丢失或积压**：视图可能短暂显示旧值，由重新订阅后的重取（D3.8）和下一次加载收敛。它不影响 Agent 实际使用的选项。
- **发起设置的视图也依赖事件**：空闲时返回值不再写选项。成功后主动取一次（D3.7），不依赖通知是否丢失。
- **不比较值就送出和广播**：值没有变也多一次通知和一次取，换来视图能确定一次设置已经处理完。
- **每个读会话事件队列的循环都要识别设置答复**：设置的答复改为随会话事件送达后，它会出现在每一处读队列的地方：prompt 循环、取消
  时的排空、回合取消的预读、空闲排空、标题轮询、MCP 刷新、恢复会话、建会话的收集窗口。这些地方现在会丢掉不属于自己的答复，漏一处
  就会让设置一直等到超时，当前选项也少一次更新。
- **没有路由的答复会被丢弃**：绑定释放后到达的答复找不到路由，因此在途设置必须由 actor 收尾，不能等答复。
- **失去 provider 是可见变化**：停止的会话会从「保留最后的选项、可以设置」变为「为下次附着选模型」。查询按是否有 provider 回答，
  不能按选项是否为空回答，因为现有的停止和空闲溢出路径释放了通道却没有清空选项。

## 本决策未解决的问题

- 命令列表等其他会话级更新是否也按同样的规则送达空闲视图。它们没有「返回值」这条路，不在本次的问题里。
- 会话 setup 区分「没有上报」和「上报为空」，由[发现契约](../../../plugin/agent/0-discovery-contract.md)的落地处理。

## 验收

核心测试用例见[来源与顺序](../../../../../test-cases/desktop/core/agent/session/options-source-and-order.md)和
[送达](../../../../../test-cases/desktop/core/agent/session/options-delivery.md)。**复现**必须在修复前失败；**回归保护**现在已经成立，防止改动中丢失；其余是新增行为。

| 编号 | 内容 | 类别 |
| --- | --- | --- |
| 1 | 同一回合内「答复 B → 推送 C」「推送 C → 答复 B」，视图和之后的加载都显示 Agent 最后的值；把答复和推送到达前端的先后交换，结果不变（P1） | 复现 |
| 2a | 建会话带模型意图时，收集窗口之后、设置答复之前到达的旧推送不被采用，之后的加载得到意图答复的值（P2） | 复现 |
| 2b | 上述旧推送不随第一条 prompt 送给视图 | 回归保护 |
| 3 | 空闲时旧推送与设置答复相继到达，当前选项是后到的帧（P3）；标题轮询进行中、MCP 刷新进行中同样成立。标题轮询先读命令再读事件，答复会抢在先到的推送之前处理 | 复现（空闲、标题轮询）；新增（MCP 刷新） |
| 4 | 设置期间会话被重建，旧绑定的答复在回合中或回合后到达，视图和之后的加载都是替代会话的选项，设置返回成功（P4） | 回归保护 |
| 5 | 标题轮询期间推送 A，随后设置得到答复 B，下一回合开始后当前选项和视图都是 B（P5） | 复现 |
| 6 | 恢复会话应用模型意图，恢复答复之后、意图答复之前到达的推送不被采用（P6） | 复现 |
| 7 | 会话已附着、期间选项变过，下一条 prompt 流以当前选项开头；加载和跟随流同样，空集合也带（D3.2） | 复现（prompt 流和空集合）；回归保护（加载、跟随流的非空选项） |

| 9 | 每采用一帧选项都随流送出并广播，值没有变、有回合在跑也一样；没有跟随该回合的视图取到新值，有流的视图以流为准 | 新增 |
| 10 | 取回的结果晚于流中更新的选项到达时不盖掉后者；流结束之前收到的广播，在流结束后补取，空闲后的变化不丢；流没有送来选项就结束时补取，加载一条没有 provider 的会话因此得知「没有 provider」 | 新增 |
| 11 | 会话失去 provider（停止、溢出、连接断开，进程被替换并入断连）后发出广播，查询答「没有 provider」，视图记下这一状态而不清空选项：可设置的模型选择器只记意图、不发设置请求，只读选择器仍显示最后的模型，没有 provider 时隐藏推理强度控件（只读节点仍显示）；重新附着后恢复使用会话的选项。仍到达的设置返回失败；回合进行中查询立即答当前选项而不是「没有 provider」 | 复现（选择器不发请求）；只读标签是回归保护；其余新增 |
| 12 | 设置超时返回失败，之后到达的答复被采用并送达视图 | 新增 |
| 13 | 在途设置由 actor 收尾，不再等待答复：`Stop` 命令（以切换 Agent 为代表）返回成功，流的接收方放弃返回成功，会话被重建返回成功，Agent 失联或失控（以队列溢出和连接断开为代表，进程被替换并入断连）返回失败；同时成立时按先检测到的原因。各个读队列的循环中收到设置答复都能完成设置 | 用户停止返回成功是回归保护；其余新增 |
| 14 | 设置成功返回之后打开的视图看到这次改动 | 回归保护 |
| 15 | Agent 返回错误时设置失败、当前选项不变；Agent 未照所选值生效时设置成功，视图显示 Agent 报告的值 | 回归保护 |
| 16 | 成功后收到选项或得知「没有 provider」才结束「进行中」：空闲、有流、有流且 Agent 答复仍是原值、`Stop` 提前结算为成功（包括成功先于流结束到达、广播又丢失），四种都能结束；成功后的读失败也结束。结束时模型和发起前不同才记一次标记，没有设置在途时 Agent 自己改的模型不记；重叠设置共用这组首个设置发起前的模型作基准，替换和撤掉只动这组自己留下的标记，失败只结束该次设置、组内全部结束后才重新取基准 | 回归保护（得到答复才结束、用户切换的标记）；其余新增 |
| 17 | 广播丢失时，重新订阅后取到新值 | 新增 |
| 18 | 广播和查询不访问 Agent，不改变会话状态，不写历史 | 新增 |
| 19 | 刷新 MCP 的 `session/load` 答复带选项时被采用；启动会话、切换 Agent 的返回值不盖掉从流收到的更新选项 | 新增 |

**验证层级**：Desktop 只有一份会话副本，多视图不做界面级验证。1、9 中「所有视图」在 runtime 层用多条加载流、跟随流和应用事件
订阅验证；前端用一份会话副本验证单个视图的写入规则（1、7–11、16、17）；2–6、12–15、19 的宿主部分在 runtime 层由用例控制 ACP 帧的
先后验证。

## 落地顺序

1. **宿主**：设置的答复改走有序的会话事件流，actor 成为唯一写入者，在途设置由 actor 收尾。空闲排空和延后重放只改选项帧的去向，
   标题等其他更新沿用原来的路。没有 provider 时的设置先沿用直接请求：D1.7 的失败和 D3.6 一起在第 2 步落地，否则这期间在
   停止的会话里选模型会报错。完成条件是验收 2–6、12–15，此时前端仍写返回值。
2. **送达**：流开头带当前选项、广播、只读查询，没有 provider 的设置返回失败，前端按 D3 更新并按 D3.6 记意图。完成条件是验收 7–11、17、18。
3. **前端改由事件写入**：返回值不再带选项。完成条件是验收 1、16、19。

三步均已落地。最终可见变化：P2、P3、P5、P6 不再显示旧值，Agent 失联或失控时在途设置返回失败，`setSessionConfig` 的返回值不再带选项，
视图只由会话流和取回的结果写入选项。
