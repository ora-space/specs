# Agent 运行时：插件供给的开放 Agent 身份、每 agent 一条受监督连接、每会话一个串行 actor

Ora 自身不包含任何 agent。用户在 Ora 里能选到的每一个 agent，都由一个已安装的 **Agent 插件**供给；
启动并独占 agent 命令行程序（下称 **agent CLI**）的是插件，Ora 只通过 **ACP** 协议与 agent CLI 对话。
**Agent 运行时**是 Ora 侧承担这件事的那一层代码：它把「用户看到的一段对话」映射到「某个 agent CLI
进程内部的一次会话」，并为这条映射提供进程监督、失败隔离、流控、历史归属与生命周期序列化。

Agent 运行时不实现任何 agent、不搜索 `PATH`、不启动任何 agent CLI，也不解析 ACP 消息的内容。据此，
本决策确定四条边界：

- **agent 身份是开放集合**——有哪些 agent 存在，完全由用户装了哪些 Agent 插件决定，编译期不可知。
- **进程监督的粒度是「一个 agent 一条 ACP 连接」**——一个 agent CLI 崩溃只影响这一个 agent。
- **并发的粒度是「一个 Ora Session 一个串行 actor」**——同一段对话的操作严格串行，不同对话并行。
- **对话的可回放事实归 Ora 拥有**——Ora 自己写一份历史文件，而不是向 agent CLI 索要它的重放。

该决策已由 `crates/backend/src/agent_runtime`（含 `plugin_agent` 子模块）、`ora-acp`、`ora-history`
与 `ora-plugin-lifecycle` 落地；`status: implemented` 表示本文描述的是最终的系统承诺，而不是实现
过程。兼容性边界有两条硬约束：会话历史的本地文件布局（sessions root 目录下每个 Ora Session 一个
只追加的 JSONL 文件），以及 Session 数据行中 `agent_ref` 列的取值空间。

本 ADR **不**承担以下义务：定义 ACP 协议本身；定义历史文件的格式、排序与失败语义（属 `ora-history`）；
定义插件的分发、安装与启用（属插件领域）；定义 Effect 的通用收敛协议（属
`desktop/core/effect/0-effect-system-foundation.md`）；改写任何既有的持久化数据（见「不能直接改写
的状态」一节）。

## 术语

本文反复使用下列名词，其中多数是 Ora 自创的概念，读者不必事先了解本项目：

| 名词 | 含义 |
| --- | --- |
| **ACP** | Agent Client Protocol，agent 与客户端之间的 JSON-RPC 协议。Ora 是客户端，agent CLI 是服务端。`session/new`、`session/load`、`session/prompt`、`session/cancel` 等方法名均来自该协议 |
| **agent CLI** | 真正干活的外部命令行程序，例如 Claude Code、opencode。它是独立的操作系统进程，会崩溃、会没装、会被卸载 |
| **Agent 插件** | 一个已安装的插件包，是 agent 的唯一来源。一个包供给一个 agent。插件负责决定启动哪个 agent CLI，并独占该进程 |
| **package address** | 插件包的地址，形如 `<namespace>/<name>`，例如 `official/ora-space.opencode`。插件生命周期用它来拥有和停止插件进程 |
| **agent 身份**（`agent_ref`） | 插件包供给的 agent 名字，即 package address 的 `name` 段，例如 `ora-space.opencode`。**每个 Ora Session 持久化的是这一个字符串**，而不是 package address |
| **provider session** | agent CLI 进程内部的一次会话，由 ACP 的 `session/new` 创建，用 `agent_session_id` 寻址。agent CLI 在它里面保存模型上下文。agent CLI 进程一旦被替换，此前所有 provider session 全部作废 |
| **Ora Session** | Ora 持久化的一行对话记录，拥有自己的 id、标题、归属 Workspace、工作目录和历史文件。它是用户眼中的「一段对话」 |
| **绑定**（binding） | 一个 Ora Session 指向的 `(agent_ref, agent_session_id)` 二元组，即「这段对话现在跑在哪个 agent 的哪个 provider session 上」。切换 agent 改变的只有绑定 |
| **连接**（connection） | Ora 与某一个 agent 之间那条 ACP 通道。同一个 agent 下的所有 Ora Session 共用它 |
| **代次**（`generation`） | 一条连接的版本号，单调递增。只有当监督器重新附着到一个新的 agent CLI 进程并完成 ACP `initialize` 时才 +1 |
| **监督器**（supervisor） | 负责让某一个 agent 的连接保持可用的那段代码：附着、握手、失败重试、退避、断路 |
| **actor** | 一个 Ora Session 专属的串行任务，所有针对这段对话的命令都排队交给它执行 |
| **prompt** | 用户发出的一轮消息，以及 agent 对这一轮的全部回应。以 ACP 的 `session/prompt` 请求开始，以其应答携带的 `stopReason` 结束 |
| **warm session** | 在用户发出第一条消息**之前**就预先创建好、暂存在内存里的 provider session。它存在的唯一理由是让模型选择器能在空聊天上渲染，详见 D10 |
| **transcript** | Ora 把自己记录的整段对话渲染成的一段纯文本。切换 agent 时它被塞进下一条 prompt，让新 agent 知道之前发生了什么 |
| **Effect** | Ora 的声明式收敛系统，负责把 Skill 等内容物化到 Workspace。它会重启 Agent 插件内部的 agent CLI 进程，这一点与本 ADR 相关，详见 D13 |

## 背景

agent CLI 是外部进程：它会崩溃、会被用户卸载、会在机器上根本不存在，也会在一轮对话进行到一半时
消失。而一个 Ora Session 是用户资产：它有标题、有可回放的历史、有归属的 Workspace 与工作目录，
必须跨 Ora 进程重启存续，并且必须能被整段交给另一个 agent。

如果让每个 Ora Session 各自启动一个 agent CLI 进程，进程数会随对话数增长，而且同一个 agent CLI 的
多个实例会争抢它自己的全局状态（配置文件、锁、缓存）。如果让所有 Ora Session 共享一条无人监督的
连接，一次 agent CLI 崩溃就会同时毁掉所有对话，而且没有任何一层代码能回答「哪些 provider session
已经作废了」。Agent 运行时因此在这两个极端之间取一个明确的中间层，并用连接代次把两层绑起来。

## 决策

### D1：Agent 身份是开放集合，监督器按插件供给的 agent 身份建键

`agent_ref` 是一个开放字符串，取值为某个已安装 Agent 插件所供给的 agent 身份，而不是编译期写死的
枚举。运行时按 `agent_ref` 为每个 agent 建立监督器。

**一个插件包同时带着两个不同的标识符**，它们是两个不同的字符串，必须严格区分：

| 标识符 | 例子 | 谁使用它 |
| --- | --- | --- |
| package address | `official/ora-space.opencode` | 插件生命周期，用来启动/停止插件进程 |
| agent 身份 `agent_ref` | `ora-space.opencode` | 每个 Ora Session 持久化的绑定，以及监督器的键 |

从 package address 到 agent 身份的翻译只在一个地方进行：持有这两个标识符的那个类型
（`AgentSource`）所在的模块，对外只暴露 `ConnectionSupervisors::agent_for_plugin` 一个入口。其余
任何地方都不得把 package address 当作 `agent_ref` 使用。**理由是这类错误的失败形态特别隐蔽**：拿
package address 去查监督器表，代码能编译、读起来也合理，但它匹配不到任何东西，结果是每一条已经
持久化的绑定都突然不可解析，而系统只会报告「这个 agent 没安装」。

其余规则：

- 只有 `agent` 类插件供给 agent。`ui` 类插件贡献界面，从不被监督。
- 如果一个插件包声明的 agent 身份已经被另一个已安装的包占用，**后来者被忽略**，而不是替换掉已有
  的监督器。把用户既有的 agent 悄悄换成另一个包提供的实现，比拒绝第二个包更坏。
- 每次插件安装、卸载、扫描之后，运行时都重新对齐一次「应该监督哪些 agent」。这是 level-triggered
  的比对（拿当前已安装列表和当前监督器表比对），而不是对某个一次性事件的响应，所以运行期装上的
  插件无需重启 Ora 就能出现在选择器和会话路由里。监督器表是在锁内原地增删的，不是整体重建，因此
  warm 池和所有存活 actor 手里已有的克隆会立即看到变化。
- 查不到某个 `agent_ref` 是**正常的运行时状态**，不是数据损坏：一个 Ora Session 完全可以比供给其
  agent 的插件活得更久。这种情况报告为 `agent_runtime_unavailable`。

### D2：每个 agent 一条受监督连接，`generation` 只表示 ACP 连接的代次

每个 agent 身份对应一条独立监督的 ACP 连接，由一条专属的运行时线程驱动——Desktop 的启动流程是
同步的，不保证存在环境 Tokio 运行时，所以监督器自己建一个。一个监督器同一时刻只运行一代 agent
CLI 进程，并且只有在上一代进程被完整回收之后才开始下一次尝试。

`generation` 是这条连接的版本号，单调递增。**只有当监督器重新附着到一个新进程并完成 ACP
`initialize` 时它才 +1。** 它是运行时判断「某个 `agent_session_id` 是否还能被解析」的唯一依据：每条
会话路由都记录着自己注册时的代次，来自更早代次的事件，以及发往已卸载会话的事件，一律作为陈旧
数据丢弃。

**插件进程归插件生命周期所有，连接只借用它这一代的通知通道。** 一代连接结束时，运行时做的是请求
插件生命周期停止该插件，而不是自己去杀进程。这样做有两个后果：设置界面报告的插件运行状态，与
agent 运行时实际在对话的对象，始终是同一件事；下一次附着拿到的是一个全新的插件进程，而不是一个
用过一半的进程。

还有一个时序细节。调用 ACP `session/new` 创建 provider session 时，agent CLI 往往在应答返回**之前**
就先推送若干条属于这个新会话的通知，而此时 Ora 还不知道新会话的 `agent_session_id`，无法把这些
通知归属给任何路由。连接因此在「有 `session/new` 正在进行中」的这段窗口里临时缓冲这类无法归属的
通知；新会话的路由注册时，把 `agent_session_id` 匹配的通知排进该路由，最后一个并发的 `session/new`
结束时丢弃仍未匹配上的部分。**权限请求和请求应答从不进入这个缓冲**：找不到路由时它们被立即取消
或丢弃，因为它们不是可以延后归属的广播，而是需要立刻有人回答的东西。

### D3：启动失败按「另一次尝试能否得到不同答案」分为三类

| 分类 | 触发它的情况 | 运行时的处置 |
| --- | --- | --- |
| 可重试，且不写日志 | 插件报告它要用的 agent CLI 在本机没安装（`agent_not_installed`）；插件被用户禁用或尚未安装 | 状态保持 `Unavailable` 并持续重试，不写日志，不计入崩溃计数 |
| 可重试，写日志 | 一般的启动失败、附着失败、ACP `initialize` 失败或超时 | 记录一条警告，按退避重试，计入崩溃计数 |
| 终态，放弃该 agent | 插件包自带的可执行文件在本机根本跑不起来（`agent_unusable`）；插件的注册信息没有覆盖完整的 agent 契约；协议版本不被支持 | 发布 `Failing` 状态，本次 Ora 进程剩余时间内不再尝试这个 agent |

**分类线只有一条：另一次尝试能否得到不同答案。**

本机没装某个 agent CLI 是**可预期的本地配置问题**——用户完全可以在 Ora 运行期间把它装上，下一次
重试就成功了。所以这一类要静默重试：如果每次重试都写一行日志，一个未安装的 agent 就会把运行日志
淹掉，而 `Unavailable` 状态已经把「没装」这个事实送到界面上了。

反过来，一个插件包**自带**的可执行文件在本机跑不起来（架构不对、文件损坏、缺少运行时），每一次
尝试都会以完全相同的方式失败。把它判为终态，是唯一能让这个包级故障**被看见一次**、而不是永远藏
在一条安静的「未安装」报告背后的做法。也正因为放弃意味着它只会产生这一次诊断，只有这一类失败会
把插件自己的错误消息原样透传出来。

插件注册信息的契约校验在附着刚完成的那一刻就执行——早于任何 provider session 存在、早于有用户在
等一次 prompt。所以「插件没实现完整契约」表现为一个不可用的 agent，而不是某个人对话进行到一半时
的失败。

重试的退避从 250 毫秒开始倍增，上限 30 秒。一分钟内超过三次**计入崩溃计数**的失败会打开这个 agent
的重启断路器：发布 `Failing`，停止本次 Ora 进程内对这个 agent 的全部自动重试。其他 agent 完全不受
影响。

### D4：每个 Ora Session 一个串行 actor，prompt 所有者唯一，加载视图只能跟随

每个持久化的 Ora Session 有且只有一个 actor，它串行执行针对这段对话的全部命令：加载、prompt、
权限应答、取消、停止、删除、用户改名。绑定到同一个 agent 的多个 Ora Session 共用该 agent 的进程和
连接；绑定到不同 agent、或属于不同 actor 的 Ora Session 并行推进。

**加载一个 Ora Session 总是看到同一段对话**，无论它当时是否正在生成：

- 空闲的 Ora Session，从 Ora 自己的历史记录恢复。
- 已经有一个 prompt 在跑的 Ora Session，加载先从该 prompt 的接入点回放历史记录，再跟随此后的实时
  事件，并在同一个轮次边界结束。加载**不会**开始第二个 prompt，也**不会**夺走第一个 prompt 的
  所有权。

一个 Ora Session 同时只接受一个 prompt 所有者，但可以有任意多个加载视图跟随这个 prompt。向跟随
视图的实时转发是有界的（每个视图 256 项），慢的视图不会拖住 prompt 所有者；队列耗尽的视图收到一条
**明确的流错误**，而不是一次没有解释的断流。关闭一个跟随视图不会取消它正在跟随的 prompt。

取消是**会话级**的控制：即使发起取消的调用方只是一个跟随视图，取消也会送达真正拥有该 prompt 的
那一方，在历史里记下这一轮被取消，并在 agent CLI 正常结算之后把 actor 留着给下一次 prompt 用。
如果只是关掉一条加载流，那就只分离这一个视图，不影响 prompt。

actor 交给调度器的定时回调只持有**弱**命令发送端。当删除、切换 agent 或运行时关停释放掉最后一个
外部发送端后，actor 的命令通道关闭，actor 随之释放它持有的连接、历史记录器、数据库句柄和调度器
克隆。回调在真正执行时才把弱发送端升级为强引用，正是为了不藏着一个让 actor 永远无法退出的克隆。

### D5：三级通道与代次绑定的路由，把爆炸半径限制在一个 agent

从 agent CLI 读到的每一条 ACP 消息，要经过三层通道才到达某个 actor：

| 层 | 形态 | 存在的理由 |
| --- | --- | --- |
| 连接读取 → 中央路由 | 无界、保序 | 连接级的读取与解析不会因为某一个 Ora Session 消费得慢而阻塞 |
| 中央路由 → 每会话事件队列 | 有界 256，保序 | 会话更新、权限请求和终结应答按 agent CLI 发出的顺序抵达 actor |
| 中央路由 → 每会话控制通道 | 独立、无界 | 连接丢失和队列溢出这两个终态失败，不会被压在已经塞满的事件队列后面 |

某个 Ora Session 的事件队列溢出、加载超时或被取消，只影响这一个 Ora Session。ACP 分帧错误、请求
应答无法匹配、传输中断，则使整条连接的当前代次失效，并且只停止注册在这个 agent 上的 Ora Session。
**因此，一个插件进程死亡的爆炸半径，与一个 agent CLI 进程死亡的爆炸半径完全相同：一个 agent。**

终态控制不得越过已经被事件队列接受的事件：处于活跃操作中的 actor 先把已接受的事件排空，再应用
终态控制。同时，actor 每消费 32 条事件就强制轮询一次命令通道，使用户命令不会被持续的实时事件流
饿死。

来自 agent CLI 的、Ora 不认识的 JSON-RPC 请求，会收到一条相关的 `-32601`（方法不存在）应答，连接
继续存活；只有畸形帧、无法匹配的应答、超尺寸帧和 stdio 中断才算连接故障。

历史回放是唯一一条**施加背压**而不是快速失败的流：一段录好的对话远大于 256 项的队列容量，而一个
还没来得及排空它的消费者并不是一个断开的消费者。

### D6：一次操作只有消费到它自己的应答才算结束

ACP 的会话事件是保序的。据此，一次加载或一次 prompt 只有在消费到与它自己的请求相匹配的那条**应答**
之后才算完成——这条应答被称为该操作的**边界**（fence）。因为顺序有保证，应答之前观察到的所有更新
和权限请求必然属于同一次操作，而应答之后的事件不会泄漏进下一次 prompt。**一轮对话只在这条边界
结算之后才被写进历史。**

取消同样要走完这条边界：取消发出后，actor 在 5 秒宽限期内继续消费事件，直到匹配的应答到达。如果
agent CLI 没有在宽限期内结算，actor 先把已经接受的事件快照记进历史，再把这条会话路由隔离掉。

Ora Session 空闲时抵达的残留事件（属于上一轮的尾巴），在 actor 接受下一个命令之前就被消费掉，因此
不会跨轮次。

### D7：Ora 拥有 transcript，agent 拥有模型上下文

Ora 自己完整记录每一段对话。加载时**仍然**调用 ACP `session/load`，但目的**只是**让 agent CLI 恢复
它回答下一条 prompt 所需的模型上下文；agent CLI 在 `session/load` 里回放的内容被排空并丢弃。用户看
到的是 Ora 自己的记录，因为那才是「无论当前绑定到哪个 agent 都一样」的那一段对话。

- **记录的是 Ora 选择保留的内容，而不是它发出去的内容。** 用户这一轮的 prompt 在调用 agent CLI
  **之前**就按请求内容记好；agent CLI 回显的用户消息块被忽略。因此 Ora 自己注入的上下文（例如切换
  agent 时的 transcript）永远不会进入记录。
- **流式更新先记录、后转发。** 中途断开的客户端只损失这条流，不损失「agent 到底产出了什么」的记录。
- **每一轮以它的 `stopReason` 收口。** 轮次边界还负责结算 agent 遗留的未终结工具调用：ACP 不强制
  agent 报告工具调用的终态，一个开了工具调用就不管的 agent 会留下永远显示「正在运行」的记录。规则
  是：**只有** agent 自行正常结束（`EndTurn`）的轮次，才把这些悬空的工具调用记为已完成；其余每一种
  结束方式（取消、超出 token、被拒绝）都让它们保持未完成——因为这些调用可能是被打断而不是做完了，
  而 `stopReason` 已经说明了是哪一种。读取方各自补全这个语义：对话视图把被截断轮次里的未完成调用
  显示为「已中断」，交给下一个 agent 的 transcript 则把它们的结果写成「未报告」，而不是声称这个工具
  从未运行过。
- **两类历史损坏都被显式报告，而不是被静默跳过。** 一条无法解码的完整 JSONL 行不参与回放，但会以
  一条带类型的完整性提示报告其总条数；历史里已有的 `Gap` 记录（见 D8）同样作为提示回放。两者都不
  猜测自己在时间线上的位置，因为文件的追加顺序不等于对话的时间顺序。Ora Session 保持可写：过去的
  损坏是一条完整性警告，而「现在还能不能继续追加」由历史状态单独描述。

删除一个 Ora Session，移除的是 Ora 自己的数据行和 Ora 自己写的历史文件，**不删除 agent CLI 那边的
历史**。ACP 的 `session/delete` 只用于一类对象：Ora 创建、从未持久化、也从未交给用户的 warm session
（见 D10）。**用户能看见的会话只被关闭，从不被删除。**

### D8：历史写入失败让 Ora Session 降级，而不是跳过这条记录继续写

一份**跳过了**若干记录的历史，比一份**停止**在某处的历史危险得多，因为中间的空洞对读它的人不可见
——包括下一个接手这段对话的 agent。因此，一次写入失败会让这个 Ora Session **永久停止记录**，而不是
跳过失败的那条继续往后追加。

- **已经在流式输出的那一轮照常完成。** agent 的工作是真实发生的，文件有没有存下来都一样；让这一轮
  失败等于告诉用户「什么都没发生」，而实际上发生了。
- **自身 prompt 都没能记下来的那一轮，在调用 agent CLI 之前就被拒绝。** 此刻还什么都没发生，拒绝
  它不损失任何东西；而把它发出去，会把对话带到记录追不上的地方。
- Ora Session 进入**降级**状态，携带操作系统给出的失败原因，后续 prompt 一律被拒绝，直到用户显式
  恢复。
- 恢复操作在接受任何新内容**之前**，先追加一条 `Gap` 记录，写明是什么中断了这个文件，然后才把
  Ora Session 变回可写。**恢复不还原丢失的内容，它记录「曾经丢失过内容」这件事。**
- 完全读不出来的历史文件以同样的方式降级：在不知道哪些位置已经被占用的情况下继续追加，会覆盖它们。
  这和「个别完整行无法解码」不同——后者保留了幸存的时间线，属于 D7 的完整性提示。
- **读不出历史的加载直接失败**，而不是完成一次空加载。加载正是用户要求看到这段对话的方式，而一个
  空视图与「这个会话从来没说过话」无法区分。

### D9：切换 agent 是「立即重绑定 + 惰性注入 transcript」，交付以 agent 接受请求为准

`switchSessionAgent` 把一段对话搬到另一个 agent 上。这个 Ora Session 保留它的 id、它的 Workspace、
它的历史；**改变的只有绑定**。

- **新绑定是从 warm 池里认领的，不在这里现场握手。** 认领用的键，与选择器展示这个 agent 的模型时
  预热所用的键是同一把（见 D10）。因此这段对话落到的是用户真正配置过的那个 provider session——切换
  之前选好的模型在搬家之后依然有效——而且常见情况下不需要任何一次 ACP 往返。查找和预留在同一个
  临界区内完成，中途没有别的调用方能把它抢走。
- **认领成功之前不拆除任何东西**，所以一个不可用的 agent 只会让这段对话原地不动。切换到这个
  Ora Session 已经在跑的那个 agent，报 `session_agent_unchanged`，而且是在认领**之前**就判定的：
  否则会先预热出第二个 provider session，再拿它去替换一个与之无法区分的当前绑定。历史已降级的
  Ora Session 拒绝切换。
- **认领之后的失败，通过丢弃预留把条目还给 warm 池**，被认领的那个 provider session 保持存活，可供
  重试使用。Ora 在这里绝不关闭它——关不关由 warm 池决定（见 D10）。
- **重绑定会停止当前绑定的 actor**，所以客户端被期望在**用户发下一条消息时**才提交这次切换，而不是
  在选中新 agent 的那一刻就提交。选择在客户端侧累积；如果用户绕了一圈又选回这个 Ora Session 当前
  已经绑定的 agent，客户端应当撤回这条记录，而不是提交一次空搬家——那正是
  `session_agent_unchanged` 要拒绝的请求。
- **transcript 是惰性注入的。** 切换动作本身不向新 agent 发送任何东西；Ora 记录的整段对话被渲染成
  一段文本，作为**前置内容块**附加到用户的下一条 prompt 上。切换之后就被弃用的 Ora Session 不产生
  任何代价。ACP 没有提供「把一段既有对话装进 agent」的方法（`session/new` 不接受上下文，
  `session/prompt` 只接受一轮用户消息），所以每一轮历史都坍缩成一条**展示给**新 agent、而不是由它
  参与过的用户消息，注入文本的开头那段前言就是用来解释这一点的。
- **「当前绑定是否还欠着 transcript」这件事从历史记录派生**，而不是靠内存标志：历史末尾如果有一条
  `AgentSwitched` 而其后没有 `HandoffDelivered`，就说明还欠着。这样，即使持有这个知识的 actor 已经
  消失、甚至 Ora 重启过，结论依然成立。
- **这笔债务只在 agent CLI 接受了携带 transcript 的那个请求之后才结算**，内存标志和历史文件一起
  结算。接受请求是 Ora 能观察到的、关于「交付成功」的最后一件事——再往后，数据帧已经在 agent CLI
  的标准输入上，Ora 无从得知它怎么处理。据此，**中途丢失的连接算作已交付**：否则会把整段对话再次
  注入一个已经持有它的 agent，而 transcript 前言声称「这段工作属于另一个 agent」，那句话就成了假话。
  反过来，如果交付记录本身写入失败，下一条 prompt 会把 transcript 再交付一次——这是无害的那个方向。
  **不能拿「历史里已经有一条用户消息」来判定 transcript 已交付**，因为 Ora 在发送之前就记录 prompt：
  一条位于切换之后的用户消息，与「transcript 已成功交付」和「请求在发出途中失败」这两种情况同样
  一致。
- transcript 没有大小上限。超出接收方模型上下文窗口的失败，由 agent CLI 报出。

### D10：warm session 让模型在用户发第一条消息之前就可选

ACP 只在 `session/new` 和 `session/load` 的应答里报告一个会话的配置选项，而模型选择器就在这些选项
里。**这意味着 provider session 不存在时无法选择模型**，可模型选择器又必须在一个空聊天上就能渲染。
Ora 因此在用户打开聊天界面时就先创建一个 provider session 并把它暂存在内存的 **warm 池**里，这就是
warm session。

**条目的形态与身份**

- warm session 只存在于内存。attach 之前不存在任何 Ora Session 数据行，所以打开又放弃一个聊天界面
  不会在 Ora 侧留下一堆空对话。
- 每个 warm 条目的键是 `(Workspace, agent_ref, owner)` 三元组。Desktop 的交互式聊天使用同一个
  `Interactive` owner；工作流节点使用内部的 `WorkflowNode { run_id, node_id }` owner，使并发的工作流
  分支不会互相认领对方的会话，同时又不必把界面侧的身份暴露进对外契约。
- **一个条目服务这个 Workspace 下、这个 agent、这个 owner 的全部聊天界面，而不是每段对话一个。**
  「每把键只有一个条目」是稳态描述，不是交接期间成立的不变量：一次认领撞上一次正在进行的 attach
  时，会临时出现第二个条目。
- **Ora Session 的 id 在 warm 的时候就铸造好**，而不是等到持久化时才生成。因此客户端从头到尾只需要
  跟一个 id。在 attach 之前，这个 id 不会出现在任何会话查询结果里。

**只有两个操作会把条目从池子里取走，而且它们用不同的方式点名条目**

| 操作 | 用什么点名条目 | 为什么必须是这个 | 点名的对象不在时 |
| --- | --- | --- | --- |
| `attachSession`（用户发出第一条消息） | 该条目的 **Ora Session id** | 这个 id 会**原样**成为持久化 Ora Session 的 id，而客户端早已用它锚定了界面上那条乐观显示的消息。换成别的条目就是换了一个 id，客户端就得跟着改 id——而「id 在 warm 时铸造」的全部意义就是让它不必跟 | 只能失败（`warm_session_not_found` 或 `warm_session_attach_in_flight`），由客户端重新 warm 一次。它没有退路，因为任何替代条目都带着不同的 id |
| `switchSessionAgent`（切换 agent） | 该条目的**键** `(Workspace, agent_ref, owner)` | 被搬走的只有绑定：Ora Session 的 id 已经存在且不变，warm 条目自带的那个 id 属于池子并被丢弃。而且客户端手里根本没有 warm 的 id 可报，它掌握的信息是「选择器刚才在展示哪个 agent 的模型」，那正好就是这把键。按键点名，是让**选择器**和**重绑定**对上的那一步 | 不会失败：查找逻辑跳过被预留的条目，一把键找不到可用条目时就地新建一个冷条目，认领过程中现场完成握手。所以预热过的条目被驱逐、被消费、正在被 attach，切换照样成功，只是多付一次握手 |

**两个操作都先预留，再动手**

预留不是「把条目取出来」，而是把它标记为 `reserved` 并**留在池子里**，同时返回一个预留值。这个
预留值在 `Drop` 时把条目还回池子，只有调用方的持久化步骤全部成功之后调用 `commit`，条目才真正被
移除。

把释放绑定在一个值的析构上、而不是绑定在「调用方记得再调一次释放函数」上，是必需的：attach 拿到
预留之后还要等待运行时的生命周期锁，而命令层会在客户端断开时把整个请求 future 丢掉，panic 展开
也会走同一条路。这两条路径都不会执行任何后续调用，但都会执行 `Drop`。而**驱逐逻辑刻意跳过被预留
的条目**，所以一个没人释放的预留会永久钉住一个 provider session——没有任何上限能把它回收回来。

**失效、重建与回收**

- 工作目录在每次请求时从 Workspace 重新解析，并与条目创建时使用的目录比对。被移动或重建过的
  worktree 会让条目退休，而不是让 agent 悄悄跑到一个陈旧路径里去工作。
- 配置改动对 warm session 和已持久化的 Ora Session 一视同仁，并且被记住。一个已经失去 provider
  session 的**冷条目**只记录用户的选择而不重建 provider session；重建时重放这些选择，被 agent 拒绝
  的重放降级为「agent 实际报告了什么选项」，而不是让用户已经输入的 prompt 失败。
- **没有任何机制因为闲置而释放一个 warm session。** warm session 按定义就是用户从未 prompt 过的
  会话，一个闲置条目不持有任何值得回收的对话，只持有 agent 那边的一个空会话。存活条目上限（16）
  与总条目上限（64）都是纯计数，并且在唯一可能越界的时刻——创建另一个 provider session 时——执行。
  基于时长的回收需要一个计时器才诚实，而且会让一个离开片刻又回来的用户白付一次完整重建。
- **删除一个 Workspace 是回收其 warm 条目的唯一时机**：删除 Task 会删除它的 Workspace，删除 project
  会级联删除其中每一个 Workspace，两者都据此丢弃对应的 warm 条目并归还 provider session。此时
  Workspace 已经消失，没有任何请求能再点名这些条目，而计数上限要等到用户开出足够多的新聊天界面
  之后才够得着它们。

### D11：首个标题的获取是一个不持久化、可被抢占的窗口

一个刚 attach 的 Ora Session 拥有一个**只存在于内存**的标题获取窗口，从 attach 那一刻起就接受
agent 主动推送的合法标题。第一轮 prompt 只有在以 `EndTurn`、`MaxTokens` 或 `MaxTurnRequests` 结束
时，才会开启后续的兜底窗口；被拒绝、被取消、请求失败、连接失败都不消耗这次资格。

- 如果 agent 在 ACP `initialize` 里公布了「支持列举会话」的能力，运行时会在那轮合格 prompt 之后的
  第 3 秒和第 10 秒各安排一次 `session/list` 兜底尝试，每次请求上限 5 秒；第 10 秒那次无论结果如何
  都关闭窗口。如果 agent 没有公布这个能力，运行时不发任何列举请求，窗口只接受推送，同样在第 10 秒
  关闭。
- 推送来的标题和列举来的标题走**同一条**校验与持久化路径。窗口开启期间，最后一个成功写入数据库的
  合法 agent 标题获胜；与当前标题相同的标题不写库也不发事件，空白、null 和超长值被忽略。
- **标题轮询是 actor 自己的低优先级工作。** 调度器的回调只往 actor 的命令队列里塞一条内部命令，
  actor 空闲时才真正发出 ACP 请求。prompt、加载、停止、切换 agent、删除、用户改名、队列失败、连接
  丢失、actor 终止，任何一件事都会关闭或抢占这个窗口。因此标题轮询永远不会延迟用户的操作。
- **用户主动改名会锁定这个窗口**，并重新持久化用户选定的标题，之后任何推送或列举来的 agent 标题都
  不能覆盖它。
- 窗口状态不写进 SQLite，恢复一个已存在的 Ora Session 时以「已禁用」状态启动。标题写库成功之后才
  发布标题失效事件，而且事件里只带 Ora Session 的 id——它是一条失效提示而不是日志，客户端收到后
  重新拉取权威标题。

### D12：权限请求当前一律自动放行

Ora 目前没有可配置的审批策略。活跃 actor 收到的每一个 ACP 权限请求都被立即授予，并优先选择那个
「同时记住这次选择」的选项，使同一轮对话里后续的同类工具调用也无需值守。

自动放行走的是与真实用户选择完全相同的应答路径。因此，将来引入审批策略时只需在这一处设闸、把请求
留在待答集合里交给前端回答，无需改动 ACP 协议、路由或流控。

`RespondToPermission` 这个命令保留给另一种情形：权限请求抵达时并没有活跃的 prompt。此时它以「不在
待答状态」失败，因为确实没有任何东西被留着没答。在 `session/load` 期间、或 Ora Session 空闲时抵达
的权限请求，一律以「已取消」作答。

### D13：agent CLI 进程被 Effect 替换之后，必须分离受影响的存活会话

Effect 协调会重启一个 Agent 插件内部的 agent CLI 进程，让它重新读取被物化到 Workspace 的内容。这个
重启会**静默作废**该进程持有的全部 provider session。Agent 运行时因此对外提供一个能力：在 agent CLI
进程被替换之后，分离受影响的存活 Ora Session，使下一次交互经由普通的加载路径重新建立绑定，而不是
拿着一个新进程无法解析的 `agent_session_id` 去发 prompt。

分离时**不调用** ACP `session/close`：那只会要求一个全新的 agent CLI 去关闭一个它从没听说过的
会话 id。分离已经足以修复而不是终结这段对话——没有活跃通道时 prompt 会被拒绝，而建立通道的加载
路径正好会调用 `session/load`，那正是被替换掉的进程所需要的重新建立。

这个通知由 Effect 侧按 **package address** 发起（Effect 只持有 package address），运行时按 D1 的
翻译规则把它换成 agent 身份，然后**向全部 actor 广播**，由每个 actor 自己判断是否绑定到这个 agent。
之所以广播而不是精确寻址，是因为 actor 注册表以 Ora Session 为键，不带 agent 索引；而一个 agent 的
连接被所有 Workspace 共用，被替换的影响本来就跨 Workspace。投递是尽力而为：一个已经结束的 actor
不可能还持有陈旧通道。Effect worker 依赖的是「分离会话」这一个能力，而不是整个 agent 运行时，因此
一次 Effect 收敛在没有 agent 运行时的情况下依然可被验证。

## 边界与上限

| 边界 | 值 |
| --- | --- |
| ACP `initialize` 握手 | 15 秒 |
| `session/load` 的不活动期限 | 30 秒，每收到一条会话更新就重置 |
| `session/new` 与配置选项请求 | 30 秒总预算 |
| prompt 流 | 无期限，由 agent CLI 或取消结束 |
| 取消的结算宽限 | 5 秒 |
| 插件确认已停止其 agent CLI 的期限 | 2 秒（刻意远小于取消宽限） |
| 连接重试退避 | 250 毫秒起倍增，上限 30 秒 |
| 重启断路器 | 一分钟内超过 3 次计入崩溃计数的失败 |
| 每会话事件队列、每个跟随视图的队列 | 各 256 项 |
| `session/new` 期间的通知缓冲 | 256 条，满时丢弃最旧的 |
| ACP JSON-RPC 单帧 | 8 MiB |
| 序列化后的结构化 prompt | 16 MiB |
| warm 条目 | 存活 16 个 / 总计 64 个，均为纯计数 |
| 切换 agent 的 transcript | 无上限 |

`session/load` 的 30 秒是**不活动**计时器而不是总预算：一个持续推送更新的 agent CLI 可以无限期地
加载下去，而一个静默 30 秒的 agent CLI 只会使这一个 Ora Session 失败。prompt 以有序的 ACP 内容块
原样透传，支持文本、图像、音频、资源链接和内嵌资源；空列表、以及只含空白文本的列表会被拒绝；
16 MiB 是在抵达 agent CLI 之前，从序列化后的载荷上度量的。

## 必须保持的不变量

1. Agent 运行时不启动任何操作系统进程，也不解析、校验或改写 ACP 消息的内容。运行哪个程序由插件
   决定，进程由宿主的子进程接口创建并拥有。
2. 一个 agent 身份对应一条受监督连接；一个 Ora Session 对应一个串行 actor。
3. `generation` 只表示 ACP 连接的代次，只在监督器重新附着到新进程并完成 `initialize` 时 +1。
4. 每条会话路由绑定它注册时的代次；来自更早代次、或发往已卸载会话的事件必须作为陈旧数据丢弃。
5. 任何单点失败的爆炸半径不得超过一个 agent。
6. 一个 Ora Session 至多有一个 prompt 所有者；跟随视图既不得阻塞所有者，也不得取消所有者的 prompt。
7. 一次加载或 prompt 必须消费到与自己的请求匹配的应答才算结束；一轮对话只在该应答结算之后才被写进
   历史。
8. Ora Session 的 id、标题与历史文件归 Ora 所有；agent CLI 那边的历史不被 Ora 删除。
9. ACP `session/delete` 只允许作用于「Ora 创建、从未持久化、也从未交给用户」的会话。
10. 历史写入失败必须让该 Ora Session 降级并拒绝后续 prompt；恢复时必须先写入 `Gap` 记录，再接受新
    内容。
11. 「当前绑定是否还欠 transcript」必须能从历史记录派生，并且只有在 agent CLI 接受了携带 transcript
    的请求之后才结算。
12. 从 warm 池取走条目必须先预留，并且预留必须在失败或调用方消失时自动归还。
13. 用户主动改名会锁定标题获取窗口，之后的 agent 标题不得覆盖它。
14. agent CLI 进程被替换之后，任何仍指向该进程的 `agent_session_id` 都必须被作废，不得继续用于
    prompt、配置或绑定。

## 为什么不是这些替代方案

| 方案 | 否决理由 |
| --- | --- |
| 每个 Ora Session 启动一个 agent CLI 进程 | 进程数随对话数增长；同一个 agent CLI 的多个实例会争抢它自己的全局状态；而且没有任何一层能统一回答「哪些 provider session 已失效」 |
| 所有 Ora Session 共享一条无人监督的连接 | 一次 agent CLI 崩溃毁掉全部对话，也无法把失败限制在一个 agent 内 |
| 用编译期枚举表示 agent 身份 | 有哪些 agent 存在在构建期不可知；每新增一个 agent 都要发一次版，而且用户运行期装上的插件不可能出现 |
| 用 package address 作为监督器的键 | package address 与 Ora Session 持久化的 `agent_ref` 是不同字符串，会让每一条既有绑定都不可解析；而且失败形态是「静默匹配不到任何东西」而不是报错 |
| 在 agent 运行时里解析 CLI 路径或搜索 `PATH` | 会把「某个 agent 是怎么装的」泄漏进一个本应通用的运行时；而且插件是被沙箱化的，它自己算不出包内可执行文件在宿主上的绝对路径 |
| 在插件运行时的请求相关性之上再包一层 ACP 相关性 | 同一个数据帧会有两个超时和两条取消路径；而且一个跑好几分钟的 prompt 会被插件控制调用的预算截断 |
| 收到一个坏帧就判定连接故障 | 单个无法识别的载荷会终结这个 agent 上的全部存活会话，等于把一个可恢复的缺陷换成一次服务中断 |
| 用 agent CLI 的 `session/load` 重放代替 Ora 自己的记录 | agent 的重放不携带 `stopReason`，被取消的一轮和正常完成的一轮无法区分；而且这样的对话无法整段交给另一个 agent |
| 历史写入失败之后跳过失败项继续追加 | 会产生一份看起来完整、中间却缺了内容的文件；空洞对读它的人和下一个 agent 都不可见 |
| 切换 agent 时立即注入 transcript | 切换之后就被弃用的 Ora Session 白付一次完整注入；而且客户端的 agent 选择本就应该能在不打断正在回复的 agent 的前提下累积 |
| 保留旧绑定以便日后切回去 | 旧绑定的模型上下文停在被离开的那一刻，切回去仍然需要中间这些轮次；把完整 transcript 注入一个全新会话，比调和一个陈旧会话更简单也更可预测 |
| 用「历史里已经有一条用户消息」判定 transcript 已交付 | Ora 在发送之前就记录 prompt，这条证据与「请求在发出途中失败」同样一致，会造成 transcript 被静默丢失 |
| 按闲置时长回收 warm session | 基于时长的回收需要一个计时器才诚实，而且会让离开片刻又回来的用户白付一次完整重建；warm 条目本来就不持有任何值得回收的对话 |
| 驱逐时把被预留的条目也计入上限 | 会为了给一个正在离开池子的会话腾位置，而退休掉用户仍在看的会话；当被预留的条目数超过上限时，更会为了达到一个永远达不到的总数而删光剩下的全部条目 |
| 把标题获取窗口的状态持久化 | 这个窗口描述的是「这个 actor 这一次 attach」这段时间；跨重启恢复它，会让一个早已被用户命名的会话再次被 agent 改名 |

## 不能直接改写的状态

- **工作流图快照里的旧式 agent 短 id。** 已保存的工作流图会把执行器选定的 agent 标识持久化在它的
  快照 JSON 里。在 agent 身份命名空间化之前保存的快照，可能存着 `open_code` 这样的旧拼写。这个值
  被原样送到运行时，因此匹配不到任何受监督的 agent，该节点报告为「provider 不可用」，直到用户重新
  选一次模型。**这里刻意不做改写**：翻译旧拼写等于加一层兼容层，而改写快照 JSON 等于做一次数据库
  迁移，两者都应当被单独决策，而不是夹带在别的改动里。安全的修复路径是在受影响的节点上重新选择
  模型，选一次就永久生效。
- **Session 数据行的 `agent_ref` 列。** 这一列本来就存着命名空间化的取值，所以「agent 身份变成开放
  集合」这件事没有引发任何数据迁移。前端的 agent 目录完全由运行期派生：一个存储下来的用户偏好即使
  指向一个当前不可达的 agent，也按原样带走而不是丢弃；而一个 Ora Session 自己的绑定始终按写入值
  报告，因为那才是这段对话真正跑在其上的东西。
- **sessions root 目录下的历史文件。** 每个文件以 Ora Session 的 id 命名，并且只被追加。删除
  Ora Session、Workspace 或 project 时，按事先收集好的 Ora Session id 尽力删除对应文件——数据行此时
  已经消失，孤儿文件不可达，在这一步失败只会留给用户一个删不掉的东西。

## 本决策未解决的问题

- **warm 池与「按连接代次缓存的模型列表」这两份副本的失效订阅并不完备。** 它们唯一的失效手段是比对
  `generation`，而 D13 里的 agent CLI 进程替换走的是对同一个插件运行时的一次 IPC——插件进程、ACP
  传输、连接对象全部原样保留，`generation` 不变。于是 D13 的分离通知只到达 actor，不到达 warm 池，
  也不到达模型列表缓存。两类陈旧副本的危害不同：陈旧的 `agent_session_id` 会造成硬故障并写下持久
  的坏数据行；陈旧的模型列表只让选择器多列或少列几个模型，且能自纠正。修正这个缺口需要同时改变
  「provider session 何时创建」和「模型发现由谁拥有」两条边界，超出本根决策的范围，留给后续 ADR。
- **权限审批策略。** D12 的一律自动放行是当前的产品状态而不是终局。引入需要用户确认的审批，需要
  定义策略的存储位置、超时语义和跨会话的记忆规则，属于独立决策。
- **Agent 插件的权限收窄。** Agent 插件因为要启动并拥有 agent CLI，目前获得了接近宿主本身的权限。
  收窄推迟到 agent 契约被证明稳定之后；届时改变的只是插件如何被启动，不改变 ACP 消息中继这条管道。
