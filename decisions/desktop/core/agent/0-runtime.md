# Agent 运行时：插件供给的开放 Agent 身份、每 agent 一条受监督连接、每会话一个串行 actor

Ora 的 Agent 运行时把「一个用户可见的对话」映射到「某个 agent 进程内的 provider session」，并为
这条映射提供进程监督、失败隔离、流控、历史归属与生命周期序列化。运行时自身不实现任何 agent、
不搜索 `PATH`、不 spawn 任何 CLI，也不解析 ACP 载荷：每个 agent 都由一个已安装的 Agent 插件供给，
插件独占其 agent 进程，运行时只中继不透明的 ACP 帧。据此，agent 身份是**开放集合**，进程监督
粒度是**一个 agent 一条连接**，并发粒度是**一个 Ora 会话一个串行 actor**，对话的可回放事实由
**Ora 自己的历史文件**而非 provider 的重放拥有。

该决策已由 `crates/backend/src/agent_runtime`（含 `plugin_agent` 子模块）、`ora-acp`、`ora-history`
与 `ora-plugin-lifecycle` 落地，`status: implemented` 表示本文描述最终系统承诺而非实现过程。
兼容性边界有两条硬约束：会话历史的本地文件布局（sessions root 下每会话一个 append-only JSONL），
以及 Session 行持久化的 `agent_ref` 取值空间。本 ADR **不**承担以下义务：定义 ACP 协议本身、
定义历史文件格式与其排序/失败语义（属 `ora-history`）、定义插件的分发与安装（属插件领域）、
定义 Effect 的通用收敛协议（属 `desktop/core/effect/0-effect-system-foundation.md`）。本 ADR 也
不承担改写既有持久化数据的迁移义务，见「不能直接改写的状态」。

## 背景

agent CLI 是外部进程：它会崩溃、会被卸载、会在机器上根本不存在，也会在一轮对话进行到一半时消失。
而一个 Ora 会话是用户资产：它有标题、有可回放历史、有归属的 Workspace 与工作目录，必须跨进程
重启存续，并且必须能被交给另一个 agent。

若每个会话各自持有一个 agent 进程，进程数随对话数增长，同一 CLI 的多实例还会争抢其自身的全局
状态；若全部会话共享一条无监督连接，一次崩溃会同时毁掉所有对话，且没有任何一层能判断「哪些
provider 身份已经失效」。运行时因此在两者之间取一个明确的中间层，并用连接代次把两层绑起来。

## 决策

### D1：Agent 身份是开放集合，按插件供给的持久化身份建键

`agent_ref` 是开放字符串，取值为已安装 Agent 插件所供给的 agent 身份（package name），而不是编译
期封闭枚举。监督器按该身份建键；插件进程则由插件生命周期以 package address（`<namespace>/<name>`）
拥有。两者是**不同字符串**，运行时在唯一一处完成翻译，其余位置不得互相代入。

- 只有 `agent` 类插件供给 agent；`ui` 类插件贡献界面，从不被监督。
- 声明了已被占用身份的包被忽略而不是替换既有监督器：把用户既有的 agent 悄悄交给另一个包，比
  忽略第二个包更坏。
- 集合在每次安装、卸载与扫描后 level-triggered 重新对齐，所以运行期安装的插件无需重启即可出现在
  选择器与会话路由中；集合以锁内替换而非重建的方式维护，使 warm 池与存活 actor 的既有克隆立即
  观察到变化。
- 查不到某个 `agent_ref` 是**正常运行状态**而非数据损坏：一个会话可以比供给其 agent 的插件活得
  更久，报为 `agent_runtime_unavailable`。

用 package address 建键会让每一条已持久化的绑定都不可解析——它是一个「编译通过、读起来正确、
却匹配不到任何会话」的错误，因此翻译必须收敛在声明了两个身份的那一处。

### D2：每个 agent 一条受监督连接，`generation` 只表示 ACP 传输代次

每个 agent 身份对应一条独立监督的 ACP 连接，由一条专属运行时线程驱动——Desktop 的同步 bootstrap
不保证存在环境 Tokio 运行时。监督器一次只运行一代进程，且只有在上一代被完整回收之后才重试。

`generation` 是单调递增的 **ACP 传输代次**：只有当监督器重新附着并完成 `initialize` 时才自增。它是
运行时判断「一个 provider session 身份是否仍可解析」的唯一依据——路由按代次绑定，来自旧代次或
已卸载会话的事件一律作为陈旧丢弃。

进程归插件生命周期所有，连接只借用该代次的通知 tap：一代结束意味着请求生命周期停止该插件，而不是
由运行时终止进程。这样「设置界面报告的插件运行状态」与「agent 运行时实际在对话的对象」始终是同
一件事，且下一次附着得到的是全新进程而不是半用过的一代。

`session/new` 的应答揭示 provider session id 之前，本连接会临时缓冲无法归属的 setup 通知；注册路由时
把匹配的通知排入该路由，最后一个并发 setup 结束时丢弃仍未匹配的部分。权限请求与响应**从不**被当作
setup 通知缓冲，没有路由时立即取消或丢弃。

### D3：启动失败按「另一次尝试能否得到不同答案」分类

| 分类 | 触发 | 处置 |
| --- | --- | --- |
| 可重试且不记录 | 插件报告其 agent CLI 未安装（`agent_not_installed`）、插件被禁用或尚未安装 | 保持 `Unavailable` 并持续重试，不写日志、不计入崩溃计数 |
| 可重试并记录 | 一般启动、附着、`initialize` 失败 | 记录警告，退避重试，计入崩溃计数 |
| 终态 | 插件自带的可执行文件在本机跑不起来（`agent_unusable`）、注册未覆盖 agent 契约、协议版本不受支持 | 发布 `Failing`，本进程剩余时间内放弃该 agent |

分类线只有一条：另一次尝试能否得到不同答案。缺失的本地 CLI 是**可预期的本地配置**——用户可以在
Ora 运行期间装上它——所以静默重试；每次重试都写一行日志会让运行日志被单个未安装的 agent 淹没，而
`Unavailable` 已经把该事实送达界面。反之，一个包自带的可执行文件在本机跑不起来，每次尝试都会
完全相同地失败；终态处理是唯一能让该包故障**被看见一次**、而不是永远藏在安静的「未安装」报告
背后的方式，这也是只有这一类失败把插件自己的消息透传出来的原因。

契约校验在附着完成的那一刻就运行——早于任何会话存在、早于有用户在等一次 prompt——所以契约不符
表现为一个不可用的 agent，而不是某个人对话中途的失败。

退避从 250 毫秒倍增至 30 秒上限。一分钟内超过三次**计入的**失败打开该 agent 的重启断路器：发布
`Failing`、停止本进程内的自动重试，其余 agent 完全不受影响。

### D4：每个 Ora 会话一个串行 actor，prompt 所有者唯一，加载视图只跟随

每个持久化 Ora 会话有且只有一个 actor，串行化其加载、prompt、权限、取消、停止、删除与用户改名
命令。绑定到同一 agent 的会话共享其进程与连接；绑定到不同 agent 或不同 actor 的会话并行推进。

加载一个会话总是暴露同一个对话：空闲会话从 Ora 的记录恢复；已有 prompt 拥有该会话时，加载先经由
其接入点回放记录，再跟随此后的实时事件与同一个轮次边界，既不开始第二个 prompt，也不夺取第一个的
所有权。实时扇出有界（每个跟随视图 256 项），慢的视图不会拖住所有者；耗尽队列的视图收到**显式**
流错误而不是无解释的断连。关闭一个跟随视图不取消它跟随的 prompt。

取消是会话级控制：它触达拥有该 prompt 的一方（即使调用者只是在跟随），记录一轮被取消的对话，并
在 provider 正常结算后保留 actor 供下一次 prompt 使用。仅取消一条加载流则只分离该视图。

actor 的调度器回调只持有弱命令发送端。当删除、切换或管理器关停释放最后一个外部发送端后，命令
通道关闭，actor 释放其连接、recorder、repository 与调度器克隆——回调在执行时升级发送端，正是为了
不隐藏一个使 actor 永生的克隆。

### D5：三级通道与代次绑定路由把爆炸半径限制在一个 agent

| 层 | 形态 | 目的 |
| --- | --- | --- |
| 连接读取 → 中央路由 | 无界、保序 | 连接级解析不因某个会话的背压而阻塞 |
| 路由 → 每会话事件 FIFO | 有界 256，保序 | 更新、权限请求与终结响应保持 provider 发出的顺序 |
| 路由 → 每会话控制通道 | 独立、无界 | 连接丢失与队列溢出不被压在事件 FIFO 之后 |

会话溢出、加载超时或取消只影响该会话；分帧、相关性或传输故障使该代次失效，并只停止注册在该
agent 上的会话。**插件进程死亡的爆炸半径因此与 CLI 进程死亡完全相同：一个 agent。**

终态控制不得越过已被 FIFO 接受的事件：活跃 actor 先排空已接受的事件再应用控制，并在有界事件突发
（32 条）之后强制轮询命令通道，使用户命令不被实时事件流饿死。来自 agent 的未知 JSON-RPC 请求得到
一个相关的 `-32601` 应答而不终止连接；畸形帧、无法匹配的响应、超尺寸帧与 stdio 丢失则是连接故障。

历史回放是唯一施加背压而非快速失败的流：一段录制的对话远大于 256 项队列，尚未排空它的消费者并
不是断连的消费者。

### D6：response fence 定义一轮对话的边界

一次加载或 prompt 只有在消费到与之匹配的响应之后才算完成。由于会话事件是保序的，响应之前观察到的
更新与权限请求必然属于同一次操作，尾部事件也不会泄漏进下一次 prompt。轮次在该 fence 结算之后才被
记录。

取消在其 5 秒宽限期内继续消费直到匹配的响应；provider 未按时结算时，actor 先记录已接受的事件快照
再隔离该路由。空闲状态下抵达的残留事件在接受下一个命令之前被消费掉，因此不会跨轮次。

### D7：Ora 拥有 transcript，agent 拥有 model context

Ora 自己记录每一次对话，`session/load` 的调用目的**只是**让 agent 恢复回答下一个 prompt 所需的
上下文；其重放被排空并丢弃。用户看到的是 Ora 的记录，因为那是无论当前绑定到哪个 agent 都相同的
那一个对话。

- 记录的是 Ora **选择保留**的内容，而不是它发出的内容：prompt 在调用 agent 之前依据请求块记录，
  provider 回显的用户消息块被忽略，因此 Ora 注入的上下文永不进入记录。
- 流式更新先记录后转发：中途断开的客户端只损失流，不损失「agent 产出了什么」的记录。
- 每一轮以其 `stopReason` 收口。轮次边界还负责结算 agent 遗留的未终结工具调用：**只有** agent
  自行正常结束的轮次才把它们记为完成；其余每一种结束（取消、超出 token、被拒）都让它们保持未完成，
  因为该调用可能是被打断而非完成的，而 `stopReason` 已经说明了是哪一种。
- 无法解码的完整 JSONL 行不参与回放，但以带类型的完整性提示报告其聚合数量；已有的 `Gap` 记录同样
  作为提示回放而不是被跳过。二者都不猜测其轮次位置，因为追加顺序不是时间线顺序。会话保持可写：
  过去的损坏是完整性警告，能否继续追加由历史状态单独描述。

删除移除 Ora 的记录与 Ora 自己写的历史文件，**不**删除 provider 端历史。ACP 的 session delete 只
作用于一类对象：Ora 创建、从未持久化、也从未交给用户的 warm session。用户能看见的会话只被关闭。

### D8：历史写入失败使会话降级，而不是跳过记录

一份**跳过**了记录的历史比一份**停止**记录的历史危险得多，因为空洞对回放它的人——包括下一个
agent——不可见。因此一次写入失败让该会话永久停止记录，而不是继续追加到空洞之后。

- 已经在流式输出的轮次照常完成：agent 的工作是真实的，文件保存与否都一样；让它失败等于告诉用户
  什么都没发生。
- 自身 prompt 无法被记录的轮次在调用 agent **之前**被拒绝：此刻什么都还没发生，拒绝它不损失任何
  东西，而发出去会把对话带到记录追不上的地方。
- 会话进入携带操作系统原因的降级状态，后续 prompt 被拒绝，直到显式恢复。
- 恢复操作在接受新内容**之前**追加一条 `Gap` 记录命名是什么中断了该文件，然后把会话变回可写。
  恢复不还原丢失的内容，它记录曾经丢失过。
- 完全无法读取的历史文件以同样方式降级：在不知道哪些位置已被占用的情况下追加会覆盖它们。这与
  个别完整行不可读不同——后者保留了幸存的时间线。
- 无法读取历史的加载**使加载失败**，而不是完成一次空加载：加载正是用户要求看到这段对话的方式，
  而空视图与「这个会话从未说过话」无法区分。

### D9：切换 agent 是「立即重绑定 + 惰性注入」，交付以 provider 接受请求为准

`switchSessionAgent` 把一段对话移到另一个 CLI 上。会话保留其标识符、其 Workspace 与其历史，只有
绑定改变。

- 新绑定从 warm 池按键**认领**而不是在此握手，键与选择器展示该 CLI 模型时预热的那一个相同：对话
  因此落到用户真正配置过的那个会话上，常见路径不付出任何往返代价。解析与预留在同一临界区完成。
- 认领成功之前不拆除任何东西，所以不可用的 CLI 让对话原地不动。切到会话已经在运行的 CLI 报
  `session_agent_unchanged`，且在认领**之前**判定——预热那个 CLI 只会造出第二个 provider session，
  再用一个无法区分的绑定替换当前绑定。历史降级的会话拒绝切换。
- 认领**之后**的失败通过丢弃预留把条目还给 warm 池，provider session 保持存活可供重试。Ora 在此
  从不关闭它：那个决定属于池。
- 重绑定会停止当前绑定的 actor，因此客户端被期望**随下一条消息**提交这次移动，而不是在选中 CLI 的
  瞬间提交。选择记录在客户端累积，回到会话当前所绑定的 CLI 时撤回记录而不是提交一次空移动。
- transcript **惰性注入**：切换本身不发送任何东西，录制的对话作为前置内容块附加到下一个 prompt。
  切换后即被放弃的会话不产生任何代价。ACP 没有把一段对话装入 agent 的方法，因此每一轮记录坍缩成
  一条被**展示**给接收方而非由它参与的用户消息，注入块的前言正是用来解释这一点。
- 绑定是否仍欠 transcript 由记录派生（末尾的 `AgentSwitched` 之后没有 `HandoffDelivered`），因此它
  能在丢失持有该知识的 actor 之后、以及一次重启之后继续成立，不依赖任何内存标志。
- 债务只在 provider **接受**了携带 transcript 的请求之后结算，内存与文件一并结算。接受请求是 Ora
  能观察到的关于交付的最后一件事，此后帧已在 agent 的 stdin 上。据此，中途丢失的连接算作已交付，
  否则会把整段对话再次注入一个已经持有它的 agent——而 transcript 前言声称这段工作属于**另一个**
  agent，那样就成了假话。反过来，交付记录写入失败会再交付一次 transcript，这是无害的那个方向。
  用户轮次不能代替交付记录，因为 Ora 在**发送之前**记录 prompt：一条位于切换之后的用户轮次，与
  「transcript 已交付」和「请求在发出途中失败」两种情况同样一致。
- transcript 没有尺寸预算。超出接收模型上下文窗口的失败由 provider 报出。

### D10：warm session 让模型在第一条消息之前可选

ACP 只在 `session/new` 或 `session/load` 的应答里报告会话配置选项，模型选择器就在其中。因此在会话
存在之前无法选择模型，而选择器必须在空聊天上就能渲染。据此，打开一个聊天面即创建 provider session
并将其池化。

- warm session 只存在于内存，attach 之前没有 Ora 会话行，放弃一个聊天面不会在 Ora 侧留下空历史。
- 以 `(target, agent_ref, owner)` 为键。Desktop 交互会话使用单一的交互 owner；工作流节点使用内部的
  节点 owner，使并发分支互不认领对方的会话，而不必把界面身份暴露进契约。
- 一个条目服务该 target 下同一 CLI 与 owner 的全部会话，而不是每个对话一个。「每键一个条目」是稳态
  而不是交接期间成立的不变量：认领撞上进行中的 attach 时会临时产生第二个条目。
- Ora 会话标识符在 warm 时铸造而非持久化时，客户端因此不必跟随标识符变化；attach 之前该标识符不
  出现在任何会话查询里。
- 两个操作把条目取出池子，且都**先预留**：attach 按**标识符**寻址，因为该标识符会成为 Ora 会话
  自己的，客户端已经用它锚定了乐观轮次；切换 agent 按**键**寻址，因为标识符属于池并被丢弃，移动的
  只有绑定。按键寻址也是切换能在预热条目已消失时解析到一个新条目、而不是失败的原因。
- 预留是**值语义**：它在 `Drop` 中归还。attach 持有预留期间还要等待生命周期锁，而命令层会在客户端
  断开时丢弃整个请求 future；只有绑定到值的释放能保证这两条路径都不搁浅一个条目——驱逐刻意跳过
  被预留的条目，因此无人释放的预留会钉住一个没有任何上限能回收的 provider session。
- 工作目录在每次请求时从 target 重新解析并与创建时比对：移动或重建过的 worktree 使条目退休，而不是
  悄悄指向陈旧路径。
- 配置改动对 warm 与已持久化会话一视同仁并被记住。冷条目只记录选择而不重建；重建时重放这些选择，
  agent 拒绝的重放降级为 agent 实际报告的选项，而不是让用户已经输入的 prompt 失败。
- **没有任何东西因为闲置而释放一个 warm session。** warm session 按定义是用户从未 prompt 过的会话，
  闲置条目不持有任何可回收的对话，只持有 agent 侧一个空会话。存活条目上限（16）与总条目上限（64）
  是纯计数，在唯一可能越界的时刻——创建另一个会话时——执行；期限式回收需要计时器才诚实，并且会
  让离开片刻再回来的用户白付一次完整重建。
- 删除 Task 或 project 丢弃其聊天面的条目，这是唯一能回收它们的时机：target 已经消失，没有请求能
  再命名该条目，而计数上限只在开出足够多新面板之后才够得着它。

### D11：首标题获取是非持久化、可被抢占的窗口

新附着的会话拥有一个仅存在于内存的标题获取窗口，自附着起就接受合法的 ACP 标题推送。首轮 prompt
只有在以 `EndTurn`、`MaxTokens` 或 `MaxTurnRequests` 结束时才开启回退窗口；拒绝、取消、请求失败与
连接失败都不消耗这次资格。

- agent 在 `initialize` 中公布了会话列举能力时，在合格 prompt 之后的第 3 秒与第 10 秒各安排一次尝试；
  每次请求上限 5 秒，最后一次尝试无论结果都关闭窗口。未公布该能力则不发任何列举请求，窗口保持
  只接受推送直到第 10 秒边界。
- 推送与列举标题共用同一条校验与持久化路径。窗口开启期间，最后一个写库成功的合法 agent 标题获胜；
  重复标题不写库也不发事件，空白、null 与超长值被忽略。
- 标题轮询是 actor 拥有的低优先级工作：调度器回调只入队内部命令，actor 空闲时才发出 ACP 请求，新的
  用户操作可以抢占它。prompt、加载、停止、切换、删除、用户改名、队列失败、连接丢失或 actor 终止都
  会关闭或抢占该窗口，因此标题轮询永不延迟用户工作。
- **用户驱动的改名锁定窗口**并重新持久化所选标题，之后的推送或列举标题都不能覆盖它。
- 获取状态不进入 SQLite，恢复既有会话时以禁用状态启动。写库成功之后才发布标题失效事件，且事件只
  携带 Ora 会话 id——它是失效提示而不是日志，客户端重新拉取权威标题。

### D12：权限请求当前一律自动放行

Ora 目前没有可配置的审批策略，活跃 actor 收到的每个权限请求都被立即授予，优先选择同时记住该选择的
选项，从而使同一轮次内后续同类调用也无需值守。放行走的是与真实用户选择相同的应答路径，因此未来
的策略只需在此处设闸并把请求留在待答集合里，无需改动协议或流控。

`RespondToPermission` 命令保留给「请求抵达时没有活跃 prompt」的情形，此时它以「不在待答状态」失败，
因为没有任何东西被留着未答。加载期间或会话空闲时抵达的权限请求一律以取消作答。

### D13：Effect 替换 agent 进程后必须分离受影响的存活会话

Effect 协调会重启一个 Agent 插件的 agent 进程，使其重新读取被物化的表面，这会静默作废该进程持有的
全部 provider 端会话。运行时因此对外提供**一个能力**：在 agent 进程被替换后分离受影响的存活会话，
使下一次交互经由普通加载路径重新建立，而不是对着新进程无法解析的 id 发 prompt。

分离时不调用 `session/close`——那只会要求一个全新的 agent 关闭它从未听说过的 id。分离已经足以修复
而不是终结会话：没有通道时 prompt 被拒绝，而建立通道的加载正好会调用 `session/load`。

通知以插件地址寻址、向全部 actor 广播，由每个 actor 自行判断是否绑定到该 agent——注册表以 Ora 会话
为键，不携带 agent 索引。投递是尽力而为：已经结束的 actor 不可能还持有陈旧通道。Effect worker 依赖
的是这一个能力而不是整个 agent 运行时，因此一次收敛在没有运行时的情况下仍可被验证。

## 边界与上限

| 边界 | 值 |
| --- | --- |
| `initialize` 握手 | 15 秒 |
| `session/load` 不活动期限 | 30 秒，每条会话更新重置 |
| `session/new` 与配置选项请求 | 30 秒总预算 |
| prompt 流 | 无期限，由 provider 或取消结束 |
| 取消结算宽限 | 5 秒 |
| 插件停止 agent 的应答期限 | 2 秒（远小于取消宽限） |
| 连接重试退避 | 250 毫秒倍增至 30 秒上限 |
| 重启断路器 | 一分钟内超过 3 次计入的失败 |
| 会话事件队列与跟随视图队列 | 各 256 项 |
| setup 缓冲 | 256 条通知，满时丢弃最旧 |
| JSON-RPC 帧 | 8 MiB |
| 序列化后的结构化 prompt | 16 MiB |
| warm 条目 | 存活 16 / 总计 64，纯计数 |
| handoff transcript | 无上限 |

`session/load` 的期限是**不活动**计时器而不是总预算：持续流式输出的 provider 可以无限期运行，而
静默 30 秒的 provider 只使该会话失败。prompt 以有序 ACP 内容块透传，包含文本、图像、音频、资源
链接与内嵌资源；空列表或只含空白文本的列表被拒绝，16 MiB 从抵达 provider 之前的序列化载荷度量。

## 必须保持的不变量

1. Agent 运行时不 spawn 任何 OS 进程，也不解析、校验或改写 ACP 载荷；运行什么由插件决定，进程由
   宿主的子进程接口创建并拥有。
2. 一个 agent 身份对应一条受监督连接；一个 Ora 会话对应一个串行 actor。
3. `generation` 只表示 ACP 传输代次，只在监督器重新附着并完成 `initialize` 时自增。
4. 路由按代次绑定；来自旧代次或已卸载会话的事件必须作为陈旧丢弃。
5. 任何单点失败的爆炸半径不得超过一个 agent。
6. 一个会话至多一个 prompt 所有者；跟随视图不得阻塞所有者，也不得取消所有者的 prompt。
7. 一次加载或 prompt 必须消费到与之匹配的响应才算结束，轮次只在该 fence 结算之后被记录。
8. Ora 会话身份、标题与历史归 Ora；provider 端历史不被 Ora 删除。
9. ACP session delete 只允许作用于 Ora 创建、从未持久化、也从未交给用户的会话。
10. 历史写入失败必须使会话降级并拒绝后续 prompt；恢复必须先记录 `Gap` 再接受新内容。
11. handoff 债务必须能从历史记录派生，且只有在 provider 接受了携带 transcript 的请求之后才结算。
12. warm 条目的每一次取出都必须先预留，且预留必须在失败或调用者消失时归还。
13. 用户驱动的改名锁定标题获取窗口，之后的 agent 标题不得覆盖它。
14. agent 进程被替换后，任何仍指向该进程的 provider session 身份都必须被作废，不得继续用于 prompt、
    配置或绑定。

## 为什么不是这些替代方案

| 方案 | 否决理由 |
| --- | --- |
| 每个会话一个 agent 进程 | 进程数随对话数增长，同一 CLI 的多实例争抢其自身全局状态，且没有一层能统一判断 provider 身份失效 |
| 全部会话共享一条无监督连接 | 一次崩溃毁掉全部对话，且无法把失败限制在一个 agent |
| 以封闭枚举表示 agent 身份 | 有哪些 agent 在构建期不可知；每新增一个 agent 都需要发版，且已安装插件无法在运行期出现 |
| 用 package address 建键监督器 | 与会话持久化的 `agent_ref` 是不同字符串，会让每条既有绑定不可解析，且失败形态是「静默匹配不到」而非报错 |
| 在运行时内解析 CLI 路径或搜索 `PATH` | 把「某个 agent 如何被安装」泄漏进通用运行时；插件被沙箱化，也无法可靠算出包内可执行文件的宿主路径 |
| 在插件运行时的请求相关性之上再包一层 ACP 相关性 | 一次帧会有两个超时与两条取消路径，多分钟的 prompt 会被控制调用预算截断 |
| 一个坏帧即判连接故障 | 单个无法识别的载荷会终结该 agent 上的全部存活会话，把可恢复缺陷换成一次中断 |
| 用 provider 的 `session/load` 重放代替 Ora 的记录 | provider 重放不携带 `stopReason`，被取消的轮次与完成的轮次无法区分，且对话无法交给另一个 agent |
| 历史写入失败后继续追加 | 产生一份看起来完整、中间却缺失的文件；空洞对回放者与下一个 agent 都不可见 |
| 切换时立即注入 transcript | 切换后即被放弃的会话白付一次完整注入；而客户端的选择本就应能在不打断进行中回复的前提下累积 |
| 保留旧绑定以便切回 | 其上下文停在被离开的那一刻，切回仍需要中间的轮次；把完整 transcript 注入一个全新会话比调和一个陈旧会话更简单也更可预测 |
| 用「用户轮次已存在」判定 transcript 已交付 | Ora 在发送之前记录 prompt，该证据与「请求在发出途中失败」同样一致，会造成静默丢失 transcript |
| 按闲置时长回收 warm session | 期限需要计时器才诚实，且会让离开片刻再回来的用户白付一次完整重建；warm 条目本就不持有可回收的对话 |
| 驱逐时把被预留的条目计入上限 | 会为一个正在离开池子的会话而退休用户仍在看的会话；预留数超过上限时更会为了一个永远达不到的总数删光全部条目 |
| 把标题获取状态持久化 | 它描述的是「这个 actor 这一次附着」的窗口；跨重启恢复会让一个早已被用户命名的会话再次被 agent 改名 |

## 不能直接改写的状态

- **工作流图快照中的旧 agent 短 id。** 已保存的图在快照 JSON 内持久化执行器的 agent 标识，早于身份
  命名空间化的快照可能存有 `open_code` 这类拼写。该值按原样送到运行时，因此匹配不到任何受监督
  agent，节点报为不可用 provider 直到重新选择模型。**不改写**：翻译旧拼写是一层兼容层，而改写快照
  JSON 是一次数据库迁移，二者都应被单独决策而不是顺手夹带。安全的修复路径是在受影响节点上重新
  选择模型，一次即永久生效。
- **Session 行的 `agent_ref` 列。** 该列早已存储命名空间化取值，身份开放化没有引发迁移。前端的
  agent 目录完全由运行期派生，存储的偏好即使指向已不可达的 agent 也按原样带走而不是丢弃；会话自身
  的绑定始终按写入值报告，因为那才是对话真正运行在其上的东西。
- **sessions root 下的历史文件。** 文件按 Ora 会话 id 命名并只被追加。删除 Ora 会话、Workspace 或
  project 时按收集到的会话 id 尽力删除对应文件；行已经消失，孤儿文件不可达，在此失败只会留给用户
  一个删不掉的东西。

## 本决策未解决的问题

- **warm 池与连接代次模型缓存的失效订阅不完备。** 二者唯一的失效手段是比对 `generation`，而 D13 的
  agent 进程替换走的是对同一插件运行时的一次 IPC，`generation` 不变。分离通知因此只到达 actor，
  不到达 warm 池与模型缓存。会话身份陈旧会造成硬故障并留下持久坏数据；模型列表陈旧只影响选择器
  且能自纠正。修正这一缺口需要改变「provider 会话何时创建」与「模型发现由谁拥有」两条边界，超出
  根决策范围，留给后续 ADR。
- **权限审批策略。** D12 的自动放行是当前产品状态而非终局；引入 human-in-the-loop 审批需要定义
  策略存储、超时语义与跨会话记忆，属独立决策。
- **Agent 插件的能力收窄。** 插件因为要 spawn 并拥有 agent CLI 而获得接近宿主的权限。收窄推迟到
  agent 契约被证明之后，且届时只改变插件如何被启动，不改变 ACP 中继管道。
