# Desktop 工作流调试从选中的节点执行继续

用户在运行页选择一次执行、编辑节点配置、预览影响，再在同一个 WorkflowRun 内继续。调度器复用能够证明仍然有效的结果，对受影响的执行创建新尝试。选择容器里的成员可以保留已经结算的轮或项，选择容器本身则从入口重新执行。

本决策确定 Desktop 运行内调试的首版行为。样例给出表单、预览、确认和调度共同使用的目标与字段。普通失败恢复沿用原有恢复范围，并从当前有效修订读取配置，编辑器继续管理草稿、图结构与发布。存量运行按实际保存的证据开放调试。[首版决策](https://github.com/ora-space/circus/issues/1426#issuecomment-7126861949)

## D1　选择一次执行，按运行记录修订

运行绑定发布快照。修订 0 使用该快照；每次调试生效生成一个递增的运行内修订，记录父修订、选中位置、补丁和生效范围。尝试绑定派发当时的实际配置与生产它的修订。查询历史可还原旧配置、输入来源、分支决定和尝试结果。两个 run 使用同一快照也各自拥有修订序列。

- 已有当前有效执行行的位置用 `runId + nodeRunId` 选择，包括已登记、正在退避等待派发的自动重试。服务端解析根执行、定义节点、容器执行（若有）、轮/项位置及选中尝试。重试可能产生多条行；历史尝试可读，预览只接受该位置当前有效的尝试。前端不能用节点标题、数组下标或“最新一次”猜行。
- 对尚未首次派发且没有当前有效执行行的位置，使用 `pendingTarget:{rootScopeId,scopeId,nodeId}`，foreach 还须携带所属容器执行和零基项索引。与 `nodeRunId` 二选一。服务端必须能证明该位置存在、属于当前路径且输入就绪。未建立的未来轮次或被排除的分支只显示禁用原因。确认后由原依赖门派发。
- 允许 Running（含 AwaitingInput 投影）、Failed、Cancelled、Succeeded 中满足条件的目标。Pending 运行走原编辑和启动入口。已删除的 run、历史根执行及已有停稳操作（包括栅栏未释放的失败操作）阻止新预览。「历史根执行」是该 run 当前根指针以外的根及其子作用域，例如整次重启前的根。看到交互节点的旧完成按钮时，迟到的确认同样受尝试校验。
- 修改成员时，从选中位置起，在同一容器执行的当前及后续轮/项使用新配置，保留前缀原修订。对同一位置再次修改，按当前有效配置叠加。若回到更早位置修订同一字段，新确认的值覆盖其重算后缀里的旧覆盖；其他字段按其原有生效边界继承。重建容器入口产生新的容器执行，旧成员修订绑定旧执行；预览须展示新容器将采用的成员配置。

**终态运行。** 从 Failed、Cancelled 或 Succeeded 调试时，新修订只授权预览所列的 schedule 及其中声明的条件下游。恢复调度后，范围外已有的 Failed/Cancelled 行保留原终态，独立的未派发位置保持无行。受理时保存调试前的终态及其原错误或取消原因。范围结算时，按当前图和有效控制路径枚举所有必需位置，包含所选分支、实际需要的轮/项和后继。只有每个必需位置均有有效成功结果，才结算为 Succeeded；否则恢复保存的终态和原原因。一个已就绪的必需后继即使尚无执行行，也参与判定。旧错误和新尝试各自的结果均可查询。[终态与恢复基线裁定](https://github.com/ora-space/circus/issues/1450#issuecomment-7149906530)

**普通失败恢复与整次运行重启。** 两者都以运行当前有效修订为配置基线。普通恢复保留原有选点、检查点及工作区策略，在实际派发位置解析该修订。整次重启在同一 run 创建新根，顶层节点的修订继续生效。任一入口重新创建容器执行时，都按新容器的入口配置执行，绑定旧容器执行的成员覆盖仅供历史查询。只有成功切换发布快照才重置配置基线。

**切换发布快照。** Failed/Cancelled 运行可沿普通恢复入口切换到兼容的新发布快照。提交前提示「运行内修改将不再生效」。成功切换时将新快照与新的运行修订一起提交，以新快照作为有效配置基线。旧补丁、实际配置和尝试留在原修订历史，均不重放；旧预览随基线变化过期。兼容性校验失败时保留原快照及生效修订。根身份按当前根指针判定，快照基线按修订判定。

### 尚未派发的目标

运行 P 处于 Running。Start 已提交 text="hello"，Agent X 的前置均已就绪，调度器尚未认领 X，库中没有它的节点执行行。页面从运行查询取得逻辑位置，表单将同一位置交给预览。根级节点的 scopeId 与 rootScopeId 相同；while 成员使用所属轮的实际 scopeId，foreach 成员的 scopeId 取容器所在作用域，另带 containerNodeRunId 和零基 index。

```json
{
  "preview":{"runId":"P","pendingTarget":{"rootScopeId":"rootP","scopeId":"rootP","nodeId":"X"},"baseRevision":0,"patch":[{"op":"replace","path":"/agentConfig/prompt","value":"复述 {{#start.text#}}"}]},
  "result":{
    "previewId":"pP","baseRevision":0,
    "target":{"rootScopeId":"rootP","scopeId":"rootP","nodeId":"X"},
    "keep":["start.text"],"invalidate":[],"stop":[],"schedule":["X","output"],
    "workspace":"keep","externalActionsMayRepeat":true
  },
  "commit":{"runId":"P","previewId":"pP","requestId":"kP"}
}
```

确认在运行门内再次证明 X 仍未派发、前置仍就绪。生效后进入正常就绪队列，首次派发才分配 nodeRunId，并以修订 1 执行一次 X。历史把首次尝试关联到此次逻辑目标。若预览后 X 已先被调度，确认返回 `stale_preview`，页面重查后使用实际尝试。

| 不能预览的输入 | 返回给页面的具体原因 |
| --- | --- |
| 已定位 X，但 Start 尚未提交 text | 缺少前置 Start 的已提交值 start.text；不返回 previewId。 |
| 只给出成员 nodeId，缺少可区分其两次容器执行的上下文 | 指出缺少的 scopeId 或 containerNodeRunId、index，要求重选具体位置；不返回 previewId。 |

## D2　编辑和预览

表单以服务端返回的执行位置、当前修订、有效配置、作用域内变量目录和可选模型为初值。输出相对于该节点规范化 `data` 的有类型补丁。`replace` 的路径须存在于规范化后的有效配置；预览、提交重放与表单使用相同的默认值和旧格式转换。仍缺少的叶子返回字段路径，表单只提供可提交的操作。禁止越过字段白名单、改动节点身份、分支 ID、顺序、端口及连线。

| 节点 | 首版可编辑字段 | 预览前校验 |
| --- | --- | --- |
| Agent | `agentConfig.prompt`、现有 executor 的 `modelId` | 模型与执行器相容，模板变量在选定作用域可见且类型适用。 |
| Condition | 既有 `cases` 内的判断条件及组合逻辑 | 保留原分支身份和 ELSE，操作符、变量选择器及比较值类型符合该图。 |
| Loop | `loopConfig.until`、已有轮变量的反馈选择器、`maxIterations` | 保留轮变量声明，校验反馈类型、退出比较及既有轮数范围。 |
| Iteration | `iterationConfig.iteratorSelector`、`collectSelector`、`errorStrategy` | 首版运行页只提供声明为数组的根变量。提交嵌套数组源时预览返回 iteratorSelector 字段错误。收集值来自区域内声明且与现有下游兼容，沿用原启动上限。 |

预览在发布快照与已生效修订组成的图上模拟，复核图、选中位置及新引用在其求值位置的作用域和类型。目标启动必需的值和计划复用的值都要有该运行、有效执行作用域、生产尝试、已提交结果与仍可达的控制路径。允许读取未赋值状态的条件（如存在性判断）将该状态纳入读集。Loop 新轮次的退出条件、反馈等引用重算产物时，按实际求值时点读取本轮产出。轮内还要能还原轮入口、反馈或冻结项值，以及本轮目标之前的变量版本。当前全局变量池的同名值、文本日志或画布位置都不足以证明来源。有效的失败账本条目可在已结算的 foreach 前缀依原错误策略保留。

预览只读。成功返回绑定具体目标、规范化补丁、修订和计划所依赖事实版本的 `previewId`，列出复用、失效、待执行/重算范围、需停稳的在途尝试及工作区提示。旧路径的已提交值从当前投影失效，与再次调度哪个节点分别表达。无法预知的分支或后续轮次标为条件范围，用户确认的是这个边界。校验失败返回字段路径或缺失事实，且没有可提交凭据。若旧数据只够证明容器入口，可显示单独的入口选项，用户选中后须重新预览更大的范围。

## D3　两个接口样例

下列对象分别对应预览请求、预览结果和确认请求。`keep`、`invalidate`、`schedule` 在样例中列出事实或执行位置的简称；真实引用须能定位到运行内的具体记录或限定了作用域的范围。确认读取预览所绑定的不可变内容。文件提示对两个操作相同。

### foreach 五项中的第三项

Start 产生 `[a,b,c,d,e]`。旧 Agent 原样返回输入项。运行 F 中 it1 已结算 a、b，第 3 项的 f3 正在尝试 t3，输入为 c，项 4/5 尚未派发。

```json
{
  "preview": {"runId":"F","nodeRunId":"f3","baseRevision":0,"patch":[{"op":"replace","path":"/agentConfig/prompt","value":"返回 new- 加 {{#iter.item#}}"}]},
  "result": {
    "previewId":"pF","baseRevision":0,
    "target":{"nodeRunId":"f3","nodeId":"agent","scopeId":"rootF","containerNodeRunId":"it1","index":2},
    "keep":["start.items","it1.frozenItems","it1.entries[0..1]","it1.item[2].input"],
    "invalidate":["f3/t3"],"stop":["t3"],
    "schedule":["agent[2]","agent[3..4]","iter.collect","downstream"],
    "workspace":"keep","externalActionsMayRepeat":true
  },
  "commit":{"runId":"F","previewId":"pF","requestId":"kF"}
}
```

成功后 F 的修订为 1。t3 的迟到输出只可查历史。可控 Agent 的开始次数依次为 `[1,1,2,1,1]`，有效成功输出为 `[a,b,new-c,new-d,new-e]`。按冻结输入索引重建 entries，每项恰有一条有效账；output 仍仅投影成功项。若从已完成的第 5 项之后回看第 3 项，则原项 3–5 的账、汇总和消费者一并列入失效，前两项各只调用一次。

### Condition 重新选路

根作用域内，Start 已提交布尔值 flag=true。实例 c1 的 IF A 判断 flag is true，ELSE 通往 B。A 和 B 分别产生 a、b，汇合 J 是按可用变量选择的 Aggregator。旧 J 已读到 a，独立分支 S 已成功。

```json
{
  "preview":{"runId":"C","nodeRunId":"c1","baseRevision":0,"patch":[{"op":"replace","path":"/cases/0/conditions/0/value","value":false}]},
  "result":{
    "previewId":"pC","baseRevision":0,"target":{"nodeRunId":"c1","nodeId":"condition","scopeId":"rootC"},
    "keep":["start.flag","S.output"],"invalidate":["c1.decision","A.output","J.output"],
    "stop":[],"schedule":["condition","B","J"],"predictedBranch":"else",
    "workspace":"keep","externalActionsMayRepeat":true
  },
  "commit":{"runId":"C","previewId":"pC","requestId":"kC"}
}
```

确认后在同一 C 中重新判断，原 IF 标识和连线仍在。有效分支为 ELSE，J 只读到 b；S 的结果可复用。累计 Start/S/A/B 各执行一次，Condition/J 各执行两次。旧 A 与旧 J 仅用于历史展示。若旧 A 仍在执行，先将它列入 stop；B 的首次执行也必须等停稳成功。

## D4　其他起点

| 选择与修改 | 保留 | 重算及可观察结果 |
| --- | --- | --- |
| 顶层 Agent X 改模型，图为 Start → X → Output，独立 S 已完成 | Start 输入和 S 结果 | X 的新尝试从同一输入开始，Output 读取新值；历史可比较 X 的两个配置。 |
| Loop 第 3 轮实例 x3 改提示词 | 轮 1、2 的有效结果，轮 3 入口的 carried values、同轮中有效前置 | 从 x3 重算本轮后继及反馈/退出。若新结果令条件成立，发布第 3 轮导出，作废旧第 4 轮起的事实及外层旧消费者；不创建第 4 轮。若继续，按新反馈开启下一轮。遇到显式 LoopExit 仍依其独立退出协议。 |
| 选 Loop 容器行，将轮数上限从 5 改为 2 | 容器入口可证明的外层输入、独立工作 | 用初始值建立全新第 1 轮；即使旧轮数为 3 也不保留旧反馈。持续未命中退出时按冻结的达到上限策略成功或失败，无第 3 轮。改退出条件或反馈亦从入口重算。 |
| 选 Iteration 容器行，将源从 [a,b,c,d,e] 换成已有变量 [e,c] | 两个源的可见上游、独立工作 | 从入口重新冻结 [e,c]，索引 0/1 各重做一次并重新收集。相同元素也按新位置执行；仅改收集选择器或错误策略同样重建账本与外层汇总。 |

例如在 D3 的 F 中先把第 3 项起的提示词改为加 `new-`，再选择 it1 把迭代源改为 [e,c]。第二次预览须显示新容器成员的有效提示词为原样返回 item，并列出 it1 的旧账和导出。确认后新容器输出 [e,c]；旧修订的 [a,b,new-c,new-d,new-e] 及其成员提示词仍可在 it1 历史中查看。

## D5　确认、停稳与重新调度

1. 确认提交 `runId, previewId, requestId`。按 run 和请求键先查已受理操作；同键同凭据返回同一操作和当前阶段，同键换凭据报 `request_conflict`。对于新请求，在同一运行门内检查已有操作；若有 `stopping` 或栅栏未释放的 `stop_failed`，整次 run 的新调试预览、新确认、普通失败恢复、整次运行重启和快照切换统一返回 `debug_operation_active`。各入口在写入、建根、切换快照及派发前检查；原请求的幂等回读仍可用。随后重新验证预览读集（修订、根、目标尝试、输入与控制事实、影响范围和在途集合）。过期返回 `stale_preview` 并要求重新预览；零停稳、零新修订。比较范围包括所读变量的生产者/版本及未赋值状态、控制边和受影响范围内的尝试集合及各尝试状态。预览后若待停稳尝试自行结束，即使 ID 集合相同也返回 stale_preview。若只有独立兄弟推进且以上事实均一致，原预览仍可确认；全 run 的版本变化可触发重查。
2. 受理事务持久保存意图、目标范围及待停稳清单，并封住该范围的新派发、重试和旧尝试对当前事实的写入。来自终态 run 的操作在 `stopping` 期间保持原 run 终态及原因，历史单独显示操作阶段。协调器在运行门外等待活动 Agent、在途重试和待处理人工动作终止或得到可证明的隔离。允许独立兄弟继续；其结果经原尝试凭据提交。共享工作区文件仍可能变化，调度独立仅表示没有工作流数据/控制依赖。
3. 停稳成功在同一持久提交中写新修订、有效性、账本/轮状态、变量与选路的新投影和待调度位置。来自终态 run 时，同一事务将 run 置为 Running、操作置为 `applied`。提交后再通知与派发。从终态启动的这次局部调试在范围结算后按 D1 归约。计划中尚无结果的节点保持依赖检查。旧尝试回调、延迟重试、人工确认即使携同一 nodeId 也不能推进新修订；独立兄弟仍可持原凭据完成。所有 Desktop 人工完成入口（含首轮确认和 force）都传 `CompleteWorkflowNodeRequest.nodeRunId`，值为页面显示的实际尝试。服务端先在运行门内比对当前尝试，再执行原有 turnKey、signalId 等适用门禁。旧客户端省略该字段时，仅在请求可唯一归属原尝试且该尝试仍有效时继续；有替代、歧义或证据不足则拒绝并要求刷新。普通执行同样适用。
4. 停稳失败将操作记为 `stop_failed`，回执包含原因和未停稳的尝试 ID，同一请求键可重读。受影响范围保持阻塞，零新修订、零新派发。确认旧尝试已终止或隔离后才释放栅栏；已被停止的工作在旧修订下按实际停止或失败记为 Cancelled 或 Failed。释放栅栏本身不触发按旧配置重派。用户可按 run 当前状态走普通失败恢复，或重新预览并用新键调试。已经发生的外部动作保留。
5. Desktop 进程启动时先读取未结束操作及其持久栅栏，包含仍保留 Failed、Cancelled 或 Succeeded 的 run；在栅栏之外按原有规则执行普通启动清理，再续办这些操作。栅栏内的旧尝试由操作重新核验；启动清理不得将相应轮/项结算为失败或写入当前账本。已生效操作重开、此后尚未派发任何尝试的轮/项不属于中断工作。范围外有工作被中断时，run 仍按原有规则以 `interrupted_by_restart` 失败；随后生效的修订及其对作废结果的撤回暂存，由下一次普通失败恢复或使 run 重新执行的调试确认在任何派发之前执行。仍无法证明外部工作结束或隔离时报告停稳失败。对已生效且 run 仍可调度的操作，**自动续派**已确认范围内尚未认领的位置。新修订下已认领又被中断的尝试走对应节点的普通启动清理（如普通 while 轮按 `interrupted_by_restart` 失败），调试协调器不再认领同一位置。取消记录和后来修订优先。run 推进与并发确认同时发生时，最多一个确认获得受理。
6. 取消与生效在同一运行门串行。取消先于生效时，撤销该意图的派发资格。对仍在原终态的 run，此时的取消只放弃调试操作，保留 run 原终态及原原因；对 Running 的 run，按整次运行取消语义转为 Cancelled。处于 `stopping` 的操作记为 `stop_failed`，固定 `reason: "run_cancelled"`，列出待清理尝试；已处于 `stop_failed` 的操作保留首次失败原因。未完成隔离的栅栏继续生效，晚到回报只能结清旧尝试。若生效先提交，此时 run 已为 Running，取消按普通运行语义终止在途执行并阻止剩余派发，已生效修订留在历史中。

工作流变量按有效生产者、作用域和分支重建；文件保留在同一 Workspace，预览提示可能读到上次生成的文件。调用外部工具、发送消息和写远端等动作可能重复，旧记录转历史不撤销这些效果。

## D6　历史、通知和事实所有者

确认受理响应举例为 `{"operationId":"opF","requestId":"kF","baseRevision":0,"state":"stopping"}`。`workflowRun.debugHistory({runId})` 返回按受理顺序排列的操作、阶段、预览目标/补丁、父与生效修订、失败原因和尝试关联。例如生效后按 kF 重查得 `{"operationId":"opF","requestId":"kF","state":"applied","baseRevision":0,"revision":1}`。applied 表示修订已生效，节点自身状态由运行详情读取。`workflowRun.debugAttempt({runId,nodeRunId})` 给出该尝试实际配置、修订、有效性和使其失效的 `retiredByOperationId`。逻辑目标首次正常派发后，历史可从原操作及 pendingTarget 定位到该次实际 nodeRunId；派发前该关联为空。存量行缺少关联时，未知的修订和配置返回 null；回看旧尝试不改变当前表单的编辑基线。

| 责任方 | 读取 | 唯一负责的写入或输出 |
| --- | --- | --- |
| 共享契约、repository | 冻结快照、历史修订、有效事实、类型化补丁 | 提供预览、确认认领、事务生效、历史/尝试查询端口。持久化修订、有效性、幂等键和操作阶段。 |
| 执行协调 | 受理意图、待停稳尝试、节点策略的影响计划 | 管理派发栅栏、停止结果和新尝试派发，经 repository 原子推进操作。 |
| 顶层 DAG 与 Condition | 有效根作用域、控制边和变量生产者 | 生成顶层重算计划，按新输入提交选择、变量及汇合。 |
| while / foreach 运行时 | 所选 scope 或容器执行、项索引、成员生产者、入口快照 | 各自生成保留/失效范围并结算轮池与导出、或对应项账本与汇总。 |
| 配置表单 / 运行页 | 当前有效配置、可用变量/模型、预览与历史 | 表单只交付已验证补丁；运行页选择实例、展示影响、确认、重查。取消编辑丢弃本地补丁。 |
| 跨包验收 | 固定输入、持久历史、调用记录、页面呈现 | 核对同一运行的调用次数、有效输出和副作用警示。 |

状态提交后沿用 `WorkflowRunInvalidated { run_id }`。事件表示该 run 应重查，失效的执行清单来自预览/持久查询。客户端在重连、漏收或重复事件后以运行详情和历史重建界面。

## 不变量

1. 同一运行、同一输入位置最多有一个当前有效结果；旧尝试可审计。
2. 预览和取消编辑均无执行副作用；一次确认最多生效一个修订。
3. 所有复用结果都有有效生产者；执行新路径或新轮次时只读取该路径/轮次可见的值。
4. 新派发以旧尝试停稳为前提；整工作区备份与外部工具撤销不在事务范围内。

## 为什么不是这些替代方案

| 备选 | 收益与代价 |
| --- | --- |
| 修改发布定义再重开运行 | 可直接使用既有启动入口，但会改变发布流程、重复上游工作，且打断运行内审计链。 |
| 所有成员都从容器入口重算 | 对旧数据要求较低，但会再调用已结算的前缀。适合作为用户另行确认的降级入口。 |
| 仅修改选中的一次尝试 | 适合逐项覆写，但用户要修复后续项时需逐项确认，预览与调用次数也不同。 |
| 暂停所有兄弟或回滚整棵工作树 | 减少局部协调，却可能中断无关会话或覆盖其已经提交的文件。 |

## 本决策未解决的问题

定义编辑器允许选择对象内的数组叶子，运行时完整图校验却会因根声明为对象而拒绝。两端对嵌套数组的统一行为另行处理，首版调试运行页按 D2 的根数组规则执行。[Iteration 嵌套数组源](https://github.com/ora-space/circus/issues/1506)

## 落地顺序

1. **选择、预览与查询。** 三个样例能从表单往返服务端，缺失来源得到可定位的错误，并能从持久查询还原目标。此阶段的预览只读，现行调度、派发和发布入口照常工作。
2. **确认与执行。** 完成条件是实际调用与持久记录能验证范围内派发、轮/项前缀、终态归约、取消和启动清理；普通恢复与重启按 D1 取当前修订。范围外的独立分支及已发布定义仍按原有规则工作。
3. **运行页验收。** 真实页面完成选择、预览、确认和重开详情后，显示的当前变量、调用次数、原尝试与修订历史须和持久事实一致。页面继续通过失效通知重查，确认和派发仍由运行端负责。验证义务见[按执行位置调试的核心用例](../../../../test-cases/desktop/core/workflow/debug-from-selected-execution.md)。
