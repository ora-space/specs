# Agent 节点可持续等待静默 prompt，以冻结配置保留取消与会话隔离

> 历史决策：D1 与不变量 2 中的无限等待现由 `unbounded` 承接。`wait` 从本次实际发送或最后一次可归属进展起最多等待 30 分钟。见[已实施的工作流等待策略](20261123-workflow-agent-wait-limit.md)。

Agent 节点可以选择持续等待长时间没有上报进展的 prompt，避免隐藏子代理仍在工作时被取消和重发。
这项选择承认 Ora 无法从静默推断 provider 已卡死，因此保留手动停止、真实错误与资源清理，而不伪造
保活信号。默认超时规则继续用于普通聊天及未配置的旧工作流。

本决策已实现并通过完整 `task test`：工作流图配置、会话运行时、交互 turn admission、编辑器及运行
详情均已接通，核心证据登记于对应测试用例。图字段是增量配置，不改变数据库或本地文件布局，不迁移
已冻结运行。

## 决策

### D1：节点显式选择静默策略，旧图保持默认行为

`agentConfig.promptInactivity` 接受 `timeout` 或 `wait`。缺失与 `null` 表示 `timeout`；可执行节点的
其他值明确拒绝。编辑器展示默认值但不会因读取或修改其他设置补写字段，保存与发布保留显式选择。

`timeout` 沿用首次 45 秒、三次重试 60/90/120 秒的无活动窗口，以及运行中工具暂停的规则。
`wait` 不因静默取消、重发或失败当前 prompt。它既不表示等待人工输入，也不表示等待节点重试。

### D2：每次 prompt 使用冻结节点策略

运行使用冻结图中的策略，覆盖首次发送、失败后的节点重试、Loop 与 Iteration 的每轮执行，以及交互
节点的后续人工消息。交互 admission 在状态转为 Running 前解析策略，解析失败不得留下已开始的 turn。
修改草稿不改变活动运行。普通聊天请求不暴露策略覆盖项。

策略类型由会话领域拥有，工作流解析与运行时共同消费。策略是当前 prompt 的输入，不是可污染其他
消费者的 session 持久状态。标题获取等并行调度路径同样不得丢失策略。

### D3：持续等待保留全部真实终止与清理路径

正常响应、provider 错误、连接丢失、队列溢出、用户取消、工作流停止、owning stream 释放和宿主关闭
仍按现有生命周期收敛。Followers 离开不取消 owner。MCP/session setup 和配置交换的 deadline，以及
取消收敛 grace 不因 `wait` 失效。真实节点失败仍遵循节点级自动重试策略。

其他 session 的更新、进程 stderr 或 connection 级 setup activity 都不得用作当前 prompt 的保活信号。

### D4：诊断表达观察到的静默，不断言子代理已挂死

记录实际策略；默认策略到期时记录尝试、窗口、静默时长、运行中与 pending 工具数量及取消响应结果。
诊断不需要模型内容或工具参数。活动信号缺失与 provider 卡死是不同判断，日志不能将前者宣称为后者。

## 不变量

1. 未配置的新旧工作流和普通聊天保持默认超时行为。
2. `wait` prompt 不因静默产生自动取消、重发或 timeout 失败。
3. 冻结策略适用于该节点的每次 turn，且不会跨会话泄漏。
4. 取消与真实故障仍可终止持续等待并释放资源。
5. 持续等待不改变节点失败重试或复合错误策略。

## 为什么不是这些替代方案

| 方案                          | 未采用的原因                                                       |
| ----------------------------- | ------------------------------------------------------------------ |
| 全局增大静默窗口              | 只推迟误杀，仍无法容纳任意长的正常委托，且影响普通聊天             |
| 用任意子会话或进程日志保活    | 缺少父 prompt 关联，会掩盖同连接上真正卡死的会话                   |
| 按工具标题推测委托            | 工具名称不构成稳定生命周期契约                                     |
| 强制先改 codeagent 再处理 Ora | 正确的父会话 InProgress 委托仍是理想契约，但外部实现不受本仓库控制 |

## 风险、未解决问题与验收

持续等待的真正卡死可能需要人工停止，这是显式选择的代价。MCP 环境修复、provider 委托生命周期
修复及默认超时与同刻响应竞争的独立问题不由本决策处理。

核心验收见[静默等待用例](../../../../test-cases/desktop/core/workflow/prompt-inactivity.md)：生产 ACP
路由与 actor 在暂停时钟下验证两小时静默后的完成、取消及默认会话隔离；Desktop 外部 provider 用例
验证工作流首轮和交互追问静默 50 秒不重发；冻结图、复合轮次、真实错误重试及双语界面均有直接证据。
