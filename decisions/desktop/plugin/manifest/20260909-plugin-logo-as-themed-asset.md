# 插件图标：本地文件是唯一来源，主题变体走目录约定，契约只承载资产 URL

插件图标从"一段随契约内联传输的 SVG 源码"改为"一个由宿主本地协议服务的资产 URL"。在此基础上补齐
当前无法表达的**主题变体**（浅色/深色分别提供图标），并把格式白名单从 SVG 扩展到 PNG、WebP 与
JPEG。图标的来源、角色与格式**完全由文件名决定**：清单不承载任何图标信息，宿主不为图标发起任何
网络请求，也不向包目录或条目目录写入任何字节。因为契约不再承载内容，图标格式对契约层完全透明，
位图随之得到支持。

本决策处于 `approved`，尚未实现；核心测试用例见
[插件图标资产](../../../../test-cases/desktop/plugin/manifest/logo-assets.md)。影响范围包括
`ora-plugin` 资产协议、marketplace 索引构建与其缓存的版本校验、`InstalledPlugin` /
`AvailablePlugin` 契约的 `logo` 字段、`ora-utils` 新增的图像头部解析模块，以及全部渲染图标的
前端 surface。**清单 schema 与 `resolver` 完全不变**：本决策不新增、不修改、不废弃任何清单字段。

兼容性边界有三处。**清单**：无变化。作者若写了 `[logo]` 之类的 table，按根决策 D2（未知字段在
任何层级被忽略）静默跳过。**文件系统**：包目录与 registry 条目目录的布局不变，十五个候选文件名
中 `logo.svg` 已经存在，只新增另外十四个，不新增任何目录。既有安装在宿主升级后仍按原 `logo.svg`
正常显示；反向降级也不丢文件——旧宿主继续读 `logo.svg`，新增的主题变体与位图对它不可见但无害。

**索引缓存**是唯一需要动作的一处，且需要的动作比看上去多。`registry_index.json` 的 `logo` 从
SVG 源文本变成变体构成，对升级前写下的缓存而言这是**类型不符而非字段缺失**——根决策"新增展示
字段都有默认值，旧缓存可直接读取"的约定挽救不了它，`#[serde(default)]` 不处理类型错误。

现状下这不会退化成"没有图标"，而会退化成整个市场不可用：`RegistryIndex::load` 只做
`serde_json` 反序列化、从不比对已有的 `INDEX_VERSION` 字段，而 `list_available_plugins` 只把
`Io(NotFound)` 降级为空列表，其余错误一律转成 `BackendError::internal`。因此本决策要求三件事
一并落地：

1. 随 `logo` 形状变更提升 `INDEX_VERSION`（`crates/plugin-registry/src/index.rs`）。
2. `RegistryIndex::load` 校验文件中的 `version` 与当前 `INDEX_VERSION` 相等，不等即视为缓存
   不可用——这正是该字段的 doc comment 已经声称的用途，但至今没有实现。
3. `list_available_plugins` 把"缓存不可用"（版本不符或反序列化失败）与"文件不存在"归为同一条
   降级路径：返回空列表与 `updated_at = 0`，而不是内部错误。

代价是升级后首次打开插件市场会看到空列表，直到用户手动同步一次——因为根决策规定该端点只读
缓存、永不触发网络。这个窗口每次索引 schema 变更出现一次，不会反复出现；本决策接受它，替代
方案见"本决策未解决的问题"。

本决策不承担：图标的 UI 尺寸与布局；作者侧打包期校验（推荐分辨率、拼错的文件名）；marketplace
审核策略；任何形式的远程图标来源；以及任何形式的宿主侧重新着色——图标的像素**原样渲染**，主题
适配完全由作者通过提供主题对完成。

## 继承与修改

本决策继承[版本化双形态清单决策](0-versioned-dual-form-manifest.md)，并参考
[插件分发根决策](../registry/0-registry-distribution.md)中关于条目目录约定与索引构建的规定，
修改以下边界：

| 前序决策的约定 | 本决策 |
| --- | --- |
| 清单解析不做 I/O，不检查被引用文件是否存在（清单 D7） | 继承，不变；图标不进清单，因此连"被引用文件"都不存在 |
| 未知字段在任何层级被忽略（清单 D2） | 继承，不变；它使作者误写的图标字段不会让整份清单失败 |
| `logo.svg` 是目录约定而非清单字段（分发根决策） | 继承并扩展：候选文件名从一个扩展为十五个（三个主题角色 × 五个扩展名），仍然只是目录约定 |
| `logo.svg` 经安全校验后内联进索引（分发根决策） | 修改：索引只记录**角色到扩展名的映射**而非源码；字节留在磁盘，由 `ora-plugin` 协议按需服务 |
| `logo.svg` 的安全校验为 ≤50 KiB、良构 XML、禁止脚本与外部引用（分发根决策） | 继承该策略并推广：50 KiB 成为全部五种格式共用的单一字节上限，位图另受像素上限约束 |
| 图标不安全或不可读只记 warning 并按"无图标"索引，绝不移除条目（分发根决策） | 继承并收窄粒度：失败的粒度从"整个条目无图标"降为"该候选文件不存在"，解析继续（D5） |
| 索引缓存的展示字段在反序列化时有默认值，旧缓存可直接读取（分发根决策） | 修改：该机制只覆盖字段缺失，不覆盖类型变化；`logo` 从 SVG 源文本改为变体构成属于后者。改由提升 `INDEX_VERSION` 并**新增**版本校验与降级路径让不匹配的缓存整体作废重建——版本字段今天只被写入，从不被读取 |

## 背景与术语

| 领域名 | 含义 |
| --- | --- |
| `Logo variant` | 图标的一个主题角色：`universal`、`light`、`dark` |
| `Logo candidate` | 十五个固定文件名之一；宿主只在这些名字上查找图标，从不解析作者提供的路径 |

"图标跟随主题"只有一种实现：**作者提供两个文件**，宿主按当前主题选一个并原样渲染。宿主不做任何
重新着色——不染色、不反色、不加底、不描边。图标的像素是作者的产物，宿主只负责选哪一份。

## 决策

### D1 图标是资产，契约只承载宿主本地协议 URL

`InstalledPlugin.logo` 与 `AvailablePlugin.logo` 不再携带图标内容，改为携带宿主本地协议地址：

```text
PluginLogo
├── Universal{ url }              # 单一图标，两个主题共用
└── Themed   { light, dark }      # 主题对，两半永远同时存在
```

字段类型为 `Option<PluginLogo>`；`None` 表示该插件没有可用图标，由各 surface 的通用回退标记渲染。
URL 由 `ora-plugin` 协议服务（`crates/surface/src/assets.rs` 的 `ASSET_SCHEME`），在
macOS/Linux 上拼作 `ora-plugin://localhost/...`，在 Windows/Android 上拼作
`http://ora-plugin.localhost/...`，两者都由宿主进程内的 handler 直接读盘应答，不经过网络栈。

四条理由使"内容"不该出现在契约里。

**格式**——这一条是位图支持成立的前提，不是附带收益。字符串只能承载文本，位图必须 base64 才能
通过契约，在已经偏大的载荷上再加三分之一。一旦契约携带的是 URL，格式就对契约层完全透明：
`asset_content_type` 按扩展名给出正确的 content-type，五个扩展名走同一条路径。

**载荷**：每次列举插件的响应都重复携带全部图标源码，marketplace 索引还把同一批源码序列化进磁盘
JSON 再反序列化读回。IPC 是 JSON 传输，内联源码要在宿主侧转义、在 webview 侧解析，而后者花的是
主线程的时间。

**按需取回**：图标的字节只在真正被渲染时才取，未进入视口的条目一次盘都不读；内联方案对全部条目
的字节都已经付过代价，无论它们是否被画出来。列表虚拟化时这个差距最大，但即使不虚拟化，详情页
与设置页这类只显示单个插件的 surface 也不再需要为整份列表的图标买单。

**内存归属**：内联内容以 JS 字符串的形式驻留在前端 store 中，只要列表还在就不能回收；由它编码
出的 `data:` URL 进不了 HTTP 缓存，每次重新编码还会在解码图像缓存里另占一份。改用 URL 后字节的
所有权归 webview 的图像缓存，可在内存压力下自行淘汰。

把变体建模成枚举而不是 `Option` 字段的组合，使前端不做任何启发式判断：判定在宿主侧完成一次，
渲染层只按变体分支，不可能出现"有 light 没有 dark"这种半成品状态。

**代价有五项，都明确接受。**

其一，`ora-plugin` 协议需要一条新的授权分支。现有分支按 surface instance 授权：URL 只命名
instance，文件根由该 instance 的注册记录决定。图标请求没有 instance 可绑——它由**主窗口**为
**任意插件**发起，且未安装的 marketplace 条目根本没有 instance。因此图标分支必须自成一路：

- 调用方必须是主窗口 label。
- URL 命名四样东西且仅此四样：**根、插件 id、主题角色、扩展名**，绝不携带路径。handler 按 URL
  指名的根解析 id——`installed` 是已安装包根，`registry` 是该 id 所属源检出下的条目目录——再由
  角色与扩展名拼出 D2 的候选文件名。
- 根取自 `installed` / `registry`，角色取自 `universal` / `light` / `dark`，扩展名取自五个允许
  值；三者都先经封闭集合校验，任何其他取值直接拒绝。两个根都经 `CanonicalPathRoot` 收敛。

**根必须出现在 URL 里**，因为两个根各自独立解析，且可以给出不同的变体构成：条目目录已经发布了
`logo.light.svg` + `logo.dark.svg`，而已安装的那一版包里仍然只有 `logo.svg`，同一个 id 于是同时
存在两种构成。若 handler 按固定优先级挑根，一侧铸出的 URL 就会由另一侧的目录应答，拼出的候选
文件名没有任何人产出过——结果是两边目录各自都有完好图标，界面却画裂图。反向把优先级改成条目
目录优先也不行：本地导入的 `local/*` 插件根本没有源检出。

因此规则是：**谁解析的目录，谁铸出指名该目录的 URL；应答只读回同一个根，绝不回退到另一个。**
`AvailablePlugin.logo` 铸 `registry`（卡片说的是这个源现在发布什么），`InstalledPlugin.logo`
铸 `installed`（列表说的是实际运行的那份字节）。两者不一致时，各自画各自的图标——这正是应有的
表现，而不是一个需要仲裁的冲突。根是一个二值封闭集合，它给路径构造带来的面与主题角色一样大：
文件名仍由宿主自己拼出，调用方提供的字符串一个字都进不了路径。

**扩展名必须出现在 URL 里**，否则 handler 拿到 id 与角色也不知道该读 `logo.svg` 还是
`logo.png`，只能回头查索引或重跑一遍 D2 的优先级扫描。带上扩展名让应答路径完全无状态，并且让
`asset_content_type` 保持为一次纯粹的扩展名查表——这正是 D3"扩展名即真相"那条规则想保住的东西。
它不构成路径注入面：扩展名不是作者提供的字符串，而是宿主从封闭集合中选出的五个常量之一。

它复用协议壳，不复用现有授权链。把条目目录作为第二个根不引入新的信任面：`readPluginReadme`
已经在按 id 读取同一批条目目录，本决策只是让同一条读取路径多认十五个文件名。

其二，**同一份字节被读两次**：一次在索引构建或包发现时校验（D5），一次在协议应答时服务。内联
方案只读一次。这是把校验前移换来的——代价落在冷启动的磁盘 I/O 上，而收益是列表渲染路径上没有
校验开销、且契约里出现的 URL 都是已验证的。

其三，**契约不再自包含**。`AvailablePlugin` 曾经可以被日志、快照测试或任何外部消费者完整理解，
图标随对象一起走；现在它是一个指向宿主本地状态的引用，只在本进程的 webview 里有意义。直接后果是
契约的快照测试不再覆盖图标内容——图标的正确性必须由候选解析层（D2）自己的测试承担，而不能顺带
由契约测试覆盖。

其四，**渲染从同步变成异步**。内联内容与列表在同一次绘制中出现；URL 是一次取回，会先绘制回退
标记再换成图标。UI 必须为图标预留固定尺寸，否则列表会抖动。

其五，URL 的拼写依平台而异（`ora-plugin://localhost/` 与 `http://ora-plugin.localhost/`），因此
它不是一个可跨平台断言或持久化的稳定字符串。任何需要识别图标 URL 的代码都必须经 `AssetUrlForm`
判断，不能字符串匹配单一拼写。

### D2 主题变体与格式由文件名约定确定，清单不承载任何图标信息

包根目录与 registry 条目目录下的候选文件名固定为十五个，即三个主题角色乘以五个扩展名：

```text
logo.svg          logo.png          logo.webp          logo.jpg          logo.jpeg
logo.light.svg    logo.light.png    logo.light.webp    logo.light.jpg    logo.light.jpeg
logo.dark.svg     logo.dark.png     logo.dark.webp     logo.dark.jpg     logo.dark.jpeg
```

解析分两步。先按角色定文件，同一角色下的扩展名优先级固定为
**`.svg` > `.png` > `.webp` > `.jpg` > `.jpeg`**：

- SVG 优先于全部位图，因为它可缩放：同一个文件在列表的小尺寸与详情页的大尺寸下都清晰。
- PNG 与 WebP 优先于 JPEG，因为它们有 alpha 通道，能贴合任意背景色；JPEG 只能带着自己的不透明
  矩形出现。
- PNG 先于 WebP、`.jpg` 先于 `.jpeg`，纯粹是为了让"作者同时放了两份"有确定结果，而不是依赖目录
  枚举顺序。这两组内部没有实质优劣。

再按三个角色的存在情况定变体（`l` = light、`d` = dark、`u` = universal）：

| l | d | u | 结果 |
| --- | --- | --- | --- |
| ✓ | ✓ | ✓ | `Themed { light: l, dark: d }`，`u` 忽略 |
| ✓ | ✓ | ✗ | `Themed { light: l, dark: d }` |
| ✓ | ✗ | ✓ | `Themed { light: l, dark: u }` |
| ✓ | ✗ | ✗ | `Universal(l)` |
| ✗ | ✓ | ✓ | `Themed { light: u, dark: d }` |
| ✗ | ✓ | ✗ | `Universal(d)` |
| ✗ | ✗ | ✓ | `Universal(u)` |
| ✗ | ✗ | ✗ | `None` |

八行覆盖全部磁盘状态，没有任何一行是错误：每种组合都有确定语义，作者不会因为少放一个文件而收到
一条无从修复的 discovery issue。第三、五行用 `u` 补齐缺失的一半，是因为"作者提供了深色版本"这个
事实本身就说明 `logo.svg` 是给浅色背景用的；第四、六行退回 `Universal` 而不是补齐，是因为没有
第二个文件可补。第一行"主题对优先、忽略 `u`"顺带成为向后兼容通道：作者三个文件都保留时，新宿主用
主题对，旧宿主继续读 `logo.svg`，双方各取所需。

角色与扩展名是**两个独立的维度**，可以自由交叉：`logo.light.svg` 配 `logo.dark.png` 是合法的，
两半只需各自通过 D3 与 D4，不需要格式一致。强制同格式会造出一类只为整齐而存在的错误，而渲染层
根本不关心两半的格式是否相同。

不把图标信息写进清单，是因为在这里清单字段是**纯复述**：文件名本身就是声明，
`[logo] light = "logo.light.svg"` 不增加任何信息量。`workbench.page_entry` 必须进清单，是因为
一个 bundle 里几十个文件无法猜出入口；图标没有这个歧义。复述的代价是实打实的——它造出"清单声明了
`logo.dark.svg` 但文件不存在"这个偏斜状态，按清单 D7 要落到包校验层，多一类错误、多一条规则；
而在纯约定下该状态不可表达。

第二个理由针对 registry 侧：索引构建扫描的是不受信任的 git 检出，目前对作者提供的路径是零解析。
让它开始解析包内相对路径，需要引入 `PortableRelativePath` 与 `CanonicalPathRoot` 收敛，是为零
信息增量打开一条本不存在的路径解析面。封闭的候选名集合则天然没有这个问题：文件名是宿主自己拼
出来的，作者的输入根本不参与路径构造。

解析的产物是**角色到扩展名的映射**，这也是索引里 `logo` 字段所记录的全部内容：

```json
"logo": null                                               // 无图标
"logo": {"universal": {"role": "universal", "extension": "svg"}}   // 磁盘上是 logo.svg
"logo": {"light":     {"role": "light",     "extension": "svg"},
         "dark":      {"role": "universal", "extension": "png"}}   // logo.light.svg + logo.png
```

映射的 key 是**主题槽位**，value 是**候选**——支撑该槽位的那个文件的角色与扩展名。两者不总是
相同：判定表第三、五行用 `universal` 补齐主题对的另一半，而那一半在磁盘上的文件名是
`logo.{扩展名}` 而非 `logo.{角色}.{扩展名}`。若只记扩展名、由 key 反推角色，被补齐的一半就会
指向作者从未提供的文件名，协议应答必然落空。

记角色与扩展名而不是文件名或路径，是因为文件名恰好是"`logo` + 可选的 `.{角色}` + `.{扩展名}`"，
这两项就是全部还缺的信息。存完整文件名会让不属于那十五个候选的值变得可表达，存路径则等于把本
决策明确拒绝的东西放回数据里。

这里必须是**扩展名而不是格式**：`.jpg` 与 `.jpeg` 是同一格式的两个扩展名，只记 `Jpeg` 就还原不出
磁盘上到底是哪一个。这是 D3 同时接受两个扩展名带来的直接约束。

候选名表与上面的判定表必须**只有一份实现**，由 registry 索引构建与包发现共用。两者面对的目录
形态相同、判定规则相同，各写一份就会在扩展名优先级或补齐规则上悄悄漂移，而漂移的表现是"同一个
插件在市场里和安装后显示不同的图标"——一种没人会主动去测的差异。

代价是"只有 `logo.light.svg`"这种状态无法区分作者的意图与作者的疏漏，宿主一律按第四行处理。这与
清单 D2 承认的"拼错的可选字段静默按缺省处理"是同一类、同一量级的问题，反馈义务同样落在打包工具。

### D3 格式由 magic bytes 判定，白名单封闭为 SVG、PNG、WebP 与 JPEG，且必须与扩展名一致

候选文件的真实格式**一律由 magic bytes 判定**，扩展名不作为判定依据。判定出的格式决定走哪套
校验；SVG 分支委托既有的 `ora_utils::svg::validate`，三种位图各自解析头部声明的尺寸。

| 格式 | 校验 | 尺寸来源 |
| --- | --- | --- |
| SVG | `ora_utils::svg::validate`（既有策略：良构 XML、禁止脚本与外部引用） | 不适用 |
| PNG | magic bytes + IHDR | IHDR 声明的宽高 |
| WebP | RIFF 容器 + 子格式判定 + 拒绝动画 | 子格式声明的画布尺寸 |
| JPEG | SOI + 逐段跳转到 SOF 标记 | SOF 段声明的宽高 |

三种位图的尺寸都能从头部直接读出，无需解码任何像素，因此**不引入任何图像解码依赖**。按仓库约定，
这类与 Ora 领域无关的头部解析逻辑放在 `ora-utils` 的图像模块。

**判定结果必须与扩展名映射出的格式一致，否则该候选按不存在处理（D5）。** 这条规则替代了"按真实
格式服务"的另一种可能做法，理由是它让 `asset_content_type` 保持为唯一的扩展名到 content-type
映射：协议 handler 应答时不需要重新嗅探字节，也不需要第二张对照表。一个内容是 SVG 的 `logo.png`
是作者的打包错误，其修复方式（改扩展名或改内容）显而易见，而按不存在处理让这个错误既不产生安全
后果，也不影响插件本身。

WebP 比另外三种多两项义务，因为它是容器而非单一格式。其一，尺寸解析必须覆盖 RIFF 下的三种子格式
（有损 `VP8 `、无损 `VP8L`、扩展 `VP8X`），三者的画布尺寸编码位置与位宽各不相同，缺一种就会把
合法图标误判为损坏。其二，**动画必须被拒绝**：只有 `VP8X` 能承载动画，其标志字节的 ANIM 位即是
判据。

白名单封闭且刻意窄。它的**唯一职责是安全与资源**——宿主必须能在不解码像素的前提下判定尺寸，且
渲染结果必须是静态图像。据此：

- **GIF** 排除：动图。列表中自行播放的图标是干扰而非信息，且无法由 CSS 停止。这与拒绝动画 WebP
  出于同一理由。
- **JPEG** 接受，尽管它没有 alpha 通道。透明背景是图标的**期望**而非**要求**：不透明背景既不
  影响安全，也不影响资源占用，只影响观感，而观感的后果完全落在作者自己身上。宿主不做任何补偿
  （不自动加白底、不抠图），并且 D2 的主题对恰好给了在意主题的 JPEG 作者一条补救路径——提供
  `logo.light.jpg` 与 `logo.dark.jpg`。拒绝 JPEG 等于用白名单替作者做审美判断，超出了白名单
  该承担的职责。

同时接受 `.jpg` 与 `.jpeg` 两个扩展名，是因为两者在作者工具链中都常见且没有任何语义差别；只认
一个会把大量合法图标静默判为缺失，而代价只是候选表多三行、优先级表多一条固定次序。

### D4 单一字节上限 50 KiB，位图另加 1024 × 1024 像素上限

**全部五种格式共用一个字节上限：50 KiB**，沿用 `ora_utils::svg::DEFAULT_MAX_SVG_BYTES` 的既有
常量值，并把它提升为图标层面的单一常量。位图另受 **1024 × 1024** 的像素上限约束。任一上限不满足，
该候选按不存在处理（D5）。

单一上限而非按格式分档，是因为**字节上限在格式判定之前就能判定**：读取时截断在上限后一个字节，
超出即拒绝，根本不需要知道这是什么格式。分档则要求先读头部、判出格式、再回头选阈值，把最廉价的
闸门排到了最贵的一步之后。50 KiB 对图标尺度的位图完全够用——一个 256 × 256 的 PNG 图标通常在
10 KiB 量级——因此这份简化不需要拿容量去换。

像素上限与字节上限**各自独立、缺一不可**：高度可压缩的巨幅图像能轻易通过字节闸门，却在 webview
的解码器里展开成解压炸弹。一张 50 KiB 的纯色 PNG 可以是 8000 × 8000，解码后占用两个数量级以上
的内存；而 marketplace 列表会同时渲染几十个图标。像素上限是唯一能挡住这条路径的闸门。

### D5 任何图标失败都等同于该候选文件不存在

一个候选文件在以下任一情况下**按不存在处理**，解析沿 D2 的扩展名优先级与判定表继续：

- 文件不可读（权限、符号链接、竞态删除）
- magic bytes 判定的格式不在白名单内
- 判定的格式与扩展名映射出的格式不一致（D3）
- 超出字节或像素上限（D4）
- SVG 未通过 `ora_utils::svg::validate`
- WebP 带 ANIM 标志

失败记 warning，**绝不使该插件从列表中消失、绝不使其无法安装、绝不使其无法加载或运行**。这继承
分发根决策已有的承诺，但把失败粒度从"整个条目无图标"收窄到"这一个文件不算数"。粒度收窄有实际
后果：作者放了一个损坏的 `logo.dark.webp` 和一个正常的 `logo.dark.png` 时，结果是深色角色用
PNG，而不是整个插件退回无图标；作者放了一个损坏的 `logo.light.svg` 和一个正常的 `logo.svg` 时，
结果是 `Universal(logo.svg)`，而不是 `None`。

**"失败即不存在"使 D2 的判定表保持全函数。** 若失败另成一个状态，判定表就要从三个布尔维度扩展到
三个三值维度，行数从八涨到二十七，而新增的十九行没有一行有独立语义——它们全都只能退回到"就当没有
这个文件"。把归一化提前到读取层，判定表因此不需要知道失败的存在。

校验发生在索引构建与包发现时，不在协议应答时。这使 `listAvailablePlugins` / `listInstalledPlugins`
的响应里出现的 URL 都是已经验证过的，前端不需要处理"URL 存在但取不到"的中间态；也使列表渲染
路径上没有重复的字节校验开销。代价是磁盘在校验之后、应答之前被改动的窗口——但改动者是作者或用户
自己，且图标经 `<img>` 渲染不执行脚本，该窗口不产生新的攻击面。

## 为什么不是这些替代方案

| 方案 | 否决理由 |
| --- | --- |
| 保持契约内联 SVG 源码，仅新增 dark 变体 | 载荷随插件数线性增长，且无论条目是否被渲染都要付；位图必须 base64 才能通过契约；marketplace 索引继续把源码序列化进磁盘 JSON 再读回。它的真实优势是契约自包含——图标随对象一起走，快照测试顺带覆盖图标内容，且校验过的字节就是送出去的字节，不存在"URL 有效但取不到"的中间态；本决策接受失去这三点（见 D1 代价三与 D5 末段） |
| 已安装插件内联内容，marketplace 条目用 URL | 已安装插件通常只有个位数到几十个，内联的载荷代价确实可以忽略，这是该方案的真实优势。但它让同一个 `PluginLogo` 概念有两条渲染路径：前端每一处图标都要分支处理内容与 URL，而两条路径的缓存行为、失败模式与测试方式各不相同。位图支持会随之分裂——内联侧要么仍需 base64，要么已安装插件干脆不支持位图。收益只是省掉已安装侧的协议往返，与这份分裂不成比例 |
| 由清单声明远程图标地址（HTTPS），随包分发变为可选 | 它确实让作者不必把字节塞进仓库、也便于更新图标，但代价不成比例：marketplace 列表会**被动**加载全部条目的图标，用户只要打开插件市场就向 N 个第三方主机暴露 IP、浏览时刻与浏览频次，并可通过 ETag 获得跨会话的稳定标识——全部发生在用户对任何作者授予信任**之前**。改由宿主取回只能把信号从"该用户何时浏览了哪个插件"降为"某台机器执行了一次同步"，消不掉；彻底消除需要 Ora 自建镜像或代理，属于基建。它还连带要求安装事务向包目录写入物化字节，从而放弃"包目录逐字节等于 `.orax` 解包结果"这一性质，并在降级到旧宿主时留下一个图标丢失的窄回归 |
| webview 直接加载作者声明的远程地址 | 在上一条之上更进一步：宿主根本看不到字节，`ora_utils::svg` 的整套安全校验完全失效；列表在离线时出现空洞；且主窗口从此永久依赖于能访问任意 origin，CSP 再也收不紧。这与 `webview` kind 的远程加载不可类比——后者需要用户显式打开某个 surface，运行在独立 webview 中，且受该清单 `allowed_origins` 约束 |
| 本地图标路径也写进清单 | 对文件名的纯复述，零信息增量；造出"声明了但文件不存在"的偏斜状态；迫使 registry 索引构建开始解析不受信任仓库中作者提供的路径 |
| 允许 `logo.svg` 与主题对共存并定义优先级链 | 本决策确实保留了"主题对优先"这一条规则，但把它收在唯一的共享 reader 中；若改为多条互相牵制的优先级规则，任何一个 consumer 上的实现遗漏都会静默生效——这正是清单 D5 把发布来源建模为互斥枚举、而非若干 optional 字段加一套仲裁规则时所否决的漂移风险 |
| 信任扩展名判定格式 | 一个内容是 SVG 的 `logo.png`，按扩展名放行即绕过全部 SVG 安全校验 |
| 按 magic bytes 的判定结果服务，允许扩展名与内容不一致 | 要求协议 handler 在应答时重新嗅探字节，或维护第二张格式到 content-type 的对照表；而"扩展名即真相"让 `asset_content_type` 保持为唯一映射，代价只是作者要改一个文件名 |
| 位图沿用更宽松的字节上限（如 256 KiB） | 字节上限是唯一能在读取时截断、无需知道格式就能判定的闸门；分档要求先判格式再选阈值，把最廉价的检查排到最贵的一步之后。50 KiB 对图标尺度的位图完全够用 |
| 只设字节上限，不设像素上限 | 一张 50 KiB 的纯色 PNG 可以是 8000 × 8000，通过字节闸门后在 webview 解码器中展开为解压炸弹，而列表会同时渲染几十个 |
| 继续排除 JPEG（因其没有 alpha 通道） | 透明背景确实更适合图标，这是 JPEG 相对 PNG/WebP 的真实劣势；但白名单的职责是安全与资源，不是审美——不透明背景既不影响安全也不影响资源，后果完全落在作者自己身上，且 D2 的主题对给了在意主题的作者补救手段 |
| 只接受 `.jpg`，不接受 `.jpeg` | 两个扩展名在作者工具链中都常见且无语义差别，只认一个会把合法图标静默判为缺失；代价只是候选表多三行与一条固定优先级 |
| 白名单放开到 GIF | 动图。列表中自行播放的图标是干扰而非信息，且无法由 CSS 停止，与拒绝动画 WebP 同理 |
| 接受 WebP 但不检测 ANIM 标志 | 容器允许动画而白名单接受该容器时，拒绝动画就不是加固而是前提 |
| 只解析 `VP8X` 而不解析 `VP8 ` / `VP8L` | 多数导出工具对小图标输出的正是这两种非扩展子格式，只解析扩展形态会把最常见的合法图标误判为损坏 |
| 校验失败单独建模为一个状态，而非等同于文件不存在 | D2 的判定表会从三个布尔维度扩展到三个三值维度，行数从八涨到二十七，而新增的十九行全都只能退回"就当没有这个文件" |
| 强制主题对的两半使用同一种格式 | 造出一类只为整齐而存在的错误；渲染层不关心两半格式是否相同 |
| 图标 URL 不含根，handler 按固定优先级（已安装优先或条目目录优先）挑一个 | 两个根各自独立解析，可以给出不同的变体构成，于是一侧铸出的 URL 会由另一侧的目录应答，拼出一个谁都没产出过的候选文件名——两边目录都有完好图标，界面却画裂图。反向优先级同样不成立：本地导入的 `local/*` 插件没有源检出。代价只是 URL 多一段来自二值封闭集合的前缀 |
| 应答时先读 URL 指名的根，找不到再回退到另一个根 | 回退把两个根的分歧藏进一次成功的应答里：卡片会画出一个不属于它所描述的那份发布的图标，而作者看不到任何异常。它还让应答变得有状态，与"应答路径完全无状态"相抵触 |
| 在协议应答时校验字节，而不是在索引构建与包发现时 | 列表渲染路径上出现重复的字节校验开销，且前端要处理"URL 存在但取不到"的中间态 |
| 宿主对单色 SVG 做染色（`mask-image` + `currentColor`），使其自动适配主题 | 它确实能修复一类真实问题——不含 `fill` 的单色图标按 SVG 规范默认为黑，在深色主题下即黑底黑图，而这类插件无需重新发版就能被修复。但它要求一套"这张图是否为单色剪影"的判定，而该判定不可能同时正确与简单：放宽会把彩色图标染成一片纯色，收紧则大部分本该受益的图标落不进来，且判定规则的每一次调整都会静默改变存量插件的外观。本决策选择让宿主只做选择、不做改写：图标的像素是作者的产物，主题适配由作者提供主题对完成 |
| 用 `filter: invert()` 实现主题适配 | 比染色更差：对彩色图标产生补色，且产物是硬编码的 `#fff` 而非主题前景色 |
| 为不透明图标（尤其 JPEG）在 UI 层统一加白底或圆角容器 | 它是渲染层的补偿手段，与图标的解析、校验和服务无关；属于 UI 决策，不应由本决策锁定 |

## 不变量

1. 契约中的图标字段只承载宿主本地协议 URL，任何形态下都不承载图标内容。
2. 图标字节永远来自本地文件；宿主与 webview 都不为图标发起任何网络请求。
3. 清单不承载任何图标信息；图标的存在、主题角色与格式完全由文件名决定，宿主从不解析作者提供的
   路径。
4. 宿主从不写入包目录与 registry 条目目录；图标是纯读取路径，包目录逐字节等于 `.orax` 的解包
   结果。
5. 图标的任何失败——缺失、不可读、格式不在白名单、扩展名与字节不符、超出上限、SVG 校验不通过、
   WebP 带动画——都等同于该候选文件不存在，且不改变插件是否被发现、被索引、可安装、可加载或
   可运行。
6. 图标格式仅由 magic bytes 判定；判定结果必须与扩展名映射出的格式一致，因此协议应答的
   content-type 永远与真实字节相符。
7. 单个图标文件不超过 50 KiB；位图不超过 1024 × 1024 像素；动画一律拒绝。
8. 宿主服务的字节逐字节等于磁盘上的候选文件：不染色、不反色、不重新编码、不合成背景或描边。
   主题适配的唯一手段是在作者提供的两个文件之间做选择。
9. 已安装插件的图标生命周期与该插件完全重合：卸载删除包目录即删除其全部图标，不留无主残留，也
   不需要独立的清理步骤。
10. 包目录与 registry 条目目录的布局不变；本决策只新增固定候选文件名，不新增目录，不移动、改名
    或删除任何既有路径。
11. 候选名表与 D2 的判定表只有一份实现，registry 索引构建与包发现共用；同一份磁盘状态在市场与
    安装后解析出相同的变体构成。
12. 索引缓存的 `logo` 形状变更伴随 `INDEX_VERSION` 提升；版本不匹配或无法反序列化的缓存被整体
    丢弃并按"尚未同步"降级，永不转化为端点错误，任何宿主都不会尝试解析形状不属于自己的索引。
13. 图标 URL 只由根、插件 id、主题角色与扩展名四段构成，除 id 外三段各取自封闭集合；协议应答
    只读回 URL 指名的那个根，不回退到另一个，也不需要读取索引或嗅探字节即可给出 content-type。

## 本决策未解决的问题

- 远程图标来源被本决策整体否决，理由是隐私（见替代方案表）。若将来重新提出，前置条件是先有
  Ora 侧的镜像或代理，使作者无法观测到任何终端用户信号；在那之前不应以任何形式引入。
- 图标的宿主侧缓存未定义：marketplace 列表会同时请求几十个图标，每次都经协议逐个读盘。本决策
  依赖 webview 对本地协议 URL 的缓存，未测量该假设是否足够；若不足，缓存层的失效边界需要单独
  决策。
- 推荐分辨率与作者侧校验（位图过小、文件名拼错、扩展名与内容不符）不在本决策范围内；清单 D2 的
  静默容错使这类反馈必须由打包工具承担。
- 升级后首次打开市场的空窗未被消除，只是被降级为"尚未同步"。可能的缓解是在宿主启动时发现索引
  版本不匹配后自动触发一次同步，但这会给启动路径加上一次网络 I/O，与根决策"打开市场不触发网络"
  的边界如何协调需要单独判断，因此不在本决策内决定。
- **存量的单色 `logo.svg` 在深色主题下仍然看不清。** 这类图标常常不含 `fill` 属性，按 SVG 规范
  默认为黑，因而在深色背景上是黑底黑图。本决策提供的唯一解法是作者补一个 `logo.dark.*` 并重新
  发版；不重新发版的插件不会被自动修复。宿主侧染色曾被考虑并否决（见替代方案表），若这类插件在
  真实数据中占比很高，需要单独决策重新评估——但那次决策必须先解决"如何可靠判定一张图是单色
  剪影"，而不是绕过它。
- JPEG 图标在与其背景色反差不足的主题下会显得突兀，宿主不做任何补偿。是否在 UI 层为不透明图标
  统一加一个容器背景，属于 UI 决策。
- marketplace 对图标内容的审核策略未定：本决策只保证格式、尺寸与 SVG 安全性合法，不保证内容
  适当；由于字节随源仓库分发，内容审核等同于对仓库内容的审核。

## 落地顺序

两个阶段可独立验收，每一步都可单独回退。

**阶段一：契约与本地主题变体，仅 SVG。** 引入 `PluginLogo`（先只含 `Universal` 与 `Themed`）、
`ora-plugin` 的图标授权分支与两个资产根、D2 的候选解析与判定表（先只认 `.svg`），并把索引改为
记录角色到扩展名的映射而非内联源码，同时提升 `INDEX_VERSION` 并补上它的校验与降级路径。完成
条件是已安装插件与 marketplace 条目的图标均经由本地协议 URL 渲染，提供 `logo.light.svg` /
`logo.dark.svg` 的包在切换主题时正确换图，只提供 `logo.svg` 的既有包显示不变，且**持有旧形状
缓存的宿主打开市场时得到空列表与 `updated_at = 0`、同步一次后恢复正常，而不是端点报错**。
此阶段之后，契约不再传输图标内容。

**阶段二：位图。** 新增 `ora-utils` 的图像模块——magic bytes 判定、PNG 的 IHDR 尺寸、WebP 的三种
子格式尺寸与 ANIM 拒绝、JPEG 的 SOF 尺寸、统一的 50 KiB 与像素上限——并把四个位图扩展名接入 D2
的候选解析与协议服务。完成条件是随包分发 `logo.png`、`logo.webp`、`logo.jpg` 或 `logo.jpeg` 的
插件正确显示；动画 WebP、超出上限的文件、以及扩展名与内容不符的文件被按不存在处理且不影响该插件
被发现；混合格式的主题对（如 `logo.light.svg` + `logo.dark.png`）两半都正确渲染。此阶段之后，
本地图标接受五个扩展名、四种格式。

两个阶段结束时，"图标在深色主题下看不清"对提供了主题对的插件已经消失，而只提供单个 `logo.svg`
的存量插件行为完全不变——它们既不变好也不变坏，修复途径是作者补一个 `logo.dark.*` 并重新发版。
阶段一可以单独上线并长期停留在那里：位图支持是对格式面的扩展，不是前一阶段的必要补完。
