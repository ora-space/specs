# 单机部署以固定版本的离线包交付，由 Compose 启动服务并保留动态 Node

Ora 单机服务端以 Deployment Bundle 交付：包中包含一组预构建容器镜像、部署配置模板、插件发行包、
运行依赖快照和可验证的版本清单。部署方在自己的 Linux Docker 主机上导入并启动；目标机不需要产品源码、
编译工具链或公网包仓库。Compose 管理常驻服务，Sandbox Server 继续按 Workspace 创建独立 Node。

本文为 `cluster/deployment` 根决策，状态为 `proposed`，不表示部署工具已实现、离线执行已通过或产品能力已
增加。影响 cluster 的发布、安装、初始化、制品分发和运维入口，以及 Node 的部署信任和运行环境装配。
已有开发栈的入口和数据不迁移；首版只承诺新的独立部署实例。正式修改既有实例的来源、密钥或存储布局需
另行给出受控迁移方案，不能借离线安装覆盖历史状态。

模型与登录是部署需要连接的外部服务，不随软件包提供模型权重或用户身份。本文不放宽模型出口策略、不
增加认证提供方、不改变工作流节点范围，也不承诺任意 Agent、MCP、Skill 或用户项目都能离线执行。

## 问题与约束

现有 cluster Compose 通过 cloud/desktop 源码目录构建镜像，并挂载宿主脚本及配置。其启动和快照工具依赖
Git checkout，开发初始化使用 `devsetup`，不能作为无需源码的正式交付契约。Node 镜像也不是常驻服务：
仅准备 Compose 常驻服务镜像会遗漏任务执行所需的动态镜像。

插件发行包可能带有 CLI，但 CLI 启动和工具执行仍可能安装 npm 依赖或下载辅助程序。已有开发缓存掩盖了
这些路径；关闭公网后，网页健康和插件安装成功均不足以证明一次真实运行可完成。

部署还要区分三种身份：发行镜像的内容身份、一个安装实例的持久身份、某次运行的租户/Workspace/代次。
重新导入软件包不能重新生成既有安装实例的密钥，也不能改写运行授权或工作负载的冻结输入。

## 决策

### D1：部署包是固定的软件交付单元，部署实例独立持有数据和秘密

一个 Deployment Bundle 对应一个 Deployment Release 和明确的操作系统/CPU架构。它包含启动所声明功能
所需的全部容器镜像，包括动态 Node、初始化、运维、插件制品和依赖服务；配置模板、安装入口和依赖清单
也必须随包存在。首个目标平台为 `linux/amd64`，其他平台各自构建和验证，不从多平台标签推导支持范围。

Deployment Site 持有站点域名、登录提供方配置、端点策略、密钥和数据卷。软件包与site目录分离，软件包
不含部署私钥、API Key、登录secret或既有数据库。替换包目录不改变site身份；安装入口按明确实例限定
project、network和volume，不根据全局模糊标签删除其他部署资源。

“离线”表示软件安装和声明的执行能力不需要公网制品源。模型、登录和业务Git仍须是部署允许且可达的
服务。某项插件功能需要未交付的工具或不可达服务时，该项不在支持集合内，必须明确显示缺失，不能把
安装成功等同运行支持。

为什么不是单个大镜像：现有数据库、网关、控制面和动态执行单元有不同身份、持久化与生命周期责任。
一个可搬运的软件包可以满足一次交付，无需为文件数量改变这些边界。

### D2：组件清单固定来源和内容，验证基于内容而不是可变标签

发行记录固定每个源码仓库的完整commit、构建工具版本、目标平台、基础及第三方镜像内容身份、插件版本
及摘要、完整运行依赖快照。编排仓库自身的commit取本次构建来源，不在同一commit的文件内递归锁定自身。
构建不得在执行中重新解析 `main`、`latest` 或未经记录的“最新版”。

镜像的registry index digest、平台manifest digest、config digest/imageID和解包后的RootFS diffIDs含义不同，
分别记录来源映射。部署采用固定release标签并禁止隐式pull；标签加载后解析出的imageID、平台及层身份
必须与清单一致。离线Docker archive不以保留RepoDigests或attestation为前提，来源证明与SBOM另行关联保存。

软件包有独立内容摘要；分片运输时记录顺序、每片和重组产物摘要。缺片、损坏、错误平台或同名标签指向
其他镜像时，在更新运行服务前拒绝。校验和只证明运输完整性，来源真实性由部署信任的交付渠道或已建立
信任的签名验证提供，不能仅凭同包携带的公钥和校验和自证可信。

同一部署版本发布后不得替换字节；修复产生新版本。这样验收记录不会因重新打tag或重打包而指向不同软件。

### D3：安装只装配既有制品，不在目标机编译或联网补齐

正式Compose仅声明预构建image与交付内或site内路径，无源码build context、编译步骤或隐式公网拉取。
安装先验证包及全部镜像，再执行部署预检，最后初始化/启动。缺失动态Node或一次性初始化镜像也要提前
失败，不能等用户开始任务时才暴露。

预检检查实测支持的Docker/Compose版本、平台、可用资源、端口、配置路径和外部服务要求；具体支持范围
随release清单发布，由直接测试建立，不把“存在docker命令”作为所有特性均可用的证据。除Docker与明确
列出的基础系统工具外，配置解析、备份、校验及浏览器验收需要的工具由交付镜像承担。

预检不消耗真实模型额度。真实模型与业务执行套件是独立操作，并明确会产生实际运行。失败返回阶段和
有限错误分类，不把含密码的完整配置、环境或底层输出打印给用户。

### D4：初始化保存部署身份，失败不以重置密钥或数据自愈

正式初始化复用已有迁移和身份引导能力，通过 `cloudctl` 等受限运维入口执行，不将仅为本地开发设计的
`devsetup` 原样作为生产bootstrap。数据库密码、Gateway签名材料、PKCE材料、管理证书、模型加密主密钥
和对象存储凭据按各自用途保存，仅交给需要的服务。

第一次创建随机材料时原子落盘并限制权限；重试保留完整既有材料。检测到半对密钥、丢失的模型主密钥、
不匹配身份或已初始化的数据与新配置冲突时，失败并保留现场，不删除数据重来。中断后只重做未完成步骤，
迁移继续遵循追加迁移、校验和与数据库锁的现有规则。

首次管理员引导使用已验证外部身份的稳定标识，不按展示名或员工工号猜测身份；已有实例不得在每次启动
重复创建租户或提升用户权限。正式Gateway保持HTTPS和选定提供方要求，未配置真实登录时不能回退任意身份
输入的开发provider。

容器重建和实例停止保留卷。恢复材料、受保护目录和业务代码不混放，密钥不进入镜像、插件、npm快照、
源码、公开构建参数或发行证据。

### D5：插件通过部署内源分发，版本选择和安装权威保持不变

部署提供Cloud可通过HTTPS同步的Git marketplace，以及Node可通过HTTPS读取的插件发行包。分发服务的内容
属于release并可校验；它不拥有Docker socket，不写Node插件目录，不替用户作Space插件选择。

镜像官方插件时保存发行包原字节、原版本和SHA，只在镜像目录中重定位下载地址，并保留上游来源及转换后
索引commit。内部修改后的包必须有真实的新版本、摘要和来源；不能冒充原官方发行物。Cloud当前默认源
保留`official`命名空间；本文不增加Desktop多源身份派生或私有插件授权机制。

空间选择、`selected_release`和已受理操作继续冻结当时的地址、身份和摘要。目录更新不得回写这些事实；
同版本重复安装也不能被当作来源迁移。首版在第一次选择插件前配置好内网源，已有部署改来源另设计受控
迁移，不直接改数据库或伪造官方域名解析。

镜像源保留当前安装、在途操作及声明可恢复版本引用的包。仅因最新版未引用，不能删除仍被冻结操作需要
的旧包。源更新遵循Git快进语义，不能通过重建无关历史使同步失败后假装已更新。

Node现有下载输入没有制品凭据。本交付默认只分发允许该部署使用者读取的已审定公共包；细粒度私有插件
访问另行决策，不把token塞进URL或假定Desktop的S3签名获取已适用于Cloud→Node。

### D6：运行依赖用无回源的快照仓库交付，会话可写状态仍独立

每个声明支持的Agent/工具组合具有Runtime Dependency Snapshot：在固定目标平台上收集的准确版本、
完整传递依赖、相关peer/optional依赖、原tarball及摘要、所需本地工具。安装脚本可能下载的额外二进制也
属于这个边界，不能仅锁定最上层npm包。

首版采用包内npm registry snapshot，通过标准包协议提供这些内容。运行配置无uplink、无proxy回源规则、
禁止客户端发布和注册；未知包必须失败。发给客户端的tarball地址指向部署内可达服务。registry版本与seed
格式一同固定；不可变seed与服务的可写工作目录分开，不能未经验证就把整个storage设为只读。

registry不承载秘密，可在受限Docker网络提供无认证只读下载；若部署要求HTTPS，使用部署分发信任材料并
正常验证。网络可达范围、内容摘要和禁止写入仍是必备约束，不能将服务暴露为宿主任意npm代理。

Agent仍在每会话私有HOME/XDG目录解析和安装依赖；不共享跨Workspace可写node_modules。部署registry地址和
禁下载策略通过Sandbox→Node→会话→Agent的真实环境装配生效，不能只在Compose静态服务上设置变量。
固定辅助工具可随Node基础环境交付，但已安装插件状态仍归D5的安装流程。

选择registry snapshot而不是复制开发机cache，是为了复用CLI正常解析并明确缺包行为。单个开发目录缓存
不能覆盖新的HOME、平台条件和依赖变更。每会话node_modules预置需要同时维护上游安装判定，首版不采用。

### D7：动态 Node 接收必要公共信任，不获得分发签发权或模型长效密钥

部署对本机制品服务的公共CA进行受控分发。Cloud同步器、Node安装器、Git及确实需要该信任的Agent客户端
分别通过其正常TLS验证入口使用它；只有服务端持有相应私钥。该CA与模型上游是否需要公司CA是不同问题。

Sandbox创建动态Node时显式装配只读公开信任和部署运行配置。普通用户的插件输入不能增加宿主挂载、覆盖
管理身份、指定任意CA或修改registry出口；新配置只影响按契约新建的执行环境，不偷偷改写旧运行冻结输入。
管理私钥继续留在保护目录，工作负载只读到需要的公开信任材料与其原有运行授权。

部署配置不能以关闭证书/主机名校验解决下载失败。新的信任装配保留Node进程身份、受保护路径及UID边界，
不把管理私钥复制进通用CA目录，也不将真实模型API Key用共享`node.env`分发。

### D8：正式发布提升已验收的同一制品，证据与被测包分开封存

构建使用固定输入产生唯一候选；源码测试、组件集成和离线包验证引用同一组镜像内容身份，最后从相同内容
导出包。正式发布只提升通过验收的候选，不重新构建或修改文件后复用旧证据。

PR路径仅验证，不登录发布仓库、不推镜像、不访问公司runner或模型秘密；可信发布路径才授予所需最小
发布权限。跨私有仓库的只读构建权限与制品发布权限分开，不能假定一个仓库的token可读所有依赖。

在干净daemon/宿主、空卷、空HOME和无公网出口环境验证最终包。受控模型/Git/IdP对端的CI结果与实际部署
模型/身份提供方的现场结果分开记录；真实应用禁用模拟工作流执行。缺少现场证据的候选明确标为待验证，
不能因CI健康检查绿色直接声明生产完整可用。

先封存包并计算内容摘要，再生成引用该摘要的验收证据，证据旁挂保存。不能把“本包验收结果”写回本包
后重新计算摘要，造成最终产物不再是刚验收的字节。用户敏感地址、密钥、Cookie、原始环境和证书私钥不进入
公开证据；现场敏感记录留在部署方允许的位置。

### D9：升级先证明身份与恢复路径，回滚软件不隐含回滚数据

升级验证候选、当前实例身份、全部镜像和历史依赖可用性；备份覆盖数据库、必要主密钥、对象成果、
Workspace数据、管理材料和恢复journal。备份必须有一致性边界：阻止新写入并确认既有写入方静止，或使用
已明确验证的一致性机制；一次检查“当前无运行”之后允许新运行进入，不构成备份边界。

迁移失败保留数据与阶段证据。数据库已经前向迁移时，不能把旧镜像启动称为完整回滚。恢复先在隔离实例
核验身份、数据和凭据可用性，再按运维流程切换；不得自动删除旧卷或强制结束不属于本实例的沙盒。

首版不承诺零停机升级、自动回退所有schema或改造已有开发栈。维护窗口、支持的升级跨度及恢复义务随
release声明并验证；未覆盖路径明确拒绝而不是最佳猜测。

## 不变量

1. 一个Deployment Release在同一平台对应固定交付内容，正式发布与最终验收引用同一内容身份。
2. 声明支持的初次执行从空状态开始不依赖公网制品源；缺依赖显式失败，不通过后台回源补齐。
3. 部署包不包含实例秘密或安装状态，实例的软件更新不重置持久身份。
4. Cloud选择插件、Node校验安装、每Workspace独立数据和每会话私有可写目录保持成立。
5. 动态Node使用已校验镜像和受控部署配置，工作负载不能扩大宿主挂载或信任范围。
6. 插件分发信任不授予工作负载签发权或真实模型密钥。
7. 迁移和恢复不通过删除未知状态或替换密钥掩盖失败。
8. 部署证据区分包完整性、服务就绪和业务执行通过，不从一层推断另一层。

## 为什么不是这些替代方案

| 方案 | 优势与取舍 |
|---|---|
| 单镜像运行所有进程，Node改为内部进程 | 搬运入口少；需要改变沙盒身份、隔离、寻址和生命周期，不是现有服务的包装 |
| Docker-in-Docker封装 | 表面可只提交一个外层容器；额外daemon、权限、存储和恢复责任不能因封装而消失 |
| 用户在内网clone源码并build | 开发调试直接；要求编译工具链和多源依赖，版本组合难以与发行验收对应 |
| 只镜像Agent `.orax` | 保留安装流程；无法涵盖CLI的npm、辅助工具及运行时下载，不能满足空环境执行 |
| 所有插件预装到Node镜像 | 初次安装快；把Space选择和安装状态固化进镜像，升级/版本归属脱离已有权威 |
| 全局可写依赖缓存 | 省磁盘；使一个Workspace能改变另一个运行读取的依赖，破坏隔离与内容身份 |
| 无依赖时自动回源 | 在线体验方便；在受限网络上变成迟发故障，并使同一包的执行内容随外部状态变化 |
| 原样启用devsetup和开发登录 | 本机试用成本低；把开发身份和初始化假设带入正式实例，与既有Gateway边界不符 |

## 风险与未解决的边界

镜像、npm metadata和原包都要占用传输及磁盘空间；压缩/分片不能替代实测的磁盘峰值和并发资源预算。
CLI升级可能改变运行依赖和禁下载开关，因此每个新组合都需要重新建立快照和冷启动证据。

本文不决定企业模型私网准入、私有Git凭据、私有插件细粒度授权、多主机调度、rootless Docker支持、
自动证书轮换体系或既有在线实例的来源迁移。这些跨越现有领域责任，分别在对应领域演进；初次交付只
使用已批准的行为。证书到期与材料不完整必须可诊断，不能以本文未包含轮换为由静默忽略。

具体归档格式、registry实现版本、镜像仓库和流水线工具由实现选取并锁定；它们必须满足上述可观察行为，
不是替代义务的配置项。本文不嵌入某个企业端点、API Key或仅对一个模型别名成立的容量假设。

## 预期验证与落地顺序

`proposed`阶段只审查边界与替代方案，不维护核心测试用例。批准时建立镜像的核心用例目录内容，再依据
最终契约登记直接证据；没有真实边界测试的义务保持Missing或Partial。

1. 固定版本清单和验证器：破损/错平台/错镜像标签在变更实例前被拒绝，证据引用准确字节。
2. 交付初始化与启动：无源码目标导入全部镜像；重复与中断初始化保留密钥和数据；真实登录边界保持成立。
3. 闭合依赖与动态Node：新Workspace/新HOME实际安装原包、通过本机npm获得完整依赖并运行工具；缺包和
   错证书失败，禁止公网时无隐式下载。动态Node实际使用的镜像/信任/环境与部署声明一致。
4. 业务与故障验收：在各领域已批准范围内验证真实模型、插件、工作流、取消、进程重启和资源释放。
   普通Agent Session的Revision与Workflow输出分别判断，不借部署ADR扩展领域能力。
5. 发布与恢复：候选包在隔离CI和目标环境验证；按同内容身份发布；验证支持的升级跨度、迁移失败保护和
   隔离恢复。声明的第一版能力必须完成该范围的证据后才发布为可用版本。

从步骤2起改变的是软件的分发与部署装配入口；Cloud业务权威、Controller派发、Node执行和运行授权仍由
其各自领域契约拥有。工作流实现和模型出口规则的未完成事项不能通过部署包绕过。
